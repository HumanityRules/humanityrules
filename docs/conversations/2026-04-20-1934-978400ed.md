**1. Different IAM principals / blast radius**
- `shared-secrets` → read by the **sidecar ECS container** (task role)
- `oidc-config` + `sidecar-jwt-key` → read by the **auth Lambda** (lambda role)

Folding means either (a) both principals get access to everything, or (b) you use JSON-key-scoped IAM (messier). Notably, `shared-secrets` holds user-supplied env vars like `OPENAI_API_KEY` set via `manage.py doh_secrets shared-set` — so giving the auth Lambda read access to the merged secret widens its reach over customer data.

**2. Different mutability / risk profiles**
- `shared-secrets` is **user-mutable** at runtime (`doh_secrets shared-set`) — merge semantics, frequent writes
- `sidecar-jwt-key` is **immutable after creation** (rotation requires coordinated Lambda+sidecar redeploy — comment at `secrets_utils.py:280`)
- `oidc-config` is **upserted on every redeploy** from `Organization` fields

A bad `shared-set` call could now corrupt auth.

**3. Different structural shapes**
- `shared-secrets` keys are **flat scalars** — injected into the sidecar container via ECS secret JSON-key references (`DOH_SIDECAR_TOKEN::`)
- `sidecar-jwt-key` is a **nested object** (`private_pem`, `public_pem`, `kid`) — not injectable as a single env var; Lambda parses the JSON

Not a blocker (Lambda can parse nested), but the two halves have different access patterns.
