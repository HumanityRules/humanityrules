It exports the filesystem ID and security group ID as CloudFormation outputs.

**2. Per-app EFS access point (at deploy time)**

In `deploy_app.py`, when an app's `cdk_stack_profile` is `"fargate_web_efs"` (which hermes is, per `seed_app_templates.py` line 218), the CDK stack:

- **Imports** the shared EFS filesystem
- **Creates an access point** scoped to `/deployments/{app_name}` with POSIX UID/GID 1000
- **Grants IAM permissions** for `ClientMount` and `ClientWrite`, conditioned on that access point

```350:373:devopshero_app/services/infra_customer/deploy_app.py

                file_system=efs_file_system,
```

**3. ECS task definition volume + container mount**

The EFS volume is attached to the Fargate task definition with transit encryption and IAM auth, then mounted into the container at `/app/workspace`:

```409:446:devopshero_app/services/infra_customer/deploy_app.py

                name="app-workspace",

                    file_system_id=self.environment_infra.efs_file_system_id,
                    transit_encryption="ENABLED",
                    authorization_config=ecs.AuthorizationConfig(
                        access_point_id=efs_access_point.access_point_id,
                        iam="ENABLED",
                    ),
                ),
            )

        if efs_access_point:
            container.add_mount_points(
                ecs.MountPoint(
                    container_path="/app/workspace",
                    source_volume="app-workspace",
                    read_only=False,
                )
            )
```

**4. Inside the container**

The hermes entrypoint writes to `/home/hermeswebui/.hermes` (line 4 of `entrypoint.sh`), and `HERMES_WEBUI_STATE_DIR` is set to `/home/hermeswebui/.hermes/webui-mvp` (Dockerfile line 16). Note that the EFS mount point is `/app/workspace`, **not** `/home/hermeswebui/.hermes` -- so the hermes state directory itself is not on EFS. The EFS mount at `/app/workspace` provides a persistent workspace that survives container replacements, while the hermes config/state in `~/.hermes` is regenerated on each boot by the entrypoint script (config.yaml is only written if absent, but `.env` is always regenerated).

**Summary of the chain:**

- **EFS filesystem** -- shared per environment, encrypted, retained on delete
- **Access point** -- per app, rooted at `/deployments/{app_name}`, UID/GID 1000
- **Task volume** -- attached via EFS volume configuration with transit encryption + IAM auth
- **Container mount** -- `/app/workspace` (read-write)
- **Isolation** -- each app can only reach its own subtree via the access point ARN condition in the IAM policy

## Assistant

Good question. We have three options, each with different trade-offs:

**1. User runs it manually via the WebUI terminal.** Hermes has a built-in terminal. The user SSHs in or uses the web terminal, runs `hermes update`, done. Zero automation from us. But it requires the user to know and remember.

**2. The entrypoint runs it on every boot.** Add `hermes update` before `exec "$@"`. Every redeployment or ECS task replacement automatically pulls the latest. But this adds latency to every cold start and assumes internet access from the container (which it has, through the NAT gateway). It also means a routine container replacement could change the hermes version as a side effect.

**3. DOH triggers it as a management action.** We add a "Update Hermes" button or a scheduled job that runs `hermes update` inside the running container (via ECS exec). Controlled, auditable, no startup penalty.

I'd lean toward **not automating it for now**. This is a pre-beta product and we don't have customer feedback on how they want to manage agent versions. Automating it introduces a failure mode (upstream breaking change on a random reboot) without clear demand. The user can always run `hermes update` through the WebUI terminal.

If we later hear from customers that they want managed updates, option 3 is the cleanest -- it's explicit, auditable, and doesn't surprise anyone.
