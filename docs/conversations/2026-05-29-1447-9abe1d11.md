## Assistant

Short answer: **there's no fixed refresh interval.** The aws-signer doesn't poll or refresh on a timer — it refreshes credentials **lazily, driven by botocore's own caching plus a reactive retry on expiry.** Two mechanisms are at play:

### 1. botocore's normal credential lifecycle (the common case)
The signer holds a single long-lived `botocore.session.Session` (`aws_signer.py:169`) and calls `session.get_credentials()` on **every** proxied request (`aws_signer.py:94`). botocore caches the credentials object on the session and, for container/instance-role providers (the ECS task role here, sourced via the `AWS_CONTAINER_CREDENTIALS_*` endpoint), it **auto-refreshes in the background before expiry** — botocore's `RefreshableCredentials` refreshes when the creds enter the "refresh window" (advisory refresh ~15 min before expiry, mandatory ~10 min before). So under normal operation the freshness is whatever the ECS credentials endpoint hands out (typically ~6 h, rotated by ECS), and botocore transparently fetches a new set before the old one lapses. The signer itself does nothing to schedule this.

### 2. Reactive fallback on `ExpiredTokenException` (the safety net)
If a signed request still comes back `403` with `x-amzn-errortype: ExpiredTokenException`, the handler forces a refresh and retries **once** (`aws_signer.py:120-132`). It does so by clearing the session's cached creds:

```python
def _reload_session_credentials(session):
    session._credentials = None   # forces re-read on next get_credentials()
```

This is a per-request, on-demand recovery path — not a schedule. It triggers only when an actual call fails due to expiry, and only retries a single time before passing the response through.

### So "how frequently"
- **No periodic refresh** — it's event-driven, never time-driven, in this code.
- In steady state: refresh happens **as often as botocore decides**, which is just-before-expiry of whatever lifetime the ECS task-role credential endpoint assigns (commonly a few hours).
- Worst case: refresh happens **reactively, on the first request that sees an expired-token 403**, then once more retried inline.

One caveat worth noting: the `_reload_session_credentials` path resets `session._credentials` to `None`, which makes botocore rebuild the provider chain from scratch on the next `get_credentials()` (re-reading env / `~/.aws` / the container endpoint). That's a heavier reset than nudging the refreshable-credentials object, but since it only fires on actual expiry errors it's infrequent by design.

If you were asking because you want a *guaranteed* max staleness (e.g. for the new billing permissions to take effect), note that **IAM policy changes don't require a credential refresh at all** — the policy is evaluated at request time against whatever the role can do, so the billing read-only actions I just added are effective immediately on the next call, regardless of credential age.
