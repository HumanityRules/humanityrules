## Option A: Dedicated `LLMUsageLog` Model (my recommendation)

A new model that records every LLM interaction as an append-only log row.

- **FK to** `Conversation` (nullable — title gen happens in a conversation context, but future calls might not)
- **FK to** `Organization` (for billing rollups)
- **FK to** `User` (who triggered it)
- **Fields:** `model_alias`, `model_id`, `source` (choices: `agent_turn`, `title_generation`, future ones), `input_tokens`, `output_tokens`, `cost_usd`, `duration_ms`, `num_turns` (nullable, only relevant for agent), `created_at`

**Pros:**
- Full per-interaction granularity — you can answer "how much did this conversation cost?", "how much did org X spend this month?", "what's my Opus vs Haiku split?"
- Append-only, no race conditions on accumulation
- Easy to add new LLM call sites (e.g., future summarization, embeddings) without touching Conversation
- Clean for building a billing/usage dashboard later

**Cons:**
- One extra row per agent turn + one per title gen = moderate write volume
- Aggregation queries needed for dashboard totals (mitigated with DB indexes or denormalized fields)

---

## Option B: Fields on `Conversation`

Add `total_cost_usd`, `total_input_tokens`, `total_output_tokens`, `llm_turns` directly to the `Conversation` model. Accumulate on each `ResultMessage` and title gen call.

**Pros:**
- Simplest to implement — a migration + a few lines in `stream_response` and `_maybe_generate_title`
- No new model, no joins for "how much did this conversation cost?"
- Dashboard queries are trivial

**Cons:**
- Loses per-turn granularity (can't see which turn was expensive)
- Race conditions if you ever have concurrent writes to the same conversation
- Doesn't cleanly handle non-conversation LLM calls (if they arise)
- Mixing cost-tracking concerns into the Conversation model

---

## Option C: Hybrid — Both

`LLMUsageLog` model for granular tracking **plus** denormalized `total_cost_usd` on `Conversation` for fast display.

**Pros:** Best of both worlds — granular history + fast reads
**Cons:** Two places to maintain, mild complexity

## My Recommendation: Option A (dedicated model)

For a platform where LLM cost is going to be a core business concern (you'll eventually bill customers or at least show them usage), a dedicated log table is the right foundation. It's only marginally more work than Option B, and it sets you up for:

- Per-org billing dashboards
- Cost-per-conversation breakdowns in the chat UI
- Model usage analytics (are customers hitting Opus when Haiku would do?)

What happens when related objects to the LLMUsageLog are deleted?

## Assistant

Good question. Here's what the plan currently specifies and the tradeoffs:

- **organization** — `CASCADE` — If an Organization is deleted, all its `LLMUsageLog` rows are deleted too. This follows the same pattern as every other org-owned model in the codebase (`AWSAccount`, `Workspace`, `Conversation`, etc.). The reasoning: if you nuke an entire org, there's no one left to bill. But it does mean you lose historical cost data for that org.

- **user** — `SET_NULL` (nullable) — If a User is deleted, the log row survives with `user=NULL`. Cost data is preserved; you just lose the "who triggered it" attribution.

- **conversation** — `SET_NULL` (nullable) — If a Conversation is deleted, the log row survives with `conversation=NULL`. This preserves the cost record for org-level billing rollups even if the conversation is cleaned up.

The main question is whether `CASCADE` on organization is what you want. The alternative would be `PROTECT` (prevent org deletion if usage logs exist) or `SET_NULL` (keep orphan logs around). For an append-only billing log, `PROTECT` could be argued as the safest choice — it forces you to explicitly archive/delete usage data before removing an org, preventing accidental loss of billing history.

That said, org deletion is a rare, heavyweight operation and every other model in the codebase uses `CASCADE` for it. So `CASCADE` keeps things consistent.

Want me to change any of these, or are you good with the current choices?

## Assistant

No, we're not missing it — the Anthropic API (used by `title_generator.py`) doesn't return a cost field. Cost-in-dollars is a feature of the Claude Agent SDK's `ResultMessage`, which computes it internally. The raw `client.messages.create()` response only gives you `usage.input_tokens` and `usage.output_tokens`.

That's why the `LLMUsageLog` row for title generation is created with `cost_usd=None`:

```341:347:devopshero_app/services/agent/agent_service.py
        await LLMUsageLog.objects.acreate(
            # ...
            input_tokens=result.input_tokens,
            output_tokens=result.output_tokens,
            cost_usd=None,
            duration_ms=None,
            num_turns=None,
        )
```

We could compute it from tokens using known Haiku pricing (currently ~$0.80/MTok input, $4/MTok output), but that means hardcoding prices that change over time. Given that title gen calls are tiny (~500 input tokens, ~20 output tokens, fractions of a cent), it's probably not worth the maintenance burden. The token counts are there if you ever want to compute it retroactively.

If you do want it, the cleanest approach would be a pricing lookup dict in `llm_client.py` mapping aliases to per-token rates, and a small helper to compute cost from tokens. But I'd suggest deferring that unless you need dollar-accurate totals across all sources.
