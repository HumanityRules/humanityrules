## The shape of the bug, generalized

The fix you just landed shows the canonical pattern:

```python
# Vulnerable
user = User.objects.filter(username=owner_username).first()

# Safe
user = User.objects.filter(
    username=owner_username,
    current_organization=environment.aws_account.organization,
).first()
```

So the bug class is: **a queryset that resolves a tenant-owned object by a client-supplied identifier, without scoping by the organization that the caller already established trust within.**

Three things make this hard to catch by eye in DOH:

1. The org pointer is often **transitive** (`environment → aws_account → organization`), so there's no single "always include `organization=`" rule.
2. There is no `OrgOwnedModel` base class — quick scan: ~30 models with `Meta`, no shared abstract base, no custom managers, only two direct FK references to `Organization` in `models.py`. Most org-ownership is implicit.
3. There are **~140+** `.objects.{filter,get,get_or_create,update_or_create}` call sites just under `devopshero_app/views/`. Manual audit is the wrong tool for that volume.

## Strategy: four layers, escalating strength

### Layer 0 — One-shot inventory and audit (do this now)

Goal: find every existing instance of this bug, today.

1. **Build the tenancy graph automatically.** Walk `apps.get_models()` and, for each model, compute the shortest FK path to `Organization` (or mark "global"). Output a static dictionary: `MODEL_TO_ORG_PATH = {"User": "current_organization", "Environment": "aws_account__organization", "IntegrationUserCredential": "environment__aws_account__organization", ...}`. Commit that as the source of truth. From this point on, *any* model not in the dict is either truly global or a gap.

2. **Static scan for the bug shape**, using the dict above. A Semgrep rule or a small AST script that flags any expression `M.objects.filter(...)` / `.get(...)` / `.get_or_create(...)` / `.update_or_create(...)` / `M.objects[<lookup>](...)` on `M ∈ MODEL_TO_ORG_PATH` whose call's keyword arguments do **not** include the expected scope key (or `id=` / `pk=` derived from a path the linter can recognize as already-scoped — see below).

3. **Triage the report.** Almost certainly more than the two views you just fixed. The token-refresh family was suspicious because it accepts a *user-supplied identifier of an org-owned object*; anywhere we accept `owner_username`, `app_slug`, `environment_slug`, `aws_account_id`, etc. from request input is high prior. Tests should also explicitly create a second org with colliding identifiers — most existing isolation tests don't, which is why these bugs survive.

This first pass is the only step that meaningfully requires human attention. Everything below is automation.

### Layer 1 — Lock the door behind us (lint in CI)

Promote the Layer-0 scan to a CI check. Two pieces:

- **Semgrep rule** (or a `manage.py check_tenancy` Django check that fails the build) for the pattern from Layer 0. Allowlist requires a `# noqa: tenancy` comment with a justification, so adding an exception is loud in code review.
- **AGENTS.md addition** in `devopshero_app/views/AGENTS.md`: "Any query against an org-owned model in a view must include an org-scope filter or call a `get_org_scoped_*` helper. Bare `.objects.filter/get` on org-owned models is a CI error."

This guarantees no *new* instance of this bug can be introduced after today. It does not, by itself, fix sneaky cases (e.g., starting from a queryset that was already scoped, then `.filter()` again) — those need Layer 2.

### Layer 2 — Make the bug class harder to spell (managers)

For each org-owned model, replace the default manager with an `OrgScopedManager` whose `.filter/.get/.all/.first/.get_or_create/...` raise unless one of:

- `.for_org(org)` was called earlier in the chain, or
- `.for_request(request)` was called earlier in the chain, or
- the explicit `__unsafe_all_orgs()` escape hatch was used (greppable, reviewable).

Sketch:

```python
class OrgScopedQuerySet(models.QuerySet):
    _org_scoped = False

    def for_org(self, organization):
        qs = self.filter(**{self.model._org_path: organization})
        qs._org_scoped = True
        return qs

    def _check_scoped(self):
        if not self._org_scoped:
            raise TenancyError(f"{self.model.__name__} accessed without .for_org(...)")

    def filter(self, *a, **kw):
        self._check_scoped()
        return super().filter(*a, **kw)
    # ...same for get, first, all, iter, etc.
```

Migration is incremental: per-model, flip the manager, run tests, fix call sites. Each fixed call site reads `Environment.objects.for_org(request.user.current_organization).filter(slug=slug)` — which **cannot** forget the scope.

This eliminates the bug class in application code. It does not protect against a raw SQL query, an ORM bug, or `Model.objects.__unsafe_all_orgs__()` misuse. For that, Layer 3.

### Layer 3 — Defense in depth at the database (Postgres RLS)

The north star. For every org-owned table, enable Postgres **row-level security** with a policy like:

```sql
ALTER TABLE devopshero_app_integrationusercredential ENABLE ROW LEVEL SECURITY;
CREATE POLICY org_isolation ON devopshero_app_integrationusercredential
  USING (
    environment_id IN (
      SELECT e.id FROM devopshero_app_environment e
      JOIN devopshero_app_awsaccount a ON a.id = e.aws_account_id
      WHERE a.organization_id = current_setting('app.current_org_id')::uuid
    )
  );
```

A request middleware sets `SET LOCAL app.current_org_id = '<request.user.current_organization_id>'` at the start of each transaction. Now the original bug — `User.objects.filter(username=...)` without org scope — would still have returned the wrong row in Python, but the DB would never have handed it over.

This is the only layer that protects against future bugs you haven't written yet, including ones in third-party packages and `manage.py shell` typos. It's also the most expensive: it requires a careful migration, performance review (the policy is essentially an extra join on every read), and discipline about connection pooling (`SET LOCAL` must happen on every transaction). Worth it for a deployment platform whose entire value prop is tenant isolation.

### Layer 4 (optional but cheap) — A property test

One pytest that, for every URL in `urlpatterns` marked `@login_required`:
- Creates Org A and Org B with deliberately colliding `username`, `slug`, etc.
- Authenticates as Org A's user.
- Replays a recorded "normal" request body but with Org B's identifiers substituted.
- Asserts 404/403 **and** asserts no outbound HTTP / no side-effecting writes occurred.

Endpoints without a payload schema can be marked `xfail` initially; the boundary shrinks over time. The two new tests in this commit are essentially the manual, per-endpoint version of this.

## Findings worth recording

### Improvement on the committed fix (working tree, uncommitted)

The committed fix in `03ca6c0` used `current_organization=...`. The **working tree** of `github_token_refresh.py`, `google_token_refresh.py`, `user_credential_vault.py`, `merge_handler.py`, and `pdp.py` has converged on `organization_memberships__organization=...`, which is more semantically correct: `User.current_organization` is the user's *currently active* org, but a user may be a member of multiple orgs. The membership-based filter avoids false negatives when a legitimate org member happens to have switched their current org elsewhere. This should land — the committed fix is functionally safe but pessimistically narrow.

### Real concern: weak environment resolution in OAuth start views

**Files:** `devopshero_app/views/integrations/google_oauth.py`, `devopshero_app/views/integrations/github_oauth.py`

The `_resolve_env_by_rd` helper iterates every `Environment` in every org and returns the first one whose `shared_alb_hosted_zone` suffixes the `rd` host:

```56:73:devopshero_app/views/integrations/google_oauth.py
def _resolve_env_by_rd(rd: str) -> Environment | None:
    """Return the Environment whose shared_alb_hosted_zone suffixes *rd*'s host, or None.
    ...
    """
    if not rd:
        return None
    parsed = urlparse(rd)
    if parsed.scheme not in ("http", "https") or not parsed.hostname:
        return None
    host = parsed.hostname.lower()
    for env in Environment.objects.exclude(shared_alb_hosted_zone="").only("id", "slug", "shared_alb_hosted_zone"):
        zone = env.shared_alb_hosted_zone.lower()
        if host == zone or host.endswith("." + zone):
            return env
    return None
```

There is no check that `request.user` is a member of `env.aws_account.organization`. Concrete consequence: an authenticated DOH user can start an OAuth flow with `?rd=https://hermes.someone-elses-zone/...` and the resulting `IntegrationUserCredential` row will be written with `environment=<stranger-org's env>`. The row's `owner_user=request.user` is correct, but the row points at an environment in an org the user does not belong to. Whether this is exploitable end-to-end depends on the user also being a member of the target org (in which case it's a feature, not a bug — they could use the same identity across orgs), but if they aren't, you get a polluted row tied to a stranger env that no one in that env can legitimately use.

**Severity:** MEDIUM. Same bug *family* as the token-refresh one (resolve org-owned object from client-controlled string without checking org), different surface. Recommended fix: add a membership check after `_resolve_env_by_rd` returns:

```python
if not OrganizationMembership.objects.filter(
    user=request.user,
    organization=env.aws_account.organization,
).exists():
    return HttpResponseBadRequest("Invalid or unknown rd")
```

Plus: the iteration-order issue. Two envs across two orgs sharing a `shared_alb_hosted_zone` would non-deterministically pick the first one. Consider either a uniqueness constraint or sorting by something stable.

### Fragile code-smell: fetch-then-verify `User` in `security_abac.py`

Roughly six sites in `devopshero_app/views/security_abac.py` follow this pattern:

```140:143:devopshero_app/views/security_abac.py
    org = request.user.current_organization
    member = get_object_or_404(User, id=user_id)

    # Verify user belongs to org
    get_object_or_404(OrganizationMembership, organization=org, user=member)
```

The first lookup is *unscoped*; the second is the gate. It's safe today (the second 404s before any mutation), but a future refactor that drops or moves the membership check immediately reintroduces the bug class — and reviewers won't easily see the dependency. Recommended: collapse into a single atomic scoped lookup:

```python
member = get_object_or_404(
    User,
    id=user_id,
    organization_memberships__organization=org,
)
```

Same suggestion applies to similar patterns in `security_people_attribute_add`, `security_people_attribute_remove`, `security_people_group_add`, `security_people_group_remove`, and `security_group_member_add`.

- **`chat.py` is the gold-standard example** of scoping: every conversation lookup uses `get_object_or_404(Conversation, id=..., user=request.user, organization=request.user.current_organization)`. Belt-and-suspenders, easy to audit, hard to break.

## Assistant

**Postgres Row-Level Security (RLS).**

The idea: tell the database itself "every query against this table must be scoped to one organization," so Django can't issue an unscoped query even by accident. The DB rejects (or silently filters) rows the current session isn't allowed to see.

How it would work for DOH:

- **One Postgres role per request**, e.g. `app_user`. The Django connection switches into it with `SET LOCAL app.current_org_id = '<uuid>'` at the start of every request (in middleware), reading the value from `request.user.current_organization_id`.
- **`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`** on every tenant-owned table.
- **A `CREATE POLICY` per table** with a predicate like `organization_id = current_setting('app.current_org_id')::uuid` — or for transitively-owned tables, a subquery that joins to the owner.
- **Migrations** add the policies; new tables get a checklist item ("add RLS policy") that CI can enforce by scanning the migration tree.

What it buys us:

- **Defense in depth.** Even if a view forgets to filter, the DB returns zero rows. The "fetch-then-verify" smell and the `_resolve_env_by_rd` weakness would have both been no-ops behind RLS.
- **Covers raw SQL and ORM equally.** Today our static analysis would miss raw queries.
- **Cheap to audit.** `\dp` and `pg_policies` show coverage.

What it costs us:

- **Background jobs are awkward.** Celery tasks, management commands, signal handlers, and cross-tenant aggregations (DOH's admin/super-admin views) all need an explicit way to opt out — usually by switching to a privileged role. Easy to get wrong.
- **`SET LOCAL` only sticks inside a transaction.** Means wrapping every request in a transaction (or using a session-pinned value), which interacts with `ATOMIC_REQUESTS` and async ORM in ways worth thinking about.
- **The transitive-ownership joins in policies are slow** if not written carefully (they run on every row read). Models like `IntegrationUserCredential` → `environment__aws_account__organization` need an index or a denormalized `organization_id` column.
- **It is a load-bearing security boundary.** A schema migration that forgets `ALTER TABLE ... FORCE ROW LEVEL SECURITY` (for superuser-owning tables) leaks. Worth a CI lint.
- **Multi-org sessions** (a user is admin of A and member of B and views B's data) need extra plumbing — the per-request `app.current_org_id` has to track which org the request is operating on, not just user identity.

Where it fits in the strategy I sketched:

- It's the *floor*, not the *ceiling*. Static analysis (semgrep) catches it in CI; custom ORM managers (`OrganizationScopedManager`) make scoping the default in app code; RLS is the catch-all if both fail. The three layers compound.

If you want, I can prototype RLS on a single high-risk table (`IntegrationUserCredential` is a good candidate — small, recently relevant, transitively-owned) so you can see what the migration, middleware, and a per-request `SET LOCAL` actually look like in our codebase before we commit to it wholesale.

## Assistant

**Mechanically, yes. Operationally, not quite.**

The DDL is reversible — `ALTER TABLE ... DISABLE ROW LEVEL SECURITY;` (or `DROP POLICY`) is a fast, non-destructive DDL change. No data is touched, just access rules. So at the database layer, you can run it for a week and walk away.

What makes it not a true blackbox:

- **No "shadow / warn-only" mode.** Unlike adding a permission check in app code that you can wrap in `if SHADOW: log_else_block(...)`, PG's RLS has two states: off, or on-and-enforced. There's no "would-have-blocked" report. The closest substitute is enabling it in **staging** first and dogfooding for a week.
- **The failure mode is loud and inconvenient.** If anything connects to the DB without setting `app.current_org_id` (a forgotten celery task, a management command, a webhook handler that runs before middleware), every query on an RLS-enabled table returns zero rows. Users see empty pages, not 500s. You will get pages.
- **Disconnecting unwinds the DDL but not the prep work.** Middleware, role split, `SET LOCAL` plumbing, per-table policy migrations — all of that stays in the repo. You can leave it dormant, but the diff happened.
- **Mitigations exist to make rollback cheap during the trial:**
  - Use `ENABLE ROW LEVEL SECURITY` *without* `FORCE`. The table owner role bypasses RLS, so emergency scripts run from a privileged shell still work.
  - Two-role pattern: keep `app_admin` as a "kill switch" — flip the web app's connection string to it and RLS effectively turns off for the app, without any DDL.
  - Roll out one table at a time. Disabling a single table's policy is a one-line migration that takes seconds.

**Honest summary:** the *database* part is a blackbox you can flip on then flip off. The *application* part — making sure every connection sets the GUC — is a one-time integration cost that doesn't unflip. The realistic trial shape is: spend ~1–2 weeks on the integration plumbing, enable in staging, dogfood for a week, then either promote to prod or shelve. The shelved version still cost you the integration work.

If you want a cheaper experiment first, **a custom Django ORM manager** that requires explicit org scoping (and raises if you call `.all()` without it) gives you ~70% of the safety with ~10% of the operational risk, and is unambiguously reversible. That's usually the right first step before reaching for RLS.

RLS_ENFORCEMENT = env("RLS_ENFORCEMENT", default="on")  # "on" | "off"

# middleware
from django.db import connection
with connection.cursor() as cur:

CREATE POLICY tenant_isolation ON integration_user_credential

USING (
