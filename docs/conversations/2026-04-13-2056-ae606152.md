## The Current Deployment Data Flow

```
Repository → App (build identity) → DeploymentBlueprint (runtime config) → Deployment (execution)
                                                                                ↓
                                                                         AppConfig (dataclass)
                                                                                ↓
                                                                   CDK: EcrStack + AppStack + optional AuroraClusterStack
```

The key intermediary is `AppConfig` in `appconfig.py` — it's the CDK input contract. `app_config_builder.py` flattens an App + Blueprint into this dataclass. Everything a template needs to control eventually lands here.

## What an AppTemplate must capture

A template is a **factory** that pre-fills two existing models — `App` (build identity) and `DeploymentBlueprint` (runtime config) — so the user doesn't have to configure 15+ fields manually.

**App-level fields** (build identity, rarely changes across deployments):
- `app_type`, `build_strategy`, `dockerfile_path`, `container_port`, `health_check_path`, `health_check_command`

**Blueprint-level fields** (runtime config):
- `cpu`, `memory`, `environment_variables`, `app_secrets`, `datastore` binding

**Repository source**: which repo to deploy from

## Proposed Model: `AppTemplate`

Platform-level entity (not org-scoped). Administered by us, seeded by script.

- **Identity** — `name`, `slug`, `description`, `icon` (for the template picker UI), `category` (e.g., `"ai-assistant"`, `"web-app"`)
- **Source repo** — `source_repo_url`, `source_repo_branch`, `repo_subpath`
- **App defaults** — `app_type`, `build_strategy`, `dockerfile_path`, `container_port`, `health_check_path`, `health_check_command`
- **Blueprint defaults** — `cpu`, `memory`
- **Variable schema** — JSON array declaring all env vars and secrets (see below)
- **Datastore config** — JSON object declaring database requirements, or `null`
- **Stack profile** — `"fargate_web"` for now (maps to `deploy_app.deploy`)
- **Lifecycle** — `is_active`, `created_at`, `updated_at`

## Key Design Decisions to Discuss

### 1. Variable Schema — the central design problem

The template needs to declare *what the app needs*, not *actual values*. OpenClaw example:

```json

    {"name": "OPENCLAW_DEFAULT_MODEL", "category": "config", "description": "Default LLM model", "default_value": "claude-sonnet-4-20250514", "required": true},
    {"name": "OPENCLAW_GATEWAY_TOKEN", "category": "secret", "description": "Gateway auth token", "auto_generate": true, "required": true},
    {"name": "ANTHROPIC_API_KEY", "category": "secret", "description": "Anthropic API key", "required": false},
    {"name": "OPENAI_API_KEY", "category": "secret", "description": "OpenAI API key", "required": false},
    {"name": "BRAVE_API_KEY", "category": "secret", "description": "Brave Search API key", "required": false},
    {"name": "SLACK_APP_TOKEN", "category": "secret", "description": "Slack app-level token", "required": false},
    {"name": "SLACK_BOT_TOKEN", "category": "secret", "description": "Slack bot token", "required": false}
]
```

When materializing a `DeploymentBlueprint` from a template:
- `category=config` entries → `blueprint.environment_variables` (list of `{name, value}`)
- `category=secret` entries → `blueprint.app_secrets` (dict of `field_name → value|None`)
- `auto_generate=true` → `app_secrets[name] = None` (triggers the existing random-value generation in `secrets_utils`)

**The question**: even in "user configures nothing" mode, someone has to provide the API keys (ANTHROPIC_API_KEY, SLACK_BOT_TOKEN). The template schema declares what's *needed*, but the actual values must come from somewhere. Options:

- **(a)** The admin provides values when setting up a template *instance* for a specific org (a separate model: `AppTemplateInstance` or similar, org-scoped, stores overrides)
- **(b)** The user fills in a minimal form at deploy time (just the required secrets that have no defaults)
- **(c)** Phase 1 just hardcodes values in the seed script into the Blueprint directly

I'd lean toward **(b)** — the template generates a form from the var_schema, config fields are pre-filled with defaults, and the user only has to type the secrets they have. This is still "one-click-ish" and avoids storing secrets in the template itself.

### 2. Repository Handling

Templates are platform-level but Repositories are org-scoped. When a user deploys from a template, we need an org-scoped Repository. Options:

- **(a)** Template stores `source_repo_url` + `source_repo_branch`. At deploy time, find-or-create a Repository record in the user's org for that URL.
- **(b)** Template has a FK to a "global repository" concept (new model).

I'd go with **(a)** — simpler, reuses existing Repository model. The `seed_local_repos` command already creates `provider=local` repos from `deployable-repos/`. For GitHub-based templates, we'd create `provider=github` repos.

### 3. CDK Stack Profile

Currently there's exactly one deployment pattern: `deploy_app.deploy()` → EcrStack + optional AuroraClusterStack + AppStack. The `AppStack` always wires up ALB routing regardless of `app_type`.

The `stack_profile` field on the template is a forward-looking extension point. For Phase 1:
- `"fargate_web"` → current `deploy_app.deploy()` (the only option)

Later:
- `"fargate_worker"` → no ALB routing, no target group
- `"fargate_scheduled"` → EventBridge-triggered tasks
- `"fargate_gpu"` → different task definition with GPU

The mapping from `stack_profile` → deploy function would live in a simple registry, not the model.

### 4. Datastore Config

JSON field on the template, `null` for apps that don't need a database. For a template that does:


## Bundled Template Repos

The `file://` approach is clean. The template repos ship inside DOH's deployment artifact — always available, no Git credentials needed, no external fetch. The `seed_local_repos` command already creates `provider=local` repos from `deployable-repos/`. So the mechanism exists.

Downside: breaks the current assumption that every Repository belongs to an org — ripple effects on ABAC, views, queries.

I'd go with **(a)**. The duplication is trivial (a few rows per org), and it means zero changes to the existing Repository model, ABAC system, or deployment executor. The seed script (or deploy-from-template flow) just creates a local Repository in the org if one doesn't exist for that `clone_url`.

## Analysis of the Three Options

### (a) Inside the DOH repo

Template code (e.g., `template_repos/openclaw_agent/`) lives directly in the DOH Git repo. `COPY . .` picks it up automatically.

- **Build**: Zero changes. It's just more files in the project.
- **In container**: Available at `/app/template_repos/openclaw_agent/`. Repository `clone_url` would be `file:///app/template_repos/openclaw_agent/`.
- **Clone behavior**: `repo_service.clone_repository` already handles `file://` via `shutil.copytree` (line 42-54 of `repo_service.py`). No git operations needed.
- **Versioning**: Tied to DOH's Git history. When DOH is at commit X, the template code is whatever was in that commit. No independent branching or pinning.
- **Updating templates**: Requires a DOH redeploy. Can't update template code independently.
- **Migration to (b)**: Clean — move the directory out, change `source_repo_path` to a URL, adjust the build. The executor code path doesn't change.

### (b) Separate repos, explicitly copied into the container

Template repos live outside DOH (like the current `deployable-repos/`), each with its own `.git`. They get into the container through an explicit build step.

Since `deployable-repos/` is outside the Docker build context, you'd need one of:

1. **Pre-build copy** — `deploy_app.sh` copies `../deployable-repos/openclaw_agent/` into `template_repos/` before `docker build`. The directory is `.gitignore`'d in DOH. Simple but fragile (depends on sibling directory existing).
2. **Broader build context** — Change to `docker build` from the parent directory. Requires rewriting the Dockerfile paths and `.dockerignore`. Messy.
3. **Git clone in Dockerfile** — Multi-stage build that clones template repos by URL. Clean, but needs Git credentials if repos are private, and adds network dependency to the build.

Because the `.git/` directory comes along, `clone_repository` could be changed to do a real `git clone --branch <ref>` from the local `.git` repo instead of `shutil.copytree`. This would give you branch and commit SHA pinning.

- **Versioning**: Full Git independence. The `AppTemplate` model can store a pinned commit SHA. Different DOH versions can reference different template versions.
- **Updating templates**: Can update template code without redeploying DOH (if using approach 3). With approaches 1-2, still requires a DOH redeploy.
- **Complexity**: Moderate — build pipeline changes, need to handle the `.git` directory correctly.

### (c) S3

Upload template repo tarballs to S3. Fetch either at container startup or at deploy time.

- **Versioning**: Full independence via S3 object versioning or keyed paths (`s3://templates/openclaw_agent/v1.2.3.tar.gz`).
- **Updating templates**: Upload new tarball, update AppTemplate record. No DOH redeploy.
- **Complexity**: High — runtime S3 dependency, IAM permissions, download/extract logic, error handling for network failures.
- **Latency**: Adds seconds per deployment for the download.

## My Take

For Phase 1, **(a)** is the pragmatic choice. The template repos we're building are tiny — a Dockerfile, a JSON config, a SOUL.md, maybe a workspace folder. They're authored by us. They'll change in lockstep with DOH features. The implicit versioning through DOH's Git history is actually a feature: if you roll back DOH, the templates roll back too.

The risk of (a) — "can't update templates independently" — doesn't bite in Phase 1 because template updates are rare and DOH deploys frequently.

Option (b) earns its complexity when:
- You have templates contributed by others (not just DOH team)
- Template update frequency diverges from DOH update frequency
- You need to pin different template versions per customer org
- You want customers to fork/customize templates

None of these apply yet. And the migration from (a) to (b) is low-cost: move the directory, change a path to a URL, adjust the build script. The executor code barely changes because `repo_service.clone_repository` already handles both `file://` and `git` URLs.

```json
    {
```

- `category=config` → `blueprint.environment_variables` as `{name, value}`
