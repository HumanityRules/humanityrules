## Plan: Fork for the Deployment Editor

There are **three pieces of work**, two backend and one frontend.

### 1. New view: `deployment_editor_fork`

A new endpoint at `GET /deploy/fork/<conversation_id>/` in `deployment_editor.py`. It:

- Validates the source conversation belongs to the user and has a `session_id`
- Creates a forked `Conversation` copying **all** context fields — the existing `chat_fork` is missing `context_app` and `context_deployment_blueprint`
- Redirects to the right deployment editor URL based on what context exists:
  - **No `context_app`** (new-app flow) — redirect to `/deploy/new/?workspace=<slug>&repo=<id>&conversation=<forked_id>`
  - **Has `context_app` + open blueprint** — redirect to `/deploy/<app_slug>/resume/` (the existing `_get_resume_conversation` naturally picks up the fork since it's the most recently created conversation for that blueprint)
  - **Has `context_app` + no blueprint** — redirect to `/deploy/<app_slug>/` (same reasoning — the existing `_get_latest_app_conversation_without_blueprint` finds the fork because it's the newest)

### 2. Modify `deployment_editor_new` to accept `?conversation=`

This is the only editor view that **always** creates a fresh conversation. The existing-app views (`deployment_editor`, `deployment_editor_resume`) already find conversations by recency, so the fork is naturally picked up.

The change: when `?conversation=<uuid>` is present in the query string, load and validate that conversation (belongs to user, correct mode, matches the workspace/repo) instead of creating a new one.

### 3. Fork button in the chat panel header

Add a small fork link/button next to the status badge in `_chat_panel.html`. It would link to `/deploy/fork/<conversation.id>/` — a simple `<a>` tag (not HTMX) since the fork endpoint does a redirect.

---

### Why this is minimal

- Only **one new view** and **one modified view** on the backend. The existing-app editor views don't need changes because they already find conversations by "most recent," and the fork is always the newest.
- The frontend change is a single button addition.
- The `chat_fork` view stays as-is for backward compatibility (though you may want to deprecate/remove it later since the old chat UI is unused).

### Edge case to be aware of

If a user forks an existing-app conversation and then manually navigates to `/deploy/<app_slug>/new/`, that view always creates a fresh conversation (ignoring the fork). But this is fine — "New Deployment" explicitly means "start fresh," so it's correct behavior.
