**Why inline is genuinely simpler, not just shorter:**

- **No thread-pool starvation.** With the polling approach, the removal job thread sits idle waiting for *another* worker thread to pick up the teardown. If the pool is small, you can starve yourself. With inline, one thread does the whole job.
- **No polling cadence / timeout to invent.** `run_teardown` is synchronous and returns success/failure. You handle the result, you move on.
- **Errors are exceptions, not states-to-poll-for.** A failed teardown returns `False` (or raises), and we bail. No "did it transition to FAILED in the last 5 seconds?" reasoning.
- **Same UI observability for free.** `run_teardown` itself flips the deployment through `TEARING_DOWN → TORN_DOWN/FAILED` and writes deployment logs via `DeploymentLogContext`. The UI shows the same teardown progress whether triggered from the button or from inside the removal job.
- **Avoids a subtle race.** With the polling approach, if a deployment is already `TEARDOWN_PENDING` (queued from UI), the removal job and the deployment teardown worker could both target it. Inline just calls `run_teardown` — no queue, no race.
