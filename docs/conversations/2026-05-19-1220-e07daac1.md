## q2: Are we rsync-ing to EFS?

**No, only for the boot-side image-owned sync** — which goes the *other* direction, *from* the image (`/opt/doh`, `/opt/hermes`) *into* the persistent root on local NVMe (the chrooted target). EFS is touched only by the checkpoint write/restore, which uses `tar` against `/hermes-checkpoint/`.

What if checkpoint *were* rsync to EFS instead of tar?

**Pros**:
- Differential — second redeploy onward writes only changed files. After the initial 5 GB seed, a typical redeploy that touched only `/workspace/webapps/projects/<slug>/` would write maybe 50–500 MB. **Probably 5-15× faster than tar** on warm checkpoints.
- No giant single-file pause at the end; writes are streaming.

**Cons / trickiness**:
- EFS rsync has well-known performance pitfalls. Each `mkdir`/`rename`/`stat` is a network RTT (~5 ms). For 5 GB across ~200k files, that's a lot of round trips. Single-file tar wins on metadata-heavy trees.
- Atomicity: `tar` writes to `rootfs.tar.tmp.$$` then atomic `mv` — checkpoint is either fully old or fully new. With rsync to EFS, you'd need a two-snapshot scheme (`current/` and `next/` dirs with a final atomic rename) to avoid mid-redeploy corruption.
- Restore-side becomes `rsync` instead of `tar -x`, which on EFS will be **slower** than tar-extract because of the same metadata-RTT problem.

So the calculus is: **rsync helps a lot on the write side because it skips unchanged data, but hurts on the restore side because EFS metadata is slow.** Whether it's net positive depends on how often you redeploy vs. how often you cold-start (e.g., scaling, ECS task replacement). For your "redeploy a lot during dev" pattern, write-side wins probably dominate.

A middle path that's often the best of both worlds: **incremental tar with snapshots** (`--listed-incremental`). First redeploy writes the full 5 GB tar; subsequent redeploys only stream changed files into a small incremental tar layered on top. Restore reads base + increments. More complex, but combines the differential write speed of rsync with tar's network-friendly streaming.

My instinct: **start with `--zstd`** (one-line change, 30% saved, no risk). Then measure for a week. If checkpoint time is still painful, then explore rsync or differential tar — but each is a real engineering project, not a one-liner.
