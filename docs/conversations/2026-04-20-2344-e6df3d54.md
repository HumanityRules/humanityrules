Good question — the confusion is worth unpacking because "expose a port" means three different things in this stack.

## Three separate layers

**1. Dockerfile `EXPOSE`** — pure documentation. It doesn't open a port, doesn't firewall anything. It's a hint to humans and to tools like `docker run -P`. The Hermes Dockerfile has `EXPOSE 8787` (`template_repos/hermes_agent/Dockerfile:26`); the sidecar Dockerfile has its own `EXPOSE`. Runtime behavior does not depend on these lines.

**2. ECS `portMappings` / `add_port_mappings`** — in Fargate `awsvpc` mode (what DOH uses), this is **also largely informational**. In `awsvpc` every task gets its own ENI, and both containers share that ENI's IP. There is no port publishing / NAT step like in `docker run -p`. Port mappings do two things: they tell the ECS agent which ports to register with a load balancer target group, and they gate Service Connect / Service Discovery. That's it. They do **not** firewall other ports or prevent a container from listening on anything else.

So in our task:
- Sidecar: `add_port_mappings(container_port=sidecar_listen_port)` — `deploy_app.py:587-589`. Used because the ALB target group points here.
- App: `add_port_mappings(container_port=app_config.container_port)` — `deploy_app.py:537`. Present so `DOH_UPSTREAM_PORT` is meaningful and so ECS knows the "app port," but not because of any firewalling effect.

**3. What the OS process actually binds to** — this is what matters. If a process calls `bind(0.0.0.0, 8787)`, the kernel will accept connections from anything that can reach the task's ENI IP, regardless of what the Dockerfile or task definition says.

## What's actually listening on the ENI

- **Sidecar process:** `bind(0.0.0.0, sidecar_listen_port)` (e.g. 8788). This is the public entry point; ALB routes to it.
- **Hermes WebUI process:** `bind(0.0.0.0, 8787)` because the upstream Dockerfile defaults `HERMES_WEBUI_HOST=0.0.0.0`. This is the hole — the WebUI listens on the ENI IP, not just loopback.
- **Sidecar → app traffic** uses `127.0.0.1:8787` (`DOH_UPSTREAM_HOST=127.0.0.1`, `deploy_app.py:568`) — the loopback interface of the shared network namespace.

## So what does each container "expose"?

- **Sidecar container:** its process listens on ENI IP + 8788. ALB reaches it there. Task def declares 8788 as a portMapping so ALB knows where to point.
- **App container (Hermes WebUI):** its process listens on ENI IP + 8787 **and** loopback + 8787 (both, because `0.0.0.0` is "all interfaces"). Task def declares 8787 as a portMapping, but nothing routes to 8787 from outside the task — it's unused by ALB. Loopback 8787 is what the sidecar uses.

## The fix, stated precisely

Set `HERMES_WEBUI_HOST=127.0.0.1` on the app container. The process then binds only to loopback — 127.0.0.1:8787 — and not to the ENI IP. The sidecar still reaches it via loopback (same network namespace). Nothing else in the VPC can, because the kernel will not accept connections on 8787 from any non-loopback address. This is the true isolation boundary, independent of Dockerfile `EXPOSE` lines, ECS port mappings, and security groups.

## Assistant

Your mental model is mostly right for standalone Docker — but ECS task design intentionally breaks it for sidecars. Here's why, and what options exist.

## Why containers in one ECS task can't firewall each other

In Fargate `awsvpc` mode, **all containers in the same task share a single network namespace** — the task's ENI. That's not a configuration choice, it's the design: it's precisely what makes `localhost` work between sidecar and app. Shared namespace means:

- One routing table, one loopback, one set of interfaces.
- No per-container firewall boundary at the network layer. iptables/nftables would see all containers as the same host, and Fargate doesn't grant `NET_ADMIN` anyway.
- Docker's `--network=host`, `--network=none`, user-defined bridges, or per-container network aliases — **none of these apply in Fargate awsvpc.** That machinery only exists in standalone Docker or ECS on EC2 with `bridge` mode.

So within a two-container task, the isolation knob is *which address the process binds to*. That's not a workaround — it is how sidecars are designed to work.

## If you want true container-boundary network isolation

You split them into **two ECS services** (one for the app, one for the sidecar) and wire them with **Service Connect** or a private ALB/NLB. Each service gets its own ENI, its own security group. The app's SG allows ingress only from the sidecar's SG on port 8787. Now the firewall is at the AWS network layer, enforced regardless of what the app process binds to.

Cost of that: two tasks per deployment (2× ENI, 2× Fargate minimum CPU/memory — roughly doubles the bill per app), extra Service Connect config, no more shared EFS mount convenience (EFS still works, but two task roles to grant), and the app now goes over the ENI rather than loopback (a few hundred microseconds and an extra TLS hop if you want encryption in transit). The PDP round trip already dominates latency, so this is negligible, but it's real.

## What the industry actually does

The standard sidecar pattern — Envoy, Istio, AWS App Mesh, service meshes generally — all bind the app to loopback and rely on the sidecar to own the public port. Nobody tries to network-isolate inside a single pod/task, because the network namespace is shared by construction. Kubernetes pods work the same way; that's why Istio's docs tell you to bind your app to `127.0.0.1` or use `localhost` as the rule.

## Recommendation

For DOH's scale (one app per task, personal-assistant-style workloads), the loopback-bind approach is the right layer. It costs one env var and is equivalent in security to the two-task alternative, because:

- The only thing that can reach `127.0.0.1:8787` inside the task is a process running in that task's namespace — i.e., the sidecar, the app itself, or something an attacker already executing inside the task would have. If the attacker is already inside the task, per-container SGs wouldn't help either.
- Nothing in the VPC can reach loopback. The kernel refuses it before any firewall rule runs.

The two-task split becomes attractive only when you need different scaling profiles per container, different IAM roles at the ENI level, or stronger blast-radius isolation (e.g. untrusted customer code in the app container that you don't want to share a namespace with the sidecar). Hermes doesn't hit any of those.
