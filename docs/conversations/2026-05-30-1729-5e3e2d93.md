## The current shape

You have **4 providers split across two "kinds"**, and the kind is what drives all the structure:

| | connect via | files | vault funcs | refresh func |
|---|---|---|---|---|
| **google** | OAuth (`google_oauth.py`) | `google_token_refresh.py` | — | `refresh_google_outcome` |
| **github** | OAuth (`github_oauth.py`) | `github_token_refresh.py` | — | `refresh_github_outcome` |
| **telegram** | paste | `telegram_vault.py` | `telegram_schema`, `save_telegram_credentials` | `refresh_telegram_outcome` |
| **slack** | paste | `slack_vault.py` | `slack_schema`, `save_slack_credentials` | `refresh_slack_outcome` |

And **3 registries across 2 files**, each with different membership:
- `_SCHEMA_BUILDERS` → {telegram, slack}
- `_CREDENTIAL_SAVERS` → {telegram, slack}
- `_OUTCOME_HANDLERS` → {google, github, telegram, slack}

## The asymmetries causing cognitive load

**1. Two file-naming conventions for the same concept.** `*_token_refresh.py` vs `*_vault.py`. Nothing in the name tells you these are all "a provider." You can't glance at the directory and see the four providers as peers — they look like unrelated modules.

**2. The same fact ("which providers do what") is written three times,** in two files, with mismatched membership. To answer "what does Slack support?" you cross-reference three dicts. Adding a 5th provider means remembering to touch the right subset of three registries in two files — easy to get wrong, and nothing enforces it.

**3. Function names don't follow one convention.** `telegram_schema` (noun-first), `save_telegram_credentials` (verb-first), `refresh_telegram_outcome` (verb-first). The provider name is baked into every function, so they're not interchangeable behind a uniform interface.

**4. Real duplication that the structure invites:**
- `_ExchangeResult` is defined identically in `google_token_refresh.py` and `github_token_refresh.py`.
- `_now()` test-indirection duplicated in both.
- The two paste-refresh outcomes (`refresh_telegram_outcome`, `refresh_slack_outcome`) are nearly identical: filter row → check secret fields present → return `has_token` with secrets/config/metadata or `absent`.
- The two OAuth refreshes share the whole skeleton (config lookup → row lookup → exchange → revoke/CAS → has_token); `github_token_refresh.py`'s docstring literally says *"Mirror of google."*

## What I'd do

The unifying insight: **there are two provider kinds (OAuth vs paste), and each provider should have exactly one home module that declares its kind and capabilities.** Make that taxonomy explicit instead of implicit-in-filenames.

Concretely, three moves, roughly in order of payoff:

**A. Collapse the three registries into one per-provider descriptor.** A single source of truth:
```python
PROVIDERS = {
    "google":   ProviderSpec(refresh=google.refresh),
    "github":   ProviderSpec(refresh=github.refresh),
    "telegram": ProviderSpec(schema=telegram.schema, save=telegram.save, refresh=telegram.refresh),
    "slack":    ProviderSpec(schema=slack.schema,    save=slack.save,    refresh=slack.refresh),
}
```
The vault surface iterates `{p for p in PROVIDERS if p.schema}`; the refresh batch iterates `{p for p in PROVIDERS if p.refresh}`. "Supported as a paste provider" becomes a derived property, not a separate dict. One place to read, one place to edit.

**B. Rename to one convention + uniform function names.** `google_provider.py`, `github_provider.py`, `telegram_provider.py`, `slack_provider.py` (or a `providers/` subpackage). Inside, drop the provider prefix: each exposes `schema()`, `save()`, `refresh()`. Now they're visibly peers implementing the same protocol, and the registry in (A) reads cleanly.

**C. Share the two skeletons.** A `paste_refresh_outcome(provider, secret_fields, cache_seconds)` helper covers telegram + slack. A shared `oauth_refresh.py` (holding `_ExchangeResult`, `_now`, and the row-lookup → exchange → revoke/CAS → has_token flow) covers google + github, parameterized by the exchange call and the revoked-code classifier. This is where the symmetry stops being cosmetic and actually removes lines.

A, B, C are independent and ship separately. **A gives the most clarity for the least risk** — it's a pure consolidation, no behavior change. C touches the most logic (the CAS semantics in github are subtle), so it's the one to do carefully with the tests as a net.
