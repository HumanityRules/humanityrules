## Root Cause: `force_ssl` in Phoenix redirects ALB health checks

The ECS task is failing ALB health checks because **Phoenix's `Plug.SSL` middleware intercepts the HTTP health check request and returns a 301 redirect to HTTPS** before the request ever reaches the `/health` route in the router.

### The request flow

```
ALB health check (HTTP GET /health)
  → ECS container port 4000
    → Phoenix Endpoint (endpoint.ex)
      → Plug.SSL (force_ssl from prod.exs) ← INTERCEPTS HERE, returns 301
      → Router (/health → HealthController) ← NEVER REACHED
```

### The smoking gun: `config/prod.exs`

```11:19:sandbox/conv-019c452e-7c3a-76b4-b976-bf571f8db3fc/src/ai_detector/config/prod.exs
# Force using SSL in production. This also sets the "strict-security-transport" header,
# known as HSTS. If you have a health check endpoint, you may want to exclude it below.
# Note `:force_ssl` is required to be set at compile-time.
config :ai_detector, AIDetectorWeb.Endpoint,
  force_ssl: [rewrite_on: [:x_forwarded_proto]],
  exclude: [
    # paths: ["/health"],
    hosts: ["localhost", "127.0.0.1"]
  ]
```

Three problems here:

1. **`force_ssl: [rewrite_on: [:x_forwarded_proto]]`** tells Plug.SSL to check the `X-Forwarded-Proto` header. ALB health checks are sent directly over HTTP and don't include `X-Forwarded-Proto: https`, so Plug.SSL sees them as non-HTTPS and issues a 301 redirect.

2. **`# paths: ["/health"]` is commented out** -- the original developer even anticipated the health check issue and wrote this comment, but left it disabled.

3. **`exclude` is at the wrong config level** -- even if `/health` were uncommented, the `exclude` key is a separate key on the endpoint config, not nested inside the `force_ssl` option list. Plug.SSL would never see it. The correct syntax would be `force_ssl: [rewrite_on: [:x_forwarded_proto], exclude: ["/health"]]`.

### Why the ALB rejects the 301

Our CDK configures the ALB target group health check to use HTTP and expect a **200 only**:

```416:420:devopshero_app/services/infra_customer/deploy_app.py
            health_check=elbv2.HealthCheck(
                enabled=True, path=app_config.health_check_path, protocol=elbv2.Protocol.HTTP,
                interval=Duration.seconds(health_check_interval), timeout=Duration.seconds(2),
                healthy_threshold_count=healthy_threshold, unhealthy_threshold_count=3, healthy_http_codes="200",
            ),
```

`healthy_http_codes="200"` -- the 301 returned by Plug.SSL is not an accepted status code.

### What the agent did vs. what it should have done

**What it did correctly:**
- Identified that a `/health` endpoint was needed
- Created `HealthController` returning `json(conn, %{status: "ok"})` 
- Added `scope "/health"` to the router without any pipeline (no auth, no CSRF -- good)

**What it missed:**
- It never examined `config/prod.exs` for `force_ssl` settings
- The `force_ssl` intercept happens at the Endpoint level, *before* the Router, so the health route in the router is irrelevant -- the request never gets there
- It should have modified `force_ssl` to exclude the `/health` path, e.g.:

```elixir
config :ai_detector, AIDetectorWeb.Endpoint,
  force_ssl: [rewrite_on: [:x_forwarded_proto], exclude: ["/health"]]
```

### Why the agent missed it

The system prompt (`system_prompt_app_deployment.md`) and the `deploy_app` tool documentation have **zero guidance** about `force_ssl` / SSL redirect issues with health checks. This is a gap that affects Phoenix, Rails (`config.force_ssl`), and potentially other frameworks.

### Summary

- **Immediate cause**: ALB HTTP health check to `/health` gets a 301 from Plug.SSL instead of 200
- **Root cause**: `force_ssl` in `prod.exs` applies to all requests before the router, and `/health` is not excluded
- **Agent gap**: No awareness of `force_ssl` configuration in Phoenix production builds
- **System gap**: No guidance in the agent's system prompt about framework-level SSL enforcement conflicting with HTTP health checks

Good questions. Let me answer both.

**1. Yes, all ALB-to-container traffic is HTTP.** The ALB terminates SSL and forwards to the container over plain HTTP. This is confirmed in the CDK code:

```412:413:devopshero_app/services/infra_customer/deploy_app.py
            port=app_config.container_port,
            protocol=elbv2.ApplicationProtocol.HTTP,
```

So the flow for regular user traffic is:

```
User → HTTPS → ALB (terminates SSL) → HTTP → Container:4000
```

And the ALB adds the `X-Forwarded-Proto: https` header to tell the app "the original request was HTTPS."

**2. Yes, your interpretation is exactly right.** `force_ssl: [rewrite_on: [:x_forwarded_proto]]` means:

> "Don't look at whether the actual connection is HTTP or HTTPS. Instead, look at the `X-Forwarded-Proto` header. If it says `https`, consider the request secure and pass it through. If it says `http` (or is missing), redirect to HTTPS with a 301."

This is the standard pattern for apps behind a load balancer -- since the ALB always forwards over HTTP, checking the actual connection scheme would redirect *everything*. The `rewrite_on` option fixes that by trusting the proxy header instead.

The problem is that ALB health checks are internal synthetic requests. They go directly from the ALB to the container over HTTP, and they either don't include `X-Forwarded-Proto` at all, or include `X-Forwarded-Proto: http`. Either way, Plug.SSL sees a non-HTTPS request and issues the 301 redirect you saw in the logs:

```
Plug.SSL is redirecting GET /health to https://ai-detector-and-humanizer.chsandbox.com with status 301
```

The `exclude` block on lines 16-19 is *intended* to carve out exceptions, but as noted it has two issues: `/health` is commented out, and `exclude` is at the wrong nesting level (should be inside the `force_ssl` option list, not a sibling key).

No. ALB health checks are internal synthetic requests generated by the load balancer itself -- you cannot customize their headers. AWS does not provide any option to add `X-Forwarded-Proto` or any other custom header to health check requests.

The fix has to happen on the app side. The Phoenix app needs to let `/health` bypass the `force_ssl` check. The correct approach for this specific app would be fixing `prod.exs` to put `exclude` inside the `force_ssl` option:

```elixir
config :ai_detector, AIDetectorWeb.Endpoint,
  force_ssl: [rewrite_on: [:x_forwarded_proto], exclude: ["/health"]]
```

The question for us is whether the agent should be taught to detect and fix this pattern, or whether there's a more general solution we should consider.

## Assistant

Good instinct. The agent would need framework-specific knowledge for Phoenix, Rails, Django, Next.js, and every other framework that can enforce HTTPS -- it's fragile. The realistic alternatives are all on the infrastructure side:

**Option A: Accept 301 as healthy -- `healthy_http_codes="200,301"`**

One-line change in `deploy_app.py`. If the app returns a 301, it proves the web server is running and processing requests. The redirect only affects health checks (real user traffic gets `X-Forwarded-Proto: https` from the ALB and passes through fine).

- Pros: Universal. Works for any framework. Zero app changes. The app is provably running if it can issue a redirect.
- Cons: The actual health endpoint logic is never executed -- you're only verifying "the web server process is alive," not "the app booted fully and can handle requests."

**Option B: TCP health check instead of HTTP**

Change the health check to just verify the port is open.

- Pros: Also universal. No HTTP semantics involved at all.
- Cons: Even weaker signal than Option A -- a port can be open while the app is stuck in a boot loop. Also loses the ability to use a health endpoint that checks database connectivity, etc. in the future.

**Option C: Teach the agent (what you're worried about)**

Add framework-specific guidance to the system prompt: "if you see `force_ssl` in Phoenix, `config.force_ssl` in Rails, `SECURE_SSL_REDIRECT` in Django... exclude the health path."

- Pros: The health endpoint actually runs, giving a real liveness signal.
- Cons: Incomplete by nature. New frameworks, custom middlewares, and edge cases will always slip through.

My recommendation would be **Option A** as the pragmatic default. The 301 is a reliable "app is alive" signal, and it eliminates an entire class of deployment failures with zero dependence on the agent's framework knowledge. Option C can be layered on top over time as a best-effort improvement, but you wouldn't be relying on it for correctness.
