## Assistant

Yes. The usual approach is **one global base rule** on the native element, not per-template classes.

I added this to `tailwindtheme_app/static_src/src/styles.css` and ran `uv run manage.py tailwind build` so `static/css/dist/styles.css` is updated:

```css
@layer base {
  button:enabled {
    cursor: pointer;
  }
  button:disabled {
    cursor: not-allowed;
  }
}
```

**Why this works well here**

- **Tailwind utilities still win** when you need an exception: e.g. `cursor-default` on `_dropdown_select.html` stays a default arrow, because utilities are layered after `base`.
- **Disabled controls** get `not-allowed` from the `[disabled]` attribute without repeating `disabled:cursor-not-allowed` everywhere (your existing `disabled:cursor-not-allowed` classes remain valid and redundant in some places).

**What it does not cover** (unless you extend the same pattern)

- **`cursor-pointer` on non-`<button>` elements** (e.g. `<a>`, `<summary>`, divs with `role="button"`) — browsers often default links to a pointer; `summary` is separate if you want consistency there.
- **`<input type="submit">`** — you don’t appear to use those in templates; if you add them later, mirror the same `@layer base` selectors for `input` types you care about.

So you get a single, centralized behavior for real `<button>` elements, and you only touch individual components when something should **not** look like a pointer (`cursor-default`) or needs a different disabled story.
