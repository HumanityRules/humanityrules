## Where the 30–60s goes

`commit_and_save()` on every die event does three serial things:

1. `docker commit` — fast (~100ms). Just copies the writable layer into the image store on local SSD.
2. *(occasionally)* `docker export | docker import` to flatten — minutes when it fires, but it's gated behind the 32-layer threshold.
3. `docker save <tag> | zstd -T0 -o <EFS>` — **this is the 30–60s**. It reads the *entire* image tarball (all layers, including the ~1GB+ toolbox base) and streams it through zstd into EFS on every die.

So you're paying the full-image cost on every tool-container exit, even though only the last writable layer actually changed since the previous save.

## Alternatives, roughly in order of how much I'd recommend them

**1. Decouple commit from save (biggest bang-for-buck, smallest change).**
Keep `docker commit` on every die — it's cheap and it's what actually captures the state onto `doh-toolbox:latest` in the local image store. Move `docker save` off the die path entirely:
- Coalesce/debounce: schedule a save ~30–60s after the most recent commit; further commits reset the timer.
- Force a save on SIGTERM (you already do this).
- Optional safety-net: a periodic timer (e.g. every 5–10 min) so idle-but-dirty states still reach EFS.

Result: die events return in ~100ms instead of ~45s. The window for loss is "whatever committed but hadn't been saved yet when the task got killed uncleanly" — which matches what you said you're willing to accept. The commit itself survives dockerd restarts within the task; only a full task-replacement loses uncommitted-to-EFS state.

**2. Push to ECR instead of `docker save` to EFS.**
`docker push` is layer-incremental — only the new commit layer gets uploaded, not the whole base. Restore is `docker pull`, also incremental. This scales better as the toolbox grows and removes the "full tarball every time" cost entirely. Downside: requires an ECR repo and credentials in the task role, and the first push is still a full upload. Worth considering if (1) alone isn't enough, or as the long-term direction.

**3. `docker export` of the dying container instead of `docker save` of the tag.**
Smaller tar (just the writable layer's flat filesystem, typically MBs not GBs), but you lose image metadata and the replay model gets awkward (now you're stacking deltas on top of the base instead of keeping a self-contained image). I'd only reach for this if (1) + (2) aren't options.

## My recommendation

Do (1) now — it's a surgical change to `snapshotter.py`: `events_stream` calls `do_commit` synchronously and hands a debounced save to a worker thread; SIGTERM drains the worker. Re-evaluate after deploying; if EFS write time is still noticeable, move to (2). The tradeoff is the one you already flagged: a task that dies uncleanly loses whatever was committed-but-not-yet-saved, which is bounded by the debounce window.

## Assistant

Short version: `docker diff <container>` shows filesystem changes in the container's writable layer relative to the **image it was created from** — not relative to anything dynamic like "last commit" or "last check." There's no reset point.

**What it covers**
- Added (`A`), changed (`C`), and deleted (`D`) files/dirs in the container's upper layer (overlay2's `upperdir`).
- Reads filesystem metadata only — it's cheap, not a full scan of file contents.

**What it doesn't cover**
- Bind-mounted paths and named volumes (not part of the writable layer). Fine for us — `/workspace` lives on a separate mount and we don't want it in the toolbox image anyway.
- In-memory state, tmpfs, anonymous volumes declared in the image's `VOLUME` directives.

**The "since when" gotcha — this is the important one**

The baseline is *container creation time*, not *last commit time*. `docker commit` on a running container snapshots the writable layer into a new image layer, but **it does not reset the container's writable layer**. The container keeps running on the same upperdir and keeps accumulating.

So after the first write, `docker diff` output is non-empty forever. Using it naively as "did anything change since last save?" doesn't work — it'd always say yes.

I'd want to verify one more claim before we design around it: whether `docker commit` on a running container with a *bit-identical* upper layer (no new writes since the last commit) produces a new image ID with an empty layer, or deduplicates to the same ID. I *think* it always produces a new layer (even empty), but I don't want to design the optimization on a hunch.

**Where this leaves us**

To actually use `docker diff` for change detection we'd need to compare output *between ticks* — e.g. hash the `docker diff` output, store the hash, and skip the save when the hash matches the previous save. That works but adds state we didn't have before.

Honestly, this is getting more elaborate than the problem warrants. Idle-session re-saves at 10-min intervals are ~45s of EFS write and a few MB of bandwidth per tick — not free, but bounded. Unless you're seeing it as a real cost, going with option (1) — drop `_dirty`, always save — is probably the right call. Want me to do that?

## Assistant

Honest answer: probably marginal, and worth sanity-checking before doing it.

**Why it's unlikely to help much**

The current pipeline already overlaps compression and EFS write: `docker save | zstd -o /efs/file` streams through zstd and writes to EFS as it compresses. Total wall-clock is `max(compress_time, efs_write_time)` plus a bit of pipeline overhead. Splitting into "zstd → SSD" then "SSD → EFS" *serializes* those stages — you pay both sequentially. If EFS is the bottleneck (which I'd bet it is for a GB-scale tarball), the EFS-write step alone takes as long as the whole current pipeline.

**Where it could plausibly help**

1. If zstd's streaming-write pattern makes the NFS client unhappy (small/irregular flushes), a subsequent big sequential `cp` from SSD could use EFS bandwidth more efficiently. Possible but I'd want a measurement before believing it.
2. If you ever want the save to be *non-blocking* for the main loop (e.g. SIGTERM: save to SSD fast, exit, mirror to EFS on next boot). That's a real win but a much bigger change — and SSD in the DinD task is ephemeral, so you'd have to accept "task dies mid-save = snapshot lost." The hermes sidecar uses this pattern (SSD-primary + rsync mirror), but it has a continuous reconciliation loop to justify it.

**Where it actively doesn't help**

- Loss window doesn't improve: DinD's SSD goes away with the task, so until it's on EFS it isn't persisted.
- Total EFS bandwidth consumed is identical.
- `rsync` specifically won't delta-transfer usefully here — zstd-compressed tarballs don't rsync well (small input change → large compressed-block churn).

**Cheap experiment if you want to know for sure**

On a live task:
```
time bash -c 'docker save doh-toolbox:latest | zstd -T0 -q -o /efs/test.tar.zst'
time bash -c 'docker save doh-toolbox:latest | zstd -T0 -q -o /tmp/test.tar.zst && cp /tmp/test.tar.zst /efs/test.tar.zst'
```

If the second is meaningfully faster, there's something to optimize. If they're within noise, current setup wins on simplicity.

My recommendation: don't do it. The 30–60s you were seeing is now gone from the die-event path; the remaining 30–60s only happens every 10 min in the background. That's already cheap. Only revisit if measurements say otherwise.
