## Assistant

I'd push back on this one. The "homogeneity" you'd gain is shallow (a shared prefix), and you'd pay for it with semantic precision and a Django convention break. Let me lay it out.

## What the two models actually are

- `IntegrationConfig` — **DOH-global, per-provider** configuration. One row per provider. It's the OAuth *client setup* (client_id, client_secret, redirect_uris from Google Cloud Console). It's the prerequisite that *enables* integrations — not an integration itself.
- `UserThirdPartyIntegration` — **per-user, per-env, per-provider** OAuth grant. The actual live integration: refresh_token, scopes, granted_at.

There's also a third related model already in the codebase:

- `GitProviderIntegration` — **per-organization** connection to a Git provider.

So you have three levels: global config, org-level integration, user-level integration.

## Why I'd vote against the proposed names

**`IntegrationConfig` → `ThirdPartyIntegration` is misleading.** The thing called "the integration" — the live grant that lets DOH act on Google's API on behalf of someone — is `UserThirdPartyIntegration`, not the config row. Renaming the config to `ThirdPartyIntegration` collapses two distinct concepts (setup vs grant) into one word and collides with `GitProviderIntegration` semantically.

**`UserThirdPartyIntegration` → `ThirdPartyIntegrationUser` reverses a Django convention.** Your own codebase uses `<Owner><Thing>` everywhere: `OrganizationMembership`, `GroupMembership`, `UserAttribute`-style. `ThirdPartyIntegrationUser` reads as "a User specialized for third-party integrations" (a User subclass), not "a user's third-party integration." `<User><Thing>` reads naturally; `<Thing>User` doesn't.

## Alternatives that actually buy something

If the itch is "these two models should look related at a glance," here are options that preserve the semantic distinction:

**Option A — drop "ThirdParty" (it's redundant; both rows are obviously external):**
- `IntegrationConfig` stays, or → `ProviderIntegration` (parallels `GitProviderIntegration`)
- `UserThirdPartyIntegration` → `UserIntegration`

That's homogeneous via the `…Integration` suffix, which both names already share, and `UserIntegration` mirrors `UserProfile` / `UserAttribute` patterns. (Side note: the May 7 conversation in the transcripts considered `UserIntegration` early on before settling on the longer name.)

**Option B — strong shared `Integration…` prefix, accurate semantics:**
- `IntegrationConfig` → `IntegrationProvider` (it's literally per-provider)
- `UserThirdPartyIntegration` → `IntegrationGrant`

**Option C — leave it.** The shared word `Integration` already groups them in the admin and in imports. The asymmetry (`<Concept>Config` vs `User<Concept>`) actually communicates the asymmetry of what they are: one is global setup, the other is a user-scoped grant.

## Cost reminder

Either rename means a `db_table` rename migration plus updating `related_name`s, admin, views, tests, management commands, and the GoogleOAuth flow. The models were added in the past two weeks ([UserThirdPartyIntegration model](2026-05-09-1236-feefa2cf), [IntegrationConfig model](2026-05-07-2234-feefa2cf)) so prod data isn't a worry — but it's still ~15 files to touch. Worth doing for the *right* names; not worth doing for a prefix tax.

My recommendation: **Option A** if you want change, **Option C** if you want zero churn. Want me to proceed with one of those — or stick with your original proposal anyway?

## Assistant

Two different things in the admin, two different sources:

**1. The label in the sidebar / changelist heading** (e.g., "Integration configs" in the left nav and on the list page) comes from `Meta.verbose_name` / `Meta.verbose_name_plural`.

**`IntegrationConfig` doesn't define one.** It has no `class Meta` block at all (`devopshero_app/models.py:1664-1682`), so Django auto-derives it from the class name: `IntegrationConfig` → `"integration config"` / `"integration configs"`, then title-cases it for display → **"Integration configs"** (note: lowercase "c", non-parallel with the other two).

Compare the other two in the cluster, which set it explicitly:

```1719:1721:devopshero_app/models.py
    class Meta:
        verbose_name = "Integration User Grant"
        verbose_name_plural = "Integration User Grants"
```

```261:264:devopshero_app/models.py
    class Meta:
        verbose_name = "Integration Git Provider"
        verbose_name_plural = "Integration Git Providers"
```

**2. The label per row** in the changelist (the link text for each object) comes from `__str__()`. For `IntegrationConfig` that's:

```1681:1682:devopshero_app/models.py
    def __str__(self) -> str:
        return f"IntegrationConfig({self.provider})"
```

So if you want `IntegrationConfig` to render as **"Integration Configs"** (capitalized, parallel with "Integration User Grants" and "Integration Git Providers") in the admin sidebar, add a `Meta` block:

```python
class Meta:
    verbose_name = "Integration Config"
    verbose_name_plural = "Integration Configs"
```
