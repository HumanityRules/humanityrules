I used three tag-scoped grants instead of a single wildcard grant. That was deliberate — because the wildcard optimization path in `filter_permitted_resources` has a bug. Look at lines 242-259 of the engine:


When a wildcard grant policy exists, the code only collects grants/denials from **wildcard** policies (line 247: `if _is_wildcard(...)`). A tag-scoped deny like "deny `!workspace:view` on `domain=finance`" is skipped entirely, and the function short-circuits returning the full queryset. The deny is silently ignored.

This means `evaluate_policies` and `filter_permitted_resources` disagree: calling `evaluate_policies` individually on the finance workspace would correctly deny the action, but `filter_permitted_resources` would include it. This is the real-world scenario — org admins get wildcard grants from the seed policies, and a tag-scoped deny should be able to carve out exceptions. The test I wrote avoids this by only using tag-scoped grants, which hides the inconsistency.

**Gap 2 — `None` conditions act as implicit wildcard**

The engine coerces `None` to `[]` via `or []` at lines 142-143:

```python
identity_match = _conditions_match(policy.identity_conditions or [], attr_set)
resource_match = _conditions_match(policy.resource_conditions or [], tag_set)
```

And `_conditions_match([], attr_set)` returns `True` (vacuously true via `all()` on an empty iterable). So a policy with `identity_conditions=None` silently matches **every user**, and `resource_conditions=None` matches **every resource**. This is security-relevant behavior that has no test. It differs from an explicit wildcard `[{"key": "*", "value": "*"}]` — notably, `_is_wildcard([])` returns `False`, so the `filter_permitted_resources` wildcard optimization path won't trigger for null conditions, creating yet another behavioral inconsistency.

**Gap 3 — `check_action` is untested**
