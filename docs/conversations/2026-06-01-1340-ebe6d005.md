**3. Docker Compose auto-sync**

## Assistant

The problem was **layer order**, not missing BuildKit magic.

## What was going wrong

Docker invalidates a layer and **every layer after it** when the layer’s inputs change. The old Dockerfile had this order:

1. `COPY doh_runtime`, skills, `webui-extension` ← changes often  
2. `uv pip install` ← ~minutes  
3. Linuxbrew bootstrap ← ~seconds  

So editing any DOH source file busted the pip-install and brew layers, even though those steps don't depend on your runtime code at all.

## The fix: put your source last

DOH-owned trees now copy **after** all expensive dependency work:

```dockerfile
# ... apt, clone agent, apply patches, uv pip install, linuxbrew ...

COPY skills/...
COPY SOUL.md, config.yaml.template
COPY doh_runtime /opt/doh/runtime
RUN chmod +x webapps && ln -sf ...
COPY webui-extension /opt/doh/webui-extension
```

After a `doh_runtime` edit, a rebuild now only reruns those last layers. Measured on your machine: **~0.9s** vs the full multi-minute build. `uv pip install` and Linuxbrew stay `CACHED`.

## Additional caching (for when layers *do* bust)

1. **BuildKit cache mounts** on apt and `uv` — speeds cold builds and patch/Dockerfile changes  
2. **Git clone cache** for the upstream Hermes agent — helps when the pin changes, not on routine edits  
3. **`.dockerignore`** — keeps docs/artifacts out of the build context  
4. **`cache_from: hermes-agent:local`** in compose — reuses the previous local image as a cache source  

## What still triggers a slow rebuild

Only changes that actually affect dependencies:

- `build/patches-webui/` or `build/patches-agent/`
- Upstream Hermes pin / `HERMES_AGENT_EXTRAS`
- Base image version
- Dockerfile structure itself

## Reliability angle

This doesn't fix the startup rsync clobber yet — that's the next piece. What it **does** give you is: **rebuild → restart → image matches your source**. No ambiguity about whether a slow rebuild actually picked up your edits; the expensive layers aren't rerun unless they need to be.

- `template_repos/hermes_agent_local/docker-compose.yml` — `cache_from`  
- `template_repos/hermes_agent_local/README.md` — documents caching behavior

how is it keyed?

## Assistant

There are two separate caches in play, and they use different keys.

## 1. Docker layer cache (does this `RUN` run at all?)

Keyed on the **exact `RUN` instruction text** plus the checksums of everything that came before it (base image, earlier layers).

If you change `v2026.5.29.2` to another tag, that string changes → this layer is a miss → BuildKit **re-executes** the whole shell block.

If you only edit `doh_runtime/` later in the Dockerfile, this layer stays **CACHED** and this block never runs.

## 2. BuildKit cache mount (what’s in `/root/.cache/hermes-agent-git`?)

Keyed on the mount descriptor, roughly:

- `type=cache`
- `target=/root/.cache/hermes-agent-git`
- `sharing=locked`
- optional `id=` (we didn’t set one, so Docker derives it from the mount)

That mount is **shared across rebuilds of this same Dockerfile** on your machine. It survives even when the layer reruns.

It is **not** keyed to the git branch/tag. The `if [ -d .../.git ]` check only asks “is there *some* clone here?” — not “is it `v2026.5.29.2`?”

So when you bump the pin:

1. Layer cache misses → `RUN` runs again  
2. Cache mount may still hold the **old** clone  
3. Hit branch runs → `rsync`s stale tree → **wrong version**

In practice that’s rare (pin changes infrequently), but it’s a real gap. A safer pattern would be something like cache path `/root/.cache/hermes-agent-git/v2026.5.29.2`, or always `git clone` into a temp dir and only use the mount as a speed hint (e.g. `--reference`).

## Summary

| Mechanism | Keyed on |
|---|---|
| Layer cache | Full `RUN` text + prior layers |
| Cache mount | Mount target/`id`, not git ref |
| Your `if` branch | Presence of `.git` / `HEAD`, not ref |

So “keyed” for speed is really **“same Dockerfile mount slot on this builder”** — not **“this Hermes version”**.

## Assistant

The fix is to **include the ref in the cache mount `id`**, and centralize the ref in an `ARG`:

```dockerfile
ARG HERMES_AGENT_REF=v2026.5.29.2

RUN --mount=type=cache,id=hermes-agent-git-${HERMES_AGENT_REF},target=...,sharing=locked \
    ...
    git clone --depth 1 --branch ${HERMES_AGENT_REF} ...
```

BuildKit treats each `id` as a separate cache volume. When you bump `HERMES_AGENT_REF`:

1. Layer cache misses (the `RUN` text changed).
2. Cache mount `id` changes → empty backing store for the new ref.
3. The `if` check fails → fresh `git clone` of the new tag.

When the ref is unchanged but the layer reruns (e.g. patch edit), the same `id` still has the clone → fast `rsync` path.

To bump Hermes upstream now, change one line:

```dockerfile
ARG HERMES_AGENT_REF=v2026.5.29.2   # → new tag
```

Old ref caches stay on disk harmlessly; they are just unused.
