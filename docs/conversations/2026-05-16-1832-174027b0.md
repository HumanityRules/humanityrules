## What `/etc/profile.d/` is in this image

It's **OS-level** (Debian's standard mechanism, shipped by the base distro), but everything *inside* it is something **DOH owns**.

The base image chain is:
```
ghcr.io/nesquena/hermes-webui:0.51.63   ← upstream Hermes WebUI (Debian/Ubuntu base)
   └─ FROM (probably) python:slim or similar Debian
        └─ ships /etc/profile + /etc/profile.d/ as-is from Debian
```

`/etc/profile.d/` is **the** Debian-blessed extension point for adding system-wide shell init. `/etc/profile` ends with a `for i in $(run-parts ... /etc/profile.d); do . $i; done` loop (we saw it in the dump). It's been there since forever and won't change between Debian point releases.

## Concretely what we'd add

A single `RUN` line in our Dockerfile, dropping a file we own:

```dockerfile

    && chmod 644 /etc/profile.d/doh-bin.sh
```

This file is created in *our* image layer, not the upstream's. It lives at `/etc/profile.d/doh-bin.sh` — but ownership-wise, it's a DOH artifact baked into the DOH-customized Hermes image.

## What happens during upgrades

Three independent upgrade tracks to think through:

| Track | Upstream changes | What happens to our profile.d file |
|---|---|---|
| **Hermes WebUI base image bump** (`0.51.63` → newer) | We change `FROM` line | Our `RUN` re-runs on rebuild; file gets re-created on the new base. **Survives.** Only breaks if upstream stops being Debian-derived (extremely unlikely; would also break the `apt-get` line above it). |
| **Hermes Agent version bump** (`v2026.5.7` → newer) | We change the `git clone --branch` arg | Doesn't touch /etc at all; only writes to `/opt/hermes/agent`. **No interaction.** |
| **Debian point release** inside the upstream base | Upstream rebuilds against newer Debian | `/etc/profile`'s `run-parts /etc/profile.d/*.sh` loop is part of Debian's `base-files` package and has been stable for ~20 years. **No risk.** |

## The design, summarized

DOH's customizations of the Hermes image fall into three buckets, each with a clear upstream-update story:

| Kind of change | Where it lives | Update behavior |
|---|---|---|
| **Patches against upstream code** | `build/patches-webui/`, `build/patches-agent/` | Applied at image build via `apply-patches.py`. **A fuzz/reject is a build failure**, surfacing drift early. Each patch should have a documented expiration. The `hermes-update-check` skill periodically checks "has this fix landed upstream?" and removes the patch when it has. |
| **DOH-owned files added alongside upstream** | `doh_runtime/`, `webui-extension/`, `skills/google-workspace/`, `skills/posthog/` | Copied in via `COPY` in our Dockerfile. Independent of upstream. |
| **Image-layer additions on top of the base** | The big `RUN` block at lines 30-50: nono, AWS CLI, `gws`, apt packages | Pinned to specific versions via `ARG`s. Re-laid-down on every rebuild. |

Adding `/etc/profile.d/doh-bin.sh` is **bucket #3** — same category as the existing `gws`, `aws`, and `nono` installs. It's a DOH-owned addition to the image that doesn't touch any file upstream owns.

## Where it does and doesn't fit cleanly

✅ **Fits the design:**
- It's in *our* Dockerfile, not upstream's.
- It writes to a Debian-standard drop-in directory, not patching `/etc/profile`.
- It needs no `hermes-update-check` review — there's no upstream code drifting underneath it. (Compare with patches, which need re-verification on every WebUI bump.)
- Symmetric with how `gws`/`aws`/`nono` already get added.

⚠️ **One nuance:** the underlying *root cause* — that Hermes' login-shell snapshot lets `/etc/profile` clobber PATH for non-root users — is arguably an upstream bug. Strictly by the doctrine in `patches-webui/README.md`:

> "Document the upstream issue/PR in the patch header — each patch should have an expiration date (the day the fix lands upstream)."

…the most rigorous version would be to file an upstream issue ("login-shell snapshot drops PATH entries set by the parent process for non-root uids") and either land a fix or carry a `patches-agent/` patch with an expiration. Then once the fix lands upstream, `hermes-update-check` would flag it for removal.

But that's overkill for a one-line system-config drop. `/etc/profile`'s reset behavior is *Debian's* design, not Hermes's bug — Hermes is just doing what login shells normally do. Even if upstream Hermes "fixed" it, our `/etc/profile.d` file would still be the right shape to ensure `/opt/doh/bin` is on PATH for any login shell anywhere in the image. So it stands on its own.
