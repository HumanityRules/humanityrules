## How the API server works in Hermes

The `gateway` (started 4th in `webui.sh:71-82`) auto-starts an OpenAI-compatible REST server when env vars are set — it's a "platform" inside the gateway, not a separate process. Activation logic is in `gateway/config.py:1368` and the adapter at `gateway/platforms/api_server.py:581`.

**Env vars** (all read from process env):
- `API_SERVER_ENABLED=true` — turns it on (presence of `API_SERVER_KEY` also enables it)
- `API_SERVER_KEY=<bearer>` — required for non-loopback bind; on `127.0.0.1` it's optional
- `API_SERVER_HOST` (default `127.0.0.1`)
- `API_SERVER_PORT` (default `8642`)
- `API_SERVER_MODEL_NAME` (default = profile name; advertised on `/v1/models`)
- `API_SERVER_CORS_ORIGINS` (CSV)

**Endpoints**: `/v1/chat/completions`, `/v1/responses`, `/v1/runs`, `/v1/models`, `/v1/capabilities`. Persists to `response_store.db` under `HERMES_HOME` (already on `/workspace`, so survives redeploys).

## What it would take in DOH

Three concrete code changes plus one design decision.

**1. nono profile (`doh_runtime/hermes-nono-profile.json`)**
- Add `API_SERVER_ENABLED`, `API_SERVER_KEY`, `API_SERVER_PORT`, `API_SERVER_HOST`, `API_SERVER_MODEL_NAME`, `API_SERVER_CORS_ORIGINS` to `allow_vars`.
- Add the port (8642 by default) to `listen_port` and `open_port` so the gateway can actually bind it inside nono.

**2. supervisor.sh `run_in_nono`**
- Either rely on `allow_vars` (if DOH already exports them in the task env) or explicitly forward them in the `runuser … env` block at line 260. Right now nothing exports them, so the gateway will silently start with the platform disabled — same as today.

**3. Where the env vars come from**
- Hermes-personal-assistant deploys (env-bearer overlay) is the natural place to inject them. `API_SERVER_KEY` should be a generated secret per app, persisted by DOH, surfaced in the user-facing UI for them to plug into Open WebUI / LibreChat / their script.

**4. Public exposure — the design call.** The api_server binds inside the nono sandbox; nothing outside the container can reach it without a route. Two options:

- **Loopback only** (recommended): no Caddy/ALB route. Useful only for in-sandbox MCP-style calls. Almost no value, since Hermes already has its own runtime there. Skip unless we have a use case.
- **Public via ALB**: add a Caddyfile route `handle_path /v1/* { reverse_proxy 127.0.0.1:8642 }` *before* the catch-all to WebUI:8789. Critical question: does it sit **behind policy-proxy's WorkOS auth** (browser-only, useless for programmatic clients), or **bypass it** and rely on `API_SERVER_KEY` alone? If the latter, policy-proxy needs a bypass rule for `/v1/*` so bearer-token clients can hit it without a session cookie. That's the real architectural decision.

## Tradeoff to flag

If we expose `/v1/*` publicly with bearer-only auth, we're adding a credential model parallel to WorkOS — separate revocation, separate audit trail, and the key itself sits in user env. That's the standard for OpenAI-compatible endpoints (Open WebUI expects exactly this), but it widens the auth surface. Worth confirming this matches the "governance built-in" pillar before plumbing it.

My recommendation: defer the work until there's a concrete user asking for Open WebUI / LibreChat integration. The plumbing is small (~30 lines across 2 files plus a Caddy route) but the auth-bypass design call should be driven by a real customer ask, not built speculatively.
