## User

what is 644, what is 755?

---

## Assistant

Unix file mode bits, in octal. Each digit is one set of permissions for **owner / group / others**, where each digit is a sum of:

- `4` = read (`r`)
- `2` = write (`w`)
- `1` = execute (`x`)

So:

- **`644`** = `rw- r-- r--` → owner can read+write, group and others can only read.
  Used for **data files / config** that nobody needs to execute. Line 57's `/etc/profile.d/doh-bin.sh` is sourced (not executed) by `/etc/profile`, so it doesn't need the `x` bit. Standard mode for files in `/etc/profile.d/`.

- **`755`** = `rwx r-x r-x` → owner can read+write+execute, group and others can read+execute.
  Used for **executables and directories**. Line 59's `prune-skills.sh` is invoked directly (`RUN /tmp/prune-skills.sh ...` on line 62), so it needs the `x` bit. Same applies to `build/apply-patches.py` on line 75.

The leading digit (`0644`, `0755`) covers setuid/setgid/sticky bits — omitted here because we don't need any of them.

Quick mnemonic: `7 = rwx`, `6 = rw-`, `5 = r-x`, `4 = r--`.

## User

by default, what's the permissions the a file has?

---

## Assistant

Determined by **umask** — a mask that *subtracts* bits from the maximum default permissions:

- Max for files (no `x` by default): `666`
- Max for directories: `777`

The resulting permissions are `max & ~umask`.

**Typical umask values:**

- `022` (most Linux systems, including Docker build by default):
  - Files → `666 - 022 = 644` (`rw-r--r--`)
  - Directories → `777 - 022 = 755` (`rwxr-xr-x`)
- `002` (Debian/Ubuntu interactive user accounts):
  - Files → `664`
  - Directories → `775`

**Implications for the Dockerfile:**

- `RUN echo ... > /etc/profile.d/doh-bin.sh` already creates the file as `644` under the default Docker build umask. The explicit `chmod 644` on line 57 is **redundant** — defensive but not strictly needed. You could drop it.
- `COPY` *preserves* the source file's mode by default — that's why `COPY --chmod=755` exists, to force a known mode regardless of what the file looked like on the host. Useful when host file modes may vary (e.g., a contributor checks out the repo on a filesystem that doesn't preserve the `x` bit).
- New files never get the `x` bit from umask alone — `chmod +x` or `--chmod=755` is the only way to make a freshly created file executable.

Want me to drop the redundant `chmod 644`? It's a one-line cleanup.


### 1. Hard-remove from `seed_app_templates.py`, or just mark `is_active=False`?

Important: **`seed_app_templates` only does `update_or_create` — it never deletes rows.** So if you delete the entries from the file:

- The next seed run leaves any existing DB rows untouched. They become orphans — still queryable, still potentially visible in the deploy UI unless filtered by `is_active`.
- You'd need a one-shot cleanup (a migration, or just an ad-hoc `doh_query` + manual update) to flip `is_active=False` on the stranded rows.

The alternative is to **keep the entries but set `is_active=False`** (plus a deprecation comment). That way:

- Next seed run automatically stamps `is_active=False` on existing rows, hiding them from the deploy UI.
- The template config stays in the source tree as a reference (which is your stated goal).
- Reversible if needed.

My vote: **keep + `is_active=False`**. It's the standard soft-deprecate pattern, and it actually achieves "kept as reference" better than deleting from the seed (because the code in seed_app_templates is more readable as reference than a raw directory).

### 2. Move risks breaking redeploys of existing apps

When `deploy-app-template` runs, it stamps `clone_url = f"doh-template://{source_repo_path}"` onto a `Repository` row that's permanently linked to the App. On redeploy, `repo_service.py` resolves that to `settings.TEMPLATE_REPOS_DIR / <path>`.

So if any prod/customer App was created from `hermes-docker-personal` or `hermes-docker-slack`, its `Repository.clone_url` is `doh-template://hermes_docker_agent`. Move the directory → next redeploy fails (clone_url resolves to a missing path).

**Do you have any live apps from these templates in prod/customer envs?** If yes, we need to either:

- Update those Repository rows via a data migration to point at `deprecated/hermes_docker_agent`, or
- Add a one-time fallback in `repo_service.py` ("if path doesn't exist, try `deprecated/<path>`"), or
- Just accept that those apps are also being deprecated and won't redeploy.

If the answer is "no live apps, project is pre-beta, nobody's deployed these in prod," we can skip this whole branch.
