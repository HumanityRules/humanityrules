## Implementation Approach

I'd recommend creating a new `RedirectStack` (or extending `CdnStack`) that looks something like this:

```python
class RedirectStack(Stack):
    """Redirect devopshero.co to devopshero.ai."""

    def __init__(self, scope: Construct, construct_id: str, **kwargs) -> None:
        super().__init__(scope, construct_id, **kwargs)

        redirect_domain = "devopshero.co"
        target_domain = "devopshero.ai"

        # Look up the hosted zone for devopshero.co
        hosted_zone = route53.HostedZone.from_lookup(
            self, "RedirectHostedZone", domain_name=redirect_domain
        )

        # Certificate for devopshero.co
        certificate = acm.Certificate(
            self,
            "RedirectCertificate",
            domain_name=redirect_domain,
            subject_alternative_names=[f"www.{redirect_domain}"],
            validation=acm.CertificateValidation.from_dns(hosted_zone),
        )

        # CloudFront Function to redirect all requests to devopshero.ai
        redirect_function = cloudfront.Function(
            self,
            "RedirectFunction",
            function_name="doh-prod-co-redirect",
            comment="Redirects devopshero.co to devopshero.ai",
            code=cloudfront.FunctionCode.from_inline(f"""
function handler(event) {{
    var request = event.request;
    var response = {{
        statusCode: 301,
        statusDescription: 'Moved Permanently',
        headers: {{
            'location': {{ value: 'https://{target_domain}' + request.uri }}
        }}
    }};
    return response;
}}
"""),
        )

        # Dummy origin (CloudFront requires an origin even though we never reach it)
        # Using devopshero.ai as origin since the function intercepts all requests
        dummy_origin = origins.HttpOrigin(target_domain)

        # CloudFront distribution for redirect
        distribution = cloudfront.Distribution(
            self,
            "RedirectDistribution",
            domain_names=[redirect_domain, f"www.{redirect_domain}"],
            certificate=certificate,
            default_behavior=cloudfront.BehaviorOptions(
                origin=dummy_origin,
                viewer_protocol_policy=cloudfront.ViewerProtocolPolicy.REDIRECT_TO_HTTPS,
                function_associations=[
                    cloudfront.FunctionAssociation(
                        function=redirect_function,
                        event_type=cloudfront.FunctionEventType.VIEWER_REQUEST,
                    ),
                ],
            ),
            price_class=cloudfront.PriceClass.PRICE_CLASS_100,
            comment="Redirect devopshero.co to devopshero.ai",
        )

        # Route53 A record for apex (devopshero.co)
        route53.ARecord(
            self,
            "RedirectApexARecord",
            zone=hosted_zone,
            record_name=redirect_domain,
            target=route53.RecordTarget.from_alias(targets.CloudFrontTarget(distribution)),
        )

        # Route53 A record for www (www.devopshero.co)
        route53.ARecord(
            self,
            "RedirectWwwARecord",
            zone=hosted_zone,
            record_name=f"www.{redirect_domain}",
            target=route53.RecordTarget.from_alias(targets.CloudFrontTarget(distribution)),
        )
```

Then in `app.py`, add:

```python
from stacks.redirect_stack import RedirectStack

# After the other stacks...
redirect_stack = RedirectStack(
    app,
    f"{prefix}-redirect",
    env=env_us_east_1,
)
```

## 302 vs 301 Redirect

Yes, we can use `302 Found` (temporary) instead of `301 Moved Permanently`. Just change the status code in the CloudFront Function:

```javascript
statusCode: 302,
statusDescription: 'Found',
```

This prevents browsers from caching the redirect permanently, so you can change your mind later.

---

## CNAMEs Instead of Redirects

There are two interpretations here:

### Option A: DNS CNAME (won't work for apex)

Standard DNS **doesn't allow CNAMEs on apex domains** (like `devopshero.co`). You can only CNAME subdomains like `www.devopshero.co`. This is a DNS specification limitation, not an AWS thing.

So you could:
- CNAME `www.devopshero.co` → `devopshero.ai` ✓
- CNAME `devopshero.co` → `devopshero.ai` ✗ (not allowed)

### Option B: Serve the same site on both domains (no redirect)

This is probably what you're thinking of. Instead of redirecting, you could **add `devopshero.co` to the existing CloudFront distribution**:

1. Update the certificate to include `devopshero.co` and `www.devopshero.co`
2. Add both domains to the existing CloudFront distribution's `domain_names`
3. Create Route53 Alias records pointing to the same CloudFront distribution

**Result**: Both `devopshero.ai` and `devopshero.co` serve the exact same app. No redirect - the URL stays as whatever the user typed.

**Downsides**:
- SEO issue: Google sees duplicate content on two domains (fixable with canonical tags)
- Session cookies might not work across domains (depends on your cookie settings)
- You'd need to update the certificate stack to cover both domains

---

If you want flexibility and don't want permanent caching:
- **302 redirect** is the safest choice - visitors end up on `devopshero.ai` but you can change it later

If you want both domains to work identically:
- **Add to existing CloudFront** - but handle the SEO/cookie implications

You're right to question it. There is a simpler approach using **S3 website hosting** with built-in redirect rules — no JavaScript needed.

## S3 Redirect Approach

S3 buckets configured for static website hosting have native redirect support:

```python
# S3 bucket with redirect - no CloudFront Function needed
redirect_bucket = s3.Bucket(
    self,
    "RedirectBucket",
    bucket_name=f"{redirect_domain}-redirect",
    website_redirect=s3.RedirectTarget(
        host_name=target_domain,
        protocol=s3.RedirectProtocol.HTTPS,
    ),
    # Block public access - CloudFront uses OAI/OAC
    block_public_access=s3.BlockPublicAccess.BLOCK_ALL,
)
```

Then CloudFront uses `S3Origin` pointing to the bucket's **website endpoint** (not the REST endpoint).

**Pros:**
- No JavaScript code
- Native AWS feature
- Arguably more "declarative"

**Cons:**
- Requires an S3 bucket (additional resource)
- S3 website hosting only supports 301 redirects, not 302 (this is the catch!)
- Slightly more complex CloudFront origin setup for website endpoints

---

## The Catch: S3 Only Does 301

S3's `website_redirect` feature **only returns 301 (permanent)**. There's no option for 302.

So if you want 302 specifically, the CloudFront Function is actually the simplest way. AWS doesn't provide a declarative "redirect behavior" in CloudFront itself — it's a frequently requested feature that hasn't been added.

---

## Summary

| Approach | 302 Support | Code Required | Extra Resources |
|----------|-------------|---------------|-----------------|
| CloudFront Function | ✓ | JS snippet | None |
| S3 Website Redirect | ✗ (301 only) | None | S3 bucket |
| Lambda@Edge | ✓ | Full Lambda | Lambda function |

For 302 redirects, the CloudFront Function is unfortunately the simplest option AWS offers. If you're okay with 301 instead, the S3 approach is cleaner.
