Yes, you're right. Django 6.0 has native connection pooling support for PostgreSQL via psycopg3. From the official docs:

**Connection pool (Django 6.0+)**

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        # ...
        "OPTIONS": {
            "pool": True,
        },
    },
}
```

This is actually **better** for your ASGI application than `CONN_MAX_AGE`. The Django docs explicitly state:

> When using ASGI, persistent connections should be disabled. Instead, use your database backend's built-in connection pooling if available.

**Key differences:**

- **`CONN_MAX_AGE`** — Per-thread persistent connections. Each thread keeps its own connection. Works poorly with ASGI because async contexts create connections outside the threadpool (this was part of your leak issue).

- **`pool=True`** — Uses psycopg3's `ConnectionPool`. A shared pool where connections are borrowed and returned. Designed to work with async code.

**Requirements:**
- Must use `psycopg` (psycopg3), not `psycopg2`
- Requires `psycopg[pool]` or `psycopg-pool` package

## Assistant

Based on the Django PR discussion and psycopg3 pool docs, here's what I understand:

**`close_all()` is still needed, but for a different reason:**

- **Without pool**: `close_all()` closes actual TCP connections to PostgreSQL
- **With pool**: `close_all()` returns borrowed connections back to the pool

The pool manages a set of connections. When Django "borrows" one via `pool.getconn()`, that connection is marked as "in use." If Django doesn't return it (via `close()` which internally calls `pool.putconn()`), the pool thinks the connection is still in use.

In our async contexts:
1. The streaming generator / background task borrows connections from the pool
2. Without explicit cleanup, those connections stay "checked out" forever (from the pool's perspective)
3. Eventually the pool runs out of available connections

So the `close_all()` calls are still required — they're not "closing" connections, they're **returning them to the pool**. The comments I wrote are accurate.

**To verify this works after deploying**, you should monitor:
1. Aurora connection count (should stay bounded)
2. psycopg pool stats (if you add logging for `pool.get_stats()`)

The key behavioral difference you'll see:
- **Before (no pool)**: Connection count would spike and never come down without the `close_all()` calls
- **After (with pool)**: Pool manages a fixed set of connections, but `close_all()` is still needed to return them for reuse
