## Diagnosis

The WebSocket fails because **the policy proxy doesn't support WebSocket upgrades**, and every request from the browser goes through it before reaching Caddy → your `ttyd` app.

The traffic path documented in `template_repos/hermes_agent/doh_runtime/supervisor.sh:256-258` is:

```
ALB → policy-proxy:8788 (auth gate) → Caddy:8787 → user app on 4xxx
```

Caddy itself handles WebSocket upgrades fine (the route block in `webapps_lib.py:134-143` is just a `reverse_proxy`, which is WS-transparent). The break is one hop earlier:

1. **`policy_proxy/proxy.py:21-24`** strips `upgrade` (and `connection`) as hop-by-hop headers before forwarding.
2. **`policy_proxy/proxy.py:84`** sends the request via `httpx.AsyncClient.send`, which speaks only HTTP, not WebSocket. There is no `@app.websocket(...)` route anywhere in `policy_proxy/`.

So the browser's `GET /webapps/terminal/ws` with `Upgrade: websocket` arrives at policy-proxy, the upgrade headers get stripped, httpx forwards it as a plain HTTP/1.1 GET to ttyd, ttyd doesn't see a WebSocket handshake, and the connection closes — that's exactly what code `1006` means (abnormal closure, no close frame). The same path is why the ttyd JS reports `connection closed`: it never got a 101 Switching Protocols.

This is unrelated to the Phoenix `/live` prefix trap in `skills/webapps/elixir.md:56-87` — your URL `/webapps/terminal/ws` already has the correct `/webapps/<slug>` prefix. The bug is in the policy-proxy layer, not in the app's URL generation.

Now append the WS proxy function. Let me think about edge cases first:

1. **Subprotocol negotiation**: Browser sends `Sec-WebSocket-Protocol: tty`. We must (a) pass that list to upstream's `ws_connect(subprotocols=[...])`, (b) wait for upstream to confirm one (`upstream.subprotocol`), then (c) pass that confirmed value to `websocket.accept(subprotocol=...)`. ## The good

**This is actually a bug fix, not just a refactor.** The original `proxy.py` had this on upstream failure:

```python
except InvalidStatus as exc:
    await websocket.close(code=1011)   # close BEFORE accept()
    return
```

Closing in `CONNECTING` state translates to HTTP 403 at the ASGI layer — the browser sees `event.code === 1006`, not 1011. The accept-then-close comment that the peer *deleted* in app.py was specifically warning about this, but the proxy.py code itself never followed that rule for the upstream-failure paths. The refactor routes those paths through `_close_ws_after_accept` and now they actually work.

The test upgrade is the proof: `TestClient` papered over this bug because it observes the ASGI `websocket.close` event directly without uvicorn's HTTP-403 conversion. Real uvicorn + real `ws_connect` exercises the same code path the browser does. That's why this one test had to go async with a real server — the others assert close codes for paths that *do* call `accept()` first, so `TestClient` is fine for them.

The exception-based decoupling is also right: proxy.py now owns transport, app.py owns policy/close codes. Clean.
