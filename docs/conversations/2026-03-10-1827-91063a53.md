## Assistant

`DOH_RUN_JOB_WORKER=0` is only a statement about the current process. It means “this Django process should not auto-start its own worker,” not “there is no worker anywhere.”

The race is:

1. `deploy_blueprint` creates a `Deployment` row in `pending`.
2. Because the web process sees `DOH_DEBUG_DEPLOYMENTS=1` and `DOH_RUN_JOB_WORKER=0`, `app_deployment_debug_simulator.maybe_start_debug_deployment()` starts a local background thread.
3. Your separate `uv run manage.py run_job_worker` process is also polling for `pending` deployments and can claim that same row.
4. Now two different executors may process the same deployment.

Why that’s bad:

- If both processes have `DOH_DEBUG_DEPLOYMENTS=1`, you can get two fake deploys racing on one deployment.
- If only the web process has `DOH_DEBUG_DEPLOYMENTS=1`, the web thread can fake success while the independent worker still runs the real AWS path.
- The final DB state becomes “whoever wrote last wins” for `Deployment.status`, `DeploymentLog`, `service_url`, and the blueprint status.

So the bug is really this: `maybe_start_debug_deployment()` currently assumes `DOH_RUN_JOB_WORKER=0` means “no worker exists,” which is false in your setup.

Safe current setup:

- If you use a separate worker, keep `DOH_DEBUG_DEPLOYMENTS=1` only on the worker process.
- Keep it off in the web process so the web app does not spawn the fallback thread.

I can patch this so debug mode works cleanly with an external worker and no local fallback race.
