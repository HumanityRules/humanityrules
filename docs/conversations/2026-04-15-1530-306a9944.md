## Diagnosis

**The container is crash-looping because of a UID mismatch between the EFS access point and the container user.**

The crash happens in the upstream `hermeswebui_init.bash` init script at this exact point:

```
HERMES_WEBUI_DEFAULT_WORKSPACE not set, setting to /workspace
chown: changing ownership of '/workspace': Operation not permitted
!! ERROR: Failed to set owner of /workspace
!! Exiting script (ID: 1)
```

**What's happening step by step:**

1. Container starts as `hermeswebui` (uid **1024**) — set by `USER hermeswebui` in our Dockerfile
2. Our `entrypoint.sh` runs, creates dirs on EFS, generates config
3. Control passes to `hermeswebui_init.bash` (upstream init script)
4. The init script sees `HERMES_WEBUI_DEFAULT_WORKSPACE` is unset, defaults to `/workspace`
5. `/workspace` is our symlink to `/home/hermeswebui/.hermes/workspace` (on EFS)
6. The script tries to `chown hermeswebui:hermeswebui /workspace` — this follows the symlink to EFS
7. **chown fails** because the EFS access point enforces uid **1000**, and a non-root process (uid 1024) cannot change ownership to a different uid (1024 != 1000) through NFS v4

**Root cause** — in `deploy_app.py`, the access point uid/gid is hardcoded to 1000:

```362:363:devopshero_app/services/infra_customer/deploy_app.py
                create_acl=efs.Acl(owner_uid="1000", owner_gid="1000", permissions="755"),
                posix_user=efs.PosixUser(uid="1000", gid="1000"),
```

But the hermes-webui container user is uid/gid **1024**. OpenClaw presumably uses uid 1000, so the hardcoded value happened to work for it.

---

## Proposed Solutions

**Solution A — Quick fix (Dockerfile only, no model change):**
1. Add `ENV HERMES_WEBUI_DEFAULT_WORKSPACE=/home/hermeswebui/.hermes/workspace` to the Dockerfile — avoids the symlink path in the chown
2. Change the hermes-webui user uid to 1000 in the Dockerfile (`RUN usermod -u 1000 hermeswebui && groupmod -g 1000 hermeswebui`) to match the EFS access point — makes any remaining chown a no-op
3. Rebuild + redeploy

Downside: Fragile. Changing the user's uid in the Dockerfile could break file ownership in the base image. Also couples the Dockerfile to the CDK's hardcoded uid.

**Solution B — Proper fix (make uid configurable per template):**
1. Add `efs_posix_uid` and `efs_posix_gid` fields to `AppTemplate` (default 1000 for backward compat with OpenClaw)
2. Propagate to `AppConfig` and the CDK stack
3. Set hermes template to uid=1024, gid=1024
4. Add `ENV HERMES_WEBUI_DEFAULT_WORKSPACE=/home/hermeswebui/.hermes/workspace` to the Dockerfile (explicit is better than relying on the symlink trick for the init script)
5. Redeploy — the CDK will replace the access point with the correct uid

This is a model migration + CDK change + seed data update + Dockerfile change. Since the current deployment is fresh (no important data on EFS), replacing the access point is safe.

**I recommend Solution B.** Want me to implement it?
