## Root Cause

The teardown operates on **infrastructure** (CloudFormation stacks), not on individual **deployment records**. The stacks are named using the pattern `doh-{env_slug}-{app_slug}-{ecr|app|aurora}`, which is derived from the **app** and **environment** — not from the specific deployment ID.

Here's what happens step by step:

1. You have two Deployment records for the same app + environment: one `running`, one `failed`.
2. You click "Tear Down" on the `failed` deployment. The view at `apps.py:58` correctly sets that deployment's status to `TEARDOWN_PENDING`.
3. The job worker picks it up and calls `run_teardown(deployment_id)` in `app_deployment_teardown_executor.py:96`.
4. `_build_teardown_app_config` at line 35 builds the config from `app.slug` and `environment.slug` — these are the **same** for both deployments.
5. `deploy_app.teardown()` at line 708 computes `resource_prefix = f"doh-{env_slug}-{app_config.app_name}"` and deletes stacks like `doh-{env}-{app}-app`, `doh-{env}-{app}-ecr`, etc.
6. These are the exact same stacks that the `running` deployment is using. So the running deployment's ECS service, ALB rules, and ECR repo get destroyed.
7. After successful teardown, only the `failed` deployment's DB record is deleted (line 168). The `running` deployment record remains in the DB, but its infrastructure is gone.

## The Core Issue

There's a **mismatch between the data model and the infrastructure model**. Multiple Deployment records can exist for the same app+environment, but there's only **one set of CloudFormation stacks** per app+environment. The teardown code doesn't distinguish between "this deployment has live infrastructure" vs. "this is just a historical failure record."

For a `failed` deployment where the currently running infrastructure belongs to a different deployment, tearing down should arguably just delete the DB record rather than destroying the shared infrastructure.

## Assistant

Roughly, yes. The key distinction is on the **status of the deployment being torn down**, not on scanning siblings:

- **Tearing down a `running` deployment** → tear down infra + delete record (as it works today).
- **Tearing down a `failed` deployment** → just delete the record. No infra teardown.

The reasoning: a `failed` deployment never reached `running`, so it doesn't own the infrastructure. Either a different deployment owns the stacks, or the stacks are in a partial/rolled-back state from the failure. In the latter case, the next successful deployment will overwrite them anyway.

This avoids the sibling scan entirely. The status of the deployment you're tearing down already tells you what to do.

The one edge case: a deployment that failed *after* CDK stacks were created but before ECS started, with no other running deployment. In that case you'd have orphaned stacks. But that would be better handled by a separate "clean up orphaned infra" path rather than complicating the normal teardown flow.

## Assistant

That would mean each deployment gets its own set of CloudFormation stacks (e.g., `doh-{env}-{app}-{deployment_id}-app` instead of `doh-{env}-{app}-app`). It's conceptually cleaner, but it has significant implications:

- **Each deployment creates new stacks** instead of updating existing ones. You'd have multiple ECS services, ALB listener rules, target groups, and potentially ECR repos running simultaneously for the same app.
- **That's essentially blue-green deployment.** The old deployment keeps running until explicitly torn down. It's a legitimate architecture, but it's a big shift from the current model where a new deployment updates the same stacks in-place.
- **Resource conflicts.** Things like the ALB listener rule priority, the Route53 subdomain, and the ECR repo name are currently derived from `app_slug` — they're naturally per-app, not per-deployment. You'd need to rework all of that.

There's a lighter-weight variant: keep the shared stacks, but **track which deployment owns them** (e.g., an `infrastructure_owner` FK on App or a flag on Deployment). But that ends up equivalent to the status-based check — the `running` deployment is always the owner, and a `failed` one never is.

So the two real options are:

- **Simple (status-based):** failed deployments just delete the DB record, running deployments tear down infra. Brittle as you noted, but minimal change.
- **Blue-green (per-deployment stacks):** correct by construction, but a substantial architectural rework of the infra layer.
