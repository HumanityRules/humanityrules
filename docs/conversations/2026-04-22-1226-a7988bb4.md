## How the attachment actually works

A single ECS Fargate task hosts multiple containers that share localhost, a task IAM role, and start/stop lifecycle. The auth-sidecar block at `deploy_app.py:548-596` is the existing model: `task_definition.add_container(...)` with its own image, env, secrets, then optional port mappings and container dependencies. The sidecar-mcp attachment lives right next to it.

**Direction differs from the auth sidecar.** Auth sidecar receives traffic from the ALB and forwards to the app (traffic flows in). Sidecar-mcp is the inverse: Hermes (the app) calls *it* over localhost (traffic flows out of the app container into the sidecar). That inverts two things:

- **No ALB target for sidecar-mcp.** No port mapping exposed to the task's ENI, no target group. The sidecar-mcp container binds to `127.0.0.1:7777` inside the task's network namespace; nothing outside the task can reach it. Port mappings exist in ECS, so you technically *can* expose a container-level port without ALB, but you don't need to — in a Fargate task, all containers share one network namespace and can already talk via localhost without port mappings. Cleaner to just not add any.
- **Container dependency reverses.** Auth sidecar declares `container=container, condition=START` — the *main container* must start before the *sidecar* (because the sidecar would 502 otherwise). For sidecar-mcp it's the opposite: Hermes's config-yaml-templating entrypoint shouldn't finish until the MCP server is listening. **CPU / memory are pooled at the task level, not per-container.** `FargateTaskDefinition(cpu=1024, memory_limit_mib=2048)` defines the whole task; the two containers share that budget. We'll need to bump `cpu` / `memory` on the Hermes AppTemplate because today's 1024/2048 was sized for Hermes alone. I'd suggest `cpu=2048, memory=4096` and tune down after profiling. ## The generalization

**AppTemplate declares a list of containers, not fields for one.** Task-level settings (`cpu`, `memory`, `efs_config`, `default_tags`, etc.) stay at the top. Per-container settings (image source, port, env, secrets, health check) move into a `containers: list[dict]` field on AppTemplate, stored as JSONField — same shape `runtime_variables` already uses.

## What each container entry carries

Five things, one of which is new, the rest are pulled up from today's flat AppTemplate fields:

- **`name`** — identifier for the container within the template (stable string, not arbitrary). Referenced by other containers' `depends_on`.
- **`image_source`** — discriminator with two values initially: `dockerfile` (built from a `source_repo_path` in `template_repos/` or the customer's repo, pushed to per-app ECR during deploy — today's primary flow) or `prebuilt` (references a pre-pushed image in per-env ECR like `doh/{env}/sidecar-mcp:{version}`, built out-of-band by a management command — today's auth-sidecar flow).
- **`image_ref`** — what the image_source resolves. For `dockerfile`: `source_repo_path`, `dockerfile_path`. For `prebuilt`: ECR repo name + version.
- **`container_port`, `health_check_path`, `health_check_command`, `alb_target`, `exposed_ports`** — all the port/health stuff, per-container. `alb_target: true` marks the one container that receives ALB traffic and defines the target group; at most one per template; can be absent entirely (a task with no ALB exposure).
- **`runtime_variables`** — per-container, not per-template. Each container gets its own env + secret projections. Eliminates the "whose env is this" ambiguity the auth sidecar currently sidesteps by hardcoding.
- **`depends_on`** — list of `{name, condition}`. Condition defaults to `START` (your call for sidecar-mcp), mapped straight onto `ecs.ContainerDependency`.
