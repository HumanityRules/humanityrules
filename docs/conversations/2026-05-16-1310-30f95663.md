For the entities they both cover, PostHog typically has more of what

- **Experiments**: Merge has 5 (CRUD), PostHog has 18 — `experiment-launch`,

## Authentication

- **PostHog first-party MCP**: OAuth (Notion-style; we verified DCR at
  `oauth.posthog.com/oauth/register/` returns a working `client_id`, with
  171 real PostHog scopes). Personal API key with the "MCP Server" preset
  is a fallback for clients that don't speak OAuth. Region detection is
  automatic during login. Org/project pinned via headers or query string.
- **Merge connector**: `API key` only. Per Merge's docs, no OAuth path
  for PostHog at all (it's in our Group B1 — single API key paste).

## So why did Merge pick API key for PostHog?

There isn't a "this is better for the customer" story I can find:

1. **It's not API surface.** PostHog's MCP server is dramatically wider
   than what Merge exposes. ~63 vs ~350+ tools; entire product areas
   (logs, APM, error tracking, LLM analytics, data warehouse, CDP
   functions) aren't in Merge at all.
2. **It's not depth on the entities they share.** PostHog's MCP has all
   of Merge's CRUD plus the operational/diagnostic tools that make
   experiments and flags useful at runtime.
3. **It's not auth UX.** PostHog's OAuth flow with auto-region detection
   is strictly nicer than asking the user to mint a "MCP Server"-preset
   personal API key in Settings.

What's left as a plausible explanation:

- **Timing.** Merge built PostHog as one of ~150 connectors, with a
  uniform "list/get/create/update/delete-per-entity" template that
  predates the first-party MCP era. Wrapping `posthog-python` against
  the PostHog REST API with a personal API key is the same pattern they
  use for ActiveCampaign, Apollo, Klaviyo, etc.
- **Uniformity over depth.** Across the connector portfolio, Merge
  reaches for a single integration shape rather than one-off OAuth +
  remote-MCP relays. PostHog's MCP would have been a special case.
- **Operational cost.** Relaying a remote MCP that streams ~350 tools is
  more work than wrapping a REST API with a fixed tool list, and it
  imposes upstream availability risk on Merge.

So the most defensible read is: **Merge's PostHog connector exists because
they hadn't (or hadn't yet) wired in the first-party MCP — not because
the API key path is better for the user.** For a customer who wants
breadth/depth, going direct to `mcp.posthog.com` is a clear win. For a
customer who only needs the basic admin CRUD across many SaaS apps with
one auth model, Merge's narrower surface is the trade-off.

(Caveat: I haven't run either MCP server end-to-end against a real
PostHog account; counts above are from the docs.)

What's that filtering mechanism that you mentioned above that Posthog uses for clients to focus on whatever they need only?

## Assistant

PostHog's MCP server lets the client narrow the exposed tool set at connection time using two query parameters on the MCP server URL:

- **`?features=<categories>`** — comma-separated list of category names (the same headings used in their tool list: `actions`, `cohorts`, `feature-flags`, `logs`, `apm`, `llm-analytics`, `error-tracking`, `data-warehouse`, etc.). The server only registers tools belonging to those categories.
- **`?tools=<exact-names>`** — comma-separated list of exact tool names (e.g., `query-trends,query-funnel,feature-flag-get-all`). The server only registers exactly those tools.

Both can appear together — when they do, the resulting tool set is the **union** of what each filter would have allowed individually (not the intersection).

There's also a related scoping mechanism that's not exactly filtering but interacts with it: pinning the session to a specific organization or project via `x-posthog-organization-id` / `x-posthog-project-id` headers (or `organization_id` / `project_id` query params). When a session is pinned, the corresponding `switch-organization` and/or `switch-project` tools are automatically dropped from the available list — there's nothing to switch to.

Why this matters in practice: with 350+ tools, PostHog's full surface blows past most LLMs' useful tool-budget. The filtering lets the client (or whoever's wiring the client up) say "for this agent I only care about feature flags and product analytics" and get back a tight ~25-tool MCP server instead of the full firehose. The first-party clients PostHog ships (Claude Desktop config, Cursor config, etc.) lean on this so the agent gets a focused surface.

For Hermes, this is the kind of feature you'd want to expose to whoever configures a PostHog integration — pick the categories the app actually needs, paste the resulting URL into the MCP aggregator's config, and the agent's tool list stays manageable.

Source: https://posthog.com/docs/model-context-protocol (the "Scoping to an Organization or Project" section, which also documents `?features=` and `?tools=`).
