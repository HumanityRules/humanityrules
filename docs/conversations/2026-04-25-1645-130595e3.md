Short answer: not via config. You'd have to fork nono.

The 169.254.0.0/16 block is layered in three places, and none of them are profile-controllable:

1. **Seccomp proxy-only filter** (`supervisor_linux.rs:582-598`) — under Fargate (Landlock V2, no TCP filtering), nono falls back to a seccomp filter that allows `connect(2)` only to `127.0.0.1:<proxy_port>`. The child literally cannot issue a syscall reaching 169.254.170.2. This is the hard floor.

2. **HostFilter deny list** (`net_filter.rs:180-184`) — the proxy itself has a `DENY_HOSTS` constant covering cloud-metadata hostnames. Applied *before* the allow check, so even `HostFilter::allow_all()` (empty `allow_domain`) can't reach them.

3. **Link-local check** — `is_link_local()` rejects the entire 169.254.0.0/16 range at resolution time.

No profile field, no CLI flag, no env var toggles any of these. It's hard-coded SSRF protection.

**Paths forward, ranked:**

1. **Fetch creds in entrypoint, before `exec nono`.** Entrypoint runs outside the sandbox and has full network. Call `sts:AssumeRole` (or just let boto3 hit 169.254.170.2) from entrypoint, write temporary creds to `/tmp/doh-secrets/` as `aws_access_key_id`/`aws_secret_access_key`/`aws_session_token` files, and inject them into the child's env via the nono profile's allow_vars. 2. **SigV4 sidecar.** Run a tiny process outside nono that owns the AWS creds and signs requests on behalf of the child. The child talks to the sidecar over loopback; sidecar signs + forwards to Bedrock. More moving parts but mirrors the nono proxy pattern and handles creds rotation cleanly.

3. **Fork nono.** Patch out the three checks. Feasible but now you're maintaining a fork, and the seccomp floor is there for a reason — loosening it weakens the whole containment story for non-Bedrock deploys too. I'd avoid this.

Option 1 is the cheap win if you can live with 6-hour-bounded creds in the child env. Option 2 is the right long-term shape if you want parity with the Bearer-auth providers.

child (boto3)  --→  nono proxy (127.0.0.1:44300/ecs-creds)
                    └─→  sidecar (127.0.0.1:6777)  [runs outside nono]
                          └─→  169.254.170.2  (real IMDS)
```

"aws-ecs-creds": {

  "inject_mode": "header",   // but we don't need injection
  ...
}
```

1. Fetch creds from 169.254.170.2 once
2. Write `[default]\naws_access_key_id=...` to `$HERMES_DIR/.aws/credentials`

Nono profile: add a route `aws-creds` with upstream `http://127.0.0.1:6777`, and set the seccomp proxy-only floor still routes child→nono→sidecar.

**Cost:** ~30 lines of Python (or just `socat TCP-LISTEN:6777,fork TCP:169.254.170.2:80`).

**Property lost:** creds *do* reach child memory (boto3 caches them to sign requests). Not on disk, not in env, but in-process. This weakens the "secrets never touch the child" story — worth weighing against the OpenAI/Tavily bar you already have.

## 2. SigV4 signing sidecar (creds stay in sidecar)

Sidecar owns the creds; child sends unsigned HTTP to sidecar; sidecar signs + forwards to `bedrock-runtime.<region>.amazonaws.com`.

Existing tool: **`aws-sigv4-proxy`** (official AWS repo, Go binary). Run it as:
```
aws-sigv4-proxy --name bedrock --region us-east-1 --host bedrock-runtime.us-east-1.amazonaws.com
```
It reads creds from the standard chain (task role → 169.254.170.2) at startup *and keeps refreshing them*, since it runs outside nono. Hermes's boto3 in the child gets static dummy creds (it must sign *something* locally to satisfy its own code path, but the sidecar replaces that signature).

Actually, for Hermes this is trickier: boto3's Bedrock client signs client-side with whatever creds it has, so you can't point it at a pre-signing proxy without patching boto3's signer out. This option is cleaner in theory but messier in practice with boto3 — more workable with LiteLLM/OpenAI-compatible Bedrock wrappers.

## 3. OpenAI-compatible Bedrock sidecar (cleanest for Hermes)

Run **LiteLLM proxy** (or similar) as a sidecar outside nono. It exposes an OpenAI-compatible API on `127.0.0.1:6777`, and on the backend talks to Bedrock using the task role. Hermes is already configured to talk to an OpenAI-style endpoint — `DOH_LLM_PROVIDER=custom`, `DOH_LLM_BASE_URL=http://127.0.0.1:44300/openai`, and nono forwards to `http://127.0.0.1:6777` (the sidecar).

Child sees zero AWS creds. No boto3 in the child at all. Bedrock-specific code paths in Hermes go away.

**Cost:** one extra process, plus model-name translation (LiteLLM does this). LiteLLM is an established project, actively maintained.

**Bonus:** same pattern works for any future provider with weird auth — Vertex AI, Azure AD, etc.

## The command

```
socat TCP-LISTEN:6777,reuseaddr,fork TCP:169.254.170.2:80 &
```

That's it. Runs in entrypoint before `exec nono`, backgrounds, and forwards every inbound connection on `:6777` to `169.254.170.2:80` byte-for-byte. No HTTP parsing, no path rewriting — boto3 sends `GET /v2/credentials/<uuid>`, socat forwards it verbatim, IMDS responds, socat forwards back.

## Why it works

Fargate's creds endpoint is plain HTTP/1.1 over TCP on `169.254.170.2:80`. No TLS, no SNI, no Host-header matching on IP (the server doesn't care what Host you send). So a dumb TCP relay is sufficient — which is exactly socat's comfort zone.

## Dockerfile

Apt already has `socat`:
```dockerfile
RUN apt-get install -y --no-install-recommends socat
```

~500KB installed. Cheaper than pulling Python into a layer that doesn't already have it (yours does, but for a minimal image this matters).

## Child env

```bash
export AWS_CONTAINER_CREDENTIALS_FULL_URI="http://127.0.0.1:6777${AWS_CONTAINER_CREDENTIALS_RELATIVE_URI}"
# AWS_CONTAINER_AUTHORIZATION_TOKEN if the task has one (ECS sometimes sets this)
```

`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` is set by ECS at task start (e.g. `/v2/credentials/abc123...`). We read it in entrypoint, prepend our loopback base, and export as `FULL_URI`. boto3 uses `FULL_URI` verbatim.

## Caveats

1. **Loopback-to-loopback in child.** Under nono's seccomp proxy-only mode, the child still can't connect to `127.0.0.1:6777` directly. It has to go through nono's proxy port (`44300`), which then forwards to a route whose upstream is `http://127.0.0.1:6777`. So you still need a profile entry — it's just that the "service" behind it is socat, not a Python process.

2. **Injected header.** Every `custom_credentials` route injects a header. You'd inject a throwaway `Authorization: Bearer <phantom>` that IMDS ignores. Ugly but harmless.

3. **socat is the blast radius.** socat has a history of CVEs. For a loopback-only bind forwarding to a link-local address, the practical risk is ~zero, but it's worth noting vs. a 10-line Python script that does the same thing with the stdlib.

## Verdict

Yes — single command, standard package, does exactly what's needed. I'd pick socat over Python here: fewer moving parts, no venv concerns, no script file to maintain.
