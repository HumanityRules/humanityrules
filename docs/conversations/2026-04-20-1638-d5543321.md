## Diagnosis

`ERR_HTTP2_PROTOCOL_ERROR` + random failures on static assets is the classic symptom of **invalid `Content-Length` framing over HTTP/2**.

Here's what's happening end-to-end:

1. Browser → ALB: **HTTP/2**.
2. ALB → sidecar: HTTP/1.1 (ALB terminates HTTP/2).
3. Sidecar → Hermes upstream: HTTP/1.1.
4. Hermes sends responses with `Content-Length: N` (small static files go out as one fixed-length body, not chunked).
5. Sidecar forwards body via `aiter_raw()` but I **strip `Content-Length`** in `_filter_response_headers`. Starlette's `StreamingResponse` sees no `Content-Length` and frames the response with `Transfer-Encoding: chunked` to ALB.
6. ALB translates this to HTTP/2 framing to the browser.

That part *should* work — but there's a subtle kill: **when Starlette's `StreamingResponse` has a `Content-Length` header in the dict, it honors it verbatim**; when it's absent, it sends `Transfer-Encoding: chunked`. Mixing that with ALB's HTTP/2 translation is usually fine, but a couple things can break it:

**a. Upstream sends `Content-Encoding: gzip` with a `Content-Length`** (typical for Hermes's static CSS). `aiter_raw()` returns the compressed bytes unchanged (good), but if any header says `Content-Length: 1234` for the gzipped body we pass through *both* content-length and the raw gzip — OK, but our code removes it. Then the browser expects chunked, gets it, decodes gzip… this path is usually fine.

**b. More likely: the background task closes the upstream connection, but a concurrent request is reusing the httpx connection pool and the close races.** Since I share one `AsyncClient` for both PDP calls and upstream, and the CSS + JS requests come as a burst in parallel, the pool can get into a state where a response stream is closed while its bytes are still being read. HTTP/2 surfaces that as `ERR_HTTP2_PROTOCOL_ERROR`.

**c. Most likely actual cause: the `httpx.AsyncClient` default has `http2=False`, so this isn't about httpx speaking HTTP/2 — but the pool has `max_keepalive_connections=20, max_connections=100`. When multiple requests burst, some get queued; the `BackgroundTask(aclose)` on a previous response can release a connection back to the pool in a bad state if the body wasn't fully drained by the downstream (ALB). If the browser drops the connection mid-stream (common for CSS that becomes moot), `aiter_raw` raises, `StreamingResponse` aborts, and `aclose` runs — but the httpx connection is left in a partial state. Next response on that pool connection corrupts the frame.**

The tell-tale is the intermittent `ERR_HTTP2_PROTOCOL_ERROR` — it's not deterministic, it depends on pool-connection ordering.

**Recommended fix (minimal, for single-user sanity):**

1. **Preserve `Content-Length` when upstream sent it**, so Starlette doesn't switch to chunked for small fixed-length assets. Only strip `Transfer-Encoding`. This is the single most impactful change — most static assets become "framed body" round-trips again instead of chunked-through-a-BackgroundTask.

2. Keep `aiter_raw` for streaming (dynamic SSE responses have neither `Content-Length` nor need it). Starlette will emit `Transfer-Encoding: chunked` only when `Content-Length` is absent.

3. Optionally: wrap the iterator so a consumer-side disconnect cleanly closes the upstream response, reducing the race window. Not strictly needed for single-user if #1 alone fixes it.

## Assistant

Short answer: **yes, it's possible; no, it's not worth doing now.**

## Is it possible?

Yes. ALB target groups have a `ProtocolVersion` attribute with values `HTTP1` (default), `HTTP2`, and `GRPC`. HTTP/2 target groups work for regular HTTPS traffic, not just gRPC. So you can make ALB → sidecar speak HTTP/2.

(I'd want to double-check the exact current AWS behavior before wiring it up — HTTP/2 target groups historically had edge cases around prior-knowledge/h2c vs. TLS-ALPN negotiation — but the capability exists.)

## Is it desirable?

For this deployment, no. A few reasons:

**1. It wouldn't have fixed the bug you just hit.**
The framing mismatch we chased was on the *sidecar → Hermes* leg (Hermes speaks HTTP/1.0, we were emitting chunked). HTTP/2 on the *ALB → sidecar* leg is a completely different hop — it doesn't change what the sidecar emits upstream. The same fix would have been needed regardless.

**2. The sidecar has to speak HTTP/2.**
Uvicorn by default serves HTTP/1.1 via h11. HTTP/2 means switching to Hypercorn, or wiring an ASGI server that supports h2. That's a new dependency, a new code path, and a new class of bugs (flow-control windows, stream resets, settings frames). Added complexity for a sidecar whose explicit goal is "transparent and fast."

**3. The benefits don't apply to single-user Hermes.**
HTTP/2's wins — connection multiplexing, HPACK, push — matter when you have many concurrent requests and many clients. This sidecar fronts one user talking to one Hermes. The ALB already reuses a keepalive HTTP/1.1 connection to the target; the marginal improvement from multiplexing is basically zero here.

**4. The upstream hop is still HTTP/1.x regardless.**
Hermes is HTTP/1.0. Even if browser → ALB → sidecar is all HTTP/2, the sidecar still has to terminate HTTP/2 and re-serialize the request to HTTP/1.x to reach Hermes. The sidecar is the translation boundary either way.

**When it *would* matter:** if you later front a protocol-native HTTP/2 or gRPC app behind the sidecar, you'd want `ProtocolVersion: HTTP2` (or `GRPC`) on the target group so streaming semantics pass through cleanly without re-framing. That's a future-you problem, not a today problem.

Leave it on HTTP/1.1 for now. The sidecar's job is to be invisible — the simplest protocol stack that works is the right one.
