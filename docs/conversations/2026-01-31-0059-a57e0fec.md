## Diagnosis Report

### What Failed

In **Conversation 1** (019c12cf), the model tried to deploy `simple-dashboard` (an existing app) to the `staging` environment. The deployment failed because:

1. `simple-dashboard` already has a running deployment in the `dev` environment
2. The domain URL is based on **app name**, not environment: `{app_slug}.{hosted_zone_name}`
3. Both deployments would try to use `simple-dashboard.chsandbox.com`
4. Route53 can't have duplicate A records pointing to different targets

### What Should Have Happened

In **Conversation 2** (019c12c3), the model correctly recognized that deploying the same repository to a different environment requires a **new app name** (e.g., `simple-dashboard-staging`), which gets a different domain (`simple-dashboard-staging.chsandbox.com`).

### Root Causes

**1. Missing information in `list_apps`**

The `AppSummary` dataclass only returns:

```python
id, name, slug, app_type, branch, repository_name,
latest_deployment_status, latest_deployment_id
```

It does **not** tell the model which environment the app is deployed to. Without this, the model has no way to know that `simple-dashboard` is already running in `dev`.

**2. Missing validation in `deploy_app`**

The `deploy_app` tool doesn't check if an app already has a running deployment in a **different** environment. It only checks for active deployments via `_check_active_deployments()`, but that doesn't filter by environment.

**3. Missing system prompt guidance**

The app deployment prompt (`system_prompt_app_deployment.md`) never explains that:
- Domain = `{app_slug}.{hosted_zone_name}` 
- The same app can't be deployed to multiple environments
- If you want the same repo in multiple environments, you need different app names

### Why Conversation 2 Worked

The user explicitly asked "What if I want the same repository but deployed as a different app to a different environment?" This prompt triggered the model to explain the naming requirement. The user then chose `simple-dashboard-staging` as the app name, avoiding the conflict.

### Recommended Fixes

**Option A (Validation):** Make `deploy_app` reject attempts to deploy an existing app to a new environment when that app already has a running deployment elsewhere. Return an error explaining the constraint.

**Option B (Information):** Enhance `list_apps` to include deployment environment info, and add guidance to the system prompt about the domain naming constraint.

**Option C (Both):** Implement validation + better information, so the model can proactively guide users to create correctly-named apps.

```python
async def _check_subdomain_conflict(subdomain: str, hosted_zone: str, exclude_app_id: str | None) -> Deployment | None:
    """Check if a subdomain is already in use by a running deployment in the same hosted zone."""
    # ...
    query = Deployment.objects.filter(
        subdomain=subdomain,
        environment__shared_alb_hosted_zone=hosted_zone,
        status__in=running_statuses,
    )
    if exclude_app_id:
        query = query.exclude(app_id=exclude_app_id)  # <-- Exclude this app's deployments
    return await query.select_related("app", "environment").afirst()
```

- With `exclude_app_id`, we skip that app's own deployments and correctly keep `simple-dashboard`

The conflict detection only flags when a **different** app is using the same subdomain.
