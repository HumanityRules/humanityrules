## Diagnosis Report: Duplicate Tool Outputs

### Root Cause

The duplication happens because **SSE reconnection replays tool_start events, but the frontend always appends without deduplication**.

### The Flow

1. **Normal operation**: Agent calls a tool → `tool_start` event → frontend appends `<div id="tool-{id}">` with spinner

2. **SSE reconnects** (tab switch, network blip, browser throttling): When SSE reconnects, `mark_client_connected()` in `agent_runner.py` replays all pending tools:

```python
# agent_runner.py lines 83-87
if runner.pending_tools:
    for tool_data in runner.pending_tools.values():
        runner.event_queue.put_nowait(AgentStreamEvent(type="tool_start", data=tool_data))
```

3. **Frontend blindly appends**: `handleToolStart()` always appends without checking if the element exists:

```javascript
// _chat_panel.html lines 422-425
while (fragment.firstChild) {
    messages.appendChild(fragment.firstChild);  // No deduplication!
}
```

4. **Result**: Each SSE reconnect = another duplicate. The screenshot shows 3x duplicates, meaning SSE reconnected twice during the long-running bash commands.

### Why SSE Reconnects

Long-running operations (like "Wait 2 more minutes for DB instance") are prime candidates for SSE drops:
- Browser throttles background tabs
- Network keepalive timeouts
- Mobile browsers aggressive connection management

### Fix

Make `handleToolStart` idempotent by checking if the tool div already exists:

```javascript
function handleToolStart(data) {
    const template = document.createElement('template');
    template.innerHTML = data;
    const fragment = template.content;
    
    processOobElements(fragment);
    
    // Skip if tool already exists (reconnection replay)
    const toolDiv = fragment.querySelector('[id^="tool-"]');
    if (toolDiv && document.getElementById(toolDiv.id)) {
        return;  // Already rendered, skip duplicate
    }
    
    while (fragment.firstChild) {
        messages.appendChild(fragment.firstChild);
    }
    maybeScrollToBottomSmooth();
}
```

Yes, this is directly related and explains the *frequency* of reconnections.

The console shows repeated `ERR_QUIC_PROTOCOL_ERROR` errors on the SSE stream URL (`/chat/.../stream/`). Each error triggers:

1. EventSource fires an `error` event (the expanded event shows `type: "error"`, `target: EventSource`)
2. EventSource auto-reconnects (built-in browser behavior)
3. Reconnection calls `mark_client_connected` → replays pending tools
4. Duplicates appear

**Why QUIC errors?** HTTP/3 (QUIC) doesn't play well with long-lived SSE connections. This is a known issue - QUIC has aggressive timeout/flow-control that can interrupt streaming connections.

**Two issues to address:**

1. **Frontend fix (the one I proposed)** — Make `handleToolStart` idempotent so reconnections don't create duplicates. This is essential regardless of the QUIC issue.

2. **Infrastructure consideration** — You could disable HTTP/3 for the SSE endpoint in CloudFront, forcing HTTP/2 which handles streaming better. Or add `Alt-Svc` headers to prevent QUIC upgrade for that path.

The frontend fix is the primary solution - SSE reconnections will always happen (network blips, tab throttling), so the UI must handle them gracefully. The QUIC issue is secondary but explains why you're seeing so many reconnections.
