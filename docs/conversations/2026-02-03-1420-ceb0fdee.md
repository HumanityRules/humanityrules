2. When you run any management command via `prod_manage.sh`, Django's `AppConfig.ready()` gets called

## Assistant

Here are several approaches to solve this:

**Option 1: Check `sys.argv` in `AppConfig.ready()`**

Detect management commands and skip the worker for non-web processes:

```python
def _init_job_worker(self):
    """Start the job worker if enabled via settings."""
    if not settings.DOH_RUN_JOB_WORKER:
        return
    
    import sys
    # Only start worker for runserver or Gunicorn (not management commands)
    if len(sys.argv) > 1 and sys.argv[1] not in ('runserver',):
        return
    
    from .services.deployment import job_worker
    job_worker.start_worker()
```

**Option 2: Detect Gunicorn specifically**

Since production uses Gunicorn, you can check for it:

```python
def _init_job_worker(self):
    """Start the job worker only when running under Gunicorn."""
    if not settings.DOH_RUN_JOB_WORKER:
        return
    
    import sys
    is_gunicorn = 'gunicorn' in sys.modules
    if not is_gunicorn:
        return
    
    from .services.deployment import job_worker
    job_worker.start_worker()
```

**Option 3: Add a skip env var in `prod_manage.sh`**

Modify the script to set an override:

```bash
# In prod_manage.sh, before the aws ecs execute-command:
-c "DOH_RUN_JOB_WORKER=0 uv run manage.py $@"
```

This explicitly disables the worker for management commands.

**Option 4: Remove auto-start entirely**

Don't start the worker in `AppConfig.ready()`. Instead:
- Run a separate ECS task/container dedicated to the job worker using `run_job_worker`
- Or, use a Gunicorn post-worker-init hook to start it

---

**Recommendation:** Option 2 (detect Gunicorn) is the cleanest because it's explicit about intent: the job worker should only run in the web server process, not in one-off management commands. It requires no changes to `prod_manage.sh` and handles all management commands automatically.

Option 3 is simpler to implement if you want a quick fix, but requires remembering to update `prod_manage.sh` (and any other place that runs management commands remotely).

1. The production container is already running Gunicorn, which has already started its own job worker (since `DOH_RUN_JOB_WORKER=1` is set in the container environment)

2. When you run `prod_manage.sh doh_customer list`, it spawns a **new Python/Django process** inside that same container

3. That new Django process goes through `AppConfig.ready()` and sees `DOH_RUN_JOB_WORKER=1` in the environment, so it starts **another** job worker thread in that process

4. You now have two job workers polling the database - the original one from Gunicorn, and one from your management command

This makes **Option 2 (detect Gunicorn)** even more appealing - it ensures only the main Gunicorn process runs the worker, not ad-hoc management commands executed in the same container.

You're right to be confused - let me clarify. The container exists, but **each command spawns a new Python process**.

Here's what's happening:

1. **The Gunicorn process** is running inside the container, serving web requests. It started its own job worker when it initialized.

2. **`ecs execute-command`** spawns a **new shell** inside the container, which runs:
   ```bash
   uv run python manage.py doh_customer teardown-env ...
   ```

3. This is a **brand new Python process** - completely separate from Gunicorn. It has its own memory, its own Django initialization, its own `AppConfig.ready()` call.

4. Since the container's environment has `DOH_RUN_JOB_WORKER=1`, this new process starts its own job worker.

So you now have **two job workers running simultaneously**:
- One in the Gunicorn process (the main web server)
- One in your management command process

When your management command exits, its job worker dies with it (it's a daemon thread). But while it's running, both workers are polling for jobs and could race to claim them.

The log you showed proves exactly this - that's a fresh Django initialization happening in a new process, not the existing Gunicorn process.

**This is the bug**: every `prod_manage.sh` command starts an extra, short-lived job worker that competes with the main one and dies when the command finishes.

When Gunicorn starts, `sys.argv` looks something like:

```python
def _init_job_worker(self):
    """Start the job worker only for web server processes."""
    if not settings.DOH_RUN_JOB_WORKER:
        return
    
    import sys
    
    # Check if running under Gunicorn
    is_gunicorn = 'gunicorn' in sys.modules
    
    # Check if running Django dev server
    is_runserver = len(sys.argv) > 1 and sys.argv[1] == 'runserver'
    
    if not (is_gunicorn or is_runserver):
        return
    
    from .services.deployment import job_worker
    job_worker.start_worker()
```

This starts the worker only when:
- Running under Gunicorn (production), OR
- Running `manage.py runserver` (local development)

And skips it for all management commands like `doh_customer`, `shell`, `migrate`, etc.

**Option 2** (just `'gunicorn' in sys.modules`) is simpler but wouldn't start the worker during local dev with `runserver`. That might be fine if you run `run_job_worker` separately during development.

## Assistant

Here's a clean method that correctly detects web server processes:

```python
def _is_web_server_process() -> bool:
    """Detect if running as a web server (Gunicorn, Uvicorn, or Django runserver)."""
    import sys
    
    # Gunicorn (production WSGI)
    if 'gunicorn' in sys.modules:
        return True
    
    # Uvicorn (production ASGI)
    if 'uvicorn' in sys.modules:
        return True
    
    # Django development server
    if len(sys.argv) >= 2 and sys.argv[1] == 'runserver':
        return True
    
    return False
```

Then use it in `_init_job_worker`:

```python
def _init_job_worker(self):
    """Start the job worker only for web server processes."""
    if not settings.DOH_RUN_JOB_WORKER:
        return
    
    if not _is_web_server_process():
        return
    
    from .services.deployment import job_worker
    job_worker.start_worker()
```

This correctly handles:
- **Gunicorn** — detected via `sys.modules`
- **Uvicorn** — detected via `sys.modules` (in case you switch to ASGI)
- **`manage.py runserver`** — detected via `sys.argv`
- **Management commands** — returns `False`, worker doesn't start

The `sys.modules` check works because when Gunicorn/Uvicorn imports your Django app, those packages are already loaded in the Python process before `AppConfig.ready()` runs.

## Assistant

That's a cleaner approach - detect `manage.py` and skip the worker:

```python
def _is_management_command() -> bool:
    """Detect if running as a Django management command."""
    import sys
    
    # Check if invoked via manage.py
    if sys.argv and sys.argv[0].endswith('manage.py'):
        return True
    
    return False
```

Then:

```python
def _init_job_worker(self):
    """Start the job worker only for web server processes."""
    if not settings.DOH_RUN_JOB_WORKER:
        return
    
    if _is_management_command():
        return
    
    from .services.deployment import job_worker
    job_worker.start_worker()
```

**One catch:** `manage.py runserver` is also a management command, so this would skip the worker during local development too.

If you want to allow `runserver`, add an exception:

```python
def _is_management_command() -> bool:
    """Detect if running as a Django management command (excluding runserver)."""
    import sys
    
    if sys.argv and sys.argv[0].endswith('manage.py'):
        # Allow runserver to start the worker
        if len(sys.argv) >= 2 and sys.argv[1] == 'runserver':
            return False
        return True
    
    return False
```

The advantage of this "blocklist" approach is it's more explicit about what you're avoiding (management commands) and automatically works with any WSGI/ASGI server without needing to enumerate them.
