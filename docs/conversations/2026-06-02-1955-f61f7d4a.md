```53:57:template_repos/hermes_agent/doh_runtime/Caddyfile

	# return 404 instead of empty 200.

		respond "unknown host" 404
	}
```

### What’s working

1. **DNS / ALB / subhosting** — wildcard infra is fine. Other subhosts on the same agent respond correctly (`tron-times` and `term` return 200 through Caddy).
2. **The Caltrain app itself** — it’s running inside the container on port 4003 and serves HTTP 200 on loopback.
3. **Process registration** — process-compose lists `caltrain` as Running/Ready.

### What’s broken

**Caddy has no route for `caltrain`.** Requests with `X-Forwarded-Host: caltrain.hermes-vmendi00.chsandbox.com` hit the catch-all and return `"unknown host"`, while the app on `127.0.0.1:4003` is healthy.

### Root cause

`webapps create` only writes `routes.caddy` **after** the app passes the readiness probe:

```74:86:template_repos/hermes_agent/doh_runtime/webapps

    state = wait_for_ready(args.slug, args.timeout)
    if state.get("is_ready") != "Ready":
        die(...)

        regenerate_routes(load_yaml())

```

Caltrain’s process-compose record shows **5 restarts** before it became Ready (~97 seconds from start to ready). The default timeout is **90 seconds**. The CLI almost certainly **timed out and exited before `regenerate_routes` ran**. Process-compose kept retrying, the app eventually came up, but Caddy was never updated — hence a live process with a dead public URL.

The agent likely reported success from “app is running” without verifying the URL route was created.

```bash

```

Alternatively, from inside the nono sandbox:

## Why 5 restarts

Process-compose hit its **`max_restarts: 5`** limit because Caltrain crashed on startup before dependencies were ready.

From CloudWatch (`doh_app_logs --container hermes --all`), every failed attempt looks like this:

```

[caltrain]   File "/workspace/webapps/projects/caltrain/app.py", line 13, in <module>
[caltrain]     import requests
[caltrain] ModuleNotFoundError: No module named 'requests'
```

That pattern repeats **6 times** (initial run + 5 restarts). On the next start it succeeds:

```
[caltrain]  * Running on http://127.0.0.1:4003
```

So the sequence was:

1. Agent registered Caltrain with `webapps create` and started it.
2. `app.py` imports `requests`, which wasn’t in the project venv yet → immediate crash (exit 1).
3. Process-compose restarted it per policy in `webapps_lib.py`: `restart: on_failure`, `backoff_seconds: 2`, **`max_restarts: 5`**.
4. While that was happening, the agent (or a manual `pip install`) added `requests`.
5. The final attempt stayed up; readiness probe passed ~97s after first start — just over the 90s `webapps create` timeout, which is why the Caddy route never got written.

The restart count is expected behavior for a crash-looping app, not a process-compose bug.

## Where logs live

There are three layers:

### 1. Per-webapp files (persistent, on EFS)

Each webapp gets a dedicated log file configured in process-compose YAML:

- **Path:** `/workspace/webapps/logs/<slug>.log` (e.g. `caltrain.log`)
- **Tail via CLI:** `webapps logs caltrain` or `webapps logs caltrain -f`

These survive container restarts because `/workspace` is on the persistent root.

### 2. Process-compose multiplexed output → CloudWatch

Process-compose captures each child’s stdout/stderr (both the on-disk `log_location` file **and** the container log stream) and prefixes lines with the process name, e.g. `[caltrain]`, `[system.webui]`.

The **process-compose daemon itself** has no separate log file — it runs as `process-compose up ... 2>&1 &` in `webui.sh`, so its own messages also go to container stdout.

### 3. Caddy → CloudWatch only

Caddy also has **no log file**. It runs as:

```bash
caddy run --config /opt/doh/runtime/Caddyfile --adapter caddyfile --watch 2>&1 &
```

Logs are JSON lines on stdout (access errors, reverse-proxy warnings, etc.), same CloudWatch stream as everything else in the **hermes** container.

### How to read them from outside the container

| What | How |
|------|-----|
| All hermes-container output (Caddy, process-compose, webapps) | `uv run manage.py doh_app_logs --account "Humanity Rules Sandbox" --env default --app hermes-vmendi00 --container hermes` |
| Filter to one webapp | pipe through `rg '\[caltrain'` |
| On-disk webapp log | `webapps logs caltrain` inside the sandbox (or read EFS at `.../workspace/webapps/logs/caltrain.log` on the host under `/var/lib/devopshero/hermes-roots/hermes-vmendi00/`) |
| Policy-proxy (auth layer) | `doh_app_logs ... --policy-proxy` (separate container) |

Note: the process-compose REST API on `:9956` doesn’t expose log endpoints in this setup (they return 404). Use CloudWatch or `webapps logs` instead.

Also worth knowing: `doh_app_exec` defaults to the **policy-proxy** container unless you pass `--container hermes`. For webapp/Caddy/process-compose debugging, always use `--container hermes`.
