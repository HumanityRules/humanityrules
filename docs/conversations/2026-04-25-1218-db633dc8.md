So the ECS container-instance ASG uses `m8g.large` Graviton instances.

Reasoning behind that choice:

- It is **ARM64**, matching the current Docker build target and Fargate runtime platform.
- It gives a reasonable first pool size for Hermes without guessing too small.
- It keeps the first implementation simple: one environment-level EC2 capacity pool shared by EC2-mode apps.

It is not currently user-configurable, template-configurable, or autosized from Hermes CPU/memory. ECS managed scaling controls the ASG size, but only within this one instance type and `max_capacity=4`.

A likely follow-up is to move this into an environment-level setting, maybe defaulting to `m8g.large` but allowing `m8g.xlarge` or similar for heavier Hermes use.

## Assistant

`m8g` is AWS’s current Graviton general-purpose EC2 family.

For our use:

- **CPU architecture:** ARM64, powered by **AWS Graviton4**.
- **Workload class:** general purpose, balanced CPU and memory.
- **Why it fits DOH:** our image build/deploy path already targets ARM64 for Fargate, so `m8g` keeps EC2-backed ECS compatible with the same images.
- **`m8g.large`:** 2 vCPU, 8 GiB RAM, EBS-only storage, up to 12.5 Gbps network, up to 10 Gbps EBS bandwidth.
- **Compared with `m7g`:** AWS positions M8g as up to ~30% better performance than Graviton3/M7g.
- **Cost shape:** more expensive than tiny burstable instances, but predictable and non-burst CPU, which is better for long-running agents than `t4g` if Hermes is active.

For Hermes specifically, `m8g.large` means one instance can fit:

- one Hermes Personal task at `1024 CPU / 2048 MiB`, with room left over;
- likely one Hermes Slack task at `2048 CPU / 4096 MiB`, with less headroom;
- multiple smaller EC2-mode apps if ECS bin-packs them.

It’s a conservative first default. If Hermes Slack is busy or runs multiple sidecars/tools, `m8g.xlarge` may become a better pool default.
