## Current Architecture Summary

The flow today is:

1. **Template definitions** (`seed_app_templates.py`) declare `runtime_variables` with `category: "secret"` or `"config"`.
2. **`template_deploy_service._materialize_app_secrets`** extracts secret vars into a `dict[str, str | None]` — where `None` means auto-generate and `""` means empty placeholder.
3. This dict is stored on `DeploymentBlueprint.app_secrets`.
4. **`app_config_builder.build_app_config_from_blueprint`** passes it straight through to `AppConfig.app_secrets`.
5. **`secrets_utils.ensure_app_secrets_exist`** creates/merges a Secrets Manager entry at `devopshero/{app-name}/secrets` — empty strings become empty placeholders, `None` becomes a random 64-char token.
6. **`deploy_app.AppStack`** references that secret via `ecs.Secret.from_secrets_manager(app_secret, field=field_name)` — ECS resolves the fields at task startup.

The pain: when you deploy `hermes-1` and `hermes-2` in the same environment, both get their own `devopshero/hermes-1/secrets` and `devopshero/hermes-2/secrets` with empty `OPENAI_API_KEY`, `TAVILY_API_KEY`, `SLACK_BOT_TOKEN`, etc. You have to fill them in twice (or N times) in the AWS console.

## Design Proposal: Shared Secrets Per Environment

### Core Concept

A single Secrets Manager entry per environment holds API keys that are common across apps:

```
devopshero/{env-slug}/shared-secrets
```

During deployment, secrets are resolved in a two-tier merge: **shared-environment first, then app-level overrides**.

### Answering your three design questions

**1. "During deployment, DOH checks if a template's runtime variables match keys in the environment's shared secrets and wires them in automatically."**

Almost correct, but it undersells the mechanism. More precisely: DOH doesn't "check if they match" — it **always** checks the shared secret for any key that the template declares as `category: "secret"`. If the shared secret has a non-empty value for that key, the app uses it. If it doesn't, the key falls through to the app-level secret with its template default (auto-generated or empty placeholder). The template declaration is the source of truth for *which* keys the app needs; the shared secret is just a value source that takes priority.

**2. How does the deployment pipeline merge shared + app-specific secrets?**

The merge happens at **`ensure_app_secrets_exist` time** (before CDK runs), not at ECS runtime. Proposed logic:

```
For each key in template's secret vars:
  1. Is there a non-empty value in devopshero/{env-slug}/shared-secrets for this key?
     → Yes: Use the shared value. Do NOT write it to the app-level secret.
  2. Does the template provide a literal value (e.g., HERMES_WEBUI_PASSWORD = "mysquirrel")
     or auto_generate=True?
     → Yes: Write it to the app-level secret as today.
  3. Otherwise: Write an empty placeholder to the app-level secret as today.
```

The ECS task definition references *both* secrets — shared and app-level — with app-level taking priority. ECS `secrets` map is built with shared keys first, then app keys overwrite, so app-level always wins.

**3. What happens when a shared secret exists but the app also defines the same key with a value — the app wins?**

Yes, **app wins**. Specifically:
- If the template declares a key with a literal `value` (like `HERMES_WEBUI_PASSWORD = "mysquirrel"`), it goes to the app-level secret and takes priority in the ECS secrets map.
- If the template declares a key with `auto_generate=True`, it goes to the app-level secret (auto-generated) and takes priority.
- If the template declares a key with `value=""` and `auto_generate=False` (the common case for shared API keys), that's the "please fill me in" signal. These are candidates for shared secret resolution. If the shared secret has a value, use it; if not, the empty placeholder goes to the app-level secret.

### Implementation Plan

**A. New Secrets Manager entry** — `devopshero/{env-slug}/shared-secrets`

- Created once per environment, initially empty `{}`.
- Managed via a Django management command (`doh_shared_secrets`) or future UI.
- DOH never auto-populates it — the human/admin fills it.

**B. Changes to `secrets_utils.py`**

New function:

```python
def get_shared_secrets(session: boto3.Session, env_slug: str) -> dict[str, str]:
    """Read the environment's shared secrets. Returns {} if none exist."""
```

Modified `ensure_app_secrets_exist`:
- Accepts an additional `shared_secrets: dict[str, str]` parameter.
- For each key in `app_config.app_secrets`:
  - If the key exists in `shared_secrets` with a non-empty value AND the app's value is `""` (empty placeholder): skip writing this key to the app-level secret.
  - Otherwise: write it to the app-level secret as today.

**C. Changes to `deploy_app.py` — `AppStack.__init__`**

The ECS secrets map is built in two passes:

```python
# 1. Wire shared secrets (lower priority)
if shared_secret_keys:
    shared_secret = secretsmanager.Secret.from_secret_name_v2(
        self, "SharedSecret", f"devopshero/{env_slug}/shared-secrets"
    )
    for field_name in shared_secret_keys:
        secrets[field_name] = ecs.Secret.from_secrets_manager(shared_secret, field=field_name)

# 2. Wire app-level secrets (higher priority — overwrites shared)
if app_config.app_secrets:
    app_secret = secretsmanager.Secret.from_secret_name_v2(
        self, "AppSecret", f"devopshero/{app_config.app_name}/secrets"
    )
    for field_name in app_config.app_secrets:
        secrets[field_name] = ecs.Secret.from_secrets_manager(app_secret, field=field_name)
```

This means if `OPENAI_API_KEY` exists in both, the app-level secret wins because it's written second.

**D. IAM changes** — task role needs read access to shared secrets

```python
task_role.add_to_policy(iam.PolicyStatement(
    actions=["secretsmanager:GetSecretValue"],
    resources=[f"arn:aws:secretsmanager:{Aws.REGION}:{Aws.ACCOUNT_ID}:secret:devopshero/{env_slug}/*"],
))
```

**E. New data to plumb through the deployment pipeline**

`AppConfig` gains a new field:

```python
shared_secret_keys: list[str] | None = None  # Keys to resolve from shared env secret
```

`template_deploy_service._materialize_app_secrets` splits the template's secret vars into two buckets:
- Keys where `value=""` and `auto_generate=False` → candidates for shared resolution.
- Everything else → app-level as today.

`app_config_builder` or `deploy_app.deploy` calls `get_shared_secrets()`, intersects with the candidate keys, and sets `shared_secret_keys` on `AppConfig` to the keys that actually exist in the shared secret.

**F. No model/migration changes needed (initially)**

The shared secret is pure AWS — no new Django model field required. The `Environment` model doesn't need a new column. The shared secret name is deterministic from `env_slug`.

If you later want a UI to manage shared secrets, a `SharedSecret` model could store metadata, but the actual values stay in Secrets Manager.

### What the user experience looks like

1. Admin runs `doh_shared_secrets set --env default OPENAI_API_KEY=sk-xxx TAVILY_API_KEY=tvly-xxx`.
2. The command writes to `devopshero/default/shared-secrets` in Secrets Manager.
3. User deploys Hermes. DOH sees `OPENAI_API_KEY` is an empty-placeholder secret, finds it in shared secrets, and wires ECS to read from the shared entry. `HERMES_WEBUI_PASSWORD` (literal value) goes to the app-level secret as always.
4. User deploys a second Hermes instance or OpenClaw — same shared `OPENAI_API_KEY` is reused automatically.

### Edge Cases

- **Shared secret doesn't exist yet:** `get_shared_secrets` returns `{}`, everything falls through to app-level — fully backward compatible.
- **Key exists in shared but is empty string:** Treated as "not set" — falls through to app-level.
- **Key removed from shared secret after deployment:** The ECS task definition still references the shared secret field. If the field is removed, the task will fail to start. This is an operational concern — the management command should warn when deleting keys that are in use.
- **Re-deploy after shared secrets change:** A re-deploy picks up new shared values. No need to touch the app-level secret.
