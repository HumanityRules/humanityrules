## Current Bookmarkable Flow

The `/chat/new/` endpoint already works as a direct-link entry point:

```
/chat/new/?workspace=<workspace_uuid>&repo=<repo_uuid>
```

When both `workspace` and `repo` are provided, `create_conversation` auto-derives the mode as `APP_DEPLOYMENT`, creates a `SYSTEM_TRIGGER` message, and redirects to the new conversation. The agent then auto-starts the deployment flow.

So **you can already bookmark a URL like:**

```
https://your-domain/chat/new/?workspace=aaaa-bbbb-cccc&repo=xxxx-yyyy-zzzz
```

Every time you visit it, it creates a fresh `APP_DEPLOYMENT` conversation pre-loaded with that workspace and repository, and the agent kicks off automatically.

## What You'd Need to Make This Practical

The one friction point is that workspace and repo IDs are UUIDs, which aren't easy to remember or type. Here are a few options to make this more ergonomic:

**Option A: Support slug-based lookups** — Allow the endpoint to accept human-readable slugs (e.g., `?workspace=my-workspace&repo=my-django-app`) instead of UUIDs. This would require adding a slug field to `Workspace` and `Repository` models (or looking up by name), and modifying `chat_new` to resolve slugs to IDs.

**Option B: A dedicated shortcut URL pattern** — Add a URL like `/deploy/<workspace_slug>/<repo_slug>/` that resolves to the same logic. This gives you clean, memorable bookmarks like:

```
https://your-domain/deploy/acme-corp/admin-dashboard/
```

**Option C: Keep UUIDs, add a "copy link" button** — Add a small "Copy deploy link" button to the workspace detail page next to each repository. Users click it once and bookmark the resulting URL. No backend changes needed — just a UI affordance.

**The repo `full_name` contains a slash** (e.g., `vmendi/ai-detector-and-humanizer`), which naturally maps to two URL segments. So the pattern would be three path components:

```
/<prefix>/<workspace_name>/<repo_owner>/<repo_name>/
```

For the prefix, I'd go with **`/deploy/`** — it's short, action-oriented, and immediately communicates intent:

```
/deploy/default/vmendi/ai-detector-and-humanizer/
```

Alternatives considered:

- **`/chat/deploy/...`** — keeps it under the `/chat/` namespace, but adds noise for a shortcut URL whose whole point is brevity
- **`/start/...`** — too generic, doesn't convey *what* you're starting
- **`/d/...`** — ultra terse, but cryptic if you share the link with someone
- **`/app/deploy/...`** — more precise but longer for no real benefit

`/deploy/` feels right because it's the verb users are thinking when they reach for the bookmark: "I want to deploy this repo." It's also distinct from any existing URL namespace in the app.

One thing to decide: should the workspace name match case-insensitively? The test harness already does `name__iexact` for lookups, so `/deploy/Default/...` and `/deploy/default/...` would both work if the view follows the same pattern.

## Assistant

Here's how the data model shapes the URL design:

**Workspace** has a `slug` field, unique per organization (`unique_together = [organization, slug]`). Perfect for URLs.

**Repository** has `name` (e.g., `flask-api`) and `full_name` (e.g., `acme/flask-api`). The uniqueness constraint is on `(organization, full_name)` — not on `(organization, name)`.

So the answer to your question: **it depends on whether repo names are unique within an organization**. Right now the constraint only guarantees `full_name` uniqueness, meaning you could theoretically have `acme/dashboard` and `bob/dashboard` in the same org — two repos with the same `name` but different `full_name`.

That gives you two approaches:

**Approach A: Include the owner, use `full_name`** — unambiguous, matches the constraint

```
/chat/app_deploy/<workspace_slug>/<repo_owner>/<repo_name>/
/chat/app_deploy/default/vmendi/ai-detector-and-humanizer/
```

The Django URL pattern would be:

```python
path("chat/app_deploy/<slug:workspace_slug>/<str:repo_owner>/<str:repo_name>/", ...)
```

**Approach B: Drop the owner, look up by `name`** — shorter URL, but fail if ambiguous

```
/chat/app_deploy/<workspace_slug>/<repo_name>/
/chat/app_deploy/default/ai-detector-and-humanizer/
```

The view would query `Repository.objects.filter(organization=org, name__iexact=repo_name)`, and if it gets more than one result, return a 404 or disambiguation error.

In practice, for a single-org setup where repos typically come from one GitHub account, Approach B would almost always work and gives you the cleaner URL. You could even handle the rare ambiguous case by falling back to a "did you mean?" page. But Approach A is the safer, zero-surprise choice since it mirrors the actual uniqueness constraint.
