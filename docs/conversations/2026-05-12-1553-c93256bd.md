**Scale-in = removing capacity from an Auto Scaling Group (ASG).**

In AWS ASG terms:
- **Scale-out** — launch more EC2 instances (grow the fleet).
- **Scale-in** — terminate EC2 instances (shrink the fleet).

In your case, the ASG `devopshero-default-ecs-container-instances` runs a **target-tracking policy** managed by the ECS capacity provider. It watches a CloudWatch metric (roughly: "how much of the fleet's CPU+memory is reserved by running ECS tasks"). Two alarms are attached:

- `AlarmHigh` → "reserved capacity too high, not enough headroom" → **scale-out** (launch instances).
- `AlarmLow` → "reserved capacity too low, instances are underused" → **scale-in** (terminate instances).

That's exactly what you saw:
- `16:57` AlarmHigh fired → ASG launched 2 new instances.

## Assistant

Honestly, that comment was too hand-wavy. The real behavior is more nuanced — let me correct it.

**What `memoryReservation=2048` actually does on your kernel:**

Docker/ECS translates it to the cgroup v2 knob **`memory.low = 2 GiB`** (we saw exactly this value when we catted `/sys/fs/cgroup/memory.low` on the live container). `memory.low` is **not a pressure valve that forces memory back down.** It's a *soft floor*:

- When the kernel needs to reclaim memory (host is under pressure), it prefers cgroups whose usage is **above** `memory.low`. Cgroups below `memory.low` are protected from reclaim "when possible."
- A container is free to grow past 2 GiB all the way up to `memory.max=4 GiB` whenever free RAM is available. Nothing proactively pushes it back down.

**The real dynamic when two hermes tasks share a node:**

1. Task A boots alone, gradually uses 3.5 GiB (plenty of free host RAM). `memory.low=2, usage=3.5, max=4`. Nothing happens — no pressure.
2. Task B is placed on the same node. Now total demand > host capacity. Kernel starts reclaiming.
3. Kernel looks at Task A (above its 2 GiB floor → reclaim candidate) and Task B (below its floor → protected).
4. Reclaim happens on **reclaimable pages only**: page cache first, then swappable anonymous pages if swap is configured. Task A's RSS may shrink as the kernel reclaims its file-backed pages, but **only pages that can actually be reclaimed.** If Task A's memory is 3.5 GiB of hot anonymous Python objects that are being referenced, the kernel can't reclaim them — it'll OOM-kill a process before violating `memory.low` protections of Task B.

**What the guarantee actually is:**

- Each task is *guaranteed* that when the kernel can give it 2 GiB, it will — even if its neighbor wants more.
- Neither task is *guaranteed* to stay at or near 2 GiB when its neighbor is idle.
- Under real pressure, reclaim happens at whatever granularity the kernel can find — not a clean "both snap to 2 GiB."

**What a more honest comment would say:**

```python
# Placement reservation: 2 GiB so two hermes tasks fit on one m8g.large
# (~7747 MiB usable). Hard cap: 4 GiB — the container can burst there
# when alone on the node. When a second task arrives, the kernel
# prefers reclaiming from whichever container is above its 2-GiB
# memory.low floor; actual usage doesn't snap to 2 GiB, but each task
# is protected from being evicted below 2 GiB by its neighbor.
```
