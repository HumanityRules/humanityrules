## What actually broke

The hermes-hud SPA was built with Vite/CRA-style defaults (`base: "/"`), so its `dist/` ships with absolute paths baked into both the HTML and the JS bundle:

```html
<!-- index.html -->
<script type="module" src="/assets/index-abc123.js"></script>
<link rel="modulepreload" href="/assets/vendor-def456.js">
<link rel="stylesheet" href="/assets/index-789xyz.css">
```

```js
// inside index-abc123.js
fetch("/api/state").then(...)
new WebSocket("/ws")
new EventSource("/events")
```

The webapps proxy lives at `/webapps/<slug>/`. So:
- `https://host/webapps/hud/` → strips prefix → fetches `index.html` from upstream. OK.
- Browser then sees `<script src="/assets/...">` → fetches `https://host/assets/index-abc123.js`. That request has **no `/webapps/<slug>` prefix**, so Caddy's `import routes.caddy` doesn't match it, it falls through to the WebUI reverse_proxy on `:8789` → WebUI returns its own catch-all (HTML or 404 JSON), MIME mismatch, page broken.
- Same story at runtime for `fetch("/api/...")` and `new WebSocket("/ws")`.

The agent's fix (rewrite HTML to relative + 30-line monkey-patch shim) is correct but ad-hoc. Doing it once in the platform is clearly the right move. The question is *how*.

## The fundamental constraint

Anything that ships a built bundle assuming `base = "/"` will hit this. The bundle contains hardcoded absolute path strings in JS that no `<base href>` or HTTP header can rewrite, because:

1. **`<base href="/webapps/slug/">` doesn't fix root-absolute URLs** (`/foo` resolves against the document's origin, not against `<base>`'s path). Per WHATWG URL parser. Only document-relative URLs (`foo`, `./foo`) honor `<base>`.
2. **`X-Forwarded-Prefix` is server-side**; the browser parses asset tags before any JS that could read it runs.
3. **Service Workers** can intercept requests, but they're not active on first navigation — chicken-and-egg.

So fixing this generically requires **either** rewriting bytes that go to the browser (HTML rewriting at create-time or response-time) **or** asking the user to rebuild with the right `base`. We can't rebuild — that's the whole point.

## The choice space

Five shapes worth considering, ranked:

**A. Per-app subdomain.** `https://hud--hermes-foo.<env>/`. Root-absolute paths just work. Architecturally cleanest by far — but explicitly rejected in `webapps_design.md` because it propagates DNS, adds per-app ALB listener rules, and forks the auth surface. Reopening this requires the customer to accept wildcard DNS + wildcard ACM cert + ALB rules dance. Big lift, big change. Probably ruled out unless you want to revisit that constraint.

**B. Static-SPA mode in the CLI (new shape).** `webapps create-spa <slug> --dist <dir>` (or `webapps create <slug> --serve-dir <dir>`). Platform owns the serving. A tiny platform-owned Python static server (`/opt/doh/runtime/serve_spa.py`) replaces `python3 -m http.server`. It does two things to each HTML response on the fly:
  - Rewrites `href`/`src`/`action` attributes whose value starts with `/` (and isn't already prefixed) → prepends `/webapps/<slug>`.
  - Injects a `<script>` shim at the top of `<head>` that monkey-patches `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon`, `Worker`/`SharedWorker` constructors, and `import.meta.url`-derived dynamic imports.
  
  Non-HTML files are served as-is. The shim file itself is served by the same server at `/__doh_path_shim.js` (relative to the slug, so `/webapps/<slug>/__doh_path_shim.js`).
  
  Slot into existing infra without surgery: the new server is just a `--command` line like any other webapp, registered in `process-compose.yaml`, port-allocated, reverse-proxied by Caddy — the existing routing model is unchanged.

**C. Caddy-side response rewriting on the existing route.** Build Caddy with the `caddy-replace-response` plugin (xcaddy) and have `routes.caddy` apply HTML rewrites + shim injection on responses from any upstream. Works for both static `dist/` (served by any static server) AND dynamic backends (e.g., a Next.js server that emits HTML with `/_next/...` references).  
  Trade-off: requires building Caddy ourselves (Dockerfile changes), and HTML response rewriting is intrusive — if a framework already prefix-aware emits `/webapps/slug/api/foo`, the regex needs to be idempotent (skip if already prefixed). Doable but more moving parts.

**D. Referer-based path-rewriting in Caddy.** When `/assets/foo.js` hits Caddy with `Referer: https://host/webapps/slug/...`, rewrite the request URI to `/webapps/slug/assets/foo.js` and re-evaluate the routes.  
  Pros: zero JS injection, fully transparent.  
  Cons: `Referer` can be stripped (`Referrer-Policy: no-referrer`, cross-origin, opted-out browsers); WebSocket `Referer` behavior is browser-dependent (Origin is sent, Referer often not); two SPAs whose Referers can race. Clever but fragile. Don't recommend as the primary mechanism.

**E. Pre-transform `dist/` on disk at create time.** Walk the dist, rewrite HTML files in place, leave a marker. Easy to implement but destructive (re-builds overwrite the transform, requiring "did the user rebuild?" detection) and confusing when the agent inspects `dist/index.html` and sees doctored bytes. Not recommended.

## Recommendation: option B (static-SPA mode), with a clear path to C later

For the case the user actually hit (a checked-in prebuilt SPA), option B is the smallest, most boring fix that solves the problem cleanly:

- **No Caddy build changes.** Reuses the existing CLI/process-compose/Caddy data path verbatim.
- **No agent-written shims.** The shim lives in `template_repos/hermes_agent/doh_runtime/spa_shim.js`, one copy, well-tested.
- **No HTML-on-disk rewriting.** Rewrites happen in the static server at response time. User's `dist/` is byte-identical to what their build emitted; debugging is sane.
- **Clear opt-in.** A separate CLI shape (`webapps create-spa <slug> --dist <dir>`) makes the contract explicit: the platform owns the prefix problem only when you ask it to. Existing `webapps create --command` apps unaffected.
- **No port allocation change, no nono-profile change** (the new server binds to `127.0.0.1:$WEBAPP_PORT` just like any user command). The only allow-list addition is reading the new files at `/opt/doh/runtime/serve_spa.py` and `spa_shim.js`.

If, later, we discover backend processes that *also* embed absolute paths in their HTML (Streamlit at root, some Dash setups, etc.), we can graduate to option C — add `caddy-replace-response` and apply the same transform to upstream-served HTML. Option B is forward-compatible with that: same shim file, same rewrite rules, just applied in a different layer.

### `serve_spa.py` (sketch)

Stdlib `http.server` is enough. Conceptually:

```python
# Pseudocode — actual impl is ~150 lines including arg parsing, MIME, etc.
class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        path = self.translate(self.path)
        if self.path == "/__doh_path_shim.js":
            return self._serve_shim()
        if not os.path.exists(path) and SPA_FALLBACK:
            path = os.path.join(ROOT, "index.html")
        if path.endswith(".html"):
            return self._serve_html_rewritten(path)
        return self._serve_static(path)

    def _serve_html_rewritten(self, path):
        html = open(path).read()
        # 1. Rewrite absolute-path attrs that aren't already prefixed.
        html = ATTR_RE.sub(lambda m: m[1] + (PREFIX + m[2] if not m[2].startswith(PREFIX) else m[2]) + m[3], html)
        # 2. Inject shim at top of <head>.
        html = html.replace("<head>", f'<head>\n<script>window.__DOH_PREFIX="{PREFIX}"</script>\n<script src="{PREFIX}/__doh_path_shim.js"></script>\n', 1)
        self._write(200, "text/html; charset=utf-8", html.encode())
```

`ATTR_RE` matches `(href|src|action|formaction|poster|data)="(\/[^"]*)"` and the same with single quotes; excludes `//` (protocol-relative) and `/__doh_` (so we don't double-prefix the shim itself). Also handles `<link rel="modulepreload" href=...>` and inline JSON manifests if needed.

### `spa_shim.js` (the canonical version)

The same ~30 lines the agent wrote inline, owned and tested by the platform. Idempotent (won't double-prefix). Specifically wraps:

## What this design deliberately doesn't do

- **No retroactive shim on existing `webapps create` apps.** Backends that handle the prefix via `X-Forwarded-Prefix` shouldn't get rewriting — they'd interfere. Opt-in via the new command keeps the contract clear.
- **No HTML transformation on dynamic backends in v1.** If hermes-hud's siblings ever ship as a Next.js or Express server (not static), we'd need option C. Not now.
- **No WebSocket protocol upgrades.** The shim rewrites the URL; Caddy already proxies WS transparently. Untouched.
- **No build-tool integration.** We're not detecting Vite/CRA configs and offering to rebuild. The whole premise is "can't rebuild."

## Re-reading the original rejection

The `webapps_design.md` rejection ("propagating DNS, adding ALB listener rules per app") assumed **per-app** DNS/ALB work. If DOH owns Route 53, ACM, and the ALB, the cost flips to **one-time-per-agent**, not per-app. Concretely:

- **TLS**: one wildcard ACM cert per agent: `*.hermes-<slug>.<env-zone>`. DNS-validated through the same Route 53 we own → fully automated. Auto-renews. Attached to the existing ALB listener as an SNI cert.
- **ALB**: the existing per-agent listener rule already matches the bare hostname; we just widen the host condition to also match `*.<agent-host>`, same target group. **Zero new rules per app.**

Per-webapp cost: zero. The "explain why my dashboard lives on a different host" framing also inverts — `dashboard.hermes-<slug>.<env>` reads more naturally as "my dashboard, hosted by my agent" than `<agent>/webapps/dashboard/`.

## What this unlocks

Once the agent hostname has wildcard DNS + wildcard cert pointed at the same ECS task, **the entire path-prefix gymnastics disappears**.
