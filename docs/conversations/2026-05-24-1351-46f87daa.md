## Assistant

## What it actually does

Hermes has "gateway"-style integrations where the sandboxed process needs the credential at **boot** (not lazily on each outbound call). Telegram's bot loop does long-polling: at startup it reads `TELEGRAM_BOT_TOKEN`, builds a URL `https://api.telegram.org/bot{TOKEN}/getUpdates`, and holds it open. By the time the request hits the proxy, it's too late to "supply credentials" — the token had to be in the URL when the gateway constructed it.

The trick: we put the **placeholder** (`000000:DOH_PLACEHOLDER`) into `TELEGRAM_BOT_TOKEN` instead of the real secret, so the gateway dutifully constructs `…/bot000000:DOH_PLACEHOLDER/getUpdates`. The broker's TLS-intercept proxy then swaps the placeholder for the real token on the wire (the same `VaultUrlRewrite` path we just refactored). The real secret never lives in `/proc/<sandbox-pid>/environ`. `TELEGRAM_ALLOWED_USERS` is a non-secret allow-list the user pasted along with the token — it gets exported as plain config because it's not sensitive.

So `load_gateway_integration_env` is the bridge: read the broker's `/integrations` cache, find connected gateway providers, project their config into env-var lines, and inject those into `run_in_nono`'s env.

## What's hardcoded that shouldn't be

1. **Provider name `"telegram"`** is hardcoded in the heredoc. Adding the next gateway (Discord, Slack RTM, IRC…) means editing `supervisor.sh`.
2. **The placeholder string `"000000:DOH_PLACEHOLDER"`** is duplicated from the `VaultUrlRewrite` spec. If someone changes one, the other silently breaks.
3. **Env-var names `TELEGRAM_BOT_TOKEN` / `TELEGRAM_ALLOWED_USERS`** and the `config.allowed_users` projection live in shell, far from the spec they describe.

## Suggested shape

Push the env-var mapping onto the spec, and have the broker render the lines server-side. Supervisor becomes provider-agnostic — it just iterates whatever the broker returns.

Add a small data class and attach it to `VaultUrlRewrite` (only vault providers need this; OAuth ones don't have a gateway-style boot-time channel):

```python
@dataclass(frozen=True)
class GatewayEnvBinding:
    """Env var the in-sandbox gateway reads at startup.

    `source` is either the literal "placeholder" (use the URL-rewrite
    placeholder verbatim — broker swaps on the wire) or a key in the
    connected `config` dict. `list_separator` joins list-shaped config.
    """
    env_var: str
    source: str
    list_separator: str | None = None


@dataclass(frozen=True)
class VaultUrlRewrite:
    placeholder: str
    gateway_env: tuple[GatewayEnvBinding, ...] = ()
    connect_mode: ClassVar[str] = "vault"
    restart_required_after_save: ClassVar[bool] = True
```

Telegram becomes:

```python
credential_method=VaultUrlRewrite(
    placeholder="000000:DOH_PLACEHOLDER",
    gateway_env=(
        GatewayEnvBinding(env_var="TELEGRAM_BOT_TOKEN", source="placeholder"),
        GatewayEnvBinding(env_var="TELEGRAM_ALLOWED_USERS", source="allowed_users", list_separator=","),

)
```

The broker either folds rendered lines into the `/integrations` payload (e.g. `item.gateway_env: ["TELEGRAM_BOT_TOKEN=000000:DOH_PLACEHOLDER", "TELEGRAM_ALLOWED_USERS=1,2,3"]`) or exposes a dedicated `/gateway-env` endpoint. Supervisor's heredoc collapses to:

## Why the file fits better

1. **Hermes already loads it.** Upstream's `_load_env_file` reads `${HERMES_HOME}/.env` and OR-merges with `os.environ`. The gateway boots inside nono via `webui.sh`, which inherits `HERMES_HOME=/workspace/.hermes`. Whether we set `TELEGRAM_BOT_TOKEN` via env or via that file, the gateway sees the same value.

2. **Drops a complex shell pipe.** `load_gateway_integration_env`'s current shape is: spawn a Python subprocess inside supervisor, have it HTTP-call the broker, `print()` lines, parse them back into a bash array, splice that array into a `runuser env` invocation. That's three serializations to land bytes in another process's env. A file write is one step.

3. **Keeps placeholder/spec/env-name knowledge co-located.** Supervisor stops knowing what "telegram" means. The spec carries `gateway_env=(GatewayEnvBinding(env_var="TELEGRAM_BOT_TOKEN", source="placeholder"), ...)`; a small helper renders those into `${HERMES_HOME}/.env`. Adding Discord = one spec entry, no shell edits.

4. **No new sandboxing tradeoff.** The values we're injecting are *placeholders*, not secrets — the broker swaps them on the wire. So whether they live in `/proc/<sandbox-pid>/environ` or in a file the sandbox can read makes no difference to leak posture. The file is fine here exactly because nothing sensitive ends up in it. (Real secrets — bearer tokens, AWS creds — stay in supervisor's env, never written.)

## Two design knobs to pick

**Who writes the file?** Two options:

- **Supervisor writes it once at boot** (still queries broker via the same /integrations call, but emits to a file instead of bash array). Smallest change. Restart-required-after-save semantics unchanged — the user already gets a redeploy when connecting Telegram.
- **Broker writes it** whenever a status changes. Cleaner separation (supervisor stops knowing about integrations entirely), but adds a write-to-sandboxed-path responsibility to the broker, and the gateway still has to restart to re-read, so the operational benefit is small.

I'd start with supervisor-writes. It collapses the immediate ugliness without taking on cross-process file-writing complexity.

**Should we keep `broker_env` (HTTPS_PROXY, GITHUB_TOKEN, etc.) in supervisor's env-splice?** I'd say *yes, leave it.* Those are static, small, and tied to the broker's own lifecycle (set when broker is up, unset when it isn't). Moving them to the file would be churn for no gain, and they're not under the spec system.

So: only the *dynamic, spec-driven* gateway env moves to `${HERMES_HOME}/.env`. Static broker plumbing stays in `run_in_nono`.

## Assistant

Yes — the broker is the right candidate. It already mediates the connect/disconnect flow:

- **Connect (vault):** WebUI POSTs `/api/integrations/credentials/submit` to DOH directly, then immediately calls broker's `/integrations/{slug}/invalidate_tls_cache`. The broker sees the invalidation and on the next request refetches the new state from DOH.

So the broker is in the loop for both transitions. Two natural write points:

1. **Event-driven** — write on every cache invalidation (covers connect, disconnect, and explicit "Refresh all").
2. **State-driven** — write on every `_refresh_provider` completion (covers token refreshes too, but those don't change `gateway_env` projections, so it's mostly redundant).

I'd do (1) — invalidation is the single chokepoint where "the connected state may have changed."

**On "respect any other env var":** the safest pattern is a managed-block sentinel:

```
# whatever the user/onboarding put here
HERMES_DEBUG=1

# === DOH-MANAGED-INTEGRATIONS BEGIN ===
TELEGRAM_BOT_TOKEN=000000:DOH_PLACEHOLDER
TELEGRAM_ALLOWED_USERS=1,2,3
# === DOH-MANAGED-INTEGRATIONS END ===
```

Read the existing file, strip lines between the sentinels, append the freshly-rendered block, write to a tempfile, `os.replace()`. Anything outside the sentinels is preserved verbatim. The block is regenerated from the spec each time, so adding/removing providers, renaming env vars, or fixing typos all converge on the next write — no migration logic needed.

**Three smaller things worth flagging:**

- **Ownership.** Broker runs as root; gateway runs as `hermeswebui`. File needs mode 0644 (world-readable). That's fine here because contents are placeholders, not real secrets — same threat model as `GITHUB_TOKEN=DOH_PLACEHOLDER` already in env. If a future provider needed a real secret in the file, we'd reconsider.

- **Persistence interaction.** `${HERMES_HOME}=/workspace/.hermes` lives on EFS. The file survives container restart, so on the next boot the gateway picks up whatever the last broker write produced — even if the broker is briefly down at boot. Today's supervisor flow loses that on every boot. (Slight benefit: faster boot — gateway doesn't have to wait for broker to be up before reading its env.)

- **Boot-time rewrite still needed.** First-ever boot has no file. The broker's *first refresh* of every provider should also write the file, so a fresh container reaches a correct state without requiring a connect/disconnect event.

Better answer: **no boot-time rewrite.** Broker writes only on connect/disconnect events. EFS persistence handles the rest. Simpler.

That actually strengthens the design: write happens at exactly the moments the source of truth changes. No boot synchronization, no "is the broker ready yet" race in supervisor.

## Open questions

1. **Failure handling.** Broker successfully writes `.env` but the process-compose API call fails (process-compose down, network glitch). Options:
   - **Fail the user-visible Save:** propagate the error back through invalidate, show "Save succeeded but gateway restart failed — redeploy the app." User confused, but no silent breakage.
   - **Fail open:** log and return success. .env is updated, so next *full* boot picks it up. User thinks Telegram works but it doesn't.
   - **Best-effort with status:** broker tracks "last gateway restart at X, requested by event Y" and exposes it in `/integrations`. UI shows a stale-state warning if the latest event hasn't been picked up.

   I'd lean (a) — surface failure clearly. process-compose being unreachable is a real problem worth surfacing, not a transient.

2. **Concurrent saves.** User clicks Save → restart in flight. Before it completes, user clicks Save again (e.g., changing `allowed_users`). Two restarts queued. process-compose handles serialization OK (each restart is stop+start), but the second restart could land before the first finished and confuse state. Boot ordering becomes:

- **supervisor.sh `start_integrations_broker`** must wait for the broker to have rendered the file once. Easy: the broker's startup performs the initial `_ensure_fresh` for all providers, then the file write, then opens the control port. Supervisor's existing `wait_for_port` on the control port becomes the synchronization point. By the time `wait_for_port` returns, the file is on disk.
