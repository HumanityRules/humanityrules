## What exists today

The environment provisioning flow currently works like this: user clicks "New Environment" on the environments page, picks an AWS account from a modal, and gets sent to the **generic chat UI** (`chat_new?aws_account=...`). The agent runs with `mode=ENVIRONMENT_SETUP`, asks about name/region/domain, calls `provision_environment`, then polls `get_environment_status`. Once done, the user has to navigate away from the chat to see the environment.

The Conversation model already has `context_aws_account` but **no `context_environment`** field.

## How I'd approach it

The deployment editor established a clean pattern: left panel = task artifact, right panel = conversation. The environment editor should follow the same structure, but it's a **simpler** case because the domain model is flatter:

- **App deployment** has a two-level artifact: `App` then `DeploymentBlueprint`, with progressive context narrowing (repo-scoped -> app-scoped -> blueprint-scoped).
- **Environment provisioning** has a single artifact: `Environment`, with context going from AWS-account-scoped to environment-scoped.

The left panel would have two sections mirroring the two concepts in play:

1. **AWS Account section** (top) — the account this environment lives in. Mostly read-only context (account name, ID, region capabilities). Analogous to the App section.
2. **Environment section** (bottom) — the environment being provisioned: name, region, hosted zone, status, VPC ID, cluster ARN, status message. Analogous to the Blueprint section. This is the "task artifact."

The conversation scoping would be:

1. Start with `context_aws_account` only (agent asks clarifying questions about name, region, domain).
2. After `provision_environment` creates the Environment record, the conversation becomes environment-scoped (`context_environment` set).
3. Left panel refreshes via the same SSE + HTMX pattern (`doh:environment-created`, `doh:environment-changed-{id}`).

The provisioning status polling (`PENDING` -> `PROVISIONING` -> `READY`/`ERROR`) maps neatly to the blueprint's `deploying` -> `active`/`failed` pattern. The environment section would auto-refresh while status is `PROVISIONING`, same as the blueprint section does during `deploying`.

## Questions you need to answer

**1. Scope of the editor — creation only, or also management?**

The deployment editor is specifically for the deployment *task* (creating an app + blueprint + deploying). Should the environment editor be limited to provisioning, or should it also cover ongoing management (teardown, editing, re-provisioning after error)? This determines whether the environment detail page stays as-is or gets absorbed.

**2. Entry point and URL structure**

Currently the environments page has a "New Environment" button with an AWS account picker modal. Two options:
- Keep the modal for AWS account selection, then redirect to `/environments/new/?aws_account=<id>` (environment editor)
- Or move the AWS account selection into the conversation itself (agent asks "which account?")

The first is consistent with how app deployment works (workspace + repo selected before entering the editor). The second is simpler but loses the structured entry point.

**3. Do we need a `context_environment` field on Conversation?**

Almost certainly yes — analogous to `context_deployment_blueprint`. But confirming because it's a model change.

**4. Resuming provisioning — same conversation or new?**

If provisioning fails (`ERROR` status), should the user resume the same conversation (like failed blueprints)? And if a user navigates away during `PROVISIONING` and comes back later, what's the experience? The deployment editor has "Resume Deployment" for this. Environments would need a similar pattern: environments in `PENDING`/`PROVISIONING`/`ERROR` status should show a "Resume" action in the environments list.

**5. What does "done" look like?**

For app deployment, "done" is clear: the app is reachable at its URL. For environment provisioning, "done" is `READY` status (VPC + cluster exist). After that, should the editor nudge the user to deploy an app? Show a "Deploy your first app" link? Or just stay on the environment detail?

**6. Left panel content — what fields during provisioning vs. after?**

Before the Environment record exists, the left panel is mostly empty (just the AWS Account section). Once created, it shows name, region, hosted zone, status. Once `READY`, it can show VPC ID, cluster ARN, etc. Should this be a progressive reveal (like the blueprint section appearing only after the app section is filled), or should all fields be visible with "pending" placeholders?

**7. Should the existing environment detail page get a chat panel?**

Two options for existing environments:
- The environment editor is only for initial provisioning; the detail page stays as-is
- The detail page gets a chat panel for ongoing environment management (teardown, troubleshooting)

This parallels a decision you deferred for app deployment (redeployment workflow for existing apps).

**8. The system prompt — how much of the environment agent's behavior changes?**

The current environment setup agent is relatively simple (pick name, region, domain -> provision -> poll). Does the agent need to get smarter? For example: analyzing existing environments to suggest configuration, checking VPC CIDR conflicts, recommending region based on team location? Or is the current tool set sufficient and we're mainly changing the UI shell?

## Implementation Plan: Environment Editor with Integrated Chat

### Summary

Transform the environment detail page into a two-panel editor (environment info left, conversation right), following the deployment editor pattern. The same page handles both new environment provisioning and ongoing management of existing environments.

### Key design difference from the deployment editor

The deployment editor has two distinct entry points: "new app" (no app exists yet) and "existing app" (app already exists). For environments, we're integrating the chat **into the detail page itself**, which means:

- **New environment**: modal picks AWS account -> redirects to `/environments/new/?aws_account=<id>` -> two-panel editor with empty left panel + fresh conversation
- **Existing environment**: `/environments/<slug>/` -> two-panel editor with populated left panel + existing or new conversation
- **Resume**: environments in `PENDING`/`PROVISIONING`/`ERROR` status show a "Resume" badge/action in the environments list that links to `/environments/<slug>/`

### Changes by layer

**1. Model: add `context_environment` to Conversation**
- Add `context_environment` ForeignKey to `Conversation` (nullable, `SET_NULL`)
- Migration

**2. View: `environment_editor.py` (new file)**

Entry points:

- `environment_editor_new` — `/environments/new/?aws_account=<id>`
  - Creates an `ENVIRONMENT_SETUP` conversation with `context_aws_account` set
  - Renders two-panel editor with no environment yet (left panel shows AWS account section + empty environment section with placeholders)
- `environment_detail` — `/environments/<slug>/` (replaces current `environment_detail`)
  - Loads the environment
  - Finds or creates an `ENVIRONMENT_SETUP` conversation scoped to this environment (`context_environment`)
  - Renders two-panel editor with populated left panel + conversation
- `environment_editor_environment_section` — `/environments/<slug>/environment-section/`
  - HTMX partial endpoint for refreshing the environment section (like `deployment_editor_blueprint_section`)

The existing tag management views (`environment_tag_add`, `environment_tag_remove`, `environment_tags_save`) stay as-is. The environments list view stays as-is.

**3. Templates**

- `environments/environment_editor.html` — two-panel layout (mirrors `deploy/deployment_editor.html`)
  - Left panel: `#aws-account-section` + `#environment-section` (with `hx-trigger="doh:environment-changed-<id>"`)
  - Right panel: `{% include "_chat_panel.html" %}`
  - JS listener for `doh:environment-created` to reload the editor at `/environments/<slug>/`
- `environments/_aws_account_section.html` — read-only AWS account info (name, account ID, status)
- `environments/_environment_section.html` — environment fields: name, region, domain, status, VPC ID, cluster ARN, status message, deployments. Shows pending placeholders when no environment exists. Auto-refreshes during `PROVISIONING` (like blueprint does during `deploying`)

**4. SSE event wiring in `chat.py`**

Add notification dispatch for environment tools:
- `mcp__devopshero__provision_environment` -> `sse-notify` `environment-created` with `slug` (when creating new) or `environment-changed-<id>` (when retrying)
- `mcp__devopshero__get_environment_status` -> `sse-notify` `environment-changed-<id>` (so left panel refreshes after each status poll)

**5. `provision_environment` tool update**

After creating/updating the Environment record, set `conversation.context_environment` on the conversation (same pattern as `save_blueprint` setting `context_deployment_blueprint`). This requires the tool to receive the conversation object (currently it doesn't — it gets `organization` and `user` only).

**6. URL patterns**

New routes:
- `environments/new/` -> `environment_editor_new`
- `environments/<slug>/environment-section/` -> `environment_editor_environment_section`

Modified routes:
- `environments/<slug>/` -> now points to the editor view instead of the old detail view

**7. AWS account picker modal update**

Change the link target from `{% url 'chat_new' %}?aws_account={{ account.id }}` to `{% url 'environment_editor_new' %}?aws_account={{ account.id }}`.

**8. Environments list update**

For environments in `PENDING`/`PROVISIONING`/`ERROR` status, show a visual indicator and link to `/environments/<slug>/` (which now opens the editor with the conversation).

**9. System prompt: no changes**

The existing `system_prompt_environment.md` and `_build_environment_prompt` work as-is. The agent's behavior doesn't need to change — only the UI shell around it. The `<after_success>` section could optionally be updated to mention a "Deploy your first app" link in the left panel, but that's cosmetic.

**10. `agent_build_prompt.py`: minor update**

When building the environment prompt and `conversation.context_environment` is set, include the environment's current state in the prompt context (so the agent knows what environment it's working with on resume).

### What we're NOT doing

- No new "EnvironmentBlueprint" concept — the Environment model itself is the artifact
- No changes to the agent's tools or intelligence level
- No teardown from the editor (deferred — can be added to the conversation later)
- No changes to the job worker or provisioning executor

### Suggested implementation order

1. Model migration (`context_environment`)
2. View + templates (environment editor, sections)
3. URL wiring + modal update
4. SSE events in `chat.py`
5. `provision_environment` tool: set `context_environment` on conversation
6. `agent_build_prompt.py`: include environment context on resume
7. Environments list: resume indicators
