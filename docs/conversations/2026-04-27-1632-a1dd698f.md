## The three-container picture

There are three distinct containers in play — it's easy to conflate them:

1. **Hermes container** (long-lived ECS task) — runs the WebUI. `pip install` here would persist.
2. **DinD sidecar** (long-lived ECS task) — just a Docker daemon that Hermes's CLI talks to via `DOCKER_HOST`.
3. **Tool container** — spawned *by* Hermes inside DinD via `docker run -d … sleep infinity` every time the agent needs to run a shell/pip/apt command. This is where the agent's commands actually execute. **This is the one pip installs into.**

When the agent runs `pip install foo`, it installs into the tool container's rootfs (e.g. `/usr/local/lib/python3.x/site-packages`) — not into our Hermes or DinD containers.

## Why it doesn't persist

In `template_repos/hermes_agent/config.yaml.template:45` we set:

```
container_persistent: false
```

Tracing that flag through the upstream code (`tools/environments/docker.py:333-354` and `tools/terminal_tool.py:920-934`, `run_agent.py:2293-2320`):

- With `container_persistent: false`, `_DockerEnvironment` mounts `/workspace`, `/home`, `/root` as **tmpfs** and the rest of the container rootfs is the ephemeral writable layer.
- At end-of-turn, `AgentLoop._cleanup_task_resources` calls `is_persistent_env(task_id)`. Because `_persistent=False`, it does **not** skip teardown — `cleanup_vm` runs and `docker rm -f` nukes the tool container.
- Next tool call → fresh container → fresh rootfs → no pip packages.

Even the idle reaper (`TERMINAL_LIFETIME_SECONDS`, default 300s) would do the same thing later, but in our case it never even gets that chance — the per-turn teardown fires first.

## If we flipped it to `container_persistent: true`

It would only *partially* fix it:

- Upstream's persistent mode bind-mounts `~/.hermes/sandboxes/docker/<task_id>/home → /root` and (if not overridden) a workspace dir → `/workspace`. Everything else in the container rootfs is still the writable layer, which is discarded when the container is recreated.
- `pip install --user` (writes to `/root/.local`) would survive ✅.
- `pip install` system-wide (writes to `/usr/local/lib/python*/site-packages`) would **not** survive ❌.
- `apt install` would **not** survive ❌.
- Upstream's own docs explicitly warn: persistence "does not promise that the same live sandbox, PID space, or background processes will still be running later" (`website/docs/user-guide/configuration.md:91`).

There's another wrinkle: our DOH config has `docker_volumes: ["/workspace:/workspace"]` — a bind-mount straight from the Hermes container's EFS. That means `/workspace` already persists today independent of `container_persistent`. Files the agent writes under `/workspace` survive; packages it installs into `/root`, `/usr/local/...`, or `/home` do not.

Also worth noting: the DinD sidecar's storage is task-local on Fargate, so on any ECS task restart you also lose whatever cached images/layers were in DinD — the tool image gets re-pulled (the entrypoint pre-warms it).

1. **Leave as-is, teach the agent**: document in `SOUL.md` / a skill that package installs don't survive between turns, so it should either (a) keep work in the same turn, or (b) put things under `/workspace` (a venv there would persist). Lowest blast radius.

3. **Bake the common deps into `TOOL_IMAGE`**: if there's a known set of packages the agent keeps reinstalling, put them in the image itself. Most durable, but you have to know what to bake in.
4. **Venv under `/workspace`**: nudge the agent to `python -m venv /workspace/.venv` so pip installs land in the already-persistent EFS mount. Works today without any config change.

My lean: option 1 + 4 together — cheap, no moving parts, and honest about what the sandbox actually guarantees. Option 2 is a reasonable small upgrade on top if you want shell/history continuity within a task. Want me to draft the SOUL.md / skill note, or change the config?

## Per-package-manager: what works, what doesn't

### Python — easy, two clean options

**Option A: redirect to `$HOME/.local` (covers user installs, free with `container_persistent`)**
- `pip install --user foo` → `/root/.local/lib/python*/site-packages` → EFS ✅
- Set `PIP_USER=1` in the container env and plain `pip install foo` starts going there too.
- No entrypoint surgery; works the minute you flip `container_persistent: true`.

**Option B: a DOH-managed venv on EFS**
- Seed `/workspace/.venv-doh` once via entrypoint if missing (`python -m venv`).
- Activate it for every shell by dropping an `/etc/profile.d/doh-venv.sh` into the tool image, or by setting `VIRTUAL_ENV` + `PATH` via Hermes's env forwarding.
- All `pip install` (global-style) lands on EFS.
- Cleaner isolation than --user, but requires TOOL_IMAGE cooperation to auto-activate.

Either one makes pip effectively persistent. B is nicer; A requires zero TOOL_IMAGE changes.

### npm — same shape, just a different prefix

- `npm config set prefix /workspace/.npm-global` (or `/root/.npm-global` if we rely on /root being on EFS).
- Add `<prefix>/bin` to PATH.
- `npm install -g typescript` persists ✅.
- Either seed the config in TOOL_IMAGE, or wire env vars (`NPM_CONFIG_PREFIX`).

### apt — the one that doesn't cooperate

apt scatters files across `/usr/bin`, `/usr/lib`, `/etc`, `/var/lib/dpkg`, `/var/lib/apt`. You can't cleanly bind-mount "all of the places apt writes" without effectively mounting the whole rootfs from EFS — at which point (a) you're bypassing the image's layered filesystem, (b) EFS small-file latency makes every binary exec slower, and (c) new TOOL_IMAGE versions constantly conflict with the EFS snapshot.

Three realistic answers for apt-level deps:

1. **Bake into TOOL_IMAGE.** The honest one. `apt-get install` for anything you *know* the agent will need. Rebuild, push, bump the pin. Best performance, simplest model, zero EFS weirdness. Weakness: requires predicting what the agent will need.

2. **Replace apt with a prefix-style package manager that lives in `/workspace`.** micromamba/pixi, nix single-user, or Homebrew-on-Linux all install system-level binaries (gcc, ffmpeg, postgres-client, etc.) into a single directory tree. Point that directory at EFS and they persist perfectly, including shared libraries.
   - micromamba: `micromamba create -p /workspace/.conda/default -c conda-forge gcc ffmpeg …` — conda-forge has apt-equivalents for most common things.
   - nix: most complete but heavyweight, and the agent would need to know nix.
   - This is the most powerful answer: it lets the agent install arbitrary "system" deps with full persistence, without us needing to know what it'll want.

3. **`dpkg -x` into an EFS prefix.** Works for self-contained binaries (`jq`, `ripgrep`, small CLIs). Falls over on anything with postinst scripts, daemons, or ldconfig dependencies. Not a real general answer — mention only as a get-out-of-jail for one-off binaries.

## Overlay-from-EFS: why I wouldn't

You could bind-mount `/usr/local/lib/python3.X/site-packages` itself from EFS (seeded on first boot by copying from the image). Tempting but bad:
- Version drift — new TOOL_IMAGE ships newer built-ins; EFS copy shadows them with old versions. Silent breakage.
- EFS latency on Python import (thousands of stat/read of tiny files). A venv on EFS has the same cost, but at least it's scoped to packages *you* installed, not the image's entire base stdlib-adjacent tree.
- The failure modes are the kind that waste a debugging afternoon months from now.

A venv on EFS has the same latency profile but a clean version-independence story. Prefer the venv.

## EFS performance, one honest caveat

Python and especially node_modules do a lot of small-file I/O. Inside a single long-lived container, the NFS client caches aggressively, so after the first read things are fine. But:
- First import after a cold start will be slower than a local rootfs.
- `npm install` of a large dep tree on EFS is noticeably slower than on local disk — but you only pay it once, and avoiding "once per turn" is the whole point.
- Make sure the EFS filesystem is Elastic throughput (or has provisioned throughput sized appropriately). Bursting mode will bite on big install bursts.

## My recommendation — the layered default

Flip these three levers together; each is independently cheap:

1. `container_persistent: true` — so upstream bind-mounts `/root` from EFS and skips per-turn teardown.
2. Env vars in the tool container:
   - `PIP_USER=1` (plain `pip install` → `/root/.local` → EFS)
   - `NPM_CONFIG_PREFIX=/root/.npm-global` + `PATH` prepend
3. Long `TERMINAL_LIFETIME_SECONDS` (e.g. 86400) so the same container lives all day.

This covers pip + npm persistently with essentially no TOOL_IMAGE surgery. For apt-level stuff, **nudge the agent via SOUL.md toward micromamba/pixi on `/workspace/.conda`**, and bake the truly common tools (git, curl, jq, build-essential, …) into TOOL_IMAGE so the agent rarely needs apt at all.

The nice property of this layering: none of it depends on the same ECS task staying up. The next task starts, mounts the same EFS, and the pip/npm installs are already there.

## Why EBS changes the calculation

Three things become viable that were marginal or bad on EFS:

1. **Overlaying `/usr/local`, `/var/lib/dpkg`, `/var/lib/apt`, `/opt` from a persistent volume** — was a non-starter on EFS because stat/read latency on thousands of small files kills Python/Node import time. On gp3 it's essentially local-disk speed.
2. **Putting DinD's graph storage (`/var/lib/docker`) on the persistent volume** — lets the *entire tool container*, including its writable layer, survive across restarts. Not just its bind-mounted subdirs. This is the real prize.
3. **`docker commit`-style workflows** become cheap because layers aren't fighting NFS.

## Two architectural shapes

Pick one up front; they diverge fast.

### Shape A: Fargate-managed EBS attachment (what we'd do if we stay on Fargate)

ECS-on-Fargate supports EBS volume attachment per task. **Caveats I'd want to verify against AWS docs before committing** (my memory of Fargate EBS is fuzzy on specifics): single-AZ, one volume per task, lifecycle policy (delete-on-terminate vs retain), and how reattachment to the next task launch works. That last one is the crux — if the volume is genuinely the same EBS across task replacements, this is beautiful; if each task replacement gets a fresh volume (just not ephemeral scratch), it doesn't solve the cross-restart problem, only the idle-reap and per-turn problems.

The layout:

```
Task boot:
  EBS attached at /mnt/doh-state (ext4)
  DinD sidecar: mount /mnt/doh-state/dind → /var/lib/docker
  Hermes container: mount /mnt/doh-state/hermes → /home/hermeswebui/.hermes
                    (replaces the EFS Hermes home mount)
  Tool container: bind /mnt/doh-state/workspace → /workspace
                  (via DOCKER_VOLUMES, which already works this way)
```

What this gets you:

- **Tool container is literally the same container across ECS restarts.** DinD starts, finds the old container in its state, we `docker start <id>`, pip/apt/npm state is all there.
- Pip, npm, apt — all persist naturally. No env-var tricks, no venv-on-EFS, no micromamba substitute for apt. The agent's mental model just works.
- Throughput: sized by gp3 baseline (3000 IOPS, 125 MB/s) — plenty.

The things you give up vs EFS:

- **Single-AZ.** An AZ failure means the task relaunches without its volume (or waits for AZ recovery). EFS is multi-AZ by default. For a single-tenant agent, probably fine.
- **No cross-task sharing.** If two Hermes tasks need to see each other's state, EBS can't do it. Today we don't — each workspace is its own task — so not a real loss.
- **Backup story becomes explicit.** Need EBS snapshot schedule (DLM or a cron) for DR. EFS basically gave you durability for free.

### Shape B: Move to ECS-on-EC2 with EBS

The heavy option. You get a real EC2 instance with a real root EBS volume (or a dedicated data volume). Full control of the Docker graph driver. You can put DinD's storage there, or skip DinD entirely and just use the host's Docker. Better performance ceiling, lower cost at scale, more ops burden (AMIs, scaling, patching).

Probably not worth it just for this. Revisit if we end up needing GPU, or if the density of running tool containers grows a lot.

## The DinD-storage-on-EBS angle is the key insight

Regardless of shape, this is the move that makes "same container" actually achievable:

- Today: DinD stores `/var/lib/docker` in Fargate ephemeral scratch. Every task restart = fresh daemon, `docker ps -a` is empty, tool image re-pulled, tool container gone.
- With EBS: DinD's entire state (images, containers, volumes, overlay2 layers) lives on EBS. Task restart = DinD comes back, sees its old containers in stopped state, we `docker start` the one matching `task_id`, we're back.

That flips the equation from "persist the interesting subdirs" to "persist the whole container." Much less fragile, much less clever, nothing to reason about per-package-manager.

Next time the Hermes task starts on the same instance, DinD wakes up, sees the old tool container in stopped state, Hermes `docker start`s it, every pip/apt/npm install is still there. Truly "same container."

You don't need `container_persistent: true` anymore (though setting it costs nothing). You don't need `TERMINAL_LIFETIME_SECONDS` hacks. The container literally persists because DinD never forgets it exists.

## The one remaining catch: instance replacement

The EC2 host is not forever. ASG scale-down, AMI roll, health-check kill, spot preemption — all can replace the instance under you. Host volume is gone with it. Three realistic answers:

**1. Accept it, use EFS as the safety net.** You already mount `/workspace` from EFS. Installed packages vanish when an instance dies, but user work doesn't. Instance churn on a sized-for-one ASG with managed scaling is rare (days/weeks between replacements in practice). Simplest; probably what I'd ship first.

**2. Snapshot-on-terminate + restore-on-launch.** ASG lifecycle hook → Lambda → EBS snapshot on instance termination. New instance userdata checks for a "latest DOH-data" snapshot tag and restores from it. Recovers state across replacements at the cost of a 30-60s boot penalty and a small Lambda. Classic pattern, well-understood, still not super pretty.

**3. Detach-and-reattach a dedicated EBS.** Keep one "DOH data" EBS volume outside the ASG, attach/detach via lifecycle hooks. True continuity, but it needs the next instance to come up in the same AZ, and coordinating attach under ASG autoscaling gets fiddly. I wouldn't reach for this unless (1) and (2) both proved insufficient.

## Other things worth considering now that we're thinking EC2

Some of this is "while we're here."

- **`m8g.large` has 8 GiB of RAM.** One Hermes task plus a few idle tool containers is fine. If agents start leaving heavy processes running in persistent containers, memory pressure becomes an actual thing. Easy to knock up the instance size later; just noting the math.
- **Scale-in protection matters more now.** With stateful host volumes, you don't want ASG casually recycling instances. `new_instances_protected_from_scale_in=False` (today's setting, `deploy_base.py:285`) is the right default for Fargate-style workloads but wrong for stateful-on-EC2. - **Density:** ECS on EC2 can pack multiple Hermes tasks on one instance, each with its own DinD, each with its own subpath under `/var/lib/doh-data/`. Cost per tenant drops vs. Fargate-per-tenant. Whether you want that tenancy model is a product question, not a tech one.
- **Bypassing DinD entirely is now an option** (bind `/var/run/docker.sock` from the host into Hermes, set `DOCKER_HOST=unix:///var/run/...`). Cheaper, faster, gets you native host Docker graph persistence for free. Weakens the isolation story — tool containers become siblings of the platform containers, sharing the host Docker daemon. For single-tenant agents running trusted-ish code, might be fine. For multi-tenant, I'd keep DinD. Worth calling out as an option, not recommending.

## Why `/var/lib/docker` on EFS doesn't work

Two independent reasons — either one alone is fatal.

### Reason 1: overlay2 can't run on NFS

Docker's default storage driver is overlay2. Overlay2 uses the kernel's overlayfs, which has hard requirements on the backing filesystem:
- `d_type` support in `readdir()` (for whiteouts).
- Specific `trusted.overlay.*` xattrs (for opaque directories, redirects, metadata-only copy-up).
- Stable, synchronous semantics for rename/link/unlink (overlay mutates the upperdir directly).

NFSv4 (EFS) doesn't reliably provide the xattr namespace overlayfs needs, and the kernel overlayfs documentation explicitly rules out NFS as an upper or lower dir. You'll get `EINVAL` at mount time, not a subtle perf issue. This includes the container's *writable layer* — `upperdir` and `workdir` are part of the overlay mount, so carving just that subdir off to EFS doesn't help either. The overlay mount still fails.

### Reason 2: the daemon's metadata stores assume a local filesystem

Even if you sidestepped overlay2, `/var/lib/docker` contains:
- `buildkit/` — BoltDB.
- `containerd/` — BoltDB-equivalent state.
- `network/files/local-kv.db` — BoltDB.
- The live Docker API socket (though we could move that separately).

BoltDB uses `mmap` + `flock` + fsync-ordering guarantees. The BoltDB project itself warns against NFS backing. In practice: silent corruption under concurrent access, stale reads via the page cache, locks that appear held after a crash. Same story applies to containerd's internal stores. You'd be running production data through a code path its authors explicitly say not to use.

## The narrow escape hatch, mentioned only to dismiss

You *could* switch Docker's storage driver to `vfs` (the only driver with no filesystem requirements). That would let the image layer tree technically live on EFS. But:
- vfs copies every layer in full on every pull — no CoW. A 1 GB tool image becomes 5 GB if it has 5 layers.
- Container start copies the entire image tree again to form the writable layer. Every time.
- You still have the BoltDB-on-NFS problem for the daemon's metadata.

Even ignoring perf (as you said), the metadata corruption risk makes this not-a-real-option. I'd rule it out.

## The shape that *does* work on EFS — worth naming for the bigger decision

There's a fundamentally different approach that keeps EFS as the durable store:

**Periodic snapshot + restore.** Instead of running Docker's graph on EFS, you run it on local disk as normal, and on a schedule (or on lifecycle signal) `docker commit` the tool container to an image, then `docker save` that image to a tarball on EFS. On next boot, `docker load` the tarball, `docker create` a container from it, start it. The state that gets preserved: the entire writable layer of the tool container — pip, apt, npm, `/etc/`, `/usr/local/`, everything.

Properties:
- Works with EFS's multi-AZ durability — state survives an entire AZ loss.
- Works across instance replacement — the next EC2 node in the ASG mounts EFS, loads the snapshot, up and running.
- Not continuous: whatever happened between the last snapshot and a hard crash is lost. You tune the cadence.
- Snapshot is expensive: `docker commit` walks the diff; `docker save` tars it up. For a tool container that's accumulated a lot of state, this is multi-second to minute-scale. Not something you do every turn.
- Each snapshot is a full image (flat tarball), not an incremental. Size bloats. A GC policy / retention is part of the design.

This is a real pattern (CI systems like Gitpod/Coder use variants of it), not exotic. It's uglier than host-volume-on-EBS but it has the property you care about: **package state survives instance loss**.

Note the `&`. It **backgrounds** the docker stop and returns immediately. The Python process can exit before the subprocess finishes. So even in the best case, Hermes's "cleanup" is fire-and-forget.

## Why that breaks for us in ECS

Two independent problems.

**1. The SIGTERM never reaches Python.** Our `start.sh` (`template_repos/hermes_agent/start.sh:36`) runs:

```sh

WEBUI_PID=$!
...
wait -n $WEBUI_PID $GATEWAY_PID
```

PID 1 is bash. bash has no trap. When ECS sends SIGTERM to PID 1, bash's `wait` is interrupted, the script exits — and **does not forward the signal to its children**. Python keeps running until the `stopTimeout` elapses and ECS SIGKILLs everything. Neither atexit nor the SIGTERM handler fires.

**2. Even if the signal got through, it'd still be racy.** `docker stop` is backgrounded. Hermes exits → ECS sees Hermes gone → ECS SIGTERMs DinD → dockerd starts shutting down → maybe before the backgrounded `docker stop` has even connected to dockerd → snapshotter may or may not see a `die` event with a still-exportable container. Undefined.

## But — the trap doesn't belong in Hermes anyway

Here's the reframe. We don't need Hermes to do anything on shutdown. The trap goes in **DinD**, not Hermes:

- ECS task stop → SIGTERM fires in all containers simultaneously (including DinD).
- DinD's wrapped entrypoint catches it: snapshot first, then gracefully stop dockerd (which in turn stops/drains all containers).
- `docker export` runs against the still-alive dockerd and the still-present (or just-stopped, doesn't matter) tool container.
- DinD exits.

Hermes dies separately, in parallel, and we don't care — DinD carries the durability responsibility.

## What about Hermes-only restart?

The one case the DinD trap doesn't cover: Hermes restarts, DinD doesn't. But in that case **the tool container keeps running inside DinD**, its rootfs state is preserved in place, nothing is lost — no snapshot needed. When the new Hermes comes up, it does a fresh `docker run` from `doh-toolbox:latest` (the last periodic snapshot). The previous still-running container becomes an orphan to be reaped.

So: **drop the Hermes trap. The DinD trap is the whole story.** You were right that Hermes isn't nice enough to stop the container for us, and we can stop caring that it isn't.

# Python style guide

## Function Signatures & Calling Conventions

To prioritize readability and eliminate "magic" behavior, we enforce strict explicitness in both how functions are defined and how they are invoked.

### 1. Enforce Explicit Argument Passing
* **Directive:** Do not use default parameter values in function or method definitions. All parameters must be mandatory.
* **Reasoning:** "Magic defaults" hide complexity and obscure the function's dependencies. We prefer explicit calls where every argument is visible at the call site.
* **Implementation:** If a value is logically optional, the caller must explicitly pass `None`.

**Bad (Implicit Defaults):**
```python
def connect_to_db(url, retries=3, timeout=30):
    # Hidden behavior: Reader assumes 0 retries? Infinite timeout?
    ...
```

**Good (Explicit Arguments):**
```python
def connect_to_db(url, retries, timeout):
    # All dependencies are visible in the signature
    ...
```

### 2. Prefer Keyword Arguments
* **Directive:** Use named arguments (keyword arguments) for function calls, particularly when passing literals (numbers, booleans, or strings) or when a function takes multiple parameters.
* **Reasoning:** Positional arguments are brittle and often illegible (the "Boolean Trap"). Keyword arguments make the code self-documenting and prevent errors caused by parameter reordering.
* **Implementation:** Explicitly state the parameter name at the call site.

**Bad (Positional Ambiguity):**
```python
# The reader cannot know what '3' and '30' represent
connect_to_db("db://localhost", 3, 30)

# Confusing booleans
create_user("jdoe", True, False)
```

**Good (Self-Documenting):**
```python
# Clarity is enforced at the call site
connect_to_db(url="db://localhost", retries=3, timeout=30)

# Intent is obvious even for optional flows
connect_to_db(url="db://localhost", retries=None, timeout=None)

# Boolean flags are readable
create_user(username="jdoe", is_admin=True, send_email=False)
```

### 3. Prefer Module-Qualified Imports for Local Modules
* **Directive:** For local/project modules, use `import module` rather than `from module import function`. Then call functions with the module prefix.
* **Reasoning:** Explicit module prefixes make dependencies visible at every call site. The reader instantly knows where a function comes from without scrolling to imports.
* **Implementation:** Import the module, then use `module.function()` syntax.

**Bad (Ambiguous Origin):**
```python
from iam_utils import get_assumed_role_session
from vpc_utils import find_available_vpc_cidr

# Reader can't tell where these come from without checking imports
session = get_assumed_role_session(...)
cidr = find_available_vpc_cidr(...)
```

**Good (Explicit Module):**
```python
import iam_utils
import vpc_utils

# Origin is immediately clear at the call site
session = iam_utils.get_assumed_role_session(...)
cidr = vpc_utils.find_available_vpc_cidr(...)
```

**Note:** This applies to local project modules. Standard library and well-known third-party packages (e.g., `from pathlib import Path`, `from dataclasses import dataclass`) are fine to import directly since their origin is universally understood.

### 4. Prefer Direct Imports Over TYPE_CHECKING
* **Directive:** Use regular imports for type hints. Only use `TYPE_CHECKING` when actually needed to resolve circular imports.
* **Reasoning:** `TYPE_CHECKING` adds complexity (conditional imports, string annotations) for a problem that may not exist. Solve circular dependencies when they occur, not preemptively.
* **Implementation:** Import types directly and use them in annotations.

**Bad (Premature Optimization):**
```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from myapp.models import User

def get_user(id: int) -> "User":  # String annotation required
    ...
```

**Good (Direct Import):**
```python
from myapp.models import User

def get_user(id: int) -> User:
    ...
```

**When TYPE_CHECKING is appropriate:**
- Actual circular import errors occur
- Heavy imports cause measurable startup delays
- Imports have side effects you need to avoid

### 5. Single-Line Function Signatures When Under 140 Characters
* **Directive:** Write function and method definitions on a single line when the total length (including `def`, parameters, return type, and trailing colon) is under 140 characters. Use multi-line formatting only when the signature exceeds this limit.
* **Reasoning:** Single-line signatures are easier to scan and search. Multi-line formatting adds vertical noise for short signatures that fit comfortably on one line.
* **Implementation:** Measure the full signature length. If under 140 characters, keep it on one line.

**Bad (unnecessary multi-line):**
```python
async def _handle_stream_event(
    message: SDKStreamEvent,
    ctx: StreamingContext,
) -> AsyncGenerator[StreamEvent, None]:
    ...
```

**Good (118 characters, fits on one line):**
```python
async def _handle_stream_event(message: SDKStreamEvent, ctx: StreamingContext) -> AsyncGenerator[StreamEvent, None]:
    ...
```

**When multi-line is appropriate:**
- Signature exceeds 140 characters
- Complex default values or annotations that benefit from vertical alignment (though we avoid defaults per rule 1)

### 6. Prefer Single-Line Docstrings for Simple Functions
* **Directive:** Use a brief single-line docstring for functions. Reserve multi-line docstrings (with Args/Returns/Raises sections) for complex functions where the signature alone doesn't convey important details.
* **Reasoning:** Verbose docstrings that restate what the function name and types already communicate add noise. A concise one-liner maintains consistency while avoiding redundancy.
* **Implementation:** Write a single-line docstring that adds context beyond the function name, or simply summarizes intent.

**Bad (overly verbose):**
```python
async def _aget_last_user_message(conversation: Conversation) -> str:
    """
    Get the last user message from a conversation.

    Args:
        conversation: The Conversation model instance.

    Returns:
        The content of the last user message.

    Raises:
        ValueError: If no user messages found.
    """
```

**Good (concise single-line):**
```python
async def _aget_last_user_message(conversation: Conversation) -> str:
    """Get the content of the most recent user message."""
```

**When multi-line docstrings are valuable:**
- Non-obvious behavior or side effects
- Complex algorithms that need explanation
- Public API functions where discoverability matters
- Unusual parameter constraints not captured by types

### 7. Require Type Hints on New/Modified Functions and Methods
* **Directive:** Every new or modified function/method must include type hints for all parameters and the return type.
* **Reasoning:** Complete signatures improve readability, reduce ambiguity, and make refactoring/tooling safer.
* **Implementation:** Annotate all parameters and returns explicitly. Use `-> None` for no-return functions. Keep annotations concrete when possible.

**Bad (missing annotations):**
```python
def check_access(request, resource, action):
    ...
```

**Good (fully annotated):**
```python
def check_access(request: HttpRequest, resource: Workspace, action: str) -> bool:
    ...
```


## Django 6.0 Async ORM

**Use native async ORM methods instead of `sync_to_async`.** Django 6.0 has full async ORM support — don't wrap sync methods.

- **Queries:** Use `await queryset.afirst()`, `await queryset.aget()`, `await queryset.acount()`, etc.
- **Create/Update:** Use `await Model.objects.acreate(...)`, `await instance.asave()`, `await instance.adelete()`
- **Iteration:** Use `async for obj in queryset:` instead of wrapping sync iteration

**Bad (outdated pattern):**
```python
from asgiref.sync import sync_to_async

async def get_user(user_id):
    return await sync_to_async(User.objects.get)(id=user_id)

async def save_item(item):
    await sync_to_async(item.save)()
```

**Good (Django 6.0):**
```python
async def get_user(user_id):
    return await User.objects.aget(id=user_id)

async def save_item(item):
    await item.asave()
```

The `a`-prefixed methods are native async and don't require `sync_to_async` wrappers.


## Logging

**Use `logger.error()` instead of `logger.warning()`.** We don't use the warning level — if something is worth logging as abnormal, log it as an error.


## File Naming Conventions

**Avoid generic file names** like `service.py`, `client.py`, `list.html`, `view.html`. Use descriptive names that include the domain context.

**Reasoning:** Generic names become ambiguous as the project grows. With 20 modules, having multiple `service.py` files makes navigation and searching difficult.

**Bad:**
```
services/agent/service.py
templates/chat/list.html
```

**Good:**
```
services/agent/agent_service.py
templates/chat/chat_list.html
```

The prefix should match the containing folder or domain. This makes file names unique and self-documenting even when viewed in isolation (e.g., in editor tabs, search results, or stack traces).

## Assistant

It cleans up **orphaned tool containers** — the ones left behind when Hermes-in-a-task restarts by itself without DinD restarting.

## The scenario it exists for

DinD and Hermes are sibling containers in the same ECS task. Normally they live and die together. But sometimes Hermes restarts on its own:
- Upstream bugfix bump
- OOMkill on the Hermes process
- Config hot-reload

In those cases DinD keeps running — and so does the tool container DinD is holding. But new-Hermes has no memory of it (`_active_environments` is a module-level Python dict that's wiped on process restart). New-Hermes's next tool call does a fresh `docker run doh-toolbox:latest`, creating a second container. The old one just sits there, still running, consuming memory, never used again.

That's the orphan.

## What `_reap_older_siblings` does

Driven by `docker events start`. Every time a new `hermes-*` container starts, the reaper:

1. Lists all running `hermes-*` containers *other than* the one that just started.
2. For each: snapshot it (so we don't lose the state it accumulated before the restart) + `docker rm -f` it.

Net effect: at any given moment DinD only has one live tool container per session. New Hermes inherits the previous one's state via the snapshot → `doh-toolbox:latest` tagging mechanism, while the old container is cleanly disposed of.

## Why it's "older siblings" specifically

"Older" = "started before the one we just saw start." The just-started container is our signal that a new Hermes wants a fresh environment; anything older than that is, by definition, left over from a prior Hermes. No timestamps needed — the events stream gives us the "started now" anchor and everything else running alongside it is older by construction.

## In plain terms

It's a cleanup sweep that runs whenever Hermes asks for a new container. Without it, every Hermes restart would leak a container into DinD until the ECS task itself restarts.

## Assistant

Crash protection during the snapshot write itself.

## The window

`do_snapshot` does roughly:

```
1. docker export container | zstd > incoming.tar.zst   # slow: 10-60s on a big rootfs
2. os.replace(LATEST, snapshots/<ts>.tar.zst)          # rotate current → history
3. os.replace(INCOMING, LATEST)                        # promote new → current
```

Step 1 is long enough that something can go wrong during it — docker daemon dies, EFS write errors, the container exits mid-export. If any of that happens after we've started writing but before step 3 completes, there's a window where `latest.tar.zst` might be corrupt or absent.

## What the `snapshots/` directory buys us

With a single retained copy, a torn write during steps 1-3 leaves us with no recoverable state — `latest.tar.zst` is either missing (step 2 finished, step 1 didn't) or truncated (step 1 died mid-write). Next DinD boot tries to restore, fails, falls back to pulling the base image. All accumulated state is gone.

With the last 3 snapshots retained:
- If `latest.tar.zst` is bad, we fall back to the newest entry in `snapshots/` — at worst we lose 15 min of state.
- If that one is *also* bad (unlikely but not zero), we've got two more.

It's the same logic banks use for backup tapes — one backup is one bug away from catastrophic loss; three is enough defense for a system where a single bad snapshot is plausible but three consecutive ones is basically impossible.

## Why 3 and not 2 or 10

- **2** is the minimum to survive a torn-write of the current snapshot. Thin margin.
- **3** covers one torn write *plus* one "oh no, a bad snapshot got rotated into history before anyone noticed." Good margin.
- **More than 3** buys very little additional safety at linear storage cost. On a 2 GB snapshot, 3 copies = 6 GB; 10 copies = 20 GB. EFS isn't expensive but it isn't free either.

## Not a point-in-time recovery feature

Worth being clear about what `snapshots/` is **not**: it's not "let the user roll back to yesterday's state if they accidentally `rm -rf /`'d something." We'd need a much longer retention and a UX for that. The directory exists purely as the crash-safety net for the rotate/promote sequence. If you ever want real snapshot-based time-travel, that's a separate feature on top.

## Related: the restore path doesn't use it today

Actually — checking the entrypoint, the restore path only reads `latest.tar.zst`. It doesn't fall back to `snapshots/<newest>.tar.zst` if `latest` is unreadable. So the retention is currently insurance we don't cash in automatically. That's fine — in a real corruption case an operator would `cp snapshots/20260427T220500Z.tar.zst latest.tar.zst` and restart DinD — but worth knowing the automatic fallback isn't wired. We could add it if you want; it's a 5-line block in the entrypoint.

## Assistant

Yes — size and mutation count, more than wall-clock container age.

## What `docker export` actually streams

Two things go into the tarball:

1. **Everything in the writable layer** — files the container has *modified or added* on top of the base image. This is the fast part per-item but grows with how much the agent has installed.
2. **Everything in the base image that's visible** — `docker export` is "export the container's view of its filesystem", not "export just the writable layer." The bytes for `/usr/bin/python3`, `/usr/lib/...`, etc. are all in the tarball too, read back out of the overlay lowerdir.

So even a completely untouched container produces a ~500 MB export — the logs showed exactly that on first boot. What makes it slower isn't the diff size per se, it's the **total bytes read** (base + writable), compressed through zstd, written to EFS.

## What drives wall-clock time

- **Base image size** — fixed cost. Our base is ~500 MB installed, so that's the floor. Every snapshot pays this.
- **Writable layer size** — the agent's pip installs, apt installs, npm installs, any files written to `/root` or `/etc`. This is the variable on top.
- **EFS throughput** — shared across the task. If workspace I/O is heavy during the snapshot, zstd's output write rate drops.
- **Compression CPU** — zstd with `-T0` (all threads) is usually not the bottleneck, but on a small instance it can become one.

The 10-second snapshots we saw in the logs (`ms=9769`, `ms=9685`) were all at ~480 MB — that's the base-image floor. Nothing installed yet. A container with a fat `pip install torch` (2 GB of wheels) would be more like 30-40 seconds.

## Why `docker diff` is cheap even when the export is expensive

`docker diff` walks the overlay upperdir only and reports path changes — metadata, no content read. It's milliseconds even on a heavily-modified container. That's why the fingerprint guard is efficient: we pay milliseconds to decide whether to pay seconds-to-minutes.

## What would make this cheaper

If we ever care about snapshot speed specifically:

1. **Exclude the base from the snapshot** — that's what `docker commit` + `docker save` does (it produces a layered image where the base is a reference, not an embedded copy). Cost: per-layer file juggling and the 127-layer ceiling to manage. We rejected this earlier but it's the real fix if size becomes a problem.
2. **Incremental snapshotting** — `tar --listed-incremental` or rsync semantics. More bookkeeping, one-way compatibility with "just re-import the tarball."
3. **Cap the writable layer size** — keep big caches (pip wheels, npm cache, apt cache) on a bind-mounted EFS volume instead of in the container rootfs. Only the "installed artifacts" are inside the rootfs. This narrows the delta we actually need to export.

For now the 15-min cadence + `docker diff` guard keeps the aggregate cost small even with the fixed-base floor. Worth revisiting if we see real pain.

1. **Shell pipeline swallows the export failure.** `shell=True` + pipe means only zstd's exit code matters. Adding `set -o pipefail` before the command, or piping through Python subprocess chaining instead of the shell, makes failures propagate.
