So that section is currently: "distinct environments seen in the app's last 20 deployment attempts, showing the latest attempt for each environment." It is not "all current deployed environments," and it is not using `DeploymentBlueprint` as its source of truth.

The spec says the conceptual ownership should be the other way around:

```68:99:docs/app_deployment_blueprint_spec.md
`DeploymentBlueprint` is the desired deployable state for one `(app, environment)` pair.

It answers: "How should this app run in this environment?"

...

`Deployment` remains the concrete execution/history record.

It represents one attempt to apply a blueprint and stores attempt status, outputs, timestamps, and logs.

Core rules:

- A `Deployment` must point to the exact `DeploymentBlueprint` it applied.
- `Deployment` does not have its own `app` or `environment` FKs. Both are reachable via the blueprint. The blueprint is the single source of truth for what app and what environment.
```

So if the section title remains `Deployed to Environments`, then yes, I think it should be based on `DeploymentBlueprint`s, not raw `Deployment`s. More specifically:

- `Recent Deployments` should stay `Deployment`-based, because that section is explicitly history/attempts.
- `Deployed to Environments` should probably be `DeploymentBlueprint`-based, because that section reads like current environment state for the app.
- If you want that label to mean "currently deployed," the cleanest source is likely `DeploymentBlueprint.status = active`.
- If you want it to also show in-progress or broken environment-specific state, you could base it on non-discarded blueprints and then render the blueprint status plus the latest deployment attempt details.

One more nuance: the app detail page is already partially blueprint-aware, because its `New Deployment` / `Resume Deployment` action is driven by `get_open_blueprint()` in the same view. So this top list looks like a leftover from the older deployment-history-centric model, while the spec is pushing the page toward a blueprint-centric model.

CSS Grid computes column sizes per grid container, so separate row grids cannot automatically say "use the widest cell from any sibling row in this list."

What would work:

- within one list: yes, absolutely
- across both lists while they remain separate containers: not automatically
