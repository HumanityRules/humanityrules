## The Problem

The current flow in `github_connect` sends the user to a static URL:

```202:204:devopshero_app/services/gitproviders/github_client.py
def get_app_installation_url() -> str:
    """Get the URL for installing the GitHub App."""
    return "https://github.com/apps/devops-hero-app/installations/new"
```

This is the GitHub App **installation** flow, which works like this:

1. User visits `/installations/new` on GitHub
2. GitHub shows a list of GitHub orgs/accounts where the user can install the app
3. User picks one and grants permissions
4. **Only if the installation is new**, GitHub redirects back to the Setup URL (`/github/setup` or `/github/callback`) with `installation_id` and `setup_action=install`

**The critical behavior**: if the app is **already installed** on a GitHub org, that org shows a "Configure" button instead of "Install". Clicking "Configure" takes the user to the app's settings page **on GitHub** — it does **not** redirect back to our Setup URL. The redirect only fires for new installations.

So the sequence is:

- **DOH Org 1**: User clicks "Connect GitHub" → goes to `/installations/new` → installs on their GitHub org → GitHub redirects back with `installation_id` → works
- **DOH Org 2**: User clicks "Connect GitHub" → goes to `/installations/new` → the GitHub org already has the app installed → user clicks "Configure" → stays on GitHub, **no redirect back**

## The Root Cause

The code conflates two concepts that GitHub treats as separate:

- **GitHub App Installation** — a one-time event per GitHub org/account. Lives on GitHub's side. Once installed, the install flow doesn't re-trigger.
- **DOH Organization Integration** — our internal record linking a DOH org to a GitHub installation. Multiple DOH orgs might need to connect to the same (or different) GitHub installation.

The current design assumes every "Connect GitHub" click will produce a fresh installation, but GitHub only creates one installation per GitHub org per app.

## The Fix

Instead of always sending the user through GitHub's installation flow (which only works once per GitHub org), the connect flow should handle two scenarios:

1. **The GitHub App is not yet installed on any GitHub org** → send the user to `/installations/new` (current behavior, works fine)
2. **The GitHub App is already installed** → let the user pick from existing installations and associate one with their current DOH org

You can use the GitHub App JWT API to list all existing installations:

```
GET /app/installations
Authorization: Bearer <JWT>
```

This returns every GitHub org/account that has installed the Devops Hero App. The connect flow for DOH Org 2 could then show a picker: "Select which GitHub organization to connect" — listing installations that already exist, plus an option to install on a new GitHub org.

No, the current behavior is not a security problem — it's a **functionality problem**. DOH Org 2 simply can't complete the connection because GitHub never redirects back. No data leaks, no unauthorized access. It just doesn't work.

However, **the fix needs to be designed carefully to avoid introducing one**. If you showed that list to the user, they could see (and potentially connect to) GitHub organizations belonging to other companies. That would be a real security problem.

The safe approach is to scope the installation picker to what the **current user** is authorized to see on GitHub. GitHub's OAuth user flow supports this: after the user authorizes with their GitHub identity, `GET /user/installations` returns only the installations **that specific user** has access to. That way DOH Org 2's admin can only pick from GitHub orgs they personally belong to — never another customer's.

## What changed

**The problem**: `github_connect` always redirected to GitHub's static install URL (`/installations/new`). If the GitHub App was already installed on the user's GitHub org, GitHub showed a "Configure" page instead of redirecting back — breaking the second DOH organization's connection.

**The fix**: Replace the direct-to-install flow with a GitHub OAuth flow that discovers existing installations and lets the user pick one.

### New flow

1. **`/github/connect`** — starts a GitHub OAuth flow (instead of going straight to `/installations/new`). Stores a CSRF `state` and the DOH org ID in the session.

2. **`/github/callback`** — GitHub redirects here with `code` + `state`. The view exchanges the code for a user token, calls `GET /user/installations` (scoped to only installations this user can see — no cross-tenant leakage), stores the results in the session, and redirects to the picker.

3. **`/github/select-installation`** (GET) — renders a picker page showing each GitHub org where the app is installed (name, avatar, type). The user selects one and clicks "Connect".

4. **`/github/select-installation`** (POST) — connects the selected GitHub installation to the current DOH organization.

5. **"Install on new GitHub organization"** link in the picker — sends the user to `/installations/new` for orgs that don't have the app yet. After install, GitHub redirects to `/github/setup`, which handles the new `installation_id`.

### Files modified

- **`devopshero_app/services/gitproviders/github_client.py`** — added `GitHubInstallation` dataclass, `get_oauth_authorize_url()`, `exchange_code_for_user_token()`, `list_user_installations()`
- **`devopshero_app/views/github.py`** — rewrote `github_connect` (OAuth), `github_callback` (code exchange), added `github_setup` (installation callback), `github_select_installation` (picker), extracted `_connect_installation` helper
- **`devopshero_app/urls.py`** — added `/github/setup` and `/github/select-installation` routes
- **`devopshero_app/views/__init__.py`** — exported new views

### Backwards compatibility

`github_callback` checks for `installation_id` in query params and delegates to the setup handler if present, so the old direct-install flow still works if the GitHub App's Setup URL points to `/github/callback`.

- **Setup URL** → `https://<your-domain>/github/setup` (for post-install redirect)
