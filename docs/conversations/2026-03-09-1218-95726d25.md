So the answer is: yes, `deployment_workspace.html` is simpler now, but the complexity was mostly moved into the generic bridge in `_chat_panel.html`.

## Best Simplification
The bridge itself is still necessary. SSE arrives under `#messages`, and the deployment sections sit outside that subtree, so some SSE-to-`document` hop is required.

The real simplification is to make each notify payload map to exactly one final DOM event. Right now the system mixes two concepts:

- Entity-scoped updates like `title-changed-<id>`
- Broad workflow events like `app-changed`

A cleaner contract would be:

- `title-changed-<conversation_id>`
- `cost-changed-<conversation_id>`
- `permissions-changed-<id>`
- `app-created`
- `app-updated-<app_id>`
- `blueprint-created`
- `blueprint-updated-<blueprint_id>`

Then `handleNotify()` can dispatch exactly one `CustomEvent`, not two.

That works well here because `save_app.py` and `save_blueprint.py` already return a `created` flag, so the server can distinguish create vs update without extra queries.

## Practical Recommendation
I would not spend time trying to DRY the two listeners in `deployment_workspace.html`; that would save lines, not complexity.

I would simplify in this order:

- Keep the `document` bridge in `_chat_panel.html`.
- Move final event naming to the server so `_chat_panel.html` dispatches one event per notify.
- Keep imperative JS only for real page transitions.
  `app-created` still needs a workspace reload because the URL and breadcrumb switch to `/deploy/<slug>/`.
- Consider changing the blueprint refresh endpoint to be app-scoped instead of blueprint-id-scoped.
  That would let `#blueprint-section` refetch itself without a full workspace reload when the first blueprint is created.

I chose `workspace:edit` for two reasons:

- `deployment_workspace` is an edit surface. It creates conversations, lets the agent change app/blueprint state, and is explicitly the “Configure and deploy” page, so the fragment endpoints should inherit the same permission model.
- HTMX fragment URLs are still normal HTTP endpoints. If those used `workspace:view`, a user who could not open the deploy workspace could still hit the section URLs directly and read live deployment config from an edit-only area.

That said, the sections themselves are read-only responses, so `workspace:view` would also be a reasonable choice if the product decision is “viewers may inspect deploy state, they just can’t mutate it.” In that case, I’d want to revisit the parent `deployment_workspace` permission too, not just these fragments, so the access model stays coherent.

For contrast, `app_detail` is intentionally a read page, so it uses `workspace:view`:

```81:88:devopshero_app/views/apps.py

    denied = abac_view_checks.check_abac(request, app.workspace, "workspace", "workspace:view")
    if denied:
        return denied
```

So the short version is: I picked `workspace:edit` for consistency with the deploy workspace’s existing access boundary, not because the fragment endpoints themselves mutate state. If you want, I can change them to `workspace:view`, but I’d recommend deciding that at the page-level contract first.
