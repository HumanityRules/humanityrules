## Analysis

### Current Autoscroll Behavior

The autoscroll logic is in lines 132-167:

**State:**
- `autoScrollEnabled = true` — starts enabled
- `disableAutoScroll()` — sets flag to false, shows the "scroll to bottom" button
- `enableAutoScrollAndScroll()` — sets flag to true, hides button, scrolls down

**Triggers:**
- **Disable:** Any `wheel` or `touchstart` event on the container (lines 163-164)
- **Re-enable:** Only when user clicks the "scroll to bottom" button (line 167)

### The Problem

Once disabled, autoscroll stays off until the user explicitly clicks the button. There's no detection of whether the user has scrolled back to the bottom manually.

### Solution

Add a `scroll` event listener that checks if the user is at (or near) the bottom of the container. When they are, re-enable autoscroll automatically.

The key insight: the `wheel` event fires *before* the scroll position updates, so detection must happen in the `scroll` event:

```javascript
container.addEventListener('scroll', function() {
    const threshold = 30; // pixels from bottom to consider "at bottom"
    const isAtBottom = container.scrollTop + container.clientHeight >= container.scrollHeight - threshold;
    
    if (isAtBottom && !autoScrollEnabled) {
        autoScrollEnabled = true;
        hideScrollButton();
    }
});
```

### Considerations

1. **Threshold value** — A buffer of 20-50px accounts for scroll imprecision and rounding. 30px is a reasonable default.

2. **No debouncing needed** — The check is lightweight (just arithmetic), so throttling isn't necessary.

3. **Don't call `scrollToBottom()`** — User is already at the bottom; just flip the flag and hide the button.

Good catch — `scrollend` is the better choice here.

### Why `scrollend` is preferable

| Event | Fires | Best for |
|-------|-------|----------|
| `scroll` | Continuously during scrolling (hundreds of times) | Real-time position tracking |
| `scrollend` | Once when scrolling stops (including momentum) | Final position detection |

For re-enabling autoscroll, we care about the **final resting position**, not intermediate positions. `scrollend`:

1. **More accurate** — Checks position after momentum/inertia completes (important for touch)
2. **Better performance** — One event vs. potentially hundreds
3. **Cleaner intent** — "User has arrived at bottom" vs. "user is passing through bottom"

### Browser Support

`scrollend` has been well-supported since ~2023:
- Chrome 114+
- Firefox 109+
- Safari 18+

By 2026, this should cover virtually all users.

### Implementation

```javascript
container.addEventListener('scrollend', function() {

    if (isAtBottom && !autoScrollEnabled) {

        hideScrollButton();
    }

```

Even simpler than the `scroll` approach — no debouncing needed since it only fires once.

Good observations. Here's the diagnosis:

## Issue 1: Wheel down disables autoscroll

**Root cause**: Line 163 disables autoscroll on *any* wheel event, regardless of direction.

```javascript
container.addEventListener('wheel', disableAutoScroll);
```

The sequence when you wheel down while already at bottom:
1. `wheel` fires → `disableAutoScroll()` runs → button appears
2. No actual scrolling occurs (already at bottom)
3. `scrollend` **doesn't fire** because no scroll happened

`scrollend` only fires when actual scrolling occurs. If you're at bottom and wheel down, nothing scrolls, so no `scrollend`.

**Fix**: Check wheel direction — only disable if scrolling up:

```javascript
container.addEventListener('wheel', function(e) {
    if (e.deltaY < 0) {  // scrolling up
        disableAutoScroll();
    }
});
```

---

## Issue 2: Multiple scrolls needed during streaming

**Root cause**: Race condition between streaming content and `scrollend` check.

Sequence:
1. Streaming adds content → `scrollHeight` increases
2. You scroll down to bottom
3. `scrollend` fires, runs `isAtBottom` check
4. **Between scroll and check**, more content arrived → `scrollHeight` grew
5. You're no longer "at bottom" because the bottom moved down
6. `isAtBottom` returns false → autoscroll stays off

With rapid SSE streaming, you're chasing a moving target.

**Fix options**:
- **Increase threshold** during active streaming (e.g., 100-150px instead of 30px)
- **Track scroll direction** — if user was scrolling down and reached near-bottom, re-enable regardless of exact position
- **Simpler**: Use a larger threshold unconditionally (50-60px is still reasonable)
