## The core design question: how does ABAC say "only Alice can use alice-hermes"?

Three options, each with different tradeoffs:

**Option A — Per-user policies (N policies for N employees)**
- Tag each PA app with `owner = vmendi`.
- Auto-create one policy per PA at deploy time: `IF identity username = vmendi AND resource owner = vmendi THEN app:use`.
- Pros: Zero new ABAC concepts. Everything fits the current model.
- Cons: Policy count grows linearly with employees. Clutters the policy list. The "Who has access" explainer is fine, but the policies page becomes noisy. Needs an "owned by user" policy category or a hide-by-default filter.

**Option B — One self-referential policy (preferred, IMO)**
- Introduce a single new primitive: `$identity.<attr> = $resource.<tag>` as a valid condition form.
- One global policy: `IF identity.username = resource.owner THEN app:use`.
- Pros: Scales to any number of users with one policy. Natural fit for "owned-by" semantics (PAs today; tomorrow personal sandboxes, per-user notebooks).
- Cons: Extends the ABAC DSL. The access explainer needs to handle it. But it's a small, principled extension — not a hack.

**Option C — Dedicated "owner" concept outside ABAC**
- Resource gets a first-class `owner_user_id` field. Sidecar short-circuits: "is current user the owner? allow. else fall through to ABAC."
- Pros: Simplest to implement; owner UI is obvious.
- Cons: Two authorization systems ("owner" plus ABAC) — exactly the thing ABAC was meant to eliminate. Audit explainer has to cover both paths.

My recommendation is **B**, with **A** as the fallback if you don't want to extend the DSL yet. C works but undermines the "ABAC is the single decision point" principle from the design doc.

## Sidecar flow for the PA case

Assuming Option B, the per-request flow is essentially what the ABAC doc already describes, with PA-specific defaults:

## 2. The redirect URL — don't try to whitelist N URLs

You're right that per-user whitelisting doesn't scale, and you shouldn't try to solve it with wildcard redirect URIs either (Okta supports them but security guidance discourages them, and it turns sidecars into potential open-redirect vectors).

The standard pattern for fleets of OAuth-protected subdomains is a **single central auth endpoint per environment** — this is how oauth2-proxy, Pomerium, and Cloudflare Access all work:

- One hostname per customer environment, e.g. `auth.chsandbox.com`. That one URL is what's registered in Okta.
- Unauth'd request to `vmendi-hermes.chsandbox.com/foo` → sidecar 302s to `auth.chsandbox.com/start?rd=https://vmendi-hermes.chsandbox.com/foo`.
- `auth.chsandbox.com` runs the OAuth dance with Okta, receives the code at its fixed callback, exchanges for tokens.
- Sets a session cookie scoped to `.chsandbox.com` (parent domain, so all subdomains see it).
- 302 back to the original `rd=` URL.
- Sidecar on `vmendi-hermes` reads the parent-domain cookie, validates it (JWT signature or session lookup), and proceeds to the ABAC check.

Implications worth flagging:

- **The auth endpoint is a new deployable.** It lives inside the customer VPC (so cookies + TLS stay on customer infra), alongside the sidecars. Roughly: a tiny ECS service + ALB + one DNS record per environment. One per env, not per app.
- **Parent domain cookie scope.** All PAs (and any future sidecar'd apps) in a given env must live under a shared parent domain (`*.chsandbox.com`). This is already implied by your URL example, just worth making explicit.
- **`rd=` must be validated.** Allowlist the parent domain on the auth endpoint — otherwise it's an open redirect. Trivial to get right, easy to forget.
- **Cookie = SSO session for all PAs in the env.** Once you've logged in for your own PA, you won't re-auth when you try to hit someone else's — you'll just get denied at the ABAC step. That's the correct behavior (auth ≠ authz), but worth naming.

Net: we trade N Okta registrations for one new service per environment. Big win.

## 3. `username` as the identity anchor

The `username` field on `User` works if it satisfies three properties:

- **Stable.** Doesn't change when a person changes name/email. If it's email-derived and email changes, the PA becomes orphaned.
- **Immutable via UI.** If a user (or admin) can edit it to match someone else's PA owner tag, that's account takeover. Either lock it in the UI or require admin approval to change.
- **Sourced from the IdP claim, not DOH-local.** Otherwise DOH admin can rename themselves to `ceo` and grab the CEO's PA.

Worth checking: does the current `username` field satisfy these? If it's just a Django default unique field editable by the user, we need to either (a) make it a read-only system attribute synced from the Okta claim at login, or (b) introduce a separate `oidc_sub`-backed identifier and use that instead of `username` in the ABAC condition.

`oidc_sub` (already exposed per commit 49daed1) is the safest anchor — opaque, IdP-owned, never changes, never reassigned. Downside: it's ugly in the UI ("owner = 00u1a2b3c4..."). The pragmatic answer is probably: use `username` as the *display* tag value, but have the policy match on `oidc_sub` under the hood, with the mapping enforced at assignment time. Or: use `username` directly and enforce immutability — simpler, and good enough if we control the edit path.

## 4. The deploy form dropdown — one subtlety

Good. The natural UX is: template picker → "New Personal Assistant" form with Workspace, Environment, and **Owner** (user search/dropdown).

The subtlety: **who is allowed to deploy a PA for someone else?** Two shapes to pick between:

- **Admin-driven model:** PAs deploy into a dedicated "Personal Assistants" workspace where only IT/admins have `workspace:edit`. An admin picks the owner from the dropdown. Users can't self-serve.
- **Self-serve model:** Any authenticated employee can deploy a PA, but the Owner field is locked to `self` (pre-filled, disabled). No dropdown for non-admins; admins see the dropdown and can deploy on behalf of others.

The second is much more in the spirit of DOH ("anyone who can vibe-code can deploy"). It also removes a failure mode: an admin can't accidentally deploy `alice-hermes` with owner `bob`, because the form doesn't let non-admins choose at all, and admins doing it explicitly is by design.

Either way, the Owner value needs to be validated server-side at deploy — not trusted from the form — and written to the resource tag in a way that can't be casually rewritten post-deploy (see point 3: treat `owner` as system-managed, or gate edits).

One small thing to nail down: **what does the URL use?** `vmendi-hermes.chsandbox.com` implies the subdomain is derived from `username`. If `username` ever changes, the URL breaks (ECS service rename, DNS record churn, bookmark rot). Either lock `username` harder, or derive the subdomain from `oidc_sub` hash / an immutable deploy-time slug. I'd pick the latter — subdomain is baked at deploy time and never changes, even if the person's display username does.

That's the **PDP-embedded** model (vs the PDP-remote model the ABAC doc currently describes). It's a real, well-trodden choice — oauth2-proxy, Istio, OPA sidecars all do this. Worth naming the tradeoffs explicitly.

**What the sidecar needs to decide locally:**
- The set of policies relevant to *this* app (base policy + route overrides).
- The identity's effective attributes (including group-inherited + system attributes).
- Evaluation logic (deny-overrides, union-of-grants, the self-referential `$identity.x = $resource.y` primitive).

**Where the data comes from:**
- **Policies for this app** — fetched from DOH at sidecar startup. Small, stable, per-app.
- **Resource tags** — same, fetched at startup.
- **Identity attributes** — the hard part. Two shapes:
  - **Embed in the session JWT at login time.** The auth Lambda, after Okta callback, calls DOH to resolve the user's attributes and bakes them into the JWT. Sidecar reads the JWT, has everything it needs, zero per-request DOH calls. Fast, simple, fully offline after login.
  - **Fetch at request time.** Adds back the per-request DOH call we were trying to avoid.

The first option is clearly better for the PA use case, with one real caveat:

- **Attribute freshness is bounded by JWT TTL.** If Bob loses `team = data-platform` today, his existing JWT still carries the old attributes until it expires (say, 8h). For the PA case this matters less — his PA is his PA regardless of team membership — but for `app:use` on sensitive shared apps, it's a real consideration. Short JWT TTLs (1h) with silent re-auth against Okta + DOH mitigates this.

**Policy updates still need propagation.** The ABAC doc already says "policy changes require a sidecar restart." A lighter version: sidecar polls DOH for its policies every N minutes, or DOH pushes a restart signal. Either is fine for v1.

**Net shape:**
- Auth Lambda: Okta → resolve identity via DOH → mint JWT with `{username, oidc_sub, attrs: [...], exp}`.
- Sidecar at startup: fetch its app's policies + tags from DOH. Cache in memory.
- Sidecar per request: verify JWT signature locally, evaluate policies locally, allow/deny. No DOH call on the hot path.
- Sidecar: re-fetch policies every N min (or on restart).

This turns the fail-closed concern inside out: a DOH outage means **existing sessions keep working** (because JWT is self-contained), but **new logins fail** (auth Lambda can't resolve attributes from DOH). That's probably the right tradeoff — better than both-fail-closed.

One thing to verify before committing: the ABAC model allows fairly rich conditions (multi-attribute AND, deny-overrides, multiple policies applying). Reimplementing the evaluation engine in the sidecar means two codebases have to agree on semantics forever. Worth considering shipping the eval logic as a shared library (Python wheel, Go module) that both DOH and sidecars import — keeps it DRY.

- **Single source of truth for semantics.** No shared library. DOH owns the evaluation logic; sidecars never need to be upgraded when we add new condition forms. The `$identity.x = $resource.y` primitive, deny-overrides, multi-value OR — all live in one place.
- **Audit for free.** Every decision flows through DOH, so the control plane has a complete access log. With the embedded model, sidecars have to ship audit events separately.
- **Cache staleness window ≈ poll interval.** 60s cache TTL gives roughly the same freshness as a 60s sync poll. Not meaningfully different.
- **Failure mode flips.** A DOH outage means cache entries expire and new decisions fail. If we want fail-static behavior, we extend TTL-on-error (serve stale when DOH is down). That's a config knob.
- **Hot path gains a network dependency, but only on cache miss.** A warm cache for an active user serves most requests locally. First request of the day, or first after a policy change, pays ~50ms.

## How they actually compare

Sharpest differences, in my view:

- **Operational simplicity.** Per-request+cache wins. No shared library to version, no policy distribution, no JWT revocation list. Just "call DOH, cache the answer."
- **Audit completeness.** Per-request+cache wins. Every decision is centrally logged without extra plumbing.
- **Independence from DOH.** Embedded PDP wins. PAs keep working through DOH outages. With per-request+cache, extended outages degrade access.
- **Latency.** Embedded wins on paper (local eval), but both serve warm requests in single-digit ms. Cold-path difference is one HTTPS round-trip.
- **Semantic drift risk.** Embedded has it (two codebases must agree forever). Per-request+cache avoids it entirely.

My honest take: **per-request+cache is the better v1**. The governance story ("DOH sees and logs every access decision") maps cleanly to DOH's pitch, the implementation is meaningfully simpler, and the only real cost — DOH-outage sensitivity — is manageable with a stale-on-error cache policy. The embedded PDP is the right architecture once we have enough sidecars that DOH can't handle the decision volume, but we're nowhere near that.

# Python style guide

## Function Signatures & Calling Conventions

To prioritize readability and eliminate "magic" behavior, we enforce strict explicitness in both how functions are defined and how they are invoked.

### 1. Enforce Explicit Argument Passing
* **Directive:** Do not use default parameter values in function or method definitions. All parameters must be mandatory.
* **Reasoning:** "Magic defaults" hide complexity and obscure the function's dependencies. We prefer explicit calls where every argument is visible at the call site.
* **Implementation:** If a value is logically optional, the caller must explicitly pass `None`.

**Bad (Implicit Defaults):**
```python
def connect_to_db(url, retries=3, timeout=30):
    # Hidden behavior: Reader assumes 0 retries? Infinite timeout?
    ...
```

**Good (Explicit Arguments):**
```python
def connect_to_db(url, retries, timeout):
    # All dependencies are visible in the signature
    ...
```

### 2. Prefer Keyword Arguments
* **Directive:** Use named arguments (keyword arguments) for function calls, particularly when passing literals (numbers, booleans, or strings) or when a function takes multiple parameters.
* **Reasoning:** Positional arguments are brittle and often illegible (the "Boolean Trap"). Keyword arguments make the code self-documenting and prevent errors caused by parameter reordering.
* **Implementation:** Explicitly state the parameter name at the call site.

**Bad (Positional Ambiguity):**
```python
# The reader cannot know what '3' and '30' represent
connect_to_db("db://localhost", 3, 30)

# Confusing booleans
create_user("jdoe", True, False)
```

**Good (Self-Documenting):**
```python
# Clarity is enforced at the call site
connect_to_db(url="db://localhost", retries=3, timeout=30)

# Intent is obvious even for optional flows
connect_to_db(url="db://localhost", retries=None, timeout=None)

# Boolean flags are readable
create_user(username="jdoe", is_admin=True, send_email=False)
```

### 3. Prefer Module-Qualified Imports for Local Modules
* **Directive:** For local/project modules, use `import module` rather than `from module import function`. Then call functions with the module prefix.
* **Reasoning:** Explicit module prefixes make dependencies visible at every call site. The reader instantly knows where a function comes from without scrolling to imports.
* **Implementation:** Import the module, then use `module.function()` syntax.

**Bad (Ambiguous Origin):**
```python
from iam_utils import get_assumed_role_session
from vpc_utils import find_available_vpc_cidr

# Reader can't tell where these come from without checking imports
session = get_assumed_role_session(...)
cidr = find_available_vpc_cidr(...)
```

**Good (Explicit Module):**
```python
import iam_utils
import vpc_utils

# Origin is immediately clear at the call site
session = iam_utils.get_assumed_role_session(...)
cidr = vpc_utils.find_available_vpc_cidr(...)
```

**Note:** This applies to local project modules. Standard library and well-known third-party packages (e.g., `from pathlib import Path`, `from dataclasses import dataclass`) are fine to import directly since their origin is universally understood.

### 4. Prefer Direct Imports Over TYPE_CHECKING
* **Directive:** Use regular imports for type hints. Only use `TYPE_CHECKING` when actually needed to resolve circular imports.
* **Reasoning:** `TYPE_CHECKING` adds complexity (conditional imports, string annotations) for a problem that may not exist. Solve circular dependencies when they occur, not preemptively.
* **Implementation:** Import types directly and use them in annotations.

**Bad (Premature Optimization):**
```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from myapp.models import User

def get_user(id: int) -> "User":  # String annotation required
    ...
```

**Good (Direct Import):**
```python
from myapp.models import User

def get_user(id: int) -> User:
    ...
```

**When TYPE_CHECKING is appropriate:**
- Actual circular import errors occur
- Heavy imports cause measurable startup delays
- Imports have side effects you need to avoid

### 5. Single-Line Function Signatures When Under 140 Characters
* **Directive:** Write function and method definitions on a single line when the total length (including `def`, parameters, return type, and trailing colon) is under 140 characters. Use multi-line formatting only when the signature exceeds this limit.
* **Reasoning:** Single-line signatures are easier to scan and search. Multi-line formatting adds vertical noise for short signatures that fit comfortably on one line.
* **Implementation:** Measure the full signature length. If under 140 characters, keep it on one line.

**Bad (unnecessary multi-line):**
```python
async def _handle_stream_event(
    message: SDKStreamEvent,
    ctx: StreamingContext,
) -> AsyncGenerator[StreamEvent, None]:
    ...
```

**Good (118 characters, fits on one line):**
```python
async def _handle_stream_event(message: SDKStreamEvent, ctx: StreamingContext) -> AsyncGenerator[StreamEvent, None]:
    ...
```

**When multi-line is appropriate:**
- Signature exceeds 140 characters
- Complex default values or annotations that benefit from vertical alignment (though we avoid defaults per rule 1)

### 6. Prefer Single-Line Docstrings for Simple Functions
* **Directive:** Use a brief single-line docstring for functions. Reserve multi-line docstrings (with Args/Returns/Raises sections) for complex functions where the signature alone doesn't convey important details.
* **Reasoning:** Verbose docstrings that restate what the function name and types already communicate add noise. A concise one-liner maintains consistency while avoiding redundancy.
* **Implementation:** Write a single-line docstring that adds context beyond the function name, or simply summarizes intent.

**Bad (overly verbose):**
```python
async def _aget_last_user_message(conversation: Conversation) -> str:
    """
    Get the last user message from a conversation.

    Args:
        conversation: The Conversation model instance.

    Returns:
        The content of the last user message.

    Raises:
        ValueError: If no user messages found.
    """
```

**Good (concise single-line):**
```python
async def _aget_last_user_message(conversation: Conversation) -> str:
    """Get the content of the most recent user message."""
```

**When multi-line docstrings are valuable:**
- Non-obvious behavior or side effects
- Complex algorithms that need explanation
- Public API functions where discoverability matters
- Unusual parameter constraints not captured by types

### 7. Require Type Hints on New/Modified Functions and Methods
* **Directive:** Every new or modified function/method must include type hints for all parameters and the return type.
* **Reasoning:** Complete signatures improve readability, reduce ambiguity, and make refactoring/tooling safer.
* **Implementation:** Annotate all parameters and returns explicitly. Use `-> None` for no-return functions. Keep annotations concrete when possible.

**Bad (missing annotations):**
```python
def check_access(request, resource, action):
    ...
```

**Good (fully annotated):**
```python
def check_access(request: HttpRequest, resource: Workspace, action: str) -> bool:
    ...
```


## Django 6.0 Async ORM

**Use native async ORM methods instead of `sync_to_async`.** Django 6.0 has full async ORM support — don't wrap sync methods.

- **Queries:** Use `await queryset.afirst()`, `await queryset.aget()`, `await queryset.acount()`, etc.
- **Create/Update:** Use `await Model.objects.acreate(...)`, `await instance.asave()`, `await instance.adelete()`
- **Iteration:** Use `async for obj in queryset:` instead of wrapping sync iteration

**Bad (outdated pattern):**
```python
from asgiref.sync import sync_to_async

async def get_user(user_id):
    return await sync_to_async(User.objects.get)(id=user_id)

async def save_item(item):
    await sync_to_async(item.save)()
```

**Good (Django 6.0):**
```python
async def get_user(user_id):
    return await User.objects.aget(id=user_id)

async def save_item(item):
    await item.asave()
```

The `a`-prefixed methods are native async and don't require `sync_to_async` wrappers.

**Bad:**

**Good:**

The prefix should match the containing folder or domain. This makes file names unique and self-documenting even when viewed in isolation (e.g., in editor tabs, search results, or stack traces).

## Design: end-to-end sidecar PA test

### Goal

Deploy a real Hermes PA (from the `hermes-personal` AppTemplate) to CH Sandbox with its sidecar + auth Lambda + per-env secrets + ECR push, then fake a real Okta login and confirm the full request flow works against the live AWS deployment:
- **happy path** — owner's browser cookie → sidecar verifies → PDP allows → Hermes WebUI served.
- **deny path** — non-owner cookie → PDP denies → 403.
- **no-cookie path** — unauthenticated → 302 to `auth.<env>/start`.

### Things that constrain the design (not obvious from the outside)

1. **`deploy_from_template` enqueues; the job worker drives the deploy.** You can't just call `deploy_from_template` and expect a deployed PA — it creates `Deployment(status=PENDING)`. The job worker picks it up and runs `app_deployment_executor.run_deployment`, which calls `infra_customer.deploy_app.deploy(...)`. Any test command has to either (a) run the worker in the same process or (b) run the deploy inline.
2. **Course Hero's default env is already READY.** That means the shared ALB + HTTPS listener + hosted zone already exist for the env the test will use. The auth Lambda stack, sidecar ECR stack, and the two-container app stack will be *new*, and attach to those existing resources.
3. **Hosted zone requirement.** Sidecar-enabled deploys refuse to run without a hosted zone. I need to confirm the `default` env already has `shared_alb_hosted_zone` set — if not, the test must either set it or tear down and re-provision the env. That's a pre-flight.
4. **Okta redirect URI.** For a real browser flow you'd have to register `https://auth.<env-hosted-zone>/callback` in Okta. For a test we'll **bypass the auth Lambda for cookie minting** — we'll use the env's JWT private key from Secrets Manager to mint a `doh_session` cookie directly, then `curl` it against the deployed sidecar. Avoids the interactive Okta redirect but still exercises every other piece (sidecar → PDP → ABAC → app).
5. **The PDP is reached over the public internet.** Sidecar calls `https://devopshero.ai/api/pdp/evaluate` (per `_resolve_pdp_url`). For local-dev testing that URL isn't reachable from CH Sandbox. Two options:
   - Make `DOH_PDP_URL` configurable per-env and point it at a publicly-reachable tunnel (ngrok or Cloudflare tunnel) pointing at the laptop's `localhost:8000`.
   - Deploy the PDP code to prod-like devopshero.ai first.
   - Stand up a temporary `sidecar_simulate`-style validator on the prod DOH control plane.
   
   For the test design I'll use **tunnel-to-localhost** — it keeps the test self-contained and doesn't depend on prod being in sync.
6. **Existing `course-hero` org has no PA seed policy** (we saw this during the earlier verification). The test must install it — either by calling `bootstrap_organization` once idempotently, or by writing a focused one-shot installer. The former is cleaner.
7. **Target user.** `vmendi@gmail.com` exists with `oidc_sub`. Good.
8. **Secrets live in CH Sandbox's AWS account.** The test command needs to assume the CH Sandbox role (same way `app_deployment_executor._get_aws_session` does) to read the JWT keypair secret and mint the cookie.

### The design — one new management command: `sidecar_e2e_test`

Single orchestration command. One-shot idempotent. Runs in the local Django process; shells out to real AWS for everything else. Structured as explicit phases so it can be rerun after a failure with `--skip-until-phase`.

#### Arguments


- Assert `Organization.oidc_*` fields are populated (auth Lambda needs them).

**Phase 1 — Seed the PA owner policy on course-hero.**

**Phase 2 — Invoke `deploy_from_template` and run deployment inline.**

Minimal runtime overrides we pass (read from `hermes-personal`'s `runtime_variables` for required-without-default): enough to make the Hermes container boot. - Curl the sidecar's health endpoint: `curl https://<app_slug>.<hz>/__sidecar/healthz`. Expect 200 "ok". This confirms the sidecar container is running and reachable.

**Phase 5 — Verify the three flows against the live deploy.**
