## GitHub Integration Architecture

### Components

**1. Models** (`models.py`) — Already GitLab-ready
- `GitProviderIntegration` — stores org-level connection with `installation_id` and status
- `Repository` — stores synced repos with `external_id`, `clone_url`, `default_branch`
- Both models already have `Provider.GITLAB` enum values defined

**2. GitHub Client** (`services/github/github_client.py`)
- JWT generation for GitHub App authentication (RS256 signed)
- Installation token exchange (short-lived tokens, no PATs)
- Paginated repository listing via GitHub API
- Sync logic that adds/updates/removes `Repository` records

**3. OAuth Flow** (`views/github.py`)
- `/github/connect` — redirects to GitHub App installation page
- `/github/callback` — receives installation_id, creates `GitProviderIntegration`, triggers sync
- `/api/github/webhook` — receives push/installation events (stubbed for auto-deploy)

**4. Repo Service** (`services/github/repo_service.py`)
- Clones repos using installation token in URL: `https://x-access-token:{token}@github.com/...`
- Re-uses existing clones for same conversation
- Safety checks for cleanup operations

**5. Configuration** (`settings.py`)
- `GITHUB_APP_ID`, `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`
- `GITHUB_APP_PRIVATE_KEY` (for JWT signing)
- `GITHUB_WEBHOOK_SECRET` (for webhook verification)

**6. UI** (`settings/git_integrations.html`)
- Connection status display
- Re-sync button
- Repository list with default branches

## What GitLab Integration Requires

### Key Differences from GitHub

- **Auth model** — GitLab uses standard OAuth 2.0 with access/refresh tokens (no App JWTs)
- **Token lifetime** — GitLab tokens expire and need refresh; GitHub installation tokens are fetched on-demand
- **Scopes** — GitLab uses OAuth scopes (`read_repository`, `api`) vs GitHub App permissions
- **API URLs** — `https://gitlab.com/api/v4/` vs `https://api.github.com`
- **Clone auth** — `https://oauth2:{token}@gitlab.com/...` vs `https://x-access-token:{token}@github.com/...`

### Implementation Tasks

**1. GitLab Client** — New `services/gitlab/gitlab_client.py`
- OAuth token exchange (authorization code → access token)
- Token refresh logic (store `refresh_token` in `GitProviderIntegration`)
- Repository listing via `/api/v4/projects?membership=true`
- Sync logic (similar pattern to GitHub)

**2. GitLab Views** — New `views/gitlab.py`
- `/gitlab/connect` — redirect to GitLab OAuth authorization URL
- `/gitlab/callback` — exchange code for tokens, create integration, sync
- `/api/gitlab/webhook` — receive push events (different payload format)

**3. Update `repo_service.py`**
- Add `Repository.Provider.GITLAB` branch in `clone_repository()`
- Use `https://oauth2:{token}@gitlab.com/{full_name}.git` format

**4. Model Changes**
- Add `access_token` and `refresh_token` fields to `GitProviderIntegration` (currently only stores `installation_id`)
- Add `token_expires_at` for refresh scheduling

**5. Configuration** — New settings
```python
GITLAB_APP_ID = os.environ.get("GITLAB_APP_ID")
GITLAB_APP_SECRET = os.environ.get("GITLAB_APP_SECRET")
GITLAB_WEBHOOK_SECRET = os.environ.get("GITLAB_WEBHOOK_SECRET")
```

**6. UI Updates**
- Add "Connect GitLab" button to `git_integrations.html`
- Show GitLab integration status alongside GitHub
- Handle both providers in the same view

**7. GitLab App Setup**
- Create OAuth application at gitlab.com/oauth/applications (or self-hosted instance)
- Configure redirect URI: `https://devopshero.io/gitlab/callback`
- Request scopes: `read_repository`, `read_api`

### Estimated Scope

- **New files:** ~3 (gitlab_client.py, gitlab.py view, __init__.py)
- **Modified files:** ~5 (models.py, repo_service.py, settings.py, urls.py, git_integrations.html)
- **Migration:** 1 (add token fields to GitProviderIntegration)
- **External setup:** GitLab OAuth app creation

The existing architecture is well-prepared for GitLab — the models already have the enum values, and the pattern is clear from the GitHub implementation. The main new work is the OAuth flow (different from GitHub Apps) and token refresh handling.

Good question. A self-hosted GitLab instance adds a few considerations compared to GitLab.com:

## Additional Requirements for Private GitLab

### 1. Instance URL Configuration

Instead of hardcoding `https://gitlab.com`, you'd need to store the GitLab instance URL per organization:

```python
# In GitProviderIntegration model
instance_url = models.URLField(
    null=True,
    blank=True,
    help_text="Custom GitLab instance URL (e.g., https://gitlab.company.com)",
)
```

All API calls would use `{instance_url}/api/v4/...` instead of `https://gitlab.com/api/v4/...`.

### 2. OAuth Application Setup

- **You create the OAuth app** on your private GitLab instance at `https://gitlab.company.com/admin/applications` (admin) or as a group-level app
- The redirect URI points to DevOps Hero: `https://devopshero.io/gitlab/callback`
- Your GitLab admin provides the `Application ID` and `Secret`

### 3. Network Connectivity

This is the main challenge with self-hosted instances:

- **DevOps Hero → GitLab** — DOH's control plane needs to reach your GitLab API for OAuth callbacks, repo listing, and token refresh
- **DevOps Hero → Clone URL** — The deployment agent needs to `git clone` from your GitLab

**Options:**
- **Public GitLab** — If your GitLab is internet-accessible (even with auth), it just works
- **VPN/Private Link** — DOH control plane would need network access to your GitLab (complex)
- **GitLab mirror to GitHub** — Some orgs mirror private repos to GitHub for CI/CD tooling
- **Webhook relay** — For push events, you'd need your GitLab to reach DOH's webhook endpoint

### 4. TLS/Certificate Handling

If your GitLab uses a private CA or self-signed cert:
- The `httpx` client needs to trust that CA
- Git clone operations need `GIT_SSL_CAINFO` or `GIT_SSL_NO_VERIFY` (not recommended)

```python
# In gitlab_client.py
client = httpx.Client(verify="/path/to/corporate-ca-bundle.crt")
```

### 5. Configuration Changes

Settings would need to support per-org GitLab instances rather than global config:

```python
# Instead of global GITLAB_APP_ID, store per integration:
# GitProviderIntegration fields:
#   - instance_url (e.g., https://gitlab.company.com)
#   - oauth_client_id
#   - oauth_client_secret (encrypted)
#   - access_token
#   - refresh_token
```

Or a hybrid: DOH provides a "bring your own OAuth app" flow where you enter your GitLab URL + OAuth credentials.

### 6. UI Flow Changes

The connect flow would need an extra step:

1. User clicks "Connect GitLab"
2. **New:** User enters their GitLab instance URL (or selects GitLab.com)
3. **New:** User enters OAuth App ID/Secret from their GitLab admin
4. User is redirected to their GitLab instance for authorization
5. Callback creates integration, syncs repos

## Summary: Private GitLab vs GitLab.com

| Aspect | GitLab.com | Private Instance |
|--------|------------|------------------|
| Instance URL | Hardcoded | User-provided |
| OAuth App | DOH creates one app | User creates on their instance |
| Network | Public internet | May need VPN/allowlisting |
| TLS | Standard certs | May need custom CA |
| Webhooks | GitLab.com → DOH | Private GitLab → DOH (firewall?) |

The **network connectivity** question is the biggest architectural decision — whether DOH can reach private GitLab instances directly or needs an agent/relay model for air-gapped environments.
