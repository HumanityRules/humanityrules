## User

I notice that we are not calling wait_for_service_stable anymore. Thoughts?

---

## Assistant

Good catch. With the old flow, `start_ecs_service` called `wait_for_service_stable` which gave us:

1. **Task failure diagnostics** — `check_stopped_tasks` reports *why* containers crash (OOM, bad entrypoint, missing env var, etc.)
2. **Granular progress logging** — "Tasks: 0/1 running, 1 pending" every time the count changes
3. **Fast early abort** — gives up after 3 consecutive failure checks instead of waiting for CloudFormation's longer timeout

Now we're relying on CloudFormation's built-in ECS service stabilization during `cdk deploy`. The CDK CLI streams CloudFormation events, so we see progress at the stack level, but not at the task level. And if a container keeps crashing, CloudFormation's error message is just "service failed to stabilize" without the container-level reasons.

There's also a behavioral difference on **first deploys**: if tasks keep crashing, CloudFormation rolls back the entire App stack (deleting the service, target group, listener rules). With the old flow, the stack stayed in place at `desired_count=0` so you could fix the image and retry without redeploying infrastructure.

On **re-deploys** this is less of a concern — CloudFormation rolls back to the previous working version, which is fine.

So the trade-off is simplicity vs diagnostics. If you want both, we could add `wait_for_service_stable` back as a post-Phase-3 verification, but only for first deploys where CloudFormation's rollback is destructive. Or we could accept the simpler flow and rely on ECS console / CloudWatch logs when things go wrong. What's your preference?
