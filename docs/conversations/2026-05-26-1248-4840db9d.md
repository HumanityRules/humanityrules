## User

Why is dev/shm prohibited?

---

## Assistant

`/dev/shm` is not prohibited by the host or ECS container. It is writable in the container. It is prohibited inside the `nono` sandbox because the active profile is allowlist-based and does not include `/dev` or `/dev/shm`.

Why omit it? Mostly sandbox hardening:

- `/dev/shm` is kernel-backed shared memory, not ordinary project storage.
- It enables POSIX named semaphores and shared-memory IPC across processes in the same IPC namespace.
- It can be used as a covert channel or shared scratch space outside the workspace policy.
- It can be abused for resource exhaustion unless tightly limited.
- `/dev` generally contains sensitive device/kernel interfaces, so profiles usually avoid allowing it wholesale.

In this case the denial is an unintended compatibility break: Python `multiprocessing.Queue` creates a `SemLock`, which uses POSIX semaphores under `/dev/shm`. Since `nono` blocks that path, Python surfaces `PermissionError: [Errno 13] Permission denied`.

So the policy is defensible, but the WebUI cron runner accidentally depends on something the policy blocks. The narrowest fix is still to avoid `multiprocessing.Queue` there and use `multiprocessing.Pipe`, which worked inside the sandbox. Allowing `/dev/shm` would also fix it, but it expands the sandbox surface.

## User

Can we allow /dev/shm in nono? Potential consequences?

---

## Assistant

Yes, we can allow `/dev/shm` in `nono`. It would likely fix the WebUI manual cron bug because Python `multiprocessing.Queue` can create POSIX semaphores again.

Potential consequences:

- It weakens IPC isolation. Processes inside the same sandbox/container can use shared memory and named semaphores as a coordination channel.
- It creates a writable kernel-backed scratch area outside `/workspace`, so it slightly expands where agent/tool code can persist temporary bytes.
- It can be abused for resource exhaustion. ECS default `/dev/shm` is usually small, often 64 MiB, but a malicious or buggy process could fill it.
- It may enable libraries to switch into shared-memory fast paths, which is usually fine but broadens runtime behavior.
- It does not expose host `/dev/shm`; this is the container’s tmpfs, not host-wide shared memory.
- It does not by itself grant access to arbitrary `/dev` devices if we allow only `/dev/shm`, not `/dev`.

My recommendation: allow only `/dev/shm`, not `/dev`, if we want compatibility broadly. It’s a reasonable sandbox exception for Python, Chromium, PyTorch, multiprocessing, and other common tools. Still, the narrower product fix is to remove `multiprocessing.Queue` from the WebUI manual cron path, because scheduled cron already works without needing `/dev/shm`.
