# Cheaper Postgres for the DOH Control Plane — Evaluation

## Where the $50 actually goes

Your current cluster (`infra_devopshero/stacks/database_stack.py`) is Aurora Serverless v2 PostgreSQL 16.4, **min 0.5 ACU / max 4 ACU**, single writer, no replicas, 7‑day backups, encrypted, private subnets.

Aurora Serverless v2 us‑east‑1 list pricing in 2026 (verified):

- **Compute floor:** 0.5 ACU × $0.12/ACU‑hr × 730 hr = **~$43.80/month** (paid even when idle)
- **Storage:** ~$0.10/GB‑month × ~5–10 GB ≈ **$0.50–1.00/month**
- **I/O standard:** ~$0.20 per million ≈ **a few $/month**

So the bill is essentially the **0.5 ACU floor**. Query volume isn't the driver — the *minimum capacity* is. That's the lever to pull.

## What's special about this workload (and what isn't)

From the codebase audit, the schema is a **standard Django app**: ~30 models, ~40 tables, JSONB fields, `select_for_update(skip_locked=True)` for the in‑process job worker. **No PostGIS, FTS, materialized views, triggers, stored procs, LISTEN/NOTIFY, or large blobs.** Nothing locks you to Aurora — any Postgres 14+ works.

Two non‑obvious traits matter for pricing:

1. **The job worker polls the DB every 1 second** (`devopshero_app/services/jobs/job_worker.py`, line ~331). That's a continuous keep‑alive on the connection.
2. **psycopg pool is configured up to 200 connections** (`devopshero_site/settings.py:130`), defensive after a Feb 2026 incident. Real concurrent usage is far lower (single ECS task, pre‑beta), but any alternative must tolerate bursts.

## The four realistic options

### Option A — Aurora Serverless v2 with **min ACU = 0** (auto‑pause)

AWS launched scale‑to‑zero on Serverless v2 in late 2024. Set `MinCapacity=0` and `SecondsUntilAutoPause=300–86400`; while paused, **compute is $0**, you pay only storage (~$1–2/month). Resume on first connection takes **up to 15 seconds**.

- **Estimated cost:** $2–5/month if it actually pauses; $44–48 if it doesn't
- **Engine compatibility:** requires Postgres ≥ 13.15 / 14.12 / 15.7 / 16.3 — you're on 16.4 ✓
- **Code change:** trivial — flip min capacity in CDK

**Critical blocker before this saves anything:** the in‑process job worker hits the DB every 1 second forever, which **prevents the cluster from ever pausing**. The Django session backend, agent runner (0.5 s polling), and SSE handlers also keep traffic flowing while users are active. To actually realize savings you'd need to:

- Make the job worker block on a long sleep (or LISTEN/NOTIFY, or SQS) instead of 1‑second polling
- Accept up to 15 s latency on the first request after a cold start — bad for HTMX polling that expects sub‑second responses; users would see hangs after overnight idle
- Move sessions out of the DB (or accept that any active session keeps the DB warm)

For a pre‑beta product with weekend/overnight idle, this is the **biggest theoretical win** but requires real engineering work and degrades user experience around cold starts.

### Option B — Switch to standard RDS PostgreSQL on a small Graviton instance ⭐ recommended

Same VPC, same Django code, same `Secrets Manager` secret structure (host/port/dbname/username/password — RDS auto‑generates the same fields). Drop‑in for `infra_devopshero/stacks/app_stack.py:108-114`.

- **`db.t4g.micro`** (2 vCPU, 1 GB RAM): $0.016/hr × 730 = **~$11.68/month** compute + ~$2.30 for 20 GB gp3 + backups within free tier ≈ **~$14/month total**
- **`db.t4g.small`** (2 vCPU, 2 GB RAM): $0.032/hr × 730 = **~$23.36/month** compute + storage ≈ **~$26/month total**

Trade‑offs:

- **No auto‑scale.** You're at fixed capacity until you `modify-db-instance`. For pre‑beta this is fine; resize takes minutes when needed.
- **Memory headroom.** `t4g.micro`'s 1 GB is tight if the 200‑connection pool ever fills (≈10 MB/conn × 200 = 2 GB). In practice pool fill is rare, but **`t4g.small` is the safer pick** if you want a single resize‑free year of runway.
- **CPU credits (T‑class burst).** Baseline 10% × 2 vCPU; bursts allowed. Migration days could exhaust credits and incur a small overage surcharge ($0.075/vCPU‑hr) until baseline restores. Not material at pre‑beta volume.
- **Single‑AZ.** Aurora's storage layer is multi‑AZ even with one writer; standard RDS Single‑AZ is not. Multi‑AZ would double the bill (~$23 or ~$47). Given `deletion_protection=False` and `removal_policy=DESTROY` already in the CDK, you've implicitly accepted this risk level.

**Savings: ~$36/month (≈70%) for `t4g.micro`, ~$24/month (≈50%) for `t4g.small`.** Lowest‑risk, lowest‑effort change.

### Option C — External managed Postgres (Neon, Supabase)

Neon Launch plan: pay‑as‑you‑go, **scales to zero after 5 minutes**, $0.106/CU‑hour active, $0.35/GB‑month storage. Realistic spend for your workload: **$5–15/month**.

- Same cold‑start problem as Option A (resume takes seconds)
- For production you really want **AWS PrivateLink** ($0.01/GB) — that's the **Scale plan only**, which has higher minimums and changes the price story
- Public‑internet egress costs go through your NAT gateway and Neon's egress pricing
- **Governance concern:** the DOH narrative is "your data stays in your AWS account" — putting the *control plane's own* DB at a third‑party SaaS muddies that story for security/compliance discussions with prospects, even though customer data lives in customer accounts

I'd skip this. Savings aren't dramatic enough to justify the new vendor + the narrative dilution.

### Option D — Self‑host on EC2 / inside the ECS task / SQLite + EFS

All disqualified for the control plane:

- **EC2 self‑host:** you lose managed backups, automated patching, and gain ops burden; tiny `t4g.nano` is ~$3/month but the operational overhead isn't worth it for a $50 line item
- **SQLite on EFS or a persistent volume:** kills the option to ever scale beyond 1 ECS task; concurrent writes between web + job worker + agent runner will fight each other; not a serious production option
- **Postgres in the ECS task:** ties DB life cycle to deploys and breaks during rolling updates

## My recommendation

**Switch to RDS PostgreSQL on `db.t4g.small`, single‑AZ, in the same VPC.** This saves ~$24/month (~50%) with essentially zero application changes and no UX regression. If the workload stays this light, drop to `t4g.micro` later (~$36 savings, ~70%).

Why not Option A (auto‑pause)? On paper it saves more, but the 1‑second job worker poll silently neutralizes the savings until you re‑architect background work, and 15‑second cold starts hurt the HTMX polling UX. Worth doing **after** Option B, not instead of it.

Why not Neon? The savings delta vs. Option B is small and the data‑residency story for the control plane gets murkier when you're selling on data sovereignty.

```22:39:devopshero_app/keep_awake_middleware.py
KEEP_AWAKE_SECONDS = 4 * 60 * 60


class KeepWorkerAwakeMiddleware:
    """Extend the worker's active-polling window on every authenticated request."""

    def __init__(self, get_response: Callable[[HttpRequest], HttpResponse]) -> None:
        self.get_response = get_response

    def __call__(self, request: HttpRequest) -> HttpResponse:
        if request.user.is_authenticated:
            job_worker.keep_awake_for(seconds=KEEP_AWAKE_SECONDS)
        return self.get_response(request)
```
