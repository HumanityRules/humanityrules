## What OpenClaw needs to persist

Based on the `.gitignore` and config:

- **`workspace/memory/`** — session memory (the `session-memory` hook)
- **`workspace/.openclaw/`** — runtime metadata
- **`workspace/*.db`** — SQLite or similar local databases
- **`HEARTBEAT.md`** — created at first run

All of this is **file-based** under `/app/workspace`. OpenClaw treats files as its memory — `SOUL.md` literally tells the agent "these files are your memory."

On plain Fargate today, **all of this dies on every container replacement** (deploy, crash, scale event).

- **Per-agent isolation.** EFS access points enforce path + UID isolation, so each deployed agent gets its own directory namespace on a shared filesystem.
- **Right cost profile.** Agent workspaces are small (KBs to low MBs of text). EFS Standard is $0.30/GB-month; Infrequent Access drops to $0.025/GB-month for stale sessions. Negligible for this use case.
- **Survives everything** — container crashes, redeployments, ECS scaling, Fargate spot reclaims.
- **Encrypted at rest** (already the pattern you use), backed up with AWS Backup.

**What needs to happen:**
- Add an EFS filesystem + security group + access point to the customer environment base infrastructure (currently `deploy_base.py` has VPC, ECS cluster, shared ALB, builder — no EFS)
- Wire the EFS mount into the app task definition in `deploy_app.py` when the template requests it
- Probably a new field on `AppTemplate` or `datastore_config` to signal "this app needs EFS"

**Downsides:**
- ~0.5-2ms latency per file op vs ~0.1ms local disk. Irrelevant for an agent writing memory files.
- NFS file locking semantics differ from local — not an issue for single-task agent workloads.
- Adds an EFS + mount target to each customer environment (one-time, shared across all agents in that env).

### 2. Fargate ephemeral storage — not viable

You can bump `ephemeralStorageGiB` up to 200GB on the task definition. Fast local disk, but **it dies with the task**. This is what you have today (the default 20GB). Not a persistence solution.

### 3. Aurora Serverless (via `datastore_config`)

DOH already supports this for other templates. But OpenClaw doesn't use SQL — it uses files. You'd need to either:
- Fork/modify OpenClaw to use a DB backend (large effort, breaks upstream compatibility)
- Build a FUSE adapter or sync layer (fragile)

Plus Aurora Serverless v2 has a minimum of 0.5 ACU (~$43/month) even when idle. Overkill for what's essentially text files.

### 4. S3 with s3fs/Mountpoint

Cheap and durable, but:
- FUSE on Fargate requires `SYS_ADMIN` capability (security concern in governed deployments)
- High latency for the random read/write patterns of an agent workspace
- Mountpoint for S3 is read-optimized and doesn't support random writes well

Could work as a **backup/archive tier** alongside EFS (periodic sync of memory to S3), but not as the primary store.

### 5. DynamoDB

Same problem as Aurora — OpenClaw writes files, not key-value records. Would need code changes upstream.

## Assistant

EFS cost is driven by two things: **storage used** and **mount targets** (the ENIs in each AZ).

## Storage

- **EFS Standard** — $0.30/GB-month
- **EFS Infrequent Access** — $0.025/GB-month (with lifecycle policy, files not accessed for 30+ days move here automatically)

For OpenClaw agent workspaces, we're talking about text files — session memory, SOUL.md, maybe some SQLite. Realistic estimate: **1-50 MB per agent**. At Standard pricing that's fractions of a cent. Even 1 GB across many agents is $0.30/month. Storage cost is effectively zero for this use case.

## Mount targets (the real cost consideration)

Each EFS mount target creates an ENI in a subnet. The ENI itself is free, but **the NAT gateway is not**. Since `deploy_base.py` puts Fargate tasks in `PRIVATE_WITH_EGRESS` subnets, the EFS mount targets go in those same private subnets and don't need NAT — NFS traffic stays within the VPC. So mount targets add **no incremental cost** beyond what the VPC already has.

## What `deploy_base` creates today (for context)

The customer environment base stacks are: VPC (with NAT gateway), ECS cluster + shared ALB, and the builder EC2 instance. Adding EFS means:

- **1 EFS filesystem** — $0/month base (pay per GB stored)
- **2 mount targets** (one per AZ, matching the VPC's 2 private subnets) — $0/month
- **1 security group** — $0/month
- **1 access point** — $0/month

## The actual cost line items

- **EFS storage** — ~$0.00 to $0.30/month (depends on total workspace size across all agents in that environment; pennies for typical usage)
- **EFS data transfer** — $0 within the same AZ, $0.01/GB cross-AZ (Fargate task and mount target will typically be in the same AZ)
- **No provisioned throughput needed** — Bursting mode gives 50 MB/s per TB stored, with burst credits. Agent file I/O is tiny; you'll never exhaust burst credits.

## Bottom line

Adding EFS to `deploy_base` is **effectively free** for the agent workspace use case. The only scenario where cost becomes non-trivial is if you store many gigabytes (e.g., agents generating large artifacts) — and even then, enabling the Infrequent Access lifecycle policy drops it to $0.025/GB-month.

The most expensive thing in the customer environment remains the NAT gateway ($32/month + data processing) and the builder EC2 instance. EFS doesn't move the needle.

The field was designed for exactly this moment. The intent is clear: different templates need different CDK stack compositions. Today there's one implicit profile (`fargate_web`), but there's no `if/match` on the value to vary behavior.

For EFS, two approaches:

**Option A: New profile `fargate_web_efs`**
- `deploy_app.deploy()` reads `cdk_stack_profile` and branches: `fargate_web` does what it does today, `fargate_web_efs` adds EFS to the app stack (volume + mount + IAM + security group)
- Change OpenClaw template to `"cdk_stack_profile": "fargate_web_efs"`
- Clean separation — EFS is opt-in per template

**Option B: Drive it from `datastore_config`**
- `datastore_config` already holds Aurora settings when present. You could add an `efs` section there (e.g., `{"efs": {"mount_path": "/app/workspace"}}`)
- `deploy_app.py` already conditionally creates Aurora when `database_config` is set — same pattern for EFS
- Downside: `datastore_config` / `database_config` name implies databases, not general storage. Naming becomes misleading.

**Option C: Both — `cdk_stack_profile` for broad patterns, config fields for details**
- `cdk_stack_profile` selects the stack *shape* (which stacks get created, what base infrastructure is expected)
- `datastore_config` (or a new `storage_config` field) holds the parameterization (mount path, UID/GID, lifecycle policy, etc.)
- Most flexible, but premature if EFS is the only non-Aurora storage for a while

- The wiring is straightforward: one branch point in `deploy_app.deploy()` where today it implicitly assumes `fargate_web`

## Assistant

Here's what's at play:

`app_config.app_name` = `app.slug`, which is unique per organization (`UniqueConstraint` on `["organization", "slug"]`). It is **not** globally unique.

Within a single environment though, this is the same identifier used for everything else — CloudFormation stacks (`doh-{env_slug}-{app_name}-app`), ECR repos (`doh/{env_slug}/{app_name}`), target groups, service names. If two apps collided on `app_name` in the same environment, CDK would already blow up long before EFS became a problem.

Your options for the access point path:

- **`app_config.app_name`** (current) — human-readable, matches all other resource naming conventions. `/deployments/my-cool-agent/`. Easy to browse and debug on EFS. Same uniqueness guarantees as every other resource in the environment.
- **`resource_prefix`** (`doh-{env_slug}-{app_name}`) — adds the environment slug, making it slightly more explicit. `/deployments/doh-default-my-cool-agent/`. Redundant since the EFS filesystem is already scoped to one environment.
- **`app.id`** (UUID7) — globally unique, zero collision risk even in pathological scenarios. `/deployments/019abc12-3456-7def-8901-234567890abc/`. Impossible to browse — you'd need a lookup table to find whose workspace is whose.

My take: `app_name` is the right choice. It matches the naming convention used everywhere else in the deployment, and any collision at this level would already be a fatal problem in the rest of the CDK stacks. The human-readability is a real win when you need to debug or inspect agent state on EFS.
