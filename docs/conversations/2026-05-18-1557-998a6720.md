## Assistant

Short answer: no, removing it costs nothing for in-container management. Sudo's only job was elevating `hermeswebui` (UID 1024) to root *inside* the nono sandbox. Outside the sandbox, every process is already root by construction:

- The Dockerfile's final `USER root` is at line 147, just before `ENTRYPOINT` — so the container's main process starts as root.
- `persistent-root-runner.sh` runs as root (it has to mount `/proc`, `/dev`, etc., and `chroot`).
- `supervisor.sh` runs as root inside the chroot — that's how it can `chown`, start the credential daemons, etc.
- The privilege drop happens *only* at `runuser -u hermeswebui -- nono …` (supervisor.sh:258), and that's the boundary the sudoers entry was trying to puncture.

What that means for `aws ecs execute-command` (which is the realistic "management commands inside the container" scenario):
- ECS exec defaults to the container's `USER`, which is root here. You land as root, with full access to `/`, `/opt/doh`, the daemons' `/proc/<pid>/environ`, everything.
- You don't go through nono unless you explicitly run `nono …` yourself, and at that point you're starting a fresh sandboxed subprocess, not inheriting the agent's locked-down session.

So the only thing we lost is the ability for the agent (running inside nono as `hermeswebui`) to escalate to root — which is precisely what the sandbox is there to prevent. That was the security regression that the user-switch fixed; the sudoers file was undermining it. Cleanup is correct.

One nuance worth flagging: if you ever `nsenter` / `docker exec` into the running container *and* explicitly `runuser -u hermeswebui` to reproduce a sandbox-side issue, you no longer have `sudo` to step back out. The fix in that case is just `exit` and re-enter as root — not a real loss.
