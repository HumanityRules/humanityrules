## The happy path

Say I want to make a DOH change to the agent (webui is identical, just a different dir):

1. **Get on the branch first.** After `submodule update --init`, the submodule is in **detached HEAD** at the pinned commit — not on `doh/vNEW`. So step zero is `git -C vendor/hermes-agent checkout doh/vNEW`. Skip this and every commit I make is an orphan.
2. **Edit the files** in `vendor/hermes-agent/`. This *is* the patch — it's a new commit on our fork branch, the direct equivalent of dropping a file in `build/patches-agent/` today.
3. **Iterate locally.** Rebuild the image; `COPY . .` / copytree grabs disk bytes, so my *uncommitted* edit is picked up. The edit-build loop works with zero commits — this is the nice part.
4. **Once it works, commit inside the submodule** onto `doh/vNEW`.
5. **Push that commit to the mirror.**
6. **Back in the superproject, commit the moved gitlink** (`modified: vendor/hermes-agent (new commits)`).

## The honest cost: one logical change is now a two-repo dance

In the old system, a DOH patch was **one file, in the monorepo, one commit, fully local.** Now the same change is: commit in another repo → push to the mirror → commit the pin in the monorepo. We sold this whole migration on *rebase ergonomics* — and that's real — but the flip side is that the **frequent, small patch path got heavier**, while the **infrequent version-bump path got easier.** If small DOH tweaks outnumber version bumps for you (they usually do), you're paying ceremony on the common case to save pain on the rare one. Worth being clear-eyed that that's the trade.

## The traps specific to this path

- **Push-before-pin.** You *can* commit a gitlink pointing to a commit that only exists on your laptop. Local build works (files on disk), even prod works (`COPY . .` from your laptop). But the SHA isn't in the mirror, so a fresh clone or a re-init can't fetch it — a silent landmine. Discipline: **push the submodule commit, then commit the pin.**
- **The vague `git status` line.** An uncommitted edit inside the submodule shows in the superproject as a single line: `modified: vendor/hermes-agent (modified content)`. Easy to miss, and because prod copies disk bytes, you can *ship an uncommitted vendor change to prod* without realizing it. The old patch file at least sat plainly in the monorepo tree.
- **Detached-HEAD orphans** (the step-zero trap above).

## The mitigation

`apply-patches.py` goes away, but I'd replace it with a tiny `vendor-commit.sh` helper that does the right thing as one unit: assert you're on `doh/vNEW`, commit in the submodule, push to the mirror, then commit the pin in the superproject. That collapses the two-repo dance back into one command and closes the push-before-pin and detached-HEAD traps in one place. It's the natural home for the discipline that AGENTS.md would otherwise have to nag about.

One thing this **doesn't** change for the better or worse: a DOH patch is still just "a new commit on the fork branch," exactly as conceptually clean as a patch file — it's only the *recording* of it that now spans two repos.

# Development Journaling

Add entries to `docs/journal.md` documenting decisions, learnings, and architectural choices from the current session.

## Workflow

1. **Review the conversation** to identify:
   - Decisions made and their reasoning
   - Learnings, mistakes, corrections
   - Architectural choices

   - **Onboarding** — User registration, organization creation, session handling
   - **AgentChat** — AI conversation interface, streaming, message rendering, tool calls
   - **Integrations** — External services: AWS accounts, GitHub, WorkOS
   - **Deployment** — Everything in customer accounts: environments, apps, datastores, VPCs, ECS, ALB
   - **DomainModel** — Core entities (workspaces, apps, datastores, environments), CRUD, relationships, refactors
   - **UI** — Shared frontend: base templates, navigation, design system, shared components
   - **ControlPlane** — DOH's own infrastructure (EFS, Aurora, CloudFront, ALB)
   - **DevEx** — Developer tooling, scripts, CLI, local development
   - **Bugfix** — Bug fixes and debugging sessions

3. **Write a thorough entry** following the format below

4. **Prepend the entry** to `docs/journal.md` (latest on top) — leave `**Conversation:**` blank for now

5. **Extract the conversation to disk** — Run the extraction script:
   ```bash
   python .claude/skills/journal/extract_conversation.py --list --search "<first few words of user's first message>" --limit 3
   python .claude/skills/journal/extract_conversation.py --uuid <UUID>
   ```

6. **Update the journal entry** with the conversation link

7. If user said `/journal commit`, also commit all changes from the session

## Entry Format

```markdown
## YYYY-MM-DD HH:MM - [Category] Title

**Conversation:** [YYYY-MM-DD-HHMM-uuid.md](conversations/YYYY-MM-DD-HHMM-uuid.md)

Describe the decision/change and WHY in sufficient detail for future reference.

**Key points:**
- Point with reasoning
- Point with reasoning
- ...
```

## Writing Guidelines

- **Be thorough** — Include enough detail to understand the context months later
- **Explain decisions** — Document what was decided and WHY, not just what changed
- **Capture learnings** — Document mistakes, corrections, and insights
- **Include technical details** — Specific configurations, error messages, solutions tried
- **No "Files Changed" sections** — Git tracks files; journal captures intent
- **Use current time** — Format: `YYYY-MM-DD HH:MM` (24-hour, local time)
