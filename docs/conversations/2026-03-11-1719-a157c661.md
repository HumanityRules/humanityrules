## Assistant

Root cause was in `devopshero_app/views/apps.py`: the `Deployed to Environments` row was choosing the right blueprint, but it was still rendering from the last launched deployment only. After a redeploy started, the row stayed on the old `succeeded` deployment, so the `Redeploy` button remained visible and a second click hit the existing guard in `app_deployment_redeploy`, which returned `422`.

I fixed the selector so it now does two separate things:
- it still picks the row’s blueprint from the latest launched deployment in that environment
- it renders the row from the latest live deployment on that blueprint, including `pending`/`building`/`pushing`/`deploying`/`starting`

That means once redeploy is triggered, the top row immediately switches to the in-progress deployment state and the `Redeploy` action disappears until the deployment settles. I also added a regression test in `devopshero_app/tests/test_abac_views_apps.py` to cover that exact case.
