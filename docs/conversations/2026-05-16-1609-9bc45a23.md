## User

In the hermes_agent, the google connector refreshes credentials every 60 minutes roughly. I am wondering if perhaps it is simpler to just refresh after a call fails with 401 (or whatever happens when the token is expired).

---

## Assistant

Doable, but it's not actually simpler once you account for the broker's role. Today the broker is mostly a transparent TLS-intercept + header-swap proxy; switching to "refresh on 401" means it has to **buffer the request body, read the upstream response, classify it (401 vs. real auth failure vs. revoked grant), refresh, and replay** — all per request. That's more code, more failure modes, and adds the user-visible latency of a refresh round-trip on the first call after every expiry, instead of paying it in the background.

The bits the timer is actually buying you:

- **Hidden latency.** Refreshing 5 min before expiry means no agent call ever waits on `oauth2.googleapis.com`.
- **Single-flight is free.** The per-provider lock plus the next-tick timer means N concurrent calls all read the same fresh `_host_token[host]` — no thundering-herd "everyone got 401, everyone tries to refresh".
- **Clean status reporting.** `/integrations` reflects connected / not_connected / revoked / transient because the loop classifies outcomes; reactive refresh would only learn revocation when an agent happens to call.
- **No request replay.** The broker can keep streaming bodies through; never has to buffer in case it needs to retry.

If the real itch is "60 minutes feels wasteful when the agent is idle", the smaller change is **lazy-but-cached**: stash `expires_at` alongside the token, and in `_current_token_for_host` refresh just-in-time if the token is within `REFRESH_LEAD_SECONDS` of expiry. No background loop, no 401 plumbing, same single-flight via the existing `_provider_refresh_locks`. You'd lose proactive status updates between calls, but pre-flight latency stays hidden as long as the lead window is wider than a refresh round-trip.

My take: keep the timer. It's ~30 lines and it's earning them. If you want to remove it, do the lazy-with-cached-expiry variant rather than 401-driven retry — much smaller blast radius on the broker's hot path.

## Assistant

Before my change, there were two endpoints:

- `GET /integrations` — read the cached state and return it (no refresh).
- `POST /integrations/google/kick` — synchronously refresh, then return the same shape.

The WebUI used GET on every render and POST after a Connect/Disconnect round-trip, when it specifically wanted "render against fresh data, not the cached state from the last timer tick."

I collapsed those into one: `GET /integrations` now refreshes every TLS-intercept provider before responding, so callers always see current state. The POST kick endpoint is gone.

**Why is that OK?** There are only ~3 callers and `/integrations` is loaded only when a human opens the Integrations tab — a few hundred ms of refresh latency on a tab they just clicked is invisible. There's no hot-path caller that would care.

**Why did I do it at all?** Two reasons:

1. The kick endpoint only existed because the cache was timer-driven and could be stale. Now that `_ensure_fresh` is the path, that staleness can't happen on a refresh-on-render GET — so the second endpoint stops earning its keep.
2. It removes one route, one handler, one fetch helper from the WebUI, one error branch (`/kick` could return 500 with a partial payload), and one concept from the mental model. Net is fewer moving parts.

**The tradeoff I'm making:** every `/integrations` GET now hits DOH once per provider. Today that's 1 call (Google) per tab open. If we add Slack/Linear/etc., it scales linearly with provider count. If that ever becomes a real cost, the right fix is the same as it was for the proxy: cache + lead-window check inside `_refresh_all_providers`. But not worth pre-optimizing.

If you'd rather I keep the GET cheap and bring the kick endpoint back, that's a one-liner — say the word.
