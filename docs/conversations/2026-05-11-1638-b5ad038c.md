- **`--unsigned-payload`.** Skips the body-hash step in signing. Used for large uploads where hashing is expensive. Not relevant for our Bedrock/STS JSON payloads.

- **`Transfer-Encoding: chunked` on the request side.** The Go binary has complex logic to force `identity` encoding because SigV4 and chunked interact badly. Hermes / boto3 always sends `Content-Length`-framed JSON bodies to Bedrock, never chunked. ✅ No action — and if this ever broke, we'd see a clean signature mismatch, not a silent buffer.

- **403/5xx error body logging (`--log-failed-requests`).** Their binary peeks into the body on error, then replays it back. We don't log, so we don't need to replay. Fine.

- **STS regional endpoint (`AWS_STS_REGIONAL_ENDPOINTS`).** The Go binary defaults to regional STS. I'm pointing at `sts.amazonaws.com` (global) — which actually works for IAM ops like `GetCallerIdentity` from any region. If we ever need regional STS (AssumeRoleWithWebIdentity latency-sensitive), we'd swap the host to `sts.{region}.amazonaws.com`. Not urgent.

**Bug in the Go binary we should NOT replicate:**

- **`copyHeaderWithoutOverwrite` after signing** (proxy_client.go:230) — they add raw client headers back *after* signing. If the client sent, say, `Content-Type: application/json` and SigV4 signed based on the already-present value, great. But if the client sent a header the signer didn't sign, it still propagates to the upstream. Arguably harmless in our setup (we control the client), but technically breaks the "the signed request is what hits AWS" invariant. We strip inbound auth-y headers before signing and add nothing after — cleaner.

**My recommendation:** Only one change is worth making proactively → **connection reuse via urllib3 pool.** It saves ~100ms per Bedrock call on reused connections, zero downside, small code delta. Everything else is either already handled, doesn't apply to our deployment, or is a Go-binary bug we correctly avoided.
