## Assistant

No, it doesn't. The ABAC system evaluates each resource type independently. Looking at the `ACTION_HIERARCHY`:

```29:32:devopshero_app/services/abac.py
ACTION_HIERARCHY: dict[str, set[str]] = {
    "workspace:admin": {"workspace:view", "workspace:edit"},
    "environment:admin": {"environment:view", "environment:deploy", "environment:approve"},
}
```

Hierarchy only works **within** a resource type — `workspace:admin` implies `workspace:view`, but nothing crosses from workspaces to apps. When `filter_permitted_resources` runs, it queries policies matching the specific `resource_type` passed in:

```273:273:devopshero_app/services/abac.py
    policies = list(Policy.objects.filter(organization=organization, resource_type=resource_type))
```

So `"workspace"` policies and `"app"` policies are completely separate evaluations.

The one connection is that apps **inherit workspace tags** for their resource conditions:

```95:99:devopshero_app/services/abac.py
    if resource_type == "app":
        for t in ResourceTag.objects.filter(organization=organization, app=resource):
            tags.append((t.key, t.value, "direct"))
        for t in ResourceTag.objects.filter(organization=organization, workspace=resource.workspace):
            tags.append((t.key, t.value, f"inherited:{resource.workspace.name}"))
```

But that's tag inheritance for matching resource conditions in `app` policies — not action propagation. A user could have `workspace:view` on a workspace but lack `app:use` on its apps, or vice versa.

The dashboard is **platform access** — it shows what exists in the DOH platform. `app:use` is **app access** — it controls who can open the deployed tool through the sidecar. These are separate concerns.

`workspace:view` is defined as "See the workspace **and its contents**." Apps are contents of a workspace. So `workspace:view` already covers "can I see this app on the dashboard." This is reinforced by `workspace:edit` being described as "Edit workspace settings, **app configuration**, create apps" and `workspace:admin` as "managing tags on the workspace **and its apps**."

The design doc treats apps-in-the-platform as workspace contents, not as independently visible resources. So option 1 is the one that matches the design: **the dashboard should filter apps by `workspace:view` on their parent workspace**, the same way it already filters datastores. `app:use` stays as the sidecar-only action and doesn't need a view counterpart.
