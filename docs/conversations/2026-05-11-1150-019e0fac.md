Yes, in V1 it should be mounted when the host comes up, but only if we explicitly build that into the EC2 host boot path.

EC2/EBS gives us an attached block device. Linux does not automatically make that a mounted filesystem. AWS’s EBS docs describe the steps as: attach volume, detect device, create filesystem if needed, create mount point, mount it, then add `/etc/fstab` if it should mount after reboot. AWS also notes that `/etc/fstab` should use the filesystem UUID because device names can change. Source: [AWS EBS docs](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-using-volumes.html).

So the V1 host boot flow should be:

```bash
# conceptually
find secondary EBS device
mkfs if empty
mkdir -p /var/lib/devopshero/hermes
add UUID mount to /etc/fstab
mount /var/lib/devopshero/hermes
start/register ECS
```

The reason I called out a readiness guard is not V2 placement enforcement. It is just to avoid a nasty V1 failure mode: ECS host bind mounts use a `sourcePath`, and if that path does not exist, Docker creates it on the host. AWS documents that ECS EC2 `sourcePath` persists at the specified host path and Docker creates it if missing. Source: [ECS bind mount docs](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/specify-bind-mount-config.html).

That means if `/var/lib/devopshero/hermes` failed to mount, the task could still start and write to the root disk path. Everything would look like it worked until restart/replacement exposes that it never wrote to the data volume.

For V1, the simple fix is: make `ecs.service` depend on the data mount. Not placement constraints, not multi-node orchestration. Just “don’t let this instance join the ECS cluster until `/var/lib/devopshero/hermes` is actually mounted.”

## Assistant

For bullet 3, I think this is the right simplification:

**V1 should not solve image upgrades or rootfs rebasing.**

The first time a Hermes deployment starts, the image initializes an empty persistent root. After that, the persistent root is the source of truth. If we deploy a newer Hermes image, it should not try to merge itself into an already-initialized rootfs.

That gives us a very clear rule:

```text
empty persistent root -> initialize from image
non-empty persistent root -> run exactly what is already there
```

Why this is good for V1:
- It makes package installs durable. If the agent changes `/usr`, `/etc`, `/app`, `/home/hermeswebui`, etc., we do not overwrite or partially merge those changes on restart.
- It avoids writing a risky “upgrade reconciler” now.
- It makes failures understandable: a broken rootfs is a broken rootfs, not a confusing mix of old persisted files and new image files.
- It keeps V2 restore testing honest because the restored thing is the whole runtime state.

The consequence is that image deploys are not normal software upgrades once a rootfs exists. A new image only affects brand-new roots or intentionally reset/rebased deployments.

For later, we can add explicit operations:
- **Reset:** delete/recreate the persistent root from the current image.
- **Snapshot before reset:** preserve rollback point.
- **Rebase:** controlled copy/merge from a newer image into an existing root.
- **Repair shell:** start into the persisted root without full Hermes boot.

But V1 should only implement initialize-on-empty and run-existing-root.

## User

what does "linux_capabilities": ["SYS_ADMIN"]," do for us?

---

## Assistant

`linux_capabilities: ["SYS_ADMIN"]` lets the Hermes container perform Linux `mount` operations.

For this V1 design, ECS performs the host bind mount into `/hermes-persistent-root`, but then our runner still needs to prepare that persistent root as a usable root filesystem by mounting:

- `proc` at `/hermes-persistent-root/proc`
- `/dev` into `/hermes-persistent-root/dev`
- `/sys` into `/hermes-persistent-root/sys`
- a tmpfs at `/hermes-persistent-root/run`

Those `mount` calls fail inside a normal container without `CAP_SYS_ADMIN`.

It does **not** give AWS/IAM permissions, and it does **not** mount the host EBS path for us. ECS still does the bind mount. This capability is only for the container-side chroot setup. It is broad, so the runner drops `SYS_ADMIN` before launching Hermes/nono.

## User

is it because before the chroot operation we need to mount those paths?

---

## Assistant

Yes.

Before `chroot /hermes-persistent-root ...`, the mounted directory is just files copied from the image. For it to behave like a real Linux root filesystem, it needs runtime kernel filesystems inside it:

- `/proc` for process/kernel views
- `/dev` for devices like `/dev/null`, `/dev/urandom`, TTY-ish paths
- `/sys` for system/device/kernel views some tools expect
- `/run` as volatile runtime state

Those are not normal persisted directories we want to copy from the image. They are live mounts. Creating them requires `mount(2)`, and inside a container that requires `CAP_SYS_ADMIN`.

So the sequence is:

1. ECS bind-mounts host storage at `/hermes-persistent-root`.
2. Runner copies image root there if empty.
3. Runner mounts `/proc`, `/dev`, `/sys`, `/run` under that root.
4. Runner `chroot`s into `/hermes-persistent-root`.
5. Runner drops `SYS_ADMIN` and starts Hermes.

## Assistant

Yes, that is the right V2 direction, with one correction: EFS should be the durable checkpoint store, not the live root filesystem. Keep EC2/EBS local root as the hot path, and use EFS for save/restore.

For V2 we need:

- **Local hot root:** same as V1, e.g. host path `/var/lib/devopshero/hermes-roots/{app_slug}` mounted as `/hermes-persistent-root`.
- **Durable checkpoint mount:** mount one EFS subdirectory into the task, e.g. `/hermes-checkpoint`, scoped per deployment/app.
- **Restore-on-empty:** runner starts, checks if `/hermes-persistent-root` is empty, and if so restores from `/hermes-checkpoint`.
- **Persist-on-termination:** runner traps `SIGTERM`, pauses/coordinates shutdown, checkpoints `/hermes-persistent-root` into `/hermes-checkpoint`, then exits.
- **Periodic or turn-boundary checkpoints:** relying only on termination is risky. ECS may kill after `stopTimeout`, the instance may die, or the process may crash. For SQLite WAL-backed state, we probably want explicit checkpoint moments too.
- **Locking / generation marker:** EFS needs metadata like `checkpoint.lock`, `generation`, `completed_at`, maybe `manifest.json`, so a second node never restores a half-written checkpoint.
- **Test proof:** create state on node A, force task placement on node B with empty local root, verify package install, SQLite state, and workspace artifact all restore.

The runner flow would be roughly:

```text
start:
  if local root empty:
    restore latest completed checkpoint from EFS
  else:
    use local root

run Hermes

on SIGTERM:
  stop accepting new work if possible
  sync/checkpoint local root to EFS atomically
  exit
```

The important design choice is atomicity. I would not rsync directly into the “latest” checkpoint directory. Safer shape:

```text
/hermes-checkpoint/
  current -> generations/000042
  generations/
    000041/
    000042/
    .incomplete-000043/
```

Write to a temp generation, fsync enough to be practical, then atomically flip `current` or write a small `manifest.json` last. Restore only from completed generations.

So: your EFS-subdirectory idea is right, but I’d phrase V2 as **local EBS hot runtime + EFS checkpoint/restore layer**, not “run from EFS.” That keeps package installs and SQLite fast while giving us node-move recovery.
