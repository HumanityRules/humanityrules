## Investigation: MCP Tool Failure Icon

### The Problem

When "Test Docker Build" fails, the custom template correctly shows "Build Failed" in red, but the **header icon** still shows the green checkmark. This is because the icon and the badge use different data sources.

### How It Works Today

The flow has two parallel status channels that don't agree:

1. **Header icon** — driven by `status`, which comes from `block.is_error` on the SDK's `ToolResultBlock`. Since the tool executes successfully (no exception), `is_error` is always `False`, so `status` is always `"success"`.

2. **Custom template badge** — driven by `custom_result_template_data.success`, which is parsed from the tool's actual response JSON. This correctly shows "Build Failed" when `success: false`.

### Root Cause (SDK gap)

The MCP protocol supports `isError: true` in tool results (for business logic failures), and the `@tool` decorator's docstring even documents this pattern:

```120:124:/Users/vmendi/websites/devopshero/.venv/lib/python3.14/site-packages/claude_agent_sdk/__init__.py
        >>> @tool("divide", "Divide two numbers", {"a": float, "b": float})
        ... async def divide(args):
        ...     if args["b"] == 0:
        ...         return {"content": [{"type": "text", "text": "Error: Division by zero"}], "is_error": True}
        ...     return {"content": [{"type": "text", "text": f"Result: {args['a'] / args['b']}"}]}
```

However, the SDK's internal `call_tool` function **strips** `is_error` and only returns the content list:

```303:304:/Users/vmendi/websites/devopshero/.venv/lib/python3.14/site-packages/claude_agent_sdk/__init__.py
            # Return just the content list - the decorator wraps it
            return content
```

So even though `query.py` checks for `is_error` downstream (line 491), it never sees `True` because the value is lost at line 304.

### Options

**Option A: Fix the SDK's `call_tool` to forward `is_error`**
- Patch the SDK to pass `is_error` through from the tool's return dict to the `CallToolResult`. This would make the documented `"is_error": True` pattern actually work.
- Pro: Fixes the root cause, all tools benefit automatically, matches MCP protocol semantics.
- Con: Requires modifying a vendored/third-party dependency. Could break on SDK updates.

**Option B: Override status in `_handle_tool_results` (agent_service.py)**
- After getting `block.is_error`, also parse the tool result content and check for a `success: false` field. Override `status = "error"` accordingly.
- Pro: Centralized in our code, handles all tools that follow the `success` convention.
- Con: Couples the agent service to a specific response shape convention. Adds parsing logic to the message handler.

**Option C: Override status in `_render_streaming_tool_result` (view layer)**
- In `chat.py`, after parsing the result, check `result_parsed` for a `success` field and override the `status` context variable before rendering.
- Pro: Only affects UI rendering, no impact on how Claude sees tool results. Clean separation.
- Con: Same convention coupling as B, but at the view level.

### My Recommendation

**Option A is the correct fix** — the SDK documents `is_error` but has a bug where it doesn't forward the value. Options B or C are reasonable workarounds if you don't want to touch the SDK.

If going with Option A, the fix in the SDK is minimal: change line ~303 from `return content` to also forward `is_error` from the result dict. Then update `_mcp_response` to accept an `is_error` parameter and include it when `True`.
