## Assistant

Both keep working — flipping `auth_provider` is not exclusive.

Here's what `auth_provider` actually gates: only the `/oidc/login/?org=<slug>` entrypoint. Look at `oidc_login` in `devopshero_app/views/auth.py:76-87` — it filters `auth_provider=OIDC`. That's the only place the field is checked.

**WorkOS login (`/auth/login/` → `/auth/callback`) is not org-scoped.** It authenticates via WorkOS globally and looks up the user by `workos_user_id` (auth.py:133). It never reads `Organization.auth_provider`. So your existing Humanity Rules WorkOS users (like `vmendi@gmail.com`) can still log in normally.

So after the flip:
- **Existing WorkOS users** (those with `workos_user_id` set) → keep using `/auth/login/`, unchanged.
- **New Okta users** (those with `oidc_sub` set) → use `/oidc/login/?org=humr`.
- They coexist in the same org, each authenticating through their own provider.

The only thing that *changes* for the org is that `/oidc/login/?org=humr` starts working.

One caveat: a *single* user can only have one identity at a time — `User.objects.get(oidc_sub=...)` and `User.objects.get(workos_user_id=...)` are separate lookups, and the model doesn't fall back from one to the other. If you want *your* account to work via both providers you'd have to attach both IDs to the same user row (and even then, each login path would only update its own fields).
