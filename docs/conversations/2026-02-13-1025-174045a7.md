## User

Sometimes I think that instead of an agent that tries to do too much, it'd be better to have a workflow with different stages, each one with clear inputs/outputs. Of course each of the stages can be driven by an agent.

---

## Assistant

That maps well to what you're already describing. The current flow is: user says "deploy my app" → agent does everything in one shot. The alternative is something like:

1. **Analyze** — agent scans repo, produces a structured app config (framework, port, dockerfile, dependencies)
2. **Generate** — agent produces CDK code + parameter file, commits to a branch, opens a PR
3. **Preview** — run `cdk diff`, present the changeset to the user for approval
4. **Execute** — `cdk deploy`, build and push image, start service
5. **Verify** — health checks pass, report the URL

Each stage has a defined input and output. Each can fail independently with a clear error. The user has natural approval points (after stage 2 and 3). And if stage 4 fails, you can re-run it without re-doing analysis and code generation.

The contrast with a pure agent loop: the agent decides on its own when to analyze, when to deploy, how to recover from errors, and the user's only control is typing messages into the chat. That works for simple cases but gets opaque for anything non-trivial.

The stages also solve a practical problem you have today — the deployment isn't reproducible because nothing is snapshotted. If stage 2 produces a concrete artifact (CDK code + config in a PR), that *is* the snapshot.

## Assistant

Good question. Going back to stage 1 would be wasteful — the analysis was correct, the CDK code is fine, the problem is specifically in the Dockerfile. You don't need to re-analyze the whole repo.

I think the failure handling depends on *what* failed, not a single "go back to step N" rule. A few scenarios:

- **Dockerfile build fails** — the CDK code and config are fine. The agent fixes the Dockerfile (or asks the user for help), pushes an updated commit to the same PR, and re-enters at stage 4 (execute). No need to regenerate infra code.

- **`cdk deploy` fails** — maybe a resource limit, a naming conflict, a permission issue. The agent fixes the CDK code or parameters, updates the PR, re-runs from stage 3 (preview) so the user can confirm the fix.

- **Health checks fail after deploy** — the infra is fine, the app is crashing. This is an app-level problem: wrong port, missing env var, startup error. The agent inspects ECS logs, suggests fixes to app code or configuration, updates the PR, re-runs from stage 4.

So rather than a single "Refine" stage, each stage has its own error-recovery loop that re-enters the pipeline at the appropriate point. The pipeline doesn't restart from scratch — it resumes from the earliest stage affected by the fix.

That said, you could model this as a "Diagnose" step that runs after any failure: inspect the error, classify it (infra/build/runtime), apply a fix, and route back to the right stage. That's where an agent is genuinely useful — the classification and fix require judgment that a rigid workflow can't provide.

## User

I just read about policies, policy packs, and policy groups. Is there an equivalent in the CDK? Is there a native AWS solution?

---

## Assistant

Pulumi CrossGuard lets you write rules ("no public S3 buckets"), bundle them into packs, and assign those packs to specific stacks. Rules run at preview time and can warn or block.

**CDK equivalent: Aspects + cdk-nag**

CDK Aspects traverse the construct tree at synth time and can validate or modify resources. You implement `IAspect`, visit each node, and call `Annotations.of(node).add_error()` to block synthesis. The library `cdk-nag` builds on this — it ships pre-built rule packs (AWS Solutions, HIPAA, NIST 800-53) that you attach with one line:

```python
Aspects.of(app).add(AwsSolutionsChecks())
```

This is close to Pulumi's model but scoped to synth time only, and there's no equivalent of policy *groups* (assigning different rule sets to different stacks from a central place).

**AWS native solutions (post-CDK):**

- **CloudFormation Guard** — policy-as-code that validates CloudFormation templates before deployment. Declarative rule language. Closest to Pulumi policies in spirit.
- **CloudFormation Hooks** — run custom validation before CF creates/updates/deletes resources. Preventive, but heavier to set up.
- **Service Control Policies (SCPs)** — organization-level guardrails that restrict what API calls accounts can make. Blunt instrument, not resource-property-level.
- **AWS Config Rules + Conformance Packs** — evaluate compliance *after* deployment. Reactive, not preventive.

For DOH's use case, the interesting angle is: if the agent generates CDK code and runs `cdk synth` before deploying, you could attach cdk-nag Aspects to enforce guardrails on what the agent produces. That's a safety net — the agent can't accidentally generate a public database or an overly permissive IAM role, regardless of what the user asked for.
