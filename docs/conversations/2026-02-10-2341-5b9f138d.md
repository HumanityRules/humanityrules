## Root Cause: psycopg3 Connection Pool Exhaustion + Main Thread Starvation

After tracing through the entire request lifecycle, I found a cascade that explains the exact symptom (site completely stuck, endpoints not replying):

### The Architecture

Your single Uvicorn worker runs **everything** in one process:
- Web server (sync views via `sync_to_async(thread_sensitive=True)` on a **single main thread**)
- SSE streaming (async generator on the event loop)
- Agent runner (async task on the event loop, ORM via main thread)
- Job worker polling thread (permanent daemon thread)
- Deployment execution threads (spawned per job, daemon threads)

### The Pool

`psycopg-pool==3.3.0` with `pool=True` (no explicit size) gives a **fixed pool of 4 connections** (`min_size=4, max_size=4`). CloudWatch confirms exactly 4 Aurora connections at steady state.

### The Bug: Job Worker Threads Leak Connections

Looking at `job_worker.py`, **none of the thread target functions call `connections.close_all()`**:

```102:107:devopshero_app/services/deployment/job_worker.py
def _run_app_deployment_thread(deployment_id: str) -> None:
    """Thread target that runs a single app deployment."""
    try:
        app_deployment_executor.run_deployment(deployment_id)
    except Exception:
        logger.exception(f"Unhandled error in app deployment {deployment_id}")
```

This means:
- The **worker polling thread** holds 1 connection permanently (polls every 1s, never exits)
- Each **deployment thread** holds 1 connection for the entire deployment duration (5+ minutes), and the connection isn't returned even after the thread exits (until GC)

### The Cascade

During an active deployment with a chat session:

1. **Pool**: 4 connections total
2. **Worker thread**: 1 connection (permanent) -- **leaked**
3. **Deployment thread**: 1 connection (5+ min) -- **leaked**
4. **Available**: 2 connections
5. **Main thread** (agent ORM + sync views): uses 1 -- leaving 1 spare

Now when the user navigates away from chat:
- Browser closes the SSE connection
- SSE generator's `finally` block runs `connections.close_all()` on the main thread, **returning its connection to the pool**
- The HTMX request for `/workspaces/` simultaneously queues on the main thread
- Agent runner's next ORM call also needs the main thread

If the agent runner's ORM call gets scheduled first and tries to check out a connection from the depleted pool (2 held by worker threads, 1 just returned but grabbed by another operation), it **blocks the main thread for up to 30 seconds** waiting for a pool connection.

**While the main thread is blocked, ALL sync views are queued and can't execute.** The site appears completely stuck.

The connection cleanup fixes the **root cause** (connections leaked by background threads reduce pool availability). The pool size increase adds **defense in depth** — even if timing is unlucky (a sync view needs a connection at the exact moment one is being cycled), the pool has headroom to create new connections instead of blocking for 30 seconds.
