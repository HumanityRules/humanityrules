---

## Assistant

`latest.tar.zst` is **not a copy** of anything in `snapshots/` — it's the live "current" snapshot. The relationship is the opposite: `snapshots/` holds the **previous** versions of `latest.tar.zst`.

**The EFS layout** (from the snapshotter's docstring):

```29:33:template_repos/doh_dind/snapshotter.py
EFS layout (under $PERSISTENCE_DIR):
    latest.tar.zst         # most recent good snapshot
    latest.meta.json       # base_image_ref, ts, fingerprint, container_id
    incoming.tar.zst       # in-flight write; atomic-renamed to latest on success
    snapshots/<ts>.tar.zst # rotated older snapshots (retention=3)
```

**Each snapshot cycle does this** (lines 167–177 in `snapshotter.py`):

1. Write the new snapshot to `incoming.tar.zst`.
2. Move (atomic) the *old* `latest.tar.zst` → `snapshots/<timestamp>.tar.zst`. **This is what populates `snapshots/`.**
3. Move (atomic) `incoming.tar.zst` → `latest.tar.zst`.

So `snapshots/` is a rolling archive of the last 3 generations of `latest.tar.zst`. Only `latest.tar.zst` is consulted at boot — `snapshots/` is never auto-restored.

**What `force_rebuild` is for:**

The restore path in `entrypoint.sh` is:

- If `latest.tar.zst` exists → `docker import` it as `doh-toolbox:latest` (carries forward all accumulated state — installed packages, npm caches, pip caches, etc., from previous Hermes sessions).
- Else → `docker pull $TOOL_IMAGE_BASE` (clean slate).

`force_rebuild` is the **operator escape hatch**: when the accumulated tool state has gone bad (broken venv, half-installed package, stale state after a `TOOL_IMAGE_BASE` bump), you want to force the next boot down the clean-pull path *without* SSH'ing into EFS to delete files.

By only removing `latest.tar.zst` + `latest.meta.json` and **keeping `snapshots/` intact**, you get:

- Next boot pulls fresh.
- If `force_rebuild` turns out to have been a mistake (e.g., the user actually wanted that state), an operator can manually copy `snapshots/<ts>.tar.zst` back to `latest.tar.zst` and recover.

The journal even calls this out explicitly:

```38:38:docs/journal.md
- **`DOH_SNAPSHOT_RESTORE=auto|skip|force_rebuild` env** on DinD — the operator escape hatch. `force_rebuild` also deletes `latest.tar.zst`. We picked this because we're deliberately deferring the "base-image rebase workflow" (what happens when `TOOL_IMAGE_BASE` gets bumped, security patches, etc.) until it becomes a real problem; this knob at least lets ops nuke a user's state without hand-editing EFS.
```

The other modes for context:
- `auto` (default) — restore if `latest.tar.zst` exists, else pull.
- `skip` — never restore, always pull. (Useful for one-off debugging without touching EFS.)
- `force_rebuild` — delete `latest.tar.zst`, then pull. **Persistent** until the next snapshot is taken, since the file is actually gone.

## User

but then, what's the difference with skip?

---

## Assistant

The runtime behavior of *this boot* is identical (both pull fresh and skip restore). The difference is **persistence and intent**:

**`skip` — one-shot, non-destructive**

- `latest.tar.zst` stays on EFS untouched.
- Just doesn't restore *this boot*.
- Remove the env var, restart the task → `auto` mode finds `latest.tar.zst` and restores it. **You can undo it by just rebooting normally.**
- Use case: "debug a boot in isolation without losing the user's accumulated state."

**`force_rebuild` — destructive, permanent**

- Deletes `latest.tar.zst` + `latest.meta.json` from EFS.
- Subsequent reboots can't go back to that snapshot — there is no `latest` to restore. The clean state sticks.
- Use case: "the user's accumulated state is genuinely broken; nuke it."

There's also a subtle second-order difference once the snapshotter starts writing again:

- Under `skip`: the snapshotter's first write sees the *old* `latest.tar.zst` still on disk and rotates it into `snapshots/<ts>.tar.zst` (preserved as one of the retained 3).
- Under `force_rebuild`: the old `latest.tar.zst` was already deleted outright, never rotated. It's gone. Recovery would require manually copying a `snapshots/<ts>.tar.zst` back to `latest.tar.zst` *before* a new snapshot pushes the rotation forward and ages it out of retention.

So: same boot behavior, but `skip` is a temporary override and `force_rebuild` is a commitment.

Done. 23 lines → 14 lines, same behavior. Quick walkthrough of why this still works correctly under `set -eu`:

1. **`if [ -s "$LATEST_SNAPSHOT" ] && zstd -dc ... | docker load; then`** — The whole `&&` chain is the test of an `if`, so `set -e` is suppressed inside it. If the snapshot doesn't exist, `[ -s ]` fails and the chain short-circuits to false → take the `else`. If the snapshot exists but is corrupt, `docker load` fails → also `else`.

2. **`[ -s "$LATEST_SNAPSHOT" ] && echo "WARN: ..."`** — POSIX rule: in an AND-OR list, `set -e` is ignored for "any command other than the last". If `[ -s ]` fails, the chain returns non-zero but doesn't trip `set -e` (this is the standard "do this if" idiom). So the WARN only prints when a snapshot existed and the load failed — the same nuance as before, just without a flag variable.

3. **The `if ! docker pull` / FATAL block** — left as-is. We could shorten it to a bare `docker pull "$TOOL_IMAGE_BASE"` and let `set -e` exit, but the explicit FATAL line is good operator signal that's worth the four extra lines.
