## Current State

The dockerfile generator is a sub-agent that receives repo analysis JSON, does focused validation reads, writes a `Dockerfile` to the repo root in `sandbox/conv-{id}/src/`, and reports the path back. It has `Write`, `Read`, `Glob`, `Grep` tools — but no `Bash`. There's no verification step: the main agent trusts the generated Dockerfile and passes it straight to `deploy_app`.

The gap is obvious: a generated Dockerfile could have syntax errors, reference wrong paths, fail to install dependencies, or produce a container that doesn't actually start. You only find out when the real deployment fails, which is a slow and expensive feedback loop.

## The Core Question

What does "testing the Dockerfile" mean here? There are a few levels:

1. **Build test** — Does `docker build` succeed? Catches syntax errors, missing files, bad `COPY` paths, wrong package names.
2. **Start test** — Does the built container actually start and stay running? Catches bad entrypoints, missing env vars, crash-on-boot issues.
3. **Health check** — Does the running container respond on the expected port? Catches binding to wrong address, app startup failures.

Each level adds confidence but also time and complexity.

## Approach: Add a `docker build` + smoke test step

The most practical approach for the agent flow:

- **Give the dockerfile generator (or a new verifier sub-agent) access to `Bash`** so it can run `docker build` inside the sandbox.
- **After writing the Dockerfile**, run `docker build -t test-{conv_id} .` from the repo root.
- **If the build fails**, the agent reads the error output and iterates — fixes the Dockerfile and retries (with a max retry count).
- **Optionally, run the container** briefly: `docker run --rm -d -p {random_port}:$PORT test-{conv_id}`, wait a few seconds, check if it's still running, and hit the health endpoint if one is known from the repo analysis.
- **Clean up** the test image/container after.

**Key trade-offs:**

- **Time**: A Docker build can take 30s-3min depending on the app. This adds latency to the agent flow. But it's way cheaper than failing at the real deployment stage.
- **Resources**: Needs Docker available in the agent's execution environment. Currently the sandbox runs locally, so Docker is available. In production (ECS), the agent container would need Docker-in-Docker or a sibling Docker socket.
- **Iteration loop**: The real power is letting the agent self-correct. If the build fails, the agent sees the error and fixes the Dockerfile — this is exactly what a human would do.
- **Scope**: Build-only testing catches ~80% of issues. The start/health check catches most of the rest but is harder (needs env vars, database connections might not exist, etc.).

## Questions to shape the design

A few things I'd want your input on:

- **Where in the flow?** Should the build test happen inside the `generate-dockerfile` sub-agent itself (give it Bash, let it iterate), or as a separate step/sub-agent after dockerfile generation?
- **How deep?** Build-only? Or also try to start the container? Starting is valuable but needs fake env vars and won't have real databases.
- **Retry budget**: How many fix attempts before giving up and surfacing the error to the user? 2-3 seems reasonable.
- **Production environment**: Is Docker available in the production agent execution environment (ECS), or is this local-only for now?

What's your thinking on these?

The two functions are nearly identical. The only differences are in the **build script** that gets sent over SSH:

**`run_remote_docker_build`** (the original — build + push):
- Takes `image_uri` parameter (e.g., `123456.dkr.ecr.us-east-1.amazonaws.com/doh/default/my-app:latest`)
- Script includes: ECR login → `docker build -t {image_uri}` → `docker push {image_uri}` → cleanup build dir

**`run_remote_docker_build_only`** (the new one — build only):
- No `image_uri` parameter
- Script includes: `docker build -t test-build:{build_id}` → cleanup build dir → `docker rmi test-build:{build_id}`

Everything else — keygen, EC2 Instance Connect key push, SSH options, SSH execution, output capture, success check — is 100% identical boilerplate.

The clean fix is to collapse them into one function with a `push` parameter (or `image_uri: str | None` where `None` means test-only). When `image_uri` is provided, the script does ECR login + build + push. When it's `None`, it builds with a throwaway tag and cleans up. One function, one SSH setup block, just a different build script.
