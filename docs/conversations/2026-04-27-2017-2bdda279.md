Practically, yes — it's designed for `FAILED` deployments, and that's how the help text describes it.

Looking at `_handle_retry_app_deployment` in `devopshero_app/management/commands/doh_control.py`:

```365:386:devopshero_app/management/commands/doh_control.py
        if deployment.status == models.Deployment.Status.PENDING:
            self.stdout.write(self.style.WARNING(f"Deployment is already pending"))
            return

        if deployment.status == models.Deployment.Status.SUCCEEDED:
            self.stderr.write(self.style.ERROR(f"Deployment already succeeded - nothing to retry"))
            return

        if deployment.status in [
            models.Deployment.Status.BUILDING,
            models.Deployment.Status.PUSHING,
            models.Deployment.Status.DEPLOYING,
            models.Deployment.Status.STARTING,
        ]:
            self.stderr.write(self.style.ERROR(f"Deployment is in progress ({deployment.status}) - cannot retry"))
            return

        deployment.status = models.Deployment.Status.PENDING
```

It explicitly bails out for:
- `PENDING` (already queued)
- `SUCCEEDED` (nothing to retry)
- `BUILDING` / `PUSHING` / `DEPLOYING` / `STARTING` (in progress)

Given the `Deployment.Status` choices, that leaves `FAILED` as the realistic target. `TEARDOWN_PENDING` would technically slip through the guards, but resurrecting a deployment that's queued for teardown isn't an intended use — the command is meant for failed deployments.

Note it also operates only on the **latest** deployment for the app (`order_by("-created_at").first()`), so if a newer deployment has already superseded the failed one, it'll act on the newer one.

### Where the current CLI command differs

The CLI **mutates the existing row** to PENDING. The UI **creates a brand new Deployment row** cloned from a source. That's the biggest semantic gap; everything else stems from it.

Concrete differences:

- **History.** UI preserves the failed/succeeded row and inserts a new one. CLI overwrites the existing row, so the prior outcome disappears from the deployment list.
- **`image_tag`.** UI computes a fresh `{slug}-{shortref}-{timestamp}` (avoids ECR cache hits and overwrite races). CLI keeps the old tag.
- **Source selection.** UI takes an explicit `deployment_id`. CLI picks `Deployment.objects.filter(app=app).order_by("-created_at").first()` — could be a deployment in any env, or a stale teardown row.
- **Allowed source statuses.** UI: `SUCCEEDED | FAILED | TORN_DOWN`. CLI today: anything that isn't PENDING / SUCCEEDED / IN_PROGRESS — i.e. accepts FAILED / TEARDOWN_PENDING / TEARING_DOWN / TORN_DOWN / ROLLED_BACK, and *rejects* SUCCEEDED.
- **In-progress guard.** UI checks "any deployment for this app in `IN_PROGRESS_STATUSES`". CLI only inspects the single latest row.
- **`PENDING_REMOVAL` guard.** UI refuses; CLI doesn't.
- **`created_by`.** UI sets `request.user`; CLI has no user context.
- **Blueprint/subdomain.** UI carries them from the source deployment; CLI doesn't touch them (irrelevant when mutating in place, required when creating a new row).

### What `redeploy-app` would look like

Mechanically straightforward — clone the UI logic and swap the inputs. Suggested shape:

```
uv run manage.py doh_control redeploy-app --app <slug> [--env <slug>] [--deployment <uuid>] [--created-by <username>]
```

- Source deployment selection: `--deployment` exact (mirrors the UI), else `--env` picks the latest `CONCLUDED` deployment in that env, else if the app has been deployed to exactly one env, use that; otherwise error out and demand `--env`.
- Reject if `app.status == PENDING_REMOVAL`.
- Reject if any deployment for the app is in `IN_PROGRESS_STATUSES`.
- Reject if source status not in `(SUCCEEDED, FAILED, TORN_DOWN)`.
- Create a new `Deployment` row, cloning `blueprint`, `environment`, `subdomain`, `git_ref` (with `app.branch` fallback), fresh `image_tag`, `status=PENDING`, `status_message="Redeploy triggered via CLI"`.
- Accept `--created-by` for attribution (same convention `deploy-app-template` already uses); leave nullable if omitted.

### Caveats

- **No ABAC.** Consistent with the rest of `doh_control` — operator-level command, no workspace:edit check.
- **Naming.** "Redeploy" implies SUCCEEDED is a valid source (it is, in the UI). The current `retry-app-deployment` explicitly *rejects* SUCCEEDED. The rename is the right move because the new behavior is a strict superset that no longer matches "retry a failed deployment".
- **Behavior change for existing callers.** Anything currently invoking `retry-app-deployment` and relying on in-place mutation (e.g. expecting the UUID of the failed deployment to be the one re-run) would see a new UUID instead. Worth grepping the journal/scripts before flipping.

### What `retry-env-provisioning` actually does today

```213:225:devopshero_app/management/commands/doh_control.py
        if env.status == models.Environment.Status.PENDING:
            self.stdout.write(self.style.WARNING(f"Environment '{slug}' is already pending"))
            return

        if env.status == models.Environment.Status.PROVISIONING:
            self.stderr.write(self.style.ERROR(f"Environment '{slug}' is already being provisioned"))
            return

        # Set to pending
        old_status = env.status
        env.status = models.Environment.Status.PENDING
        env.status_message = f"Retry triggered (was: {old_status})"
```

That's it. It blocks `PENDING` and `PROVISIONING` and flips everything else to `PENDING`. The journal was being polite when it said "refuses to re-run against successful/ready targets" — it actually *will* re-run a `READY` env today; what it lies about is the name.

The implementation has three latent problems:

- **Name lies** — operators reading `retry-env-provisioning` reasonably assume it's only for failure recovery. They then either don't use it for the most common operational case (re-converge a `READY` env) or doubt it's the right tool.
- **Accepts dangerous states** — `TEARDOWN_PENDING`, `TEARING_DOWN`, and `DISCARDED` all fall through and get flipped to `PENDING`. Flipping `TEARING_DOWN → PENDING` is a real footgun: now you have the teardown executor and the provisioning executor racing on the same CFN stack.
- **`DISCARDED` accepted** — this status means "abandoned setup draft". Re-provisioning it makes no semantic sense.

### What the closest UI/agent equivalent looks like

There's **no UI "Redeploy" button for environments** — I checked `views/environments.py`. The post-failure recovery path is the agent: `Environment.Status.ERROR` keeps the env in `SETUP_EDITOR_STATUSES`, the user resumes the editor, and the AI calls the `provision_environment` tool:

```63:85:devopshero_app/services/agent/tools/provision_environment.py
    if environment.status == models.Environment.Status.READY:
        raise ValueError(
            f"Environment '{environment.name}' is already ready. "
            "Use it directly for deployments."
        )

    if environment.status == models.Environment.Status.PROVISIONING:
        raise ValueError(...)

    if environment.status == models.Environment.Status.PENDING:
        raise ValueError(...)

    if environment.status not in (models.Environment.Status.DRAFT, models.Environment.Status.ERROR):
        raise ValueError(
            f"Environment '{environment.name}' is in '{environment.status}' state and cannot be provisioned. "
            "Only draft or error environments can be queued."
        )
```

The agent tool's contract: `DRAFT` or `ERROR` only. `READY` is a hard refusal.

### Why this is *not* a clean mirror of the redeploy-app rename

For apps, "redeploy a SUCCEEDED deployment" is a normal, expected operator action — you changed the code, push it again. The UI's Redeploy button accepts `SUCCEEDED` for exactly that reason.

For environments, the analog is "re-converge a READY env". And here the agent tool *deliberately* refuses it. The reasoning, charitably reconstructed: env provisioning is CloudFormation; re-running CDK against a converged stack is normally a no-op, but if the CDK code has changed since the env was first provisioned, the operator can get an unintended changeset. The agent tool errs on the side of "if you want to change a READY env, use a separate flow". There isn't a separate flow today, but that's the design intent.

So the operator's "I need to re-run CFN on this env" use case is currently served *only* by the CLI, deliberately. Which means the CLI shouldn't be a strict mirror of the agent tool — it's the SRE escape hatch.

### What I'd actually recommend

**Rename to `redeploy-env`** and tighten the guards, but keep the operator-friendly looser source-status set.

- **Allow:** `DRAFT`, `ERROR`, `READY`
- **Soft-block (warn no-op):** `PENDING` (already queued)
- **Hard-block:** `PROVISIONING`, `TEARDOWN_PENDING`, `TEARING_DOWN`, `DISCARDED`

Net effect:

- `READY` stays accepted, matching today's de-facto behavior and the operator's actual need.
- The dangerous `TEARDOWN_PENDING` / `TEARING_DOWN` / `DISCARDED` paths get blocked. This is the silent bug fix.
- Name matches mental model. Same parallelism as `redeploy-app`.

What it costs: nothing meaningful. Two journal entries reference `retry-env-provisioning` (this morning's DinD entry mentions it as "rename deferred"; an old 2026-02-03 entry references the rename history). The skill docs (`prod-manage`) have an example to update — single line. No UI/API/agent code calls this command.

What I'd *not* fold in:

- **No `--created-by`.** Environments don't carry deploy attribution like Deployments do. The status_message line ("`Redeploy triggered (was: {old})`") is enough audit trail; matches the existing pattern.
- **No `--force` to override the new hard-blocks.** If you're tearing down an env you don't get to "actually I changed my mind, provision it"; the right path is to wait for teardown to finish or land in `ERROR`, then redeploy.

### One question worth flagging

The agent tool refusing `READY` is suspicious — either:

1. It's an intentional design decision and the CLI should match (i.e. `redeploy-env` should *not* allow `READY`, and operators wanting to re-converge should use a future "drift-fix" command), or
2. It's a leftover from when the agent flow was the only flow and "you wouldn't redeploy a working env via chat" was the assumption.

I'd guess (2). If you confirm, I'd also tighten the agent tool to match the new CLI semantics — but that's a separate change, and probably wants a quick sanity check with whoever owns the agent tool contract.
