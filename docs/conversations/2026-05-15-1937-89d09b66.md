# Debug Customer App Deployments

For investigating issues with apps deployed into customer AWS accounts — ECS task crashes, deployment failures, container errors, CloudFormation stack issues.

**Localhost by default.** Unless the user explicitly says "in production," assume the DOH control plane is running locally and the customer exists in the local DB:

- **Localhost:** `uv run manage.py <command> ...` — queries the local DB, uses credentials from `.env`
- **Production:** `cd infra_devopshero && ./prod_manage.sh <command> ...` — runs the same command on the production ECS container, queries the production DB

All commands below work identically in both modes — just swap the prefix.

Customer accounts are accessed via IAM role assumption. The `.env` file in the project root has `DOH_AWS_ACCESS_KEY` and `DOH_AWS_SECRET_KEY` — these are DOH's control plane IAM credentials, loaded into `django.conf.settings`. They're used to STS-assume `arn:aws:iam::{account_id}:role/devopshero-{external_id}` in the customer account. All management commands handle this internally via `iam_utils.get_assumed_role_session()`. The `account_id` and `external_id` come from the `AWSAccount` model in the DB.


## Step 1: Gather Context from the DB

Always start by querying the DB with `doh_query` (see the `manage-commands` skill) to understand what you're dealing with. Key models: `AWSAccount` (get `aws_account_id` and `external_id`), `Environment` (get `slug` and `aws_region`), `App`, `Deployment`, `DeploymentLog`.


## Step 2: Access the Customer's AWS Account

Check the `manage-commands` skill first — commands like `doh_app_shell`, `doh_app_exec`, `doh_app_logs`, and `doh_efs_browse` handle the assume-role dance internally.

For non-interactive probes, use `doh_app_exec` (stdin script, structured output, `--as <user>`):

## Command Reference

- **doh_query** — Ad-hoc model queries (fields, filters, ordering). Use instead of `shell -c`.
- **doh_control** — Control plane ops: provision/teardown environments; deploy from AppTemplate (`deploy-app-template`), redeploy, teardown, and remove apps (`teardown-app --remove-app` for full cleanup including secrets/persistent-data/policies).
- **doh_efs_browse** — Browse EFS filesystem via ECS Exec (interactive shell in customer environment).
- **doh_app_logs** — Fetch CloudWatch logs for a customer app (works for running and crashed/stopped tasks), by account + env + app slug.
- **doh_app_shell** — Interactive shell in a deployed customer app *container* (ECS Exec / SSM). For humans.
- **doh_app_exec** — Non-interactive script execution in a customer app *container*. Script on stdin or `--script-file`; supports `--as USER`, `--timeout`, `--cwd`, `--set KEY=VALUE`, `--format json`. Prefer over `doh_app_shell --command` for scripted probes.
- **doh_node_shell** — Interactive shell on the customer EC2 *host* (container instance) via SSM Session Manager. Use for host-level inspection — kernel, Docker/containerd, host bind-mount dirs (e.g. `/var/lib/devopshero/hermes-roots/`), disk space. Not for container internals (use `doh_app_shell`). Supports `--list` (inventory of instances + tasks), `--app <slug>` (auto-pick the instance running an app), `--instance-id <id>`.
- **doh_secrets** — Manage customer Secrets Manager secrets: list, purge, and shared environment secrets (shared-list/shared-set/shared-delete). All subcommands take --account and optional --org (name or slug).
- **doh_reset_org_abac** — Full factory reset of ABAC Policy rows for one organization (`--org` slug or name; optional `--admin-email`). Deletes all org policies, re-runs seed bootstrap, recreates default per-app open-access policies.
- **run_job_worker** — Background job worker for deployments and environment provisioning.
- **seed_test_apps** — Seed orgs, workspaces, environments, and apps for UI testing.
- **seed_test_groups** — Seed test groups with attributes for ABAC testing.
- **seed_test_users** — Seed test users with group memberships.
- **seed_local_repos** — Scan local directory and create Repository records.
- **setup_oidc_org** — Create/update an organization with OIDC (Okta) auth config.
- **ensure_superuser** — Create or promote a user to superuser.

## Issue 2: Slow load — possible solutions

In rough order of effort vs. payoff:

1. **Lazy-load logo images.** Add `loading="lazy"` (and `decoding="async"`) to `<img class="doh-integration-logo">`. Today the browser eagerly fetches ~150 logos when the page renders. One-line change.

2. **Render skeleton first, swap in real data.** On rail click, immediately show ~10 placeholder rows; replace with real cards once `/__doh_broker/integrations` returns. Improves *perceived* latency without changing the actual data path.

3. **Pre-fetch on page load.** Kick off `fetchIntegrations()` from `init()` so the response is already in `_current` by the time the user clicks Integrations. Cuts the round-trip out of the click latency. Cost: one extra request per session, even if the user never opens the page.

4. **In-broker caching of the connector list.** The broker likely re-hits Merge.dev for the connector catalog on each request. Cache the catalog (it changes rarely) for N minutes in the broker process. Eliminates network for repeat visits.

5. **Search/filter UI instead of full list.** Render a search box and only render cards that match (or the first ~20 by default). 150 cards becomes ~20 cards in the initial paint. Best long-term UX since 150 is unwieldy regardless.

6. **Group by category, lazy-render groups.** "CRM (12) ▶", "ATS (8) ▶" — render category headers immediately, render cards on expand. Same DOM-cost saving as filter, different UX.

7. **Virtualize the list.** Only render cards visible in viewport; mount/unmount as user scrolls. IntersectionObserver-based. Worth it only if the DOM cost (not the network) dominates.

8. **Persist cache in localStorage with a TTL.** Save last response in localStorage; render from cache instantly, then revalidate in the background. Kills latency for repeat sessions.

9. **Build cards off-screen in a `DocumentFragment`.** Already effectively what my code does (we append to a detached `list` node before attaching), so this is mostly a no-op unless we're appending one-by-one elsewhere. Not worth pursuing alone.

10. **Measure first.** Add a `performance.now()` around (a) `fetch()` and (b) the render loop, log to console. Spend effort on whichever is the actual bottleneck. The shape of the fix (network vs. DOM) hinges on this.

My recommendation: **#10 (measure)** → **#1 (lazy-load images)** → **#3 (pre-fetch) or #4 (broker cache)** depending on what #10 tells us. If the network is fast and 150 cards is just a lot of DOM, jump to **#5 (filter UI)**.
