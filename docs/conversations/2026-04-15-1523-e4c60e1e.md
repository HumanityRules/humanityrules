## Analysis: What Went Wrong and What's Missing

### The core confusion: Two planes, no map

DOH operates across two distinct AWS planes, and the documentation never states this explicitly:

1. **DOH's control plane** — DOH's own AWS account where the platform runs (ECS cluster `doh-prod-cluster`, etc.)
2. **Customer accounts** — AWS accounts where customer apps get deployed (e.g., "Humanity Rules Sandbox")

The `prod-debug` skill covers plane 1. Nothing covers plane 2 from a debugging perspective. When you said "hermes-vmendi01 is crashing in Humanity Rules Sandbox," the agent likely matched on "crashing" + "ECS" and gravitated toward `prod-debug`, which is entirely the wrong plane.

### Gap 1: No "localhost by default" convention stated anywhere

Your rule is simple: unless I explicitly say "in production", I mean localhost. This means `uv run manage.py doh_query ...` for DB queries, not `prod_manage.sh`. This convention isn't in `AGENTS.md` or any skill.

### Gap 2: No customer-account debugging skill

The existing skills cover:
- **manage-commands** — what commands exist (catalog)
- **prod-debug** — DOH's own infra (wrong plane)
- **prod-manage** — running commands on DOH prod ECS (wrong plane)

Nobody tells the agent: "To debug a customer app, query the local DB for context, then access the customer's AWS account via the assumed-role pattern in `iam_utils`."

### Gap 3: The assumed-role pattern is only visible in code

The cross-account access pattern is clear in `iam_utils.get_assumed_role_session()` and used by `doh_raw`, `doh_app_shell`, and `doh_efs_browse`. But there's no skill-level explanation that says: "DOH credentials in `.env` -> STS AssumeRole -> customer account session." An agent that doesn't know this has to read source code to figure it out, which is exactly what happened.

### Gap 4: No management command for customer ECS logs

This is the tooling gap. When a customer app task is **crashing**, you can't `doh_app_shell` into it because it's not running. You need to check CloudWatch logs for the stopped task. Today that requires manually:
1. Looking up the account, environment, and app in the DB
2. Assuming the customer role
3. Knowing the log group naming convention
4. Finding the right log stream
5. Fetching the log events

There's no `doh_app_logs` equivalent of `doh_app_shell`.

### Gap 5: "Humanity Rules Sandbox" isn't documented as the go-to test account

The agent has no context that "Humanity Rules Sandbox" is your standard sandbox customer account used for both local and production testing. It's just a row in the DB with no special documentation.
