Here's the versioning story for the Hermes template:

**Two independently-versioned pieces**

The template bakes together two codebases owned by different upstreams:

- **Hermes WebUI** (`ghcr.io/nesquena/hermes-webui:0.50.87`) — the server binary from `nesquena/hermes-webui`. This is pinned in the `Dockerfile` `FROM` line and ships as the base image.
- **Hermes Agent** (`NousResearch/hermes-agent`) — the agent framework itself. We `git clone --depth 1` from GitHub at image-build time into `/opt/hermes-defaults/hermes-agent`. No tag, no pin — whatever `HEAD` of the default branch is when the image is built is what gets frozen into that image.

**Why they're split**

They have different lifecycles on the customer side:

- The **WebUI** lives in the ephemeral container filesystem (from the base image). Bumping it = new base image tag → rebuild → redeploy each customer app. No auto-rollout; it's manual per deployment (README §"How to bump the WebUI base image").
- The **agent framework** lives on **EFS** at `/home/hermeswebui/.hermes/hermes-agent`. The entrypoint seeds it from `/opt/hermes-defaults/hermes-agent` only on first boot (`if [ ! -d … ]`). After that, the EFS copy is authoritative — image rebuilds don't touch it. Users update it in-place with the built-in `hermes update` command, which DOH does not invoke automatically (README §"Updating hermes").

**Knock-on effects**

- The agent-framework pin is implicit and not reproducible — two builds of the same Dockerfile on different days ship different agent code. If that matters, you'd need to pin to a tag/SHA in the `git clone` line.
- Patches in `template_repos/hermes_agent/patches/` are re-applied on **every** boot by `entrypoint.sh` against the EFS copy of hermes-agent. This is deliberate: it lets a new image roll fixes onto already-deployed EFS volumes, and makes them idempotent no-ops once upstream absorbs them (`personal_assistant_deployment_state.md:13`, `entrypoint.sh:78-84`).
- On a first boot today you get: pinned WebUI 0.50.87 + whatever `hermes-agent` `HEAD` was at image build, with patches applied on top. On a later boot of the same app after a WebUI bump redeploy, you get: new WebUI + the **original** EFS agent code (unless the user ran `hermes update`), with the *new* image's patches applied to it.

## Assistant

Yes, I'd pin it — the current `git clone --depth 1` with no ref means image builds aren't reproducible (two builds days apart ship different agent code, and the patches in `patches/` are written against specific upstream line numbers, so silent drift can break them). Pinning to a tag or SHA in the Dockerfile costs nothing and makes the WebUI/agent pair explicit.

The tradeoff: you take on a manual bump cadence for `hermes-agent` (like you already have for `hermes-webui`), and you lose the "free" upstream fixes that currently land whenever you rebuild. Given that the patch system is explicitly designed to absorb upstream changes idempotently, that trade seems worth it — but it does mean someone has to periodically bump the pin and re-check the patches.
