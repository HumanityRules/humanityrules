## The Problem

When debugging agent conversations, the pain points are:

1. **Conversations always start from zero** — if a failure happens at turn 15, you re-run turns 1-14 (expensive in tokens and time, and non-deterministic so you might not even reproduce the path)
2. **Iterating on prompts/tools requires full reruns** — changing a system prompt or fixing a tool means starting over
3. **The existing fork mechanism is CLI-only and end-of-conversation only** — the `test_main_agent.py` fork copies `session_id` and passes `fork_session=True` to the Claude SDK, but always branches from the *last* message

## What You Already Have

The building blocks are solid:

- **All messages persisted** in the DB with full tool call params + results in `Message.metadata`
- **Claude SDK session files** stored as `.jsonl` at `~/.claude/projects/{slug}/{session_id}.jsonl` — these contain the complete conversation history
- **`fork_session` flag** already wired through `_create_agent_options` -> SDK — the SDK natively supports branching a session into a new session ID
- **`test_main_agent.py`** already demonstrates the fork pattern:

## Debugging Scenarios to Design For

Before picking a solution, here are the concrete scenarios I see:

- **S1 — Tool broke, fix and retry**: A tool call at turn 12 raised an error. You fix the tool code. You want to retry from turn 11 (the user message that triggered the tool call).
- **S2 — Bad agent decision, steer differently**: The agent went down a wrong path at turn 8. You want to fork from turn 7 and give a different user message to steer it.
- **S3 — Iterating on system prompt**: You're tweaking the system prompt. You want to re-run the exact same user messages but with the new prompt. (This is more "replay" than "fork".)
- **S4 — Quick retry from the end**: The last turn failed or was unsatisfying. Fork from the end with a corrected message. (This is what the CLI already does.)

## Solution Ideas

### Idea 1: Mid-Conversation Fork via Session File Truncation

The Claude SDK stores sessions as `.jsonl` files. The idea:

1. Add a **"Fork from here"** action on any message in the UI (or CLI)
2. Backend reads the source conversation's session `.jsonl` file
3. Truncate it to the corresponding turn (need a mapping between DB `Message` sequence and `.jsonl` line numbers — could use timestamps or content matching)
4. Write the truncated content as a new session file
5. Create a new `Conversation` with `session_id` pointing to the truncated session
6. Copy DB `Message` records 1..N to the new conversation
7. Use `fork_session=True` on the next `stream_response` call

**Pros**: True mid-conversation branching. The agent sees exactly the history up to that point. Deterministic.
**Cons**: Couples to Claude SDK's `.jsonl` format (fragile if they change it). Need to figure out the DB-to-session-line mapping. Sandbox filesystem state won't match (repo modifications made by the agent are lost).

### Idea 2: Synthetic History Injection (No Session File Manipulation)

Instead of truncating session files, start a fresh session but pre-load context:

1. Fork creates a new conversation with **no** `session_id` (fresh)
2. Build a "conversation history summary" from DB messages 1..N
3. Inject this as a system prompt prefix: "You're continuing a prior conversation. Here's what happened..."
4. Or better: use the Claude SDK's message history format to pre-seed the conversation with alternating user/assistant messages from the DB

**Pros**: Doesn't depend on SDK internals. Works even if session files are lost. Portable.
**Cons**: Token-expensive (re-sending all the history). May lose nuances that were in the original session but not in the DB (e.g., partial tool call context, thinking blocks). The agent might behave slightly differently because it's a "retold" history rather than its own memory.

### Idea 3: Checkpoint-Based Snapshots

A more robust version — periodically snapshot conversation state:

1. After each agent turn, save a "checkpoint" — the `session_id` + a turn number + sandbox filesystem hash/tarball
2. To fork from turn N, restore the checkpoint closest to N
3. Create a new conversation with the checkpoint's `session_id`, use `fork_session=True`
4. Optionally restore the sandbox filesystem from the tarball

**Pros**: Most complete — restores both LLM state and filesystem state. Fast to fork from any point.
**Cons**: Storage cost for filesystem snapshots. Implementation complexity. Overkill for early-stage debugging.

### Idea 4: Pragmatic Middle Ground (Recommended)

Combine the simplest parts of the above:

1. **Fork from end** (already works) — surface it in the UI with a "Fork" button on the conversation
2. **Fork from message N** via session truncation — invest in understanding the `.jsonl` format once. It's probably just one JSON object per line with `role`, `content`, etc. Truncation is just "keep lines 1..M"
3. **Don't bother with filesystem snapshots** — just re-clone the repo fresh. For most debugging scenarios, the agent's repo modifications are part of the problem, not part of the solution
4. **Add a "Replay" mode for S3** — a separate concept: take an existing conversation's user messages and replay them against a new system prompt. No forking needed, just a loop that sends messages one by one

## Data Model Additions

Minimal additions to support this:

- **`Conversation.forked_from`** — nullable FK to source conversation (for traceability)
- **`Conversation.forked_at_message`** — nullable FK to the `Message` at which the fork occurred
- **`Message.turn_number`** — integer, auto-incremented per conversation, to make ordering/truncation explicit (currently relying on `created_at` ordering)

## Session File Format Investigation

Before committing to Idea 1 or 4, we'd need to inspect the actual `.jsonl` format to confirm truncation is straightforward. The files live at `~/.claude/projects/.../{session_id}.jsonl`. If each line is a self-contained message with a clear role/turn marker, truncation is trivial. If there's complex interleaved state, it gets harder.

## What I'd Suggest Starting With

Given the current stage, I'd go with **Idea 4** in phases:

- **Phase 1**: Add fork-from-end to the web UI. This is low-hanging fruit — the mechanism exists in the CLI, just wire it up to a button. Immediately useful for S4.
- **Phase 2**: Investigate the `.jsonl` format and implement fork-from-message-N. This unlocks S1 and S2.
- **Phase 3** (if needed): Add a "Replay with different prompt" mode for S3.

## User

When forking a conversation, we get a new session_id?

---

## Assistant

Yes. When `fork_session=True` is passed to the SDK:

1. It reads the source session file (`f4bb1b1a...`) to load the full conversation history
2. It creates a **new** session with a fresh UUID (`22334904...`) that branches from that history
3. The new session ID is returned in the `ResultMessage` and saved to `conversation.session_id`

You can see both files in the forked conversation's project directory — the copied source (`f4bb1b1a...jsonl`, 30KB) and the newly created fork (`22334904...jsonl`, 29KB). The source copy is just there so the CLI can find it during initialization; from that point on, only the new session is used.

## User

and in our code, we also create a new Conversation with its new id, which we use for the cwd, correct?

---

## Assistant

Correct. The `chat_fork` view creates a new `Conversation` with a fresh UUID. Then when `stream_response` runs, it calls `get_sandbox_paths(conversation.id)` which gives it `sandbox/conv-{NEW_ID}/src/` as the `cwd`. That new path is what the SDK uses for the project directory, and it's where the new session file ends up living.

So the full mapping per conversation is:

- **Conversation ID** (Django) → **sandbox path** (filesystem) → **project directory** (Claude CLI) → **session file** (`.jsonl`)
- `019c39b7...` → `sandbox/conv-019c39b7.../src/` → `~/.claude/projects/-...-conv-019c39b7...-src/` → `f4bb1b1a....jsonl`
- `019c39db...` → `sandbox/conv-019c39db.../src/` → `~/.claude/projects/-...-conv-019c39db...-src/` → `22334904....jsonl`

Each conversation gets its own isolated sandbox, its own project directory, and its own session file. The fork just seeds the new one from the source's history.
