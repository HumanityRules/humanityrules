**Root Cause Found: Background Thread Connection Leak**

## The Problem

The **job worker** background thread is leaking database connections:

```python
# job_worker.py - polls every 1 second
def _worker_loop() -> None:
    while not _stop_flag.is_set():
        deployment = _claim_pending_deployment()  # Opens DB connection
        environment = _claim_pending_environment()  # Opens DB connection  
        teardown = _claim_pending_teardown()  # Opens DB connection
        _stop_flag.wait(timeout=1.0)  # Sleep 1 second, connections stay open
```

## Why Connections Accumulate

1. **Django's `conn_max_age=0`** closes connections after each HTTP request via the `request_finished` signal
2. **Background threads never fire that signal** — they bypass Django's request/response cycle
3. **Each poll creates new connections** that are never closed
4. **Connections pile up** — 3 queries × 1 poll/second = ~180 connections/minute if not reused

Additionally, when connections fail (as we saw in logs), the worker catches the exception and retries immediately, creating even more connection attempts.

## The Fix

Add `close_old_connections()` to the worker loop:

```python
from django.db import close_old_connections

def _worker_loop() -> None:
    while not _stop_flag.is_set():
        try:
            deployment = _claim_pending_deployment()
            # ... spawn threads ...
        except Exception:
            logger.exception("Error in worker loop")
        finally:
            close_old_connections()  # <-- FIX: Close connections after each poll
        
        _stop_flag.wait(timeout=1.0)
```

Also need to close connections in the spawned threads (`_run_deployment_thread`, etc.) since they run in separate threads too.

## Assistant

Django's connection cleanup is tied to HTTP request handling:

```python
# django/core/handlers/base.py (simplified)
class BaseHandler:
    def get_response(self, request):
        response = self._middleware_chain(request)
        return response

# django/core/handlers/wsgi.py  
class WSGIHandler(BaseHandler):
    def __call__(self, environ, start_response):
        request = WSGIRequest(environ)
        response = self.get_response(request)
        
        # THIS is when connections get closed
        signals.request_finished.send(sender=self.__class__)  
        
        return response
```

The `request_finished` signal triggers `django.db.close_old_connections()`:

```python
# django/db/__init__.py
from django.core.signals import request_finished
request_finished.connect(close_old_connections)
```

**Background threads bypass this entirely:**

```
HTTP Request Flow:
  Browser → WSGI/ASGI Handler → View → Response → request_finished signal → close_old_connections()
                                                          ↑
                                                   Connections closed here

Background Thread Flow:
  threading.Thread(target=_worker_loop).start()
  → _worker_loop() runs queries
  → No HTTP handler involved
  → No signal fired
  → Connections never closed ❌
```

The job worker is just a plain Python thread — it never touches Django's HTTP machinery. Django has no way to know when your thread is "done with a request" because there *is* no request.

This is a known Django pattern issue. The official solution is to manually call `close_old_connections()` in long-running threads, which is exactly what we need to add.

```python
# django/db/utils.py (simplified)
import threading

class ConnectionHandler:
    def __init__(self):
        self._connections = threading.local()  # Thread-local storage
    
    def __getitem__(self, alias):
        # Check if this thread already has a connection
        if hasattr(self._connections, alias):
            return getattr(self._connections, alias)
        
        # No connection for this thread yet - create one
        conn = self.create_connection(alias)
        setattr(self._connections, alias, conn)  # Store it for reuse
        return conn

connections = ConnectionHandler()
```

**The connection IS being reused within the same thread** — that's the design. Django caches it in `threading.local()` so subsequent queries don't reconnect.

The problem is:

```python

Thread starts

  → Query 2: Django reuses same connection ✓
  → Query 3: Django reuses same connection ✓
  → ... thread keeps running forever ...
```

1. The thread dies (thread-local storage is cleared)
2. Someone calls `close_old_connections()` (removes from thread-local)

**Django's automatic connection management:**

```python
    for conn in connections.all():
        # Close if: max_age exceeded OR max_age=0 OR connection is broken
        if conn.connection is not None:
            if conn.get_autocommit():  # Not in a transaction
                conn.close_if_unusable_or_obsolete()
```

With `CONN_MAX_AGE=0`, it closes the connection after every request.

**The problem with async/ASGI:**

In sync WSGI:
```
Request starts → request_started signal → View runs → Response sent → request_finished signal → close_old_connections()
```

In async ASGI, **the signal fires, but there's a threading issue:**

```python
# The connection is stored in thread-local storage
connections._connections = threading.local()

# In async, your code might run across different threads/contexts
# Thread A: Opens connection, stores in thread-local
# Thread B: request_finished fires, but sees different thread-local storage
# Result: Connection in Thread A is never closed
```

**So the question is:** Is Django's async ORM properly handling this, or is there a bug?

Let me check how Django 6.0 handles async connections:

---

## Assistant

The search results clarify the issue:

> "Django's connection management relies on **thread-local storage** for maintaining database connections per request. In ASGI environments with async handling, this model breaks down because **async operations don't map directly to OS-level threads**."

Here's the fundamental problem:

**Sync Django (WSGI):**
```
Thread 1:
  → Request starts
  → Opens connection, stores in Thread 1's thread-local storage
  → View runs
  → Response sent
  → request_finished signal fires in Thread 1
  → close_old_connections() finds the connection in Thread 1's storage
  → Connection closed ✓
```

**Async Django (ASGI):**
```
Event Loop (single thread, but many coroutines):
  → Coroutine A: Request starts
  → Coroutine A: Opens connection, stores in... where exactly?
  → Coroutine A: awaits something, yields control
  → Coroutine B: Runs while A waits
  → Coroutine A: Resumes, finishes
  → request_finished signal fires
  → close_old_connections() runs... but which connection does it see?
```

The issue is that **async coroutines share the same thread** but conceptually are separate "requests". Django's thread-local storage can't distinguish between them properly.

So `close_old_connections()` might:
1. Close the wrong connection (Coroutine B's instead of A's)
2. Not find the connection at all (if the storage context changed)
3. Leave connections orphaned

**This is why the Django docs say:**
> "Persistent connections should be disabled when using ASGI. The CONN_MAX_AGE setting does not work properly with ASGI."

But even with `CONN_MAX_AGE=0`, the cleanup mechanism itself is broken because it relies on thread-local storage that doesn't map to async coroutines.
