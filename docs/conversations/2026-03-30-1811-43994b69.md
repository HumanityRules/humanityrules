## Assistant

Good question. Here's what I found after digging through the code.

**Current state:** The app detail page has a "Deployed to Environments" section that renders one row per active `DeploymentBlueprint` (via `_app_blueprint_row.html`), but those rows only show environment name, account/region, git ref, service URL, status, and actions. The datastore, env vars, and secrets fields on `DeploymentBlueprint` are not surfaced anywhere on this page — they're only rendered in the deployment editor (`_blueprint_section.html`).

The key design tension is that each environment's blueprint can have **different** values for these fields. An app deployed to `staging` and `production` might have completely different env vars, secrets, and even datastores. So the rendering approach matters. Here are the options:

---

**Option A — Expandable rows (accordion).** Each row in the existing "Deployed to Environments" table gets a disclosure toggle. Clicking it reveals the datastore, env vars, and secrets for that blueprint inline, below the row. Minimal layout disruption; you only see config when you ask for it.

**Option B — Tabs per environment.** Add a new "Configuration" section below the current cards. It has one tab per deployed environment (`staging | production | ...`). Each tab shows the full blueprint config: env vars, secrets, datastore. Good for focused inspection of one environment at a time.

**Option C — Unified/diff view.** A single table that merges all env vars and secrets across all environments, with columns per environment. Values that differ across environments are visually highlighted. Great for cross-environment comparison ("why does staging have `DEBUG=true` but production doesn't?"), but more complex to build and can get noisy if the environments diverge heavily.

**Option D — Separate section per config type.** Three new sections on the page: "Datastores", "Environment Variables", "Secrets". Each one lists values grouped by environment. Similar to C but vertically stacked rather than columnar.

**Option E — Don't show it here; link out.** Keep the app detail page lean. Add a "View config" link on each environment row that navigates to a dedicated blueprint detail page (or opens a modal). Cleanest app detail page, but adds a click to reach the information.

---

My take on the trade-offs:

- **A (accordion)** is the least disruptive and reuses the existing row structure. It's also the most natural fit since the data is already per-blueprint and the rows are already per-blueprint. The downside is that comparing across environments requires expanding multiple rows.
- **B (tabs)** is clean but duplicates the "per environment" grouping that the rows already provide — you'd essentially have two sections both organized by environment.
- **C (diff view)** is the most powerful for operators but the most complex to build and maintain, and it gets unwieldy with many variables.
- **E (link out)** is the simplest change but buries the information one more click away.

Which direction appeals to you?
