### Deep Dive: #1 Priority — Add Multishot Examples

**Why this is the highest-impact improvement:**

The deployment flow has 8 steps with multiple branching paths (new app vs. existing, single vs. multiple environments, database vs. no database, success vs. failure). The current prompt describes these branches in prose, but the docs are explicit: *"Examples dramatically improve accuracy, consistency, and quality"* and *"reduces misinterpretation of instructions."*

The prompt already contains *fragments* that hint at the need for examples — the environment list format, the options format for existing apps, the pre-deployment summary checklist. These are scattered output templates without surrounding conversational context. The agent has to synthesize the right behavior from prose rules alone.

**What's going wrong without examples:**

- **Inconsistent formatting** — The agent has template snippets but no full response examples, so it may frame them differently each time.
- **Ambiguous tool-use sequencing** — The 8-step flow is described but the agent doesn't see *when* tool calls happen relative to user messages. Does it call `list_apps` before speaking? After greeting? The prose doesn't make this obvious.
- **Tone calibration** — "Friendly but efficient" and "celebrate successes warmly" are subjective. An example of a success message would anchor the tone concretely.
- **Decision boundary ambiguity** — "Ask questions when multiple valid options exist" is a fuzzy guideline. An example showing *which* questions get asked (and which get silently resolved) would calibrate this precisely.

**Recommended examples (5 scenarios covering the key branches):**

- **Example 1: Happy path — new app, single environment.** Shows: environment check → `list_apps` (no match) → repo analysis → brief clarifying question → `deploy_app` → polling loop → DEPLOYED with URL. This is the canonical path and anchors the baseline behavior.

- **Example 2: Existing app, multiple environments.** Shows: environment check (multiple READY) → `list_apps` (match found) → the "Presenting Options for Existing Apps" format in full conversational context → user picks re-deploy → `deploy_app` → polling → success.

- **Example 3: App with database and secrets.** Shows: repo analysis detects Postgres + Secrets Manager usage → agent creates datastore first → creates app with `app_secrets` and datastore binding → deployment. Demonstrates the most complex configuration path.

- **Example 4: No environments available.** Shows: the agent checking infrastructure, finding no READY environments, and delivering the guidance message. This is a short example but critical because the agent must *stop* the deployment flow gracefully rather than improvise.

- **Example 5: Deployment failure.** Shows: polling loop → FAILED status → agent reads logs → suggests specific fixes (e.g., "Your health check is returning 404 — check that your app listens on port 3000 and has a `/health` endpoint"). Demonstrates error analysis behavior.

**Implementation considerations:**

- **Length vs. quality tradeoff** — Full tool-use examples (showing tool calls and results) are verbose. The prompt already has ~225 lines. Adding 5 complete examples with tool calls could double or triple its size, increasing cost per conversation. Mitigation: use condensed examples that show the *decision points* and *response format* rather than every tool call/result verbatim. The tool mechanics are well-handled by the Claude Agent SDK; what needs calibration is the *conversational* behavior.

- **Example format** — Wrap in `<examples><example>` XML tags per the docs. Use `<user>` and `<assistant>` sub-tags (or `H:` / `A:` shorthand) to show the conversation turns. Summarize tool calls inline (e.g., `[calls list_apps → no results]`) rather than reproducing full JSON.

- **Diversity criteria from the docs** — The 5 examples above cover: simple vs. complex apps, single vs. multiple environments, new vs. existing apps, success vs. failure, with vs. without database. This satisfies the "diverse enough to avoid Claude picking up unintended patterns" recommendation.

- **Where to place examples** — The docs recommend putting longform data at the top. However, since examples serve as *behavioral calibration* rather than reference data, placing them after the rules (but before the dynamic AWS Infrastructure context) makes more sense. The agent needs to read the rules, then see them demonstrated, then see the current infrastructure data.

**Expected impact:**

Based on the docs' claims and general experience with multishot prompting, adding well-crafted examples would likely:

- Eliminate formatting inconsistencies in environment lists and deployment summaries
- Reduce cases where the agent asks unnecessary questions (or fails to ask necessary ones)
- Standardize the tone and verbosity of responses
- Improve tool-use sequencing (right tool at the right time)
- Handle edge cases (no environments, failed deployments) more reliably

## Workflow

   - **Onboarding** — User registration, organization creation, session handling

   - **UI** — Shared frontend: base templates, navigation, design system, shared components

