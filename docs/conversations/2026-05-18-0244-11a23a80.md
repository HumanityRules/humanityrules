## Current routing topology

- The ALB routes by **host header**: `hermes-myagent.chsandbox.com` → ECS task port `8787`. There's no path-based ALB rule per app — and we don't want one (would require a CFN update per app, slow).

- The agent runs **inside** a nono sandbox as `hermeswebui` with `/workspace` as its writable home. Anything it generates lives there.
- We already patch upstream WebUI in `build/patches-webui/` and ship a sidecar bundle via `webui-extension/` — both are extension points we own.

So "loads at `https://hermes-myagent.chsandbox.com/my_beautiful_app`" means: **something inside the container, listening on 8787, has to recognize `/my_beautiful_app` as a non-WebUI path and serve user code.**

## Three viable shapes

**(A) Tiny reverse-proxy on 8787, WebUI moves to 8788**
A small aiohttp/Caddy front-end on 8787:
- `/apps/<slug>/*` → user app process or static files
- everything else → WebUI on 8788
Pros: zero patches to upstream, works for both static and dynamic apps, easy to add an "app manifest" (`/workspace/.doh/apps.yaml`) that the supervisor reads to start user processes. Cons: one more hop, one more process, need to expand nono `listen_port` range for user app ports (e.g. 8800-8899).

**(B) Patch WebUI to mount sub-apps**
Add a patch in `patches-webui/` that mounts `/apps/<slug>` → static dir or sub-ASGI app, driven by a manifest. Pros: no extra process, in-process routing. Cons: tighter coupling to upstream internals; every Hermes bump risks a patch conflict (we already have this pain).

**(C) Static-only, served by WebUI**
Same as (B) but only for static files — agent writes to `/workspace/sites/<slug>/`, WebUI serves them at `/sites/<slug>/`. Mirrors how `webui-extension` is already exposed at `/extensions/`. Tiny patch surface. Cons: no dynamic backend (no Python FastAPI / Node app), only HTML/JS/CSS.

Start with **(C)** as a v1 — it's the smallest patch, no new processes, no nono profile change, and "build me a beautiful app" is overwhelmingly a static-frontend ask (the agent can call APIs from the browser via the WebUI's existing endpoints or via fetch through the broker). - **Dockerfile**: Elixir/Erlang aren't in the base image. Either bake them in (`apt-get install -y elixir`, ~150MB) or accept that "Elixir app" means the agent does `apt-get install` at runtime into the persistent root. I'd bake them in for v1 — predictable cold start.

3. **Languages** — committing to Elixir specifically (bake elixir+erlang) vs. building a generic "any-language backend" extension and just documenting Phoenix as one example. Generic is more work up front but doesn't paint us into Elixir-shaped corners.

## Assistant

Yeah, there is one — and it's instructive, even if I think it loses on inspection.

## fd handoff (inetd-style)

A tiny router binds 8787, accepts the TCP connection, **peeks** the first ~256 bytes (`recv(MSG_PEEK)`), parses the request line to read the path, then passes the raw socket fd to the chosen backend over a Unix socket via `SCM_RIGHTS`. From that point on the backend owns the fd — kernel pipes bytes directly between client and backend, no userspace bytes in the data path, no proxy at all.

This is the Plan 9 / inetd / systemd-socket-activate lineage. It's beautifully minimal. The router is maybe 150 lines of C/Python. Phoenix never knows it's behind anything.

**Why I'd still pick Caddy over this for our case:**

1. **HTTP/1.1 keep-alive breaks the model.** Once handed off, *that TCP connection* belongs to one backend. The next request on the same connection might be `/apps/foo/...` followed by `/apps/bar/...` — wrong backend. You'd have to force `Connection: close` (kills perf, breaks LiveView's long-poll fallback) or peek-and-handoff per request, which means... staying in the data path, which means... you're a proxy.
2. **Frameworks don't accept pre-accepted fds.** systemd activation passes a *listening* socket to one process. We need to pass *accepted* sockets to one of N. Phoenix/Cowboy, Express, FastAPI — none support this out of the box. You'd be writing per-language shims.
3. **HTTP/2 makes it worse.** One TCP connection multiplexes streams to potentially different paths.

## eBPF sockmap

The other "real" low-level option: an eBPF program in `sk_msg` / `sk_skb` parses the request line in-kernel and redirects to one of N userspace sockets registered in a sockmap. Cilium does this kind of thing. Same handoff benefits, no userspace copy. But: HTTP parsing in eBPF's bounded-loop world is genuinely painful, and you've now got a kernel-program dependency that ECS Fargate may or may not let you load (Fargate restricts `CAP_BPF` / `CAP_SYS_ADMIN`). Worth checking, but I'd bet it's blocked.

## The honest conclusion

The "low-level primitives" route is real and elegant in a thought-experiment sense, but HTTP/1.1 keep-alive + HTTP/2 multiplexing fundamentally make L7 routing a per-*request* decision, not a per-*connection* one. Anything that wants to stay out of the data path has to either pin one backend per connection (breaks the model) or push L7 parsing into the kernel (overkill, possibly disallowed on Fargate).

Caddy wins because it's already optimal at the things that *do* matter — `splice(2)` for zero-copy forwarding, native HTTP/2 demux, WS upgrades — without any of the fragility.

- **TCP_REPAIR** — snapshot/restore a live TCP connection in another process. Real (CRIU uses it), but exotic and `CAP_NET_ADMIN`-gated.

Once you've handed the fd to backend A, request #2 going to backend B is wrong.

The only way the OS-level handoff works is if you force `Connection: close` on app paths. Then each request gets a fresh connection, the first-packet peek correctly chooses the backend, and you really do get out of the data path. But "no keep-alive" hurts SPAs (every fetch is a new TCP+TLS handshake — TLS terminates at ALB, so just TCP, which is cheap-ish, but it still kills LiveView's long-poll fallback and HTTP/2 entirely).

## What's actually out there

**Caddy itself: no.** Caddy is a reverse proxy. It doesn't supervise child processes. There's a `caddy-exec` plugin for one-shot commands, but no long-running-service supervision. Dead end.

**The real candidates:**

- **s6 / s6-overlay** — the gold standard for container supervision. Directory-driven (each service is `/etc/s6/<name>/run`), restart policies, log rotation via `s6-log`, readiness/health via `notification-fd`. Battle-tested in thousands of images.
- **supervisord** — Python, ini-config, well-known. Has an XML-RPC API for dynamic add/remove. Heavier than s6 but more familiar.
- **process-compose** — newer (single Go binary), docker-compose-style YAML, REST API for runtime control, health checks, TUI. Specifically designed for "compose, but no docker."
- **runit** — like s6 but older. Still good.

All four give us crash-loop policy, restart backoff, log capture, signal handling, graceful shutdown — the stuff I was about to write 250 lines of Python for.

## What we still have to write either way

The supervisor handles the *process* part. It doesn't handle:

1. **Watching `/workspace/.doh/apps/` and translating YAML → supervisor config.** Our spec is "agent writes a file, app starts." No off-the-shelf supervisor watches an arbitrary directory of YAML files in our schema.
2. **Driving Caddy's admin API when an app becomes healthy.** Adding/removing routes on health transitions.
3. **Surfacing status back to the agent** in the shape we want (`state.json` or whatever).

That's ~50–80 lines of Python, not 250. The supervisor itself is off the shelf.

## So the honest design is

```
inotify on /workspace/.doh/apps/
        │
        ▼
   tiny translator (≤80 lines)
        │
        ├──► writes /etc/s6/<slug>/run  → s6 supervises
        └──► POSTs to Caddy :2019       → routes update
```

s6 owns "is the process alive, restart it if not, capture its logs." We own "what does the agent's intent translate to."

- **Directory-of-files model matches our `apps/` source-of-truth one-to-one.** `process-compose` and `supervisord` want a single config file we'd have to regenerate atomically; s6 wants exactly the directory shape we already want.
- **Single static binary, ~1MB.** Already common in `ghcr.io/nesquena/hermes-webui` lineage images — worth checking if it's already there before adding.
- **No daemon coordination protocol.** We just write files and `s6-svscanctl -a` to rescan. supervisord/process-compose mean an extra API client to maintain.

The only argument for `process-compose` over s6 is the nicer TUI for humans, which we don't need (the agent is the user).
