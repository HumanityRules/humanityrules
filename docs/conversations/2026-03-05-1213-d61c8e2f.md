Correct — it's a special case. Looking at the SDK docs:

> Claude requests user input in two situations: when it needs permission to use a tool, and when it has clarifying questions (via the `AskUserQuestion` tool). **Both trigger your `canUseTool` callback**, which pauses execution until you return a response.

So when Claude calls `AskUserQuestion`:

1. It does **not** appear as a `ToolUseBlock` in an `AssistantMessage` (which is the normal path your `_handle_assistant_message` processes)
2. It does **not** produce a `ToolResultBlock` in a `UserMessage` (which your `_handle_tool_results` processes)
3. Instead, the SDK intercepts it and routes it to the `canUseTool` callback
4. Your callback returns `PermissionResultAllow(updated_input={"questions": ..., "answers": ...})`
5. The SDK feeds the answers back to Claude internally

This is the same pathway used for tool approval prompts (e.g., "Allow Claude to delete this file?"). The SDK treats user-facing interactions — whether permissions or clarifying questions — as a separate channel from the normal tool execution flow.

That's why your current setup (no `canUseTool` callback + `permission_mode="acceptEdits"`) means `AskUserQuestion` would either auto-approve with empty answers or simply not work — which aligns with what the GitHub issue #29530 describes. You need the callback to actually collect and return the user's choices.
