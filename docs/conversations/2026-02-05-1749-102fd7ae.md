## Assistant

Good question. Let me trace the flow to understand why it's where it is.

**Current state: trigger message lives in endpoint code**

- `chat.py` line 99-109: defines the trigger content map and creates the `SYSTEM_TRIGGER` message
- `test_main_agent.py` (new): duplicates the same content map and creation logic
- `agent_service.stream_response`: doesn't know about triggers — it just reads the last user message via `_aget_last_user_message`, and for auto-start conversations that last message happens to be the trigger

**Why it ended up in the endpoint**

The web flow has a timing dependency: `chat_new` creates the trigger synchronously, redirects to `chat_view`, which opens an SSE connection, which calls `agent_runner.ensure_agent_running`. The trigger message must exist in the DB *before* the agent starts, because `stream_response` reads it as the "last user message." The endpoint was the natural place to put "create the data the agent will need."

**The problem now**

With two callers (`chat.py` and `test_main_agent.py`), the trigger content map is duplicated. If you change the wording or add a new mode, you need to update both. This is the classic DRY violation that signals the logic belongs one layer down.

**Where it should live**

The trigger content is agent domain knowledge — it's about how the agent conversation bootstraps. It belongs in `agent_service`. A clean approach:

- `agent_service` exposes a function like `create_conversation_with_trigger(user, organization, workspace_id, repo_id, aws_account_id, mode)` that creates the conversation, derives the mode, and creates the trigger message
- Both `chat_new` and `test_main_agent._create_new_conversation` call it
- The trigger content map lives in exactly one place

The alternative — having `stream_response` detect "first turn with no real user messages" and inject the trigger internally — is trickier because it would mean `stream_response` both creates and reads the seed message, and the SSE auto-start detection in the web UI relies on the message already existing.

**My recommendation**: extract a helper in `agent_service` that owns conversation creation + trigger logic. Both endpoints become thin callers. The mode derivation logic (which is also duplicated from `chat_new`) would move there too.
