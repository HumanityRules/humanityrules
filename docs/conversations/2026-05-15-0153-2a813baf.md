## Q1: API key approach — yes, and there's no alternative

Merge Agent Handler authenticates **everything** with one bearer token in the `Authorization` header:

- `POST /api/v1/registered-users` (creating users)
- `POST /api/registered-users/{id}/link-token` (minting Link tokens for the frontend)
- `streamable-http` calls to `/api/v1/tool-packs/{pack}/registered-users/{user}/mcp` (the actual MCP traffic)

There is no per-user OAuth-style credential. Multi-tenancy is achieved by **scoping in the URL path** (`registered_user_id`), not by swapping the auth principal. So:

- **One API key per DOH environment**, not per DOH-customer. The same Merge key authorizes operations for every Registered User we ever create.
- Merge issues one production key + optional sandboxed test keys (Settings → API Keys).
- The docs are explicit: *"Never expose the API key client-side. It authorizes operations on behalf of every Registered User."*

### What this means for our trust model

The key is roughly equivalent to **`DOH_ENV_BEARER`** in `integrations_broker.py` — a secret that authorizes calls on behalf of *all* DOH users. So the obvious home for it is the **DOH control plane**, not the customer's AWS account, and definitely not the Hermes container.

That said, putting it only in the control plane means every Hermes-to-Merge MCP call has to make an outbound hop to DOH first to get a per-call signed thing — which is awkward for a streaming MCP transport. The realistic split is:

- **Master Merge API key** → DOH control plane only. Used for `registered-users` admin calls and link-token minting (low-frequency, control-plane-shaped operations).
- **For MCP traffic from the Hermes container** → the key has to live somewhere the broker sidecar (outside the sandbox, inside the customer's container) can reach. That's exactly the same trust level as `DOH_ENV_BEARER` today: injected as env on the broker process, never visible to the sandbox.

## Q2: When to call `register-users`

The Merge endpoint is **idempotent on `origin_user_id`** — same input always returns the same `registered_user_id`. That property reshapes the question: it's not really *"when do we register?"* but *"where do we cache the ID?"* and *"what's the natural trigger?"*

### The two real options

**Option A — Eager, at DOH signup.** Hook into the user-creation flow, fire `POST /registered-users`, store the ID on the User row.
- Pros: ID is always available when any code path needs it; no special-case handling later.
- Cons: We create a Merge-side record for every DOH user even if 90% never touch a Merge integration. Not a security issue (Merge users without connections hold no credentials), but it's noise on Merge's side and an extra failure mode at signup (what if Merge is down — does signup fail?).

**Option B — Lazy ensure-on-demand.** Add `merge_registered_user_id` (nullable) to the DOH User model. A helper `ensure_merge_registered_user(user)` fills it on first need.
- Pros: No Merge dependency at signup; pay only for users who actually use Merge integrations.
- Cons: Every code path that needs the ID has to call the helper (cheap, one DB read after first call).

I'd go with **B** — it matches how we already handle the Google integration (state created when the user first connects, not at signup) and avoids coupling signup availability to Merge's uptime.

### Trigger points for the lazy ensure

There are exactly two places where DOH needs a `registered_user_id`:

1. **Minting a link token** for the frontend (when the user clicks "Connect Slack via Merge"). This is the unavoidable trigger — a link token can't be minted without a registered user, and a link token is the only way the user authenticates a connector. So `ensure_merge_registered_user(user)` runs as the first step of the link-token endpoint.

2. **Constructing the MCP URL** for a Hermes container. The URL embeds `registered_user_id` in the path. Two sub-options:
   - **Inject at deploy time** as part of the env-bearer overlay (sibling to `DOH_OWNER_USERNAME`). Container boots with `DOH_MERGE_REGISTERED_USER_ID` set; broker uses it forever. This matches the existing pattern in `integrations_broker.py`.
   - **Fetch on demand** from the broker via DOH control plane (similar to the Google token refresh). Adds an HTTP hop per cold start; unnecessary because the ID is stable.

   Inject at deploy time is the obvious choice. The ID is immutable for the user's lifetime, so caching it in container env is fine.

### What this means for ordering

At deploy time, if the user has *any* Merge integrations connected (or even just the capability enabled for their tenant), the deploy_app overlay calls `ensure_merge_registered_user(user)` synchronously and includes the ID in the broker env. If the user has never used Merge, we can either skip injection entirely (broker has no Merge config, MCP aggregator doesn't expose Merge tools) or pre-register anyway — I'd skip, to keep the "user has zero Merge state" case clean.

### Summary

- Add `merge_registered_user_id` to the DOH `User` model, nullable.
- Add `ensure_merge_registered_user(user)` helper in DOH's control plane (idempotent — checks DB first, calls Merge if empty, stores ID, returns it).

This one is straightforward — Merge is shaped exactly like Notion, and we already built `mcp_aggregator.py` for that shape.

### Why aggregator wins for Merge

The MCP aggregator already does the right thing: a local FastMCP server on 127.0.0.1:9952, with a `ProxyProvider` per upstream and a `client_factory` that supplies whatever auth the upstream wants. Adding Merge is just another `PROVIDERS` entry with a factory that builds:

```python
url = f"https://ah-api.merge.dev/api/v1/tool-packs/{tool_pack_id}/registered-users/{registered_user_id}/mcp"
return Client(url, headers={"Authorization": f"Bearer {api_key}"})
```

That's it. No OAuth dance (unlike Notion — Merge's user-side connector auth happens through Link, which is a separate browser flow we'll handle in Q4, not part of the sandbox→Merge MCP traffic).

### Why TLS interception is worse here

- **The URL itself is the auth scope.** It embeds `tool_pack_id` and `registered_user_id`. With TLS interception, the sandbox has to know that URL to call it — so we'd inject `DOH_MERGE_REGISTERED_USER_ID` into the sandbox env. The aggregator hides this entirely; the sandbox just talks to localhost.
- **Streaming HTTP is awkward to body-rewrite.** MCP over `streamable-http` isn't a clean request/response shape. The broker's TLS interception was built for REST-shaped Google APIs where header swap + forward is enough. Doing it for MCP means re-implementing what FastMCP's ProxyProvider already does.
- **No multiplexing benefit.** Sandbox already gets one unified MCP endpoint via the aggregator. TLS interception would force the sandbox to know about each MCP upstream as a separate hostname — fragmenting what's currently one well-defined surface.
- **Tool composition for free.** Aggregator merges Merge tools + Notion tools + future-MCP tools into one tool list. TLS interception keeps them as N separate endpoints the sandbox has to discover.

### Sketch of the change to `mcp_aggregator.py`

```python
MCP_PROVIDERS = {
    "notion": { ... existing ... },
    "merge": {
        "label": "Merge",
        "auth_kind": "api_key",        # vs "oauth_dcr_pkce" for notion
        "url_template": "https://ah-api.merge.dev/api/v1/tool-packs/{tool_pack_id}/registered-users/{registered_user_id}/mcp",
    },
}
```

Then split the attach logic by `auth_kind`:
- `oauth_dcr_pkce` → existing path (DCR, browser flow, token refresh).
- `api_key` → factory that returns `Client(url, headers={"Authorization": f"Bearer {api_key}"})`. No OAuth state needed.

Merge's `ProxyProvider` attaches **once at boot** (after the registration call from Q2 returns the `registered_user_id`) and stays attached for the container's lifetime. No refresh loop, no token storage, no `_OAuthState` for Merge.

### Failure mode

If the boot-time registration call fails or the API key is rejected, the Merge ProxyProvider just doesn't attach — the sandbox sees no Merge tools, same graceful degradation as Notion-not-yet-OAuthed today. The `/status` endpoint can surface the failure to the WebUI.

### One thing that's *not* the aggregator's job

Connector-level auth (the user clicking "Connect Slack" and going through Slack's OAuth via Merge's Link component) is separate. That's MCP-orthogonal — it determines whether Merge can fulfill a tool call, but the sandbox→aggregator→Merge MCP transport doesn't know or care about it. Per-tool errors come back as MCP responses (`reauth_required` etc.), which the agent handles in-band. That's Q4 territory.

- Bearer → DOH resolves env → DOH knows the owning org and (for app-scoped endpoints) the app slug.
- DOH inspects the requested URL (or method+path+body) and validates that any `registered_user_id` in the URL matches the derived `f"doh_{owner_pk}_{app_slug}"` for *this* env.
- Reject otherwise.

So cross-org isolation is achievable with one endpoint plus a validator, same as with four narrow ones. Within-org behavior is identical to either design (and identical to the existing Google pattern). My "single proxy = anyone can do anything against Merge" framing was wrong.

## What's actually different between one vs. four

Now that the security argument collapses, the choice is engineering taste:

**Single proxy:**
- One endpoint, one validator. Validator has to understand Merge's URL structure (regex out `registered_user_id`, compare).
- Adding new Merge functionality = no DOH code change. Customer broker just starts calling new paths and DOH forwards.
- *Risk:* validator missing a code path, future Merge endpoint ships with a new URL shape we didn't anticipate, or a Merge endpoint that takes the user identity in the *body* instead of the URL — validator has to evolve in lockstep with Merge's API.

**Four endpoints:**
- Each is ~30 lines. URL construction is server-side, no parsing or regex.
- Adding new Merge functionality = explicit DOH change. Slower to ship, but intentional.
- Easier to reason about and audit one-by-one. Easier to log/monitor per-operation rates and errors.

## My take

For us specifically, **four narrow endpoints** is still the right call, but the reasoning is now:

- The four operations we need are stable and well-understood (link-token, list connectors, disconnect, MCP relay). Two of them are ~10 lines, one is a list-and-merge, one is the streaming MCP relay. There isn't really a fifth operation around the corner.
- The streaming MCP relay (#4) is meaningfully different code from the other three — it's bidirectional streaming, not request/response JSON. A single endpoint would have to handle both shapes, awkwardly.
- Server-side URL construction beats regex-validating client-supplied URLs as a *defensive coding* matter, even if both are equally secure when implemented correctly.

But I'd say it's a 60/40 preference, not a clear-cut decision. If you'd rather have one passthrough endpoint with a validator, that's also a defensible answer.

## Question 5 — Failure modes at boot

The aggregator process boots inside the Hermes container. Three things can go wrong with Merge:

- **DOH control plane is down** (the relay endpoint can't be reached at all).
- **`DOH_ENV_BEARER` is rejected** by DOH (rotated, hash mismatch, env mis-resolved).
- **Merge itself is down** (DOH reaches it but gets 5xx).

These cascade differently because the broker no longer talks to Merge directly — DOH is in the path.

### Existing pattern (the precedent)

Looking at `mcp_aggregator.py:132-135`, Notion's behavior at boot today:

```python
async def serve(self) -> None:
    for slug in MCP_PROVIDERS:
        if self._oauth_states[slug].has_token:
            self._attach_provider(slug=slug)
```

It only attaches providers that already have OAuth tokens. Anything else, the aggregator boots fine without that provider attached. Failure mode: tools missing, agent gets a clean "no such tool" instead of a hung session.

Google's broker side (`integrations_broker.py`): `_refresh_loop` runs continuously per provider. On `not_connected` it polls every 60s. On `transient` failures it backs off exponentially. **The whole broker process never dies because of a provider failure.** Provider state goes to `transient_error` or `fatal_error`, broker keeps serving everything else.

### Merge in this design

The Merge ProxyProvider is special: there's no per-Merge OAuth state to gate on. The bearer always exists. So at boot, do we always attach unconditionally, or do we probe?

**Option A — Attach unconditionally, fail per-call.**
- ProxyProvider for Merge always attaches at boot.
- If DOH is down or returns 5xx, individual MCP calls fail.
- Sandbox sees Merge tools in `list_tools()` even when the relay is broken; calling them errors out.
- Aggregator never has to know whether Merge is up.

**Option B — Health-probe at boot, attach if healthy.**
- Aggregator hits `GET /__doh_broker/integrations` (or a dedicated `/healthz`) at boot. If DOH responds, attach Merge.
- If unhealthy at boot, schedule a retry loop (similar to Google's refresh loop).
- Sandbox sees Merge tools only when the relay is reachable.

**Option C — Lazy attach on first WebUI integrations-pane open.**
- Don't attach at boot at all. When the user opens the integrations pane, the polling fetch tries to reach DOH; if it succeeds, attach.
- Cleaner story: aggregator only commits to Merge when there's evidence Merge works.

### My take

**Option A — attach unconditionally, fail per-call.**

Reasoning:
- It mirrors how Notion behaves *after* the user has authenticated. Once the OAuth state says "connected," the ProxyProvider is attached unconditionally; if Notion is later down, individual calls fail. We don't health-probe Notion at boot. Same posture for Merge.
- DOH being temporarily down at the moment a customer container happens to boot is a real but transient situation. Health-probing at boot would mean those containers come up *without* Merge tools and stay that way until something triggers re-probing. That's worse than "tools exist but transiently fail."
- Simpler code path. No probe, no retry-attach loop, no boot-time race.
- The agent gets actionable error messages from MCP tool failures — these can include "DOH-relay unavailable, retry shortly" — vs. silently missing tools.

The error surface needs to be reasonable: when a Merge MCP call fails because DOH is down, the broker (FastMCP ProxyProvider) propagates the failure. The sandbox sees a tool error, the agent reports it.

For the WebUI status pane: `GET /__doh_broker/integrations` itself calls DOH. If DOH is down, the pane shows the *Google* and *Notion* parts (which don't depend on DOH at runtime), and the Merge section shows an error state ("Couldn't reach DOH; retrying"). That's the natural feedback channel, and it doesn't require any special boot-time logic.

### What about `DOH_ENV_BEARER` invalid (auth failure)?

This one is more concerning because it's not transient — bearer hashes don't suddenly mismatch unless something is wrong with secret rotation. If DOH responds 401 to every Merge call, the entire Merge integration silently fails forever from this container.

**Handling:** structured logging + WebUI surfacing. The pane shows "Merge unavailable: authentication failed (contact support)." Doesn't require special boot-time logic — same as the "DOH down" case from the user's perspective, just with a different error message.

We do *not* want to trigger automatic bearer rotation from the broker side. That's a control-plane operation.

### Edge case: aggregator process can't bind 9952

That kills *all* MCP integrations (Notion + Merge), and the existing `serve()` already raises and the supervisor restarts. Not a Merge-specific concern.

We agreed registration is **lazy** — DOH calls Merge's `POST /registered-users` only when needed. Two specific places need the registered user to exist:

1. **Minting a link token** (`POST /api/integrations/merge/link-token`). Can't mint without a registered user.

3. `GET /api/integrations/merge/connectors` — needs the registered user to query per-user connection state.
4. `GET /api/integrations/merge/connector-status` — same.
5. `POST /api/integrations/merge/disconnect` — same.

So **every DOH endpoint** for Merge needs a valid registered user. The question is how to handle the "first call ever for this env+app" case.

### Three placements

**Option A — Implicit ensure on every call.**
Each DOH view calls `ensure_registered_user(env, app_slug)` as its first step. The helper:

```python
def ensure_registered_user(env, app_slug) -> str:
    # Idempotent against Merge — same input always returns same id
    response = merge_post("/registered-users", {
        "origin_user_id": f"doh_{env.owner.pk}_{app_slug}",
        "origin_user_name": app_slug,
        "origin_user_email": env.owner.email,
    })
    return response["registered_user_id"]
```

Every call hits Merge twice: once for ensure, once for the actual operation. Slow.

**Option B — Cache the registered_user_id in DOH's database.**
Add a model `MergeRegisteredUser(env, app_slug, registered_user_id)`. First call fills it; subsequent calls read from DB. One Merge call saved per request after the first.

But we explicitly said earlier: **no DB column for this**, lean on Merge's idempotency.

**Option C — Cache in process memory on DOH.**
Module-level dict keyed by `(env_id, app_slug)`. Lost on Django restart, repopulated lazily. Each Django worker holds its own copy.

**Option D — Implicit ensure, but only on the cheap endpoints.**
The MCP relay (#2) is hot-path streaming; we don't want to add a Merge call to its setup. So:
- Link-token mint, connectors list, status, disconnect → call `ensure_registered_user` first. These are already low-frequency control-plane calls.
- MCP relay → assumes the registered user exists (because at least one of the cheap endpoints must have been called first to even know Merge is connectable).

That's a slight assumption, but in practice the WebUI loads the integrations pane before the agent makes any MCP call, so connectors-list runs first. Still, "we get bad luck and the agent calls MCP before any pane load" is a real edge case.

### My take

**Option C: in-memory cache in DOH**, with `ensure_registered_user` called on every endpoint as the first step. The cache makes that essentially free after the first call.

```python
_REGISTERED_USER_CACHE: dict[tuple[int, str], str] = {}

def ensure_registered_user(env, app_slug) -> str:
    key = (env.id, app_slug)
    if cached := _REGISTERED_USER_CACHE.get(key):
        return cached
    response = merge_post("/registered-users", {...})
    rid = response["registered_user_id"]
    _REGISTERED_USER_CACHE[key] = rid
    return rid
```

Reasoning:
- **Idempotent + cached = fast.** First call ever: ~100ms (Merge round-trip). Every subsequent call: dict lookup.
- **No DB schema change.** Memory-only.
- **Survives the multi-worker case correctly.** Each Django worker independently warms its cache. Merge's idempotency means even if worker-1 and worker-2 both call `ensure` simultaneously for a new env, they both get the same `registered_user_id`. No coordination needed.
- **Restart story is fine.** DOH restart → cache empty → first request per env+app warms it again with one Merge call. Acceptable.

The MCP relay endpoint also calls `ensure_registered_user` as its first step. After warmup that's a dict lookup; before warmup it's one Merge call before the streaming begins. Tolerable for the streaming setup path.

### Cache eviction?

I'd say **no eviction**. The cache key is `(env_id, app_slug)`; once an env+app exists, it doesn't change. The cache grows linearly with active env+apps, which is bounded by the number of deployed Hermes containers. Memory cost: ~50 bytes per entry. Even at 10k env+apps that's 500KB.

**One subtlety:** if an env is destroyed and recreated under the same slug (different `env.id`), the new env gets a new cache entry. The old entry leaks until DOH restart. Negligible.

### What about the disconnect-everything case?

If we ever build "destroy env" → "delete registered user on Merge" cleanup (deferred earlier), that operation needs to invalidate the cache entry. Add a `_REGISTERED_USER_CACHE.pop((env_id, app_slug), None)` to that path when we get to it. Not now.

# Python style guide

## Function Signatures & Calling Conventions

To prioritize readability and eliminate "magic" behavior, we enforce strict explicitness in both how functions are defined and how they are invoked.

### 1. Enforce Explicit Argument Passing
* **Directive:** Do not use default parameter values in function or method definitions. All parameters must be mandatory.
* **Reasoning:** "Magic defaults" hide complexity and obscure the function's dependencies. We prefer explicit calls where every argument is visible at the call site.
* **Implementation:** If a value is logically optional, the caller must explicitly pass `None`.

**Bad (Implicit Defaults):**
```python
def connect_to_db(url, retries=3, timeout=30):
    # Hidden behavior: Reader assumes 0 retries? Infinite timeout?
    ...
```

**Good (Explicit Arguments):**
```python
def connect_to_db(url, retries, timeout):
    # All dependencies are visible in the signature
    ...
```

### 2. Prefer Keyword Arguments
* **Directive:** Use named arguments (keyword arguments) for function calls, particularly when passing literals (numbers, booleans, or strings) or when a function takes multiple parameters.
* **Reasoning:** Positional arguments are brittle and often illegible (the "Boolean Trap"). Keyword arguments make the code self-documenting and prevent errors caused by parameter reordering.
* **Implementation:** Explicitly state the parameter name at the call site.

**Bad (Positional Ambiguity):**
```python
# The reader cannot know what '3' and '30' represent
connect_to_db("db://localhost", 3, 30)

# Confusing booleans
create_user("jdoe", True, False)
```

**Good (Self-Documenting):**
```python
# Clarity is enforced at the call site
connect_to_db(url="db://localhost", retries=3, timeout=30)

# Intent is obvious even for optional flows
connect_to_db(url="db://localhost", retries=None, timeout=None)

# Boolean flags are readable
create_user(username="jdoe", is_admin=True, send_email=False)
```

### 3. Prefer Module-Qualified Imports for Local Modules
* **Directive:** For local/project modules, use `import module` rather than `from module import function`. Then call functions with the module prefix.
* **Reasoning:** Explicit module prefixes make dependencies visible at every call site. The reader instantly knows where a function comes from without scrolling to imports.
* **Implementation:** Import the module, then use `module.function()` syntax.

**Bad (Ambiguous Origin):**
```python
from iam_utils import get_assumed_role_session
from vpc_utils import find_available_vpc_cidr

# Reader can't tell where these come from without checking imports
session = get_assumed_role_session(...)
cidr = find_available_vpc_cidr(...)
```

**Good (Explicit Module):**
```python
import iam_utils
import vpc_utils

# Origin is immediately clear at the call site
session = iam_utils.get_assumed_role_session(...)
cidr = vpc_utils.find_available_vpc_cidr(...)
```

**Note:** This applies to local project modules. Standard library and well-known third-party packages (e.g., `from pathlib import Path`, `from dataclasses import dataclass`) are fine to import directly since their origin is universally understood.

### 4. Prefer Direct Imports Over TYPE_CHECKING
* **Directive:** Use regular imports for type hints. Only use `TYPE_CHECKING` when actually needed to resolve circular imports.
* **Reasoning:** `TYPE_CHECKING` adds complexity (conditional imports, string annotations) for a problem that may not exist. Solve circular dependencies when they occur, not preemptively.
* **Implementation:** Import types directly and use them in annotations.

**Bad (Premature Optimization):**
```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from myapp.models import User

def get_user(id: int) -> "User":  # String annotation required
    ...
```

**Good (Direct Import):**
```python
from myapp.models import User

def get_user(id: int) -> User:
    ...
```

**When TYPE_CHECKING is appropriate:**
- Actual circular import errors occur
- Heavy imports cause measurable startup delays
- Imports have side effects you need to avoid

### 5. Single-Line Function Signatures When Under 140 Characters
* **Directive:** Write function and method definitions on a single line when the total length (including `def`, parameters, return type, and trailing colon) is under 140 characters. Use multi-line formatting only when the signature exceeds this limit.
* **Reasoning:** Single-line signatures are easier to scan and search. Multi-line formatting adds vertical noise for short signatures that fit comfortably on one line.
* **Implementation:** Measure the full signature length. If under 140 characters, keep it on one line.

**Bad (unnecessary multi-line):**
```python
async def _handle_stream_event(
    message: SDKStreamEvent,
    ctx: StreamingContext,
) -> AsyncGenerator[StreamEvent, None]:
    ...
```

**Good (118 characters, fits on one line):**
```python
async def _handle_stream_event(message: SDKStreamEvent, ctx: StreamingContext) -> AsyncGenerator[StreamEvent, None]:
    ...
```

**When multi-line is appropriate:**
- Signature exceeds 140 characters
- Complex default values or annotations that benefit from vertical alignment (though we avoid defaults per rule 1)

### 6. Prefer Single-Line Docstrings for Simple Functions
* **Directive:** Use a brief single-line docstring for functions. Reserve multi-line docstrings (with Args/Returns/Raises sections) for complex functions where the signature alone doesn't convey important details.
* **Reasoning:** Verbose docstrings that restate what the function name and types already communicate add noise. A concise one-liner maintains consistency while avoiding redundancy.
* **Implementation:** Write a single-line docstring that adds context beyond the function name, or simply summarizes intent.

**Bad (overly verbose):**
```python
async def _aget_last_user_message(conversation: Conversation) -> str:
    """
    Get the last user message from a conversation.

    Args:
        conversation: The Conversation model instance.

    Returns:
        The content of the last user message.

    Raises:
        ValueError: If no user messages found.
    """
```

**Good (concise single-line):**
```python
async def _aget_last_user_message(conversation: Conversation) -> str:
    """Get the content of the most recent user message."""
```

**When multi-line docstrings are valuable:**
- Non-obvious behavior or side effects
- Complex algorithms that need explanation
- Public API functions where discoverability matters
- Unusual parameter constraints not captured by types

### 7. Require Type Hints on New/Modified Functions and Methods
* **Directive:** Every new or modified function/method must include type hints for all parameters and the return type.
* **Reasoning:** Complete signatures improve readability, reduce ambiguity, and make refactoring/tooling safer.
* **Implementation:** Annotate all parameters and returns explicitly. Use `-> None` for no-return functions. Keep annotations concrete when possible.

**Bad (missing annotations):**
```python
def check_access(request, resource, action):
    ...
```

**Good (fully annotated):**
```python
def check_access(request: HttpRequest, resource: Workspace, action: str) -> bool:
    ...
```


## Django 6.0 Async ORM

**Use native async ORM methods instead of `sync_to_async`.** Django 6.0 has full async ORM support — don't wrap sync methods.

- **Queries:** Use `await queryset.afirst()`, `await queryset.aget()`, `await queryset.acount()`, etc.
- **Create/Update:** Use `await Model.objects.acreate(...)`, `await instance.asave()`, `await instance.adelete()`
- **Iteration:** Use `async for obj in queryset:` instead of wrapping sync iteration

**Bad (outdated pattern):**
```python
from asgiref.sync import sync_to_async

async def get_user(user_id):
    return await sync_to_async(User.objects.get)(id=user_id)

async def save_item(item):
    await sync_to_async(item.save)()
```

**Good (Django 6.0):**
```python
async def get_user(user_id):
    return await User.objects.aget(id=user_id)

async def save_item(item):
    await item.asave()
```

The `a`-prefixed methods are native async and don't require `sync_to_async` wrappers.


## Logging

**Use `logger.error()` instead of `logger.warning()`.** We don't use the warning level — if something is worth logging as abnormal, log it as an error.


## File Naming Conventions

**Avoid generic file names** like `service.py`, `client.py`, `list.html`, `view.html`. Use descriptive names that include the domain context.

**Reasoning:** Generic names become ambiguous as the project grows. With 20 modules, having multiple `service.py` files makes navigation and searching difficult.

**Bad:**
```
services/agent/service.py
templates/chat/list.html
```

**Good:**
```
services/agent/agent_service.py
templates/chat/chat_list.html
```

The prefix should match the containing folder or domain. This makes file names unique and self-documenting even when viewed in isolation (e.g., in editor tabs, search results, or stack traces).
