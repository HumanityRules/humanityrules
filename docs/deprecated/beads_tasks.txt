[devopshero-prq] P1 task      created 2026-01-19
  Deployment: Agent recovery tools for failed deployments/environments
    **Note: This analysis was generated by Claude. More thought and discussion required before implementation.**
    
    ## Analysis: Recovery Tools for the Deployment Agent
    
    Based on the current architecture, here's what can fail and what tools would help:
    
    ### Current State
    
    **What exists:**
    - `deploy_app` — Creates PENDING deployment, worker executes it
    - `get_deployment_status` — Shows status + logs for a single deployment
    
    **What can fail:**
    1. **Deployment failures** — Docker build, ECR push, CDK deploy, health checks
    2. **Environment provisioning failures** — VPC/cluster creation (environment stuck in ERROR)
    3. **AWS account issues** — IAM role problems, permissions, credential expiry
    
    ### Recovery Tools Needed
    
    #### Tier 1: Essential Recovery
    
    **`retry_deployment`** (optional convenience)
    - `deploy_app` already works for failed apps (FAILED isn't an "active" status that blocks new deployments)
    - But a dedicated retry tool could be cleaner: takes `deployment_id`, resets to PENDING
    - Preserves deployment lineage vs creating new records
    
    **`get_environment_status`**
    - Check environment state (PENDING/PROVISIONING/READY/ERROR) and `status_message`
    - Currently no way for agent to see why environment provisioning failed
    - Would return: `{status, status_message, vpc_id, cluster_arn, vpc_stack_name, cluster_stack_name}`
    
    **`retry_environment`**
    - Reset an ERROR environment back to PENDING
    - Next deployment will trigger re-provisioning
    - Critical for recovering from base infra failures
    
    **`list_deployments`**
    - Get deployment history for an app (recent N, filtered by status)
    - Agent needs this to say "Your last 3 deployments failed, here's the pattern..."
    - Currently can only check one deployment by ID if you already know it
    
    **`cancel_deployment`**
    - Mark an in-progress deployment as CANCELLED
    - Sets a flag that worker checks and aborts gracefully
    - Needed for stuck deployments or user abort requests
    
    #### Tier 2: Deeper Debugging
    
    **`get_stack_events`**
    - Fetch CloudFormation events for a deployment's stacks
    - When CDK deploy fails, the real error is in CFN events
    - Would need stack names (already tracked on Environment/Deployment)
    
    **`verify_aws_account`**
    - Test AssumeRole and basic permissions (sts:GetCallerIdentity, etc.)
    - Returns pass/fail with specific permission errors
    - Helps diagnose "AWS connection stopped working"
    
    **`teardown_app`**
    - Delete CDK stacks for an app (ECR, ECS service, ALB target group)
    - Cleanup after repeated failures before retrying fresh
    - Dangerous — needs confirmation
    
    #### Tier 3: Runtime Operations
    
    **`get_ecs_logs`**
    - Fetch CloudWatch logs from ECS tasks
    - For debugging "app deployed but crashes at runtime"
    
    **`restart_service`**
    - Force ECS service restart without full redeploy
    - For "try turning it off and on again" fixes
    
    **`list_environments`**
    - Show all environments in an AWS account
    - For multi-environment support later
    
    ### Suggested Implementation Order
    
    1. **`list_deployments`** — Low effort, high value. Agent can't help with history otherwise.
    2. **`get_environment_status`** — Essential for diagnosing provisioning failures.
    3. **`retry_environment`** — Unblocks stuck environments.
    4. **`cancel_deployment`** — User escape hatch for stuck deployments.
    5. **`get_stack_events`** — Makes CDK failures actually debuggable.
    
    The first three tools close the most critical gap: **the agent can't see or recover from environment-level failures** today. A failed environment blocks all future deployments to that account until someone manually fixes the database.
    
    ### Implementation Notes
    
    For `cancel_deployment`, the worker needs a check in the loop to abort if status changes to CANCELLED.
    
    For `retry_environment`, reset status to PENDING and clear status_message. Next `deploy_app` will see PENDING and trigger `_provision_environment()`.

[devopshero-bxr] P2 task      created 2026-01-21
  Deployment: Configurable secrets path for deployed apps
    ## Problem
    
    When DOH deploys an app, it creates secrets in AWS Secrets Manager using a path derived from the app slug:
    
    ```python
    # secrets_utils.py:37
    secret_name = f"devopshero/{app_config.app_name}/secrets"
    ```
    
    Where `app_config.app_name` comes from `app.slug` (set in `app_config_builder.py:105`).
    
    However, many apps have hardcoded expectations about their secret path. For example, db_portal:
    
    ```elixir
    # secrets_manager_config_provider.ex:15
    @default_secret_name "devopshero/db-portal/secrets"
    ```
    
    **The mismatch:** If someone deploys db_portal with slug "my-db-portal", DOH creates `devopshero/my-db-portal/secrets`, but the app looks for `devopshero/db-portal/secrets`. The app fails to start because it can't find its secrets.
    
    ### How This Was Discovered
    
    The Main Agent created the same app (db-portal) twice in a conversation. The `create_app` tool uses `slugify()` with uniqueness checks, so the second creation got slug "db-portal-1" instead of "db-portal". When deployed, DOH created secrets at `devopshero/db-portal-1/secrets`, but the app was still looking for `devopshero/db-portal/secrets`. The app failed to start.
    
    This revealed the tight coupling between app slug and secrets path — a coupling that breaks whenever the slug doesn't match what the app expects.
    
    ## Alternatives Considered
    
    ### Option 1: Make apps accept configurable secret path (CHOSEN)
    
    The app reads its secret path from an environment variable (e.g., `DOH_SECRET_NAME`) with a fallback to a default for local dev.
    
    **Pros:**
    - Apps become truly portable — deploy the same app multiple times with different configs
    - DOH keeps a simple, predictable naming convention
    - Single source of truth — DOH tells the app where its secrets are
    - Apps don't need to have "devopshero" in their codebase
    
    **Cons:**
    - Requires establishing a convention for all deployable apps
    - App developers need to understand the convention
    
    ### Option 2: Make secret path configurable in DOH
    
    Add a `secrets_path` field to the App model. If set, use that path; otherwise generate from app_name. Agent would analyze app code to find hardcoded paths.
    
    **Pros:**
    - Apps don't need modification
    - Works with existing/legacy apps
    
    **Cons:**
    - Agent must analyze app source to find hardcoded paths (fragile)
    - Grepping for "devopshero/" won't work — apps shouldn't need to know about DOH
    - Config drift risk: app code changes but DOH config doesn't update
    - More complexity in DOH configuration layer
    
    ## Decision
    
    **Go with Option 1.** Since we haven't released anything yet, there's no backward compatibility concern. This is the cleaner architecture:
    
    1. Apps receive their secret path via environment variable
    2. DOH injects the env var during deployment
    3. Apps can use any secret path they want for local dev (e.g., "data-eng/db-portal/secrets")
    
    ## Implementation Plan
    
    1. **Modify db_portal** to read secret path from `DOH_SECRET_NAME` env var with fallback to default
    2. **Update DOH** to inject `DOH_SECRET_NAME` env var during deployment
    3. **Test** by deploying db_portal with secret path "data-eng/db-portal/secrets" (proves apps don't need "devopshero" in their config)
    4. **Document** the convention for future deployable apps
    
    ## Files Involved
    
    - `deployable_repos/db_portal/lib/db_portal/secrets_manager_config_provider.ex` — add env var support
    - `devopshero_app/services/infra_customer/secrets_utils.py` — may need to accept custom path
    - `devopshero_app/services/deployment/app_config_builder.py` — wire through the secret path
    - `devopshero_app/services/infra_customer/appconfig.py` — add secrets_path field to AppConfig
    - `devopshero_app/models.py` — possibly add secrets_path to App model

Caused by get_claude_env() mapping AWS_BEDROCK_* to AWS_* which propagates to all subprocesses. MCP tools work correctly (use AssumeRole), but arbitrary code execution leaks Bedrock creds.
    ## Problem
    
    When Claude Agent SDK executes code in its sandbox (python, bash), boto3 picks up AWS credentials from the Bedrock API account (315915642113) instead of having no AWS access.
    
    ## Root Cause
    
    In `agent_service.py`, credentials are passed to `ClaudeAgentOptions`:
    
    ```python
    env = {
        **get_claude_env(),  # Maps AWS_BEDROCK_* → AWS_*
        "TMPDIR": str(settings.CLAUDE_SANDBOX_DIR),
    }
    ```
    
    `get_claude_env()` maps:
    - AWS_BEDROCK_REGION → AWS_REGION
    - AWS_BEDROCK_ACCESS_KEY_ID → AWS_ACCESS_KEY_ID  
    - AWS_BEDROCK_SECRET_ACCESS_KEY → AWS_SECRET_ACCESS_KEY
    
    These are needed for Claude Code to call the Bedrock API, but they propagate to all subprocess execution (sandbox).
    
    ## Why Two AWS Accounts
    
    - **555553041615** — DevOps Hero control plane (ECS, customer deployments)
    - **315915642113** — Bedrock API access (cross-account IAM user)
    
    Bedrock access uses explicit credentials from account 315915642113, not the ECS task role.
    
    ## Impact
    
    - MCP tools work correctly (use `iam_utils.get_assumed_role_session()` with AssumeRole)
    - Sandbox code (arbitrary python/bash) gets Bedrock account credentials
    - Security: sandbox can access Bedrock account resources
    
    ## Potential Fixes
    
    1. **Clear credentials in sandbox env** — Explicitly set AWS_*="" in env dict (if SDK supports separation)
    2. **SDK feature request** — Ask for sandbox env isolation from runtime env
    3. **System prompt guidance** — Tell agent not to use boto3 directly, use MCP tools instead

[devopshero-1pg] P1 task      created 2026-01-15  closed 2026-03-03
  DomainModel: Multi-repo support design
    ## Context
    
    Currently: one workspace = one repo. Apps inherit repo from `workspace.primary_repo_url`.
    This was a deliberate v1 simplification (see journal 2026-01-15 "Workspace Pinning").
    
    ## Use Cases to Support
    
    1. **Microservices in separate repos** — Frontend in one repo, backend in another, both deployed together
    2. **Shared infrastructure** — Multiple unrelated apps sharing the same VPC/datastores
    3. **Team ownership** — One team manages multiple apps across repos, wants single dashboard
    
    ## Design Options Discussed
    
    ### Option A: Add `repo_url` back to App (nullable, fallback to workspace)
    
    ```python
    class App:
        repo_url = models.URLField(blank=True, null=True)  # If null, use workspace.primary_repo_url
    ```
    
    **Pros:** Simple migration, backward compatible, each app can optionally override
    **Cons:** Two sources of truth, agent needs to handle both cases, ambiguous "where does this app come from?"
    
    ### Option B: Separate Repository model, M2M with Workspace
    
    ```python
    class Repository(models.Model):
        url = models.URLField()
        name = models.CharField()
        organization = models.ForeignKey(Organization)
    
    class Workspace(models.Model):
        repositories = models.ManyToManyField(Repository)
        # Remove primary_repo_url
    
    class App(models.Model):
        repository = models.ForeignKey(Repository)  # Required
    ```
    
    **Pros:** Clean normalization, repos are first-class (credentials, webhooks), clear app-to-repo mapping
    **Cons:** More complex model, harder migration, workspace becomes more abstract
    
    ### Option C: Keep workspace = one repo, create multiple workspaces
    
    No model changes. Two repos = two workspaces. They can share AWS account/region.
    
    **Pros:** No changes needed, clear mental model, workspace isolation
    **Cons:** Can't see "all my apps" in one place, datastores not easily shared
    
    ## Open Questions (to resolve when implementing)
    
    1. **Primary use case?** Microservices across repos, or more general multi-repo?
    2. **Should repos be first-class entities?** Matters for git provider integration (credentials, webhooks per repo)
    3. **Datastore sharing importance?** If two apps from different repos need same Aurora cluster, that drives putting them in one workspace
    4. **Agent flow implications:** Should pinning a workspace still make sense? Or pin a repo within workspace?
    
    ## Current Model Reference
    
    - `Workspace.primary_repo_url` — required, single repo for workspace
    - `App.branch` — branch to deploy from
    - `App.dockerfile_path` — path within repo to Dockerfile (supports monorepos)
    - App has no `repo_url` field (removed in workspace pinning work)
    
    ## Recommendation
    
    Option B (Repository as first-class entity) is likely the right long-term choice because:
    - Git provider integration will need per-repo credentials/webhooks anyway
    - Clean data model beats convenience hacks
    - Supports all use cases cleanly
    
    But Option A could be a quick interim solution if needed before full git integration.
